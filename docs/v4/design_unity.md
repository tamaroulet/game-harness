## 9. Unity への接続の方針

- 要件の台帳の源は、操縦士の企画書。人は企画と受け入れの基準（ふつうの言葉の完了の条件と遊びの手触り）を決める。そこから、中くらいの仕事と要件の台帳を作るのは、上流の系の仕事（憲章 §1・§6）。作り方は E-2 で決める。
- 位置づけ：Unity は対照実験の土俵ではなく、実戦の最も賢いモデルで中くらいの仕事を積み上げる本番基盤とする。手元の既存ゲームのテストを流用してベンチ競争をするのではなく、「人がテストを書かない前提（憲章 §6）」で任意の自作 Unity 企画に通用する汎用的な接続と検査体系を確立する。
- 置き場と閉じ込め（操縦士の決め、2026-11-17。G0-6 の実測と調べの後）：
  - 形は ①：エージェントは WSL のコンテナで動き、Windows の Unity は、アダプタ（Windows の側のハーネスの処理）だけが、ハーネスの持つクローンに対してバッチモードで呼ぶ。Unity Personal のライセンスは Hub でしか有効にできず、Linux の Unity をコンテナの中で有効にする手順が無いので、② は採らない（P-041）。
  - Core（Unity に依らない C#）は、.NET のプロジェクトで分けてビルドし試験する（falling-blocks の src/Core と tests/Core.Tests の形）。Unity を起こさないので、1 回 1〜2 秒（P-039）。
  - エージェントの読み書きは WSL のコンテナの中に閉じ、Windows の Unity に渡すのは、アダプタが決めた形（クローンの作業ツリーへの変更の当て込みと、バッチモードの呼び出し）だけにする。ネイティブの Windows ではサンドボックスが効かず、手元の Windows 11 Home では Windows Sandbox も使えない（P-017）。
  - Unity は、操縦士が Editor で開いている元のプロジェクトでなく、ハーネスが持つクローンで動かす。Editor が同じプロジェクトを開いていると、バッチモードは理由の文を残さずに終わりの符号 1 で止まる。別のクローンなら並べて走る（P-039）。
- アダプタの作り（G0-6 の実測から）：
  - Unity.exe だけを待ち、走りの後に子孫のプロセス（コンパイルサーバーの dotnet・UnityPackageManager）を job object で止める（Windows PowerShell 5.1 の Start-Process -Wait は子孫まで待つ）。
  - 走りの前に、クローンの Temp/UnityLockfile と、ライセンスの状態（Hub のサインインが切れると符号 198）を見て、走らせない理由を記録する。
  - 新しいクローンは、Library ごと写すと、取り込みが 94 秒から 36 秒に縮む（小さいプロジェクトの 1 回の測り。M-07）。
- Editor を操る口：AI Assistant パッケージの MCP サーバーは非推奨になり、代わりは Unity CLI（P-040）。関門はバッチモードだけで組む。CLI は、評価役が動くものを外から見る段（下の 5）を作るときに調べる。
- 実戦 Unity 開発で満たすべき検査要綱と関門の割り当て（多段。速い段を先に通す。4-4 の ②。時間の目安は、小さいプロジェクトで、コンパイルを含む 1 回の起動が 6 秒前後、EditMode のテストの往復が 7 秒前後、.NET の Core の試験が 1.4 秒。P-039）：
  1. 層・型・安全の境界（第 1 関門）：Pure C# の Core 層（.NET 分離ビルド）と Unity 依存層（`.asmdef` 等）の依存境界、危険なホスト実行 API や保護ファイル改変の起動前遮断、C# コンパイル。
  2. アセット・シーン・参照の整合（第 1 関門）：既存 `.meta` の GUID 非破壊、Scene・Prefab の消えたスクリプト（Missing Script）や明示必須参照切れの検出、台帳の口（クラス・メソッド・Prefab・Scene）の実在。
  3. 決定論ロジックと非退行（第 1・第 2 関門）：台帳の振る舞いに対するテスト（.NET / EditMode、Unity Test Framework のバッチモード、結果は XML。H#C19）と、合格済み仕事の積み上げによる非退行（P2P）。実装役から独立した第 2 関門の適用範囲は原則この決定論領域に限定し、誤爆率を確かめてから押し返しに使う。
  4. 人手テスト非前提の UI 操作・状態追随と非決定挙動（PlayMode 関門）：
     - UI 操作・状態追随：対象 Scene の読み込み・入力や操作経由での例外 0・入力遮蔽やグリフ欠落の検出に加え、状態変化が UI へ追随することを、描画方式や UI フレームワーク差による誤爆を避けながら機械検証する。
     - 時間経過・物理・乱数など非決定論を含むゲーム挙動：厳密値一致に頼らず、固定ステップやシード制御などのフックと、不変条件・範囲・保存則・停滞検知・複数シード実行（モンテカルロ）で破綻を捉える。
  5. 見た目・手触り・音（人間との境界）：機械で固められない視覚品質・遊びの手触り・音は、自動合否に無理に押し込めず、ビルド済み実行ファイルでの人間のプレイテスト（`dispatch --playtest`）へ委ねる。画面確認の自動化は、実シーンの描画方式（Overlay Canvas 等）で誤爆しない範囲の補助にとどめる。
- 検査器自体の検証（メタ検証。実戦投入前に利用枠 0 で確認する）：
  - アダプタの基盤契約として、終了コード単独での合否判定を採らず、NUnit XML の直接解釈・対照テスト（必ず通る／必ず落ちる）・skip 上限監視・保護テスト改変拒否を備える。
  - 健全なプロジェクト状態で誤爆（偽陽性）が 0 であること、および上記 1〜4 の各要綱に対応する意図的な不具合（型・層境界違反、危険 API、GUID 破壊、Missing Script、UI 遮蔽・未配線・例外、非決定挙動の破綻、テスト改変・skip 増加など）を注入したときに該当の関門が確実に検知・局所化できることを機械検証する。
- 持ち込みは、台帳の中身・周回の粒度・実行環境のアダプタ・エージェントの実行口を替えて行う。制御核は替えない（§5-1）。1 つの会話に任せる粒度は、実戦のモデルの推論の力に合わせて大きくする（4-4 の ①）。
- 組み立ての前の調べ（済み。G0-6、2026-11-17。席が一次資料を読み、手元のクローンで測った。記録は docs/research/R-20261117-unity-connection-g06、測りは[実験と計画](experiments.md)の M-07）：公式の MCP の今（P-040）・バッチモードの速さと、速くコンパイルを確認する方法（P-039。Core は .NET で分ける）・Linux の Unity のライセンス（P-041）・Windows での閉じ込め（P-017）・Editor が同じプロジェクトを開いているときの振る舞い（P-039）。
- 時期：組み立ては外部ベンチでの検証（E-2・E-3）の後。1 回の検証にかける時間と関門の粒度は、E-3 の積み重ねの周回を設計するときに、M-07 の時間を使って決める。リポジトリの C# の読み書きを拒む設定は、2026-11-13 に外した。
