# 設計の根拠：先人の知見・手元の実測・前提の台帳との対応（v4 の第 2 層の一部）

- [設計と仮説](design.md)から 2026-11-20 に分けた。節の番号は design.md と同じで、文中の §（節の番号）は design.md の節を指す。前提が変われば、この文書の節を書き直す（末尾に足さない）。経緯は Git と PR に任せる。

## 2. 先人の知見の要点

### 2-1. 状態は外に、構造化して置く

- 長く走るエージェントの核の課題は、セッションが記憶なしに始まること（H#C1）。Anthropic は、初期化役が機能の一覧（JSON。全部「未達」から）・進捗のファイル・最初のコミット・起動の手順を作り、実装役が 1 回に 1 機能を進める形にした（H#C2・H#C3）。
- JSON にしたのは、モデルが Markdown より書き換えにくいから（H#C2）。2 つの役の違いは最初の頼みだけで、ハーネスは同じ（H#C4）。価値は仕掛けではなく、環境（ファイル・テスト・起動の手順）の設計にある。
- 新しい文脈に入るエージェントは向き直りに時間を使う（H#C16）。引き継ぎのファイルは、それを短くするためにある。

### 2-2. 検証の背圧

- 検証器がほぼ完璧でないと、違う問題を解く（H#C14）。テスト・型・静的解析など、何でも背圧として配線して不正な生成を拒む（H#C29）。
- FeatureBench では、正解の単体テストを見せると解決率が大きく上がった（B#C11。表 7 で Lite の Gemini 3 Pro が 10% → 60%）。何をもって完了かが分かることの効きが最大。ただし、それは正解の実装から作られたテストを見せた条件の数（§4-2）。
- エージェントが自分で書いたテストは合否の根拠として弱い（P-016）。受け入れの検証は、実装役から独立に系が作り、合否を実装役の自己採点に依らせない（憲章 §6）。作り方の知見は 2-8。

### 2-3. 文脈とキャッシュ

- 1 つの仕事の中は、頼みの先頭を固定して追記だけにし、キャッシュの当たりを守る（H#C20・H#C21）。本番のエージェントでは入力が出力の約 100 倍（H#C22）。
- GitHub Copilot の本番の記録では、KV キャッシュの当たりは 1 ターンの中で平均 90%、ターンの境で 55% に落ち、モデルの切り替えや文脈の圧縮の後は大きく外れる（A#C10）。
- 圧縮は戻せる形にする（パスや URL を残す。H#C23）。最も安全で軽い圧縮は、古い道具の結果を消すこと（H#C11）。古い観測を伏せるだけで、費用は半分、解決率は要約と同じかやや上だった（H#C31。論文は A#C14）。
- 区切りで仕事を引き継ぐとき、文脈を持つ引き継ぎ（生の記録・要約のメモ・構造化のメモ）は、リポジトリだけの引き継ぎより、後任のイベント数の中央値を 20〜59%、累積の入力トークンを 42〜63% 減らした（Handoff Debt。A#C9）。
- 学習で畳む方式（Context-Folding）は RL で学ばせることが前提（H#C30）。手元では学習できないので、学習の効きを当てにしない（P-028）。
- キャッシュの値段は提供元で違う。Claude は先頭の一致で会話をまたいで当たり、読みは 0.1 倍（H#C17）。Gemini API は 2.5 以降で implicit caching が既定（H#C18）。手元の agy の gemini-4-hydrogen-medium は、新しい会話の 2 ステップ目から当たる（1 ステップ目のキャッシュしない入力は約 8.2 千〜10.1 千トークンで、文面の長さで変わる）。旧 gemini-3.8-flash-medium は、文脈が約 1.6 万〜2.1 万トークンを越えるまで当たらなかった（M-01、P-021）。

### 2-4. リセットか継続かは、モデルと仕事の長さで決まる

- Sonnet 4.5 は文脈が満ちると早く切り上げる（context anxiety）ので、リセットが要った（H#C5）。Opus 4.5 ではその振る舞いが消え、リセットを外して 1 本の続くセッションにした（H#C6）。
- 毎回新しい文脈で回す Ralph も、仕様の読み直しは無駄と承知のうえ（H#C28）。

### 2-5. 部品は「モデルの弱さの仮定」として外す条件を付ける

- ハーネスの部品は、モデルが単独でできないことの仮定（H#C7）。1 つずつ外して確かめ、新しいモデルで見直す。
- 評価役は、課題がモデルの単独で確実にできる範囲の外にあるときだけ費用に見合う（H#C8）。

### 2-6. 書き手は 1 本、検証は文脈を分ける

- 多役は、書き込みを 1 本の流れに保ち、ほかの役が知恵を足すときに最もよく効く（H#C24）。検証役は書き手と文脈を共有しないときに最もよく効いた（H#C25）。
- 多役は約 15 倍のトークンを使う（H#C13）。

### 2-7. 費用の構造

- トークンの量が性能を大きく左右し、エージェントはチャットの約 4 倍、多役は約 15 倍のトークンを使う（H#C13）。
- 公式の長い課題は 1 課題で 100 万を超える入力トークン（B#C14）。3 役のハーネスは単独の 20 倍超の費用で、出来の差は大きかった（H#C9、1 例）。

### 2-8. 受け入れの検証をいつ・何から作るか

- 仕様からテストを作る研究の数（どれも既存のコードの課題）：
  - イシューから再現のテストを作る課題（SWT-Bench）では、5 つの案から最良を選んでも、修正前のコードで落ちるテストを作れた課題は 62.7%、正解の後で通るテストを作れた課題は 22.1%（A#C2）。表から読めるのは、直す前に落ちたテストのうち正解でも落ちたものが課題の約 4 割、ということまで（落ちの理由は記録で未確認）。作ったテストでパッチを絞ると、再現率は 20% だが、適合率は 2 倍を超えて 47.8% になる（A#C1）。
  - 修正前のコードでの落ち方が、妥当性を予測する。AssertionError で落ちたテストは 57.1% が正解の後で通り、例外で落ちたテストは 3.7% だった（Otter の表 6。A#C4）。
  - 変異で導くテスト生成（Meta の ACH）は、既存のコードに対して懸念に特化した変異を作り、その変異を殺すテストを作る。生成テストの 73% がエンジニアに受け入れられた（A#C5・A#C6）。
  - 既存のコードの性質のテストの自動生成では、報告の 56% が有効な不具合（点の上位 21 件では 86%）。残りは誤った報告（A#C7）。
  - 既存のコードに対するテスト作りでも、最良のモデルの平均のカバレッジは 35.2% で、実行の推論と assertion の誤りが主な理由（A#C8）。
  - 実装の前に別の役が受け入れのテストを書く形を、リポジトリの規模で、実装役が自分で書く場合と比べた一次の実測は見つからなかった（R-20261023-m2 の確かめられなかったこと）。
- 最前線のハーネスの形（Anthropic の長く走るアプリ）：実装の前に、生成役と評価役が、何をもって完了とするかを確かめられる振る舞いで取り決めた（sprint contract。K#C1・K#C2）。実装の後に、評価役が Playwright で動いているアプリを外から操作して確かめた（K#C3）。テストのコードを先に書く形ではない。評価役は放っておくと甘く、問題を見つけても通してしまい、記録を読んで頼みを直す周回を何周もして較正した。それでも、深い所の不具合は見落とした（K#C4〜C7）。強いモデルでは、評価役を走りの最後の 1 回に減らした（K#C8。費用に見合う条件は H#C8）。
- v1・v2 の手元の記録（タグ archive/pre-v4 の v2_contract_foundry.md）：
  - v1 では、前もって作った受け入れの仕組みが誤爆した。文字列だけを見る静的な門で B の 6 回の試行が全部落ち、実装の前から通るテストを偽物としてはね（T2 の 7 件中 4 件）、落ちた仕事のテストが次に持ち越されて ABORT が連鎖した。その間、素の A は 2 回とも 5 つの仕事を通した。
  - v2 では、何もしない実装や壁キックしない実装が性質を通りえた。性質の前提の除外漏れは、正しい実装ができるまで表に出なかった。
- この設計での使い方：
  - 実装の前に作るのは、何をもって完了とするかの取り決め（要件の台帳）まで。実装の前にテストのコードを作って、関門や実装役の目標にはしない。手元で A が落ちた所は、課題の文から作るテストが届かない所だった（§3）。
  - 機械で走る受け入れの確かめは、実装役から独立に作り、正しい実装で通る割合を、正解のある所で測ってから押し返しに使う（P-034）。
  - 評価役の甘さは、頼みの文面の較正（憲章 §5 では効きに数えない）でなく、仕組みで手当てする：合否を機械の確かめの結果だけで決める・期待する値を候補の実装を見る前に固める・押し返す力を台帳に根拠のある確かめに限る（§4-2）。

### 2-9. 企画の粒度と分解

- SWE-EVO は、リリースの変更を、仕様を付けた PR の列に分ける正解の分解を意図して伏せ、最終の状態で採点する（A#C11）。
- リリースノートだけの条件は、PR と課題の文を足した条件より、多くのモデルで解決が少し下がる（gpt-5 の OpenHands で 14.58% と 18.75%。48 課題で 1 課題が 2.08 ポイント。A#C12・A#C13）。

- 手元の環境は、FeatureBench の Fast（CPU で走る 100 課題）を回せる。Lite の 19 課題は GPU を求め、手元の Docker では走らない（M-04、P-033）。
- テストを隠した素の A（Hydrogen）は、Fast の小さい 5 課題で 1 つを解いた。落ちた 4 課題のうち 3 課題は、落ちが課題の文に無い要求（例外の文言・出力の書式・引数の扱い）だけだった。どの手順でも届かない（§3）。
- 正解のテストを見せた（白箱の）素の A は、小さい 5 課題で 4、大きい 5 課題で 3、X-02 の 4 課題で 1 を解いた。落ちた 6 課題は 6 つとも、確かめを自分の作った範囲に絞るか、見えている落ちを外のせいにして終えた（§3・§4）。軌跡を詳しく読んだ 3 課題では、A は課題の文が名指す部品を作り終えていて、落ちたのは文が名指さない部品（残ったコードが呼んでいるもの）だった。実装役に任せると、確かめは自分の作った範囲に縮む。
- 1 つの仕事の中の既存のテストの退行（採点の P2P）は、X-01 と X-02 の 19 回の走りで 0 件。
- 記録のパッチの再生（E-1 の段 a。利用枠 0。[実験と計画](experiments.md)の §5-4、P-037）：
  - 第 1 関門の検出の絶対の数は、正しい実装（正解）でも 15 課題中 13 課題で 0 にならなかった。ライブラリにもとからある検出（astropy の動的な名前空間・任意の依存など）と、コンテナの環境で落ちる既存のテスト（ネットワークを切ったことによる失敗・入っていない任意の依存・TeX など）による。押し返しには、最後に合格した状態との差だけを使う（§4-2）。
  - 差で読むと（正解の状態を基準の代わりにした段 a の読み。比較条件の中では使わない。§4-2）、記録の A のパッチの未解決 10 本のうち 7 本で検出が出て、7 本とも、隠しのパッチが消した名か変えたファイルに当たった。解決 9 本のうち 4 本でも検出が出た。4 本とも、残ったコードが呼ぶ名を戻していない本当の未完成で、正解では通る既存のテストが NameError などで落ちる。FeatureBench は、実装を消した状態で落ちるテストを P2P から外すので、これらを解決に数える。
  - 漏れた未解決の 3 本は、どれもテストを隠した条件の走り。根拠のある落ち（2 本・5 項目）は、作った口の引数の扱い（astropy の broadcast_arrays の subok=False）と、不正な入力の拒み方（seaborn の Plot.pair の 3 項目）だった。残りは、課題の文に無いエラーの文言（6 項目）。
