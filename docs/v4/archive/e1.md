### 5-3. 段 a：記録のパッチに第 1 関門を当てて再生する（利用枠 0）

- 状態の作り方：FeatureBench の評価と同じ手順にする（featurebench/harness/runtime.py の Level 1。コミット 08b25d9）。
  1. 課題のイメージから元のリポジトリを戻す。ただし、イメージの /testbed が元のリポジトリのコピー（/root/my_repo）と一字一句同じ（diff -r で差が無い）ならコピーしない。FeatureBench は cp -r でコピーするので、ファイルの mtime だけが新しくなり、pandas の editable install（meson-python）が、検査の import のたびに C/C++ の全体の再ビルド（ninja の 154 ステップ）を始める。開発用の 6 つのイメージは、すべて差が無かった。違うのは mtime だけで、ファイルの中身は FeatureBench の手順と同じ。
  2. 隠しのパッチを当てる。
  3. 公式のテストのファイルを消す（テストを隠す通常の条件）。
  4. リポジトリごとの環境の直しを当て、バイトコードを消し、git を作り直す。
  5. パッチを当てる。白箱の走りのパッチは、公式のテストのファイルへの変更を外して当てる（隠した条件では、そのファイルが無いため）。
  - 箱の網は切る。
- 再生ツールの安全策：
  - 始まりのコミットは、git rev-parse の標準出力だけから読む。40 桁の SHA でなければ止める。
  - 候補ごとに始まりのコミットに戻し、HEAD が始まりのコミットで、変更も追跡外のファイルも無いことを確認する。違えば、その課題を止める（前の候補の変更の上に、次の候補を当てない）。
  - editable install のビルド（開発用では pandas のイメージだけ）：検査の前に、`ninja -n` で C/C++ のビルドのステップ（と build.ninja の再生成）が 0 であることを確認する。残っていれば、import とテストを走らせず、その状態をエラーとして記録する。検査の後に、ビルド成果物（.so・.o）の mtime が変わっていないことを確認する。
  - import とテストは新しいセッションで走らせ、終わったら（タイムアウトでも）セッションに残ったプロセスを全部止める。検査の前後に、コンテナの PID 1 に付け替えられた孤児プロセスを数えて止める。
  - pyflakes はスタックの大きいスレッドで走らせる。それでも再帰の上限に当たるファイルは、検出に数えず、検査しなかったファイルとして別に数える。
- 当てる状態は 3 種：
  - 始まり（パッチなし）。
  - 正解：データの patch を逆にしたもの（FeatureBench の preprocess_hf_patch）。
  - A のパッチ 19 本：X-01 の隠した条件 5・白箱の小 5・白箱の大 5、X-02 の段 1 の 4。解決 9・未解決 10。
- 第 1 関門の確かめ（ハーネスが箱の中で走らせる。harness/fb_gate_probe.py）：
  - 未定義の名：パッケージのソース（テストのファイルを除く）の全部に pyflakes をかけ、未定義の名（UndefinedName・UndefinedExport・UndefinedLocal）と構文の誤りを数える。
  - import：パッケージのソースのモジュールを 1 つずつ import し、落ちを数える。パッケージの外のモジュールが無いことによる ModuleNotFoundError（任意の依存）は数えない。
  - 属性：次の条件のクラスで、メソッドが self.名 で読む名が、そのクラスにも、祖先にも、子孫（とその祖先）にも定義されていないもの。
    - 祖先がすべてパッケージの中で辿れる（object・ABC・Generic・Protocol は可）。
    - __getattr__ などの動的な仕組みが無い。
    - 子孫に、辿れない祖先を持つものが無い。
  - テスト：次の 2 つを、ファイルごとに -k なしで走らせる。
    - 台帳の口の Path のモジュールと、パッチが変えたソースのモジュールを、直に import している既存のテストのファイル。
    - パッチが足したか変えたテストのファイル。
    - コマンドは課題の設定の test_cmd と timeout_one。1 ファイル 300 秒、1 つの状態で 600 秒まで。始まりの状態では走らせない。
- 物差し：
  - 正解での誤検出：正解の状態での、4 つの確かめの落ちの数。目標は 0。
  - 未解決 10 本：
    - 確かめのどれかが落ちを出したか（押し返せる）。
    - 出した落ちが、落ちの元に当たっているか。消された名か、隠しのパッチが変えたファイルに関わるものを、当たりとする。
  - 解決 9 本：確かめが落ちを出したか（解けた課題を押し返すことになる）。
  - 始まりの状態：落ちの数（始まりの時点で、実装役に見せられるもの）。
  - 根拠の分け（§5-2）ごとの、未解決のパッチの落ちた項目の数。
- 限界：
  - 白箱のパッチ 14 本は、テストを見て作った最後の状態で、隠した条件で A が作るものとは違いうる。
  - A のパッチは、同じモデルの 1 回ずつ。
  - テストは、選んだファイルを時間の上限の中で走らせた分だけ。

### 5-5. 第 2 関門の仕様（E-1 での形。設計 §4-2）

- 入力（検証役に渡すもの）：
  - 課題の文（要件の台帳に当たる。全文）。
  - 課題の始まりの状態のリポジトリ（隠しのパッチを当て、公式のテストのファイルを消した状態。実装の前のコードと既存のテスト）。
  - 渡さないもの：候補の実装（A のパッチ・正解）・実装役の会話・実装役のテスト・公式のテスト。
- 出力：決まった置き場の pytest のファイル 1 つ。テストの関数ごとに、docstring の決まった形で、確かめる課題の文の項目と、期待する値の根拠になる課題の文の引用を書く。引用は、課題の文に一字一句あるもの。
- 走らせ方：
  - 課題ごとに 1 回、新しい agy の会話（gemini-4-hydrogen-medium、P-032）で作る。箱の網は agy の宛先だけを通す。
  - 始まりの状態の箱の中で、検証役は自分のテストを走らせてよい。実装が無いので落ちるが、名前と引数の誤りには気づける。
  - 作ったファイルは箱の外に写して固める（SHA-256 を記録）。候補（正解・A のパッチ）ごとに、候補の状態の箱でハーネスが走らせる。当て直しはトークン 0。
- 押し返す力の分け（静的。作った後、走らせる前に機械で決める）：
  - 作ったテストの関数ごとに、§5-2 の規則 2〜5 を当てる。「隠し：文言」「隠し：名」に当たるもの（課題の文にも、始まりの状態のソースにも無い文言・名を確かめるもの）は「知らせるだけ」。
  - 引用が課題の文に無い関数も「知らせるだけ」。
  - ほかは「押し返す」。
- 誤った実装の追認を防ぐ仕組み：検証役は候補の実装を見ない。期待する値は、候補の状態で走らせる前に固める。候補ごとに作り直さない。
- 誤検出を防ぐ仕組み：押し返す力を、根拠のある確かめに限る（上の分け）。正解の状態での精度を、押し返しに使う前に測る（§5-6）。
- 前の版の案で「25 回」としていた数は誤り。作るのは課題ごとに 1 回（15 回）で、正解と A のパッチには当て直すだけ。
- 狙う落ち（段 a の漏れ。§5-4）：第 1 関門が漏らした根拠のある落ちは、口はできていて、引数の扱いと不正な入力の拒み方が違うものだった。検証役のテストは、課題の文の口ごとの引数の組み合わせと、不正な入力のときの例外の型を中心にする。例外の文言は、課題の文に一字一句あるときだけ押し返しに使う。
- FeatureBench の開発用では、この的を持つ未解決のパッチが 2 本しか無いので、段 b は走らせない（§5-6）。この仕様は、E-3 か Unity で第 2 関門を測るときに使う。

#### R0 の規則（G0-3 の集計の前に書いた。集計の後は変えない）

1. 静的な検査（harness/fb_gate_probe.py の未定義の名前・import・属性）：t=0 に無かった検出だけを押し返す。比べる鍵は、未定義の名前が（ファイル・種類・名前）、import が（モジュール・誤りの種類）、属性が（ファイル・クラス・属性の名前）で、行番号は使わない（harness/fb_replay.py の keysets と同じ）。パッケージの外のモジュールが無いことによる import の誤りは数えない。
2. テストの選び方（-k などで絞らない）：
   - 群 1：候補が足したか変えたテストのファイル（名前が test_ で始まるもの）。
   - 群 2：台帳の Path（課題の文の Interface の Path）のモジュールを import する、t=0 にあるテストのファイル。
   - 群 3：候補が変えたソース（テストのファイルを除く）のモジュールを import する、t=0 にあるテストのファイル。
   - モジュールの名のうち最上位のもの（`.` を含まない名。例 `pandas`）は、群 2・3 の選びに使わない。最上位の `__init__.py` が変わると、ほぼすべてのテストのファイルが当たる（run3 の正解の状態で、pandas の 2 課題が 891〜897 ファイルを選び、課題と関係の無い pandas/tests/api/test_api.py まで入った）。最上位のパッケージの import の壊れは、1 の import の検査が拾う。
   - 走らせる順は群 1 → 群 2 → 群 3 で、群の中はパスの順。1 つのファイルは、最初に当たった群にだけ入れる。
3. テストの時間（1 回の関門）：
   - test_budget：テストの段の全体で 300 秒。残りが 0 になったら、後のファイルは走らせず「走らせなかった」と残す。
   - file_timeout：1 ファイルの上限。300 秒と、test_budget の残りの短いほう。この上限で止めたファイルは項目の結果が出ないので、そのファイルの項目はすべて不明とする（落ちに数えない）。
   - timeout_one：1 項目の上限。課題の設定のまま（pytest-timeout）。
4. 押し返すテストの落ち：走らせた項目の FAILED・ERROR のうち、誤りの文が次の環境の型（E1〜E6）に当たらず、判別できないもの（U）でもないもの。
   - E1 ネットワークの遮断と、外部のデータの取得・更新の失敗：誤りの文に `URLError`・`urlopen error`・`Name or service not known`・`Temporary failure in name resolution`・`Network is unreachable`・`Connection refused`・`ConnectionError`・`Max retries exceeded`・`gaierror`・`auto-update failed`・`is expired` のどれかがある（run3 の正解の状態の例：astropy の leap-second のファイルの期限切れと自動更新の失敗）。
   - E2 パッケージの外のモジュールの欠け：`No module named 'X'` で、X の最上位の名が対象のパッケージ（課題の設定の library_name）でない（例：pyspark・IPython、sphinx のテスト用の fish_licence.halibut）。
   - E3 パッケージの外の依存の版のずれ：`module 'X' has no attribute` か `cannot import name '…' from 'X'` で、X の最上位の名が対象のパッケージでない（例：moto の mock_s3）。
   - E4 リポジトリの外の状態の欠け：`FileNotFoundError`・`NotADirectoryError`・`IsADirectoryError`・`PermissionError` で、誤りの文の絶対パスがリポジトリの根（/testbed）の外にある（例：/root/.mlflow/envs）。
   - E5 外部コマンドの欠けと失敗：誤りの文に `exited with return code` か `command not found` がある（例：lualatex・xelatex）。
   - E6 1 項目の時間切れ：`Timeout (>…s) from pytest-timeout`。
   - U 判別できないもの：誤りの文が空の落ち。run3 では、収集の誤り（終わりの符号 2 のファイル）がこれになる。JUnit XML の収集の誤りの本文を項目に結び付けられず、空になった。
   - 対象のパッケージの名に当たる `No module named`・`module '…' has no attribute`・`cannot import name … from` は、環境の型にしない（消された部品の穴として押し返す）。
5. テストの改変：t=0 で git が追うテストのファイルを、候補が変えるか消したら押し返す（import の行だけを許す例外は無い）。新しく足したテストのファイルは、改変に数えない。
6. 1 つの状態で、1・4・5 のどれかが 1 つ以上あれば「押し返す」。

### §5 の前書き（取り下げの理由と、監査の数の扱いの訂正）
