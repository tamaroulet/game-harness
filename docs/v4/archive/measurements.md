### M-01 agy の新しい会話のキャッシュの立ち上がり（2026-11-13）

- 材料：箱の中の実装役（agy 1.5.3、gemini-3.8-flash-medium）の stream-json の記録。3 本のラン（A の会話の形の 1 ステージ目 1 回、B の 6 ステージ、前の A の 18 ステージ）で、新しい会話の始まりが計 25 回。
- 読み方：応答ごとの `cache_read_tokens` と `input_tokens`。キャッシュの読みが 0 でなくなる最初の応答と、その手前の文脈の長さ（入力＋キャッシュの読み）を見た。
- 結果：
  - 25 回とも、最初の 5〜12 応答はキャッシュの読みが 0。当たり始めるのは、手前の文脈が約 1.6 万〜2.1 万トークンを越えた所（最初の当たりの読みは 1.5 万〜2.1 万。1 回だけ 4,681 で当たり、次の応答で 0 に戻った）。
  - 1 回の始まりの、キャッシュの読みが 0 の応答の入力の計：5.6 万〜13.6 万トークン（中央 約 8.5 万）。
  - 会話を続けた A は、2 ステージ目以降、最初の応答から前の会話のキャッシュに当たった（読み 63,654 → 183,605）。
- 公開の文書との差：Gemini API の文書は、3.8 Flash の implicit caching の最低を 4,096 トークンとする。agy の経路はこれと合わない。仕組みは公開されていないので、実測で扱う。
- 前提：P-021。

### M-02 同じ課題での、続く会話と毎ステージの新しい会話の費用（2026-11-13）

- 材料：自作の鎖の課題 B07（6 ステージ）を 1 回ずつ。公開の記録（件数と費用）は、タグ archive/pre-v4 の bench/records/chains/ の e5-chat2-b07 と e5-lean-b07。A は 1 つの会話と 1 つの作業の場所を続けた。B はステージごとに新しい会話で、作業の場所を課題の範囲に絞った。モデル・箱・上限・採点は同じ。
- 結果（6 ステージの計、トークン）：

| | A（続く会話） | B（毎ステージ新しい会話） |
|:--|--:|--:|
| キャッシュでない入力 | 510,953 | 1,107,545 |
| 出力 | 166,118 | 260,741 |
| キャッシュでない分（入力＋出力） | 677,071 | 1,368,286 |
| キャッシュの読み | 17,399,084 | 10,234,262 |
| 入力のうちキャッシュでない割合 | 2.9% | 9.8% |
| 1 ステージ平均の秒・応答 | 262 秒・24.7 | 421 秒・40.8 |

- 2〜6 ステージの 1 ステージ平均のキャッシュでない分は、A 8.8 万・B 23.6 万（2.7 倍）。1 ステージ目だけは B が安い（19.0 万と 23.6 万）。
- B のキャッシュでない入力の 46% が、立ち上がり（M-01）の応答だった。2〜6 ステージの差の約半分が立ち上がり、残りがターンの多さ（前の仕様・本体・テストの読み直しと、試しのやり直し）。
- 1 ターンのキャッシュでない入力は、約 2,800〜2,900 トークンの基礎の分に、前の道具の出力が乗る（A 2,874・B 2,815）。時間は出力（思考）の量で決まる。並べて呼ぶ道具は 0 回（1 応答に道具 1 つ）。
- 限界：課題 1 つ・1 回ずつ。品質は両方とも満点で、品質の差は見えない（M-03）。
- 前提：P-022。

### M-04 手元の環境（2026-11-13〜14）

- WSL2 の Ubuntu、Docker 29.1.3（linux/amd64）、20 コア、WSL のメモリ 15GB。C ドライブの空き 466GB。
- SWE-EVO のイメージは課題ごと（Docker Hub の 42 個で圧縮 70.9GB、中央 1.37GB、最大 3.01GB。ほかに ghcr.io の 6 個）。FeatureBench のイメージはリポジトリごと（24 個）。
- FeatureBench の像は大きい（Docker Hub の圧縮で 1 つ 10.2〜19.5GB）。Lite の 30 課題は 13 個（計 約 167GB）、Fast の 100 課題は 18 個（計 約 203GB）を使う。展開の大きさと取り込みの時間は、seaborn 28.5GB・1,610 秒、astropy 29.1GB・1,294 秒、pandas 33.3GB・689 秒、mlflow 36.8GB・958 秒、xarray 30.5GB・653 秒、hatch 28.3GB・400 秒、setuptools 28.1GB・371 秒、scikit_learn 48.9GB・2,470 秒、sphinx 28.8GB・419 秒、sympy 28.9GB・516 秒（2026-11-14）。10 の像で WSL のディスクは 174GB 使用。
- GPU：FeatureBench は、課題の設定（docker_specs.run_args.cuda_visible_devices）が GPU を求めると、コンテナに GPU を渡そうとする。Lite（v1.1）は 30 課題のうち 19 課題が求め、手元の Docker では始まらない（NVIDIA の container toolkit が無い。WSL から RTX 4070 Laptop は見える）。Fast（v1.1）の 100 課題は求めない。同じ課題の ID でも split の設定で変わる。
- SWE-EVO のデータセット：48 課題（dvc 26・dask 8・requests 4・pydantic 3・modin 3・conan 2・scikit-learn 2）。パッチの行の中央 392（四分位 153・392・1,200）。リリースノートだけの語数の中央 75.5（リンクの PR と課題の文を足すと、論文の平均 2,390 語）。

### M-05 Gemini の利用枠の目盛り（2026-11-08〜13）

- 目盛りの減りは、キャッシュでない分（入力＋出力）100 万トークンあたり約 2.1〜2.3 ポイント（11-08 の基準のランと 11-13 のランから）。
- キャッシュの読みを数えるかは、まだ分からない。これまでのランはキャッシュの読みがキャッシュでない分の 10〜13 倍で、どちらの数え方でも見込みが同じ幅に入った。キャッシュの読みが入力の 97% を占める A の長い会話の前後で目盛りを読めば分かる。
- 枠の分かれ方（操縦士の読み、2026-11-13 の夜）：Gemini Models の週の枠（残り 21%。リセットは土曜 10:35）と 5 時間の枠（残り 96%）、Gemini 4 Argon の週の枠（残り 15%）が別にある。gemini-4-hydrogen と 3.8 Flash は Gemini Models の枠を使う。
- Hydrogen（X-01 の 3 回の走り、2026-11-14）：目盛りの減りは、API の値段での換算 1 ドルあたり、週 0.8〜1.1 ポイント・5 時間 3.2〜3.6 ポイント。キャッシュでない分 100 万トークンあたりでは、週 2.9〜4.2 ポイント（1% 刻みの丸めを含む。§3 の目盛りとトークンから）。
- 2026-11-14 から、目盛りは席が agy の /quota で直接読む（操縦士の指示。トークン 0。harness/agy_quota.py が、1% に丸める前の小数と次のリセットを JSONL に残す）。目盛りは使っていないあいだにも動く：13 時台に、使っていないのに、時刻を取らなかった少し前の読み（週 0.9036・5 時間 0.6860）から 13:23 の読み（週 0.9126・5 時間 0.6942）まで戻った（13:27 も同じ）。走りの前後の差には、走りのあいだの戻りが混じるので、直後に加えて少し置いた読みも残す。
- 11-13 は朝の残り 34% から夜の 21% まで 13 ポイント減った。B07 の 2 本のランの見込みは 5〜6 ポイントだったが、副操縦士の Gemini の利用とキャッシュの読みの数え方が混ざっていて、分けられない。X-01 では、走りの直前と直後に、ほかの Gemini の利用を挟まずに目盛りを読む。

### M-06 FeatureBench の課題の大きさ（2026-11-14）

- 大きさは、隠しのパッチ（データの patch）が消した実装の行の数と、実装のファイルの数で測った（テストのファイルを除く。データだけを読み、利用枠 0）。
- Fast（v1.1）：100 課題（すべて lv1・CPU）。消した行の中央 472・上位 4 分の 1 の境 925・最大 4,495。ファイルの中央 8。
- Full（v1.1）：200 課題（lv1 166・lv2 34）で、手元の CPU で走るのは 82（lv1 67・lv2 15）。CPU の lv1 の大きさは Fast と変わらない（消した行の中央 432・ファイルの中央 8）。lv2 の 15 課題は、隠しのパッチで実装を消す形でない（消した行 0。中身は確かめていない）。→ 手元で走る FeatureBench の課題のうち大きいのは、Fast の上の層。
- X-01 の 5 課題は、Fast の中で小さい側だった（消した行 149〜432・ファイル 1〜5。Fast の中の順位で下から 7〜41%）。
- 4 つの像の課題（X-01 の 5 課題を除く 58）のうち、消した行が 925 以上（Fast の上位 4 分の 1）は 16 課題（pandas 8・astropy 4・mlflow 3・seaborn 1。ファイルの中央 21）。Fast 全体では 25 課題（10 の像）。
- Fast の 100 課題のうち 37 課題は、隠しのパッチが F2P のテストのファイルも変える（消した部品の import の行を消すなど）。白箱で見えるテストは、そのぶん公式のテストと違う。評価は公式のテストに戻してから走らせる。

### M-07 Unity の実行の時間と振る舞い（G0-6、2026-11-17。利用枠 0）

- 対象：falling-blocks（Unity 6000.3.23f1。.cs 9 ファイル・asmdef 3・EditMode のテスト 1 件）を `git clone --no-hardlinks` で写したクローン。元のプロジェクトと dispatch には触れていない（元の作業ツリーの差分は前後とも 0）。手元は Windows 11 Home（論理 CPU 20）。
- バッチモード（-batchmode -nographics。時間は Unity.exe の起動から終わりまで。各 1 回）：
  - Library の無いクローンの取り込み（-quit）：94.3 秒（取り込みの Refresh 91.2 秒）。
  - 変更なしの起動：6.1 秒。Core の 1 ファイルを変えた後（再コンパイル込み）：6.3 秒。
  - EditMode のテスト（-runTests -testPlatform EditMode）：7.2 秒。1 ファイルを変えてからは 6.9 秒（コンパイルとテストを 1 回の起動で）。
  - Library ごとクローンを写すと（1,512MB）13.1 秒。写した先の初めの起動は 35.9 秒（パスが変わり、Bee の依存グラフを作り直した。Refresh 30.3 秒）。
  - Unity.exe が終わった後も、子のプロセス（Roslyn のコンパイルサーバーの dotnet と UnityPackageManager）が数分残る。Windows PowerShell 5.1 の `Start-Process -Wait` は子孫まで待つので、Unity.exe だけを待つ。
- ライセンス（Unity Personal）：Hub のサインインが切れていると、バッチモードは 9.1 秒で終わりの符号 198 で止まった（`No valid Unity Editor license found`。headless の利用権が見つからない）。操縦士が Hub でサインインし直した後は通った。
- Editor（GUI）が開いているとき：
  - GUI の Editor でクローンを開くのに 9.9 秒（`[Project] Loading completed`）。
  - 同じプロジェクトにバッチモードを当てると、0.4 秒で終わりの符号 1。ログに理由の文は無い。
  - 別のクローンなら並べて走る（起動 35.9 秒・EditMode のテスト 9.6 秒。1 件が通過）。
  - GUI を閉じた後は、同じプロジェクトのバッチモードが 7.1 秒で通った。
- .NET の道（Unity を起こさない）：src/Core/Core.csproj（net8.0。Assets/Core の .cs をそのまま含む）のビルドは、変更なしで 0.5 秒、1 ファイルの変更の後で 0.6 秒。tests/Core.Tests（NUnit 30 件）は、再ビルド込みで 1.4 秒。Unity に依るコード（MonoBehaviour・Editor のスクリプト）は、この道ではコンパイルできない。
