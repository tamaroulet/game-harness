## 1. 問題の見立て：素のチャットは、大きい仕事でどう落ちるか

先人の記録と公式のベンチが示す落ち方は、次の 4 つにまとまる。

| 落ち方 | 出どころ |
|:--|:--|
| 仕様の読み違いと、完了の早合点。一気に作ろうとして途中で文脈が尽き、半端で記録の無い状態を残す。後のセッションが進みを見て「完了」と言う | H#C1・H#C3（Anthropic）。SWE-EVO では gpt-5 の失敗の 6 割超が指示の読み違い（B#C4） |
| 多ファイルの整合の崩れ。別のファイルの部品を読まずに推測し、参照を壊す | FeatureBench の失敗の最多は NameError、次が推測の怠け（B#C12・B#C13） |
| 退行。新しい機能のたびに既存の機能を壊す | 大きいプロジェクトの終盤（H#C15） |
| 長い文脈での劣化。入力が長くなるほど、情報を正しく引き出す力が一様でなく落ちる | H#C10・H#C27 |

- 規模の差：公式の長い課題では、強いモデルでも解決は 1〜2 割台（SWE-EVO の最高 25%、FeatureBench の Claude 4.5 Opus 11.0%。B#C2・B#C10）。単発の課題（SWE-bench）は飽和に近い（B#C7）。
- 手元の課題では落ちなかった：v3 の自作の鎖の課題（6 ステージ）では、素の A が 6/6 を 1 回で完了し、B のゲートは 42 ステージすべてで 1 回目に合格した（[実験と計画](experiments.md)の M-03、P-023）。課題がモデルの単独の範囲の内にあると、ハーネスの価値は原理的に測れない。

## 2. 先人の知見の要点

### 2-1. 状態は外に、構造化して置く

- 長く走るエージェントの核の課題は、セッションが記憶なしに始まること（H#C1）。Anthropic は、初期化役が機能の一覧（JSON。全部「未達」から）・進捗のファイル・最初のコミット・起動の手順を作り、実装役が 1 回に 1 機能を進める形にした（H#C2・H#C3）。
- JSON にしたのは、モデルが Markdown より書き換えにくいから（H#C2）。2 つの役の違いは最初の頼みだけで、ハーネスは同じ（H#C4）。価値は仕掛けではなく、環境（ファイル・テスト・起動の手順）の設計にある。
- 新しい文脈に入るエージェントは向き直りに時間を使う（H#C16）。引き継ぎのファイルは、それを短くするためにある。

### 2-2. 検証の背圧

- 検証器がほぼ完璧でないと、違う問題を解く（H#C14）。テスト・型・静的解析など、何でも背圧として配線して不正な生成を拒む（H#C29）。
- FeatureBench では、正解の単体テストを見せると解決率が大きく上がった（B#C11。表 7 で Lite の Gemini 3 Pro が 10% → 60%）。何をもって完了かが分かることの効きが最大。
- ただし、エージェントが自分で書いたテストは合否の根拠として弱い（P-016）。受け入れの確かめは、実装役と別の役か人が先に決める。

### 2-3. 文脈とキャッシュ

- 1 つの仕事の中は、頼みの先頭を固定して追記だけにし、キャッシュの当たりを守る（H#C20・H#C21）。本番のエージェントでは入力が出力の約 100 倍（H#C22）。
- 圧縮は戻せる形にする（パスや URL を残す。H#C23）。最も安全で軽い圧縮は、古い道具の結果を消すこと（H#C11）。古い観測を伏せるだけで、費用は半分、解決率は要約と同じかやや上だった（H#C31）。
- 学習で畳む方式（Context-Folding）は RL で学ばせることが前提（H#C30）。手元では学習できないので、学習の効きを当てにしない（P-028）。
- キャッシュの値段は提供元で違う。Claude は先頭の一致で会話をまたいで当たり、読みは 0.1 倍（H#C17）。Gemini API は 2.5 以降で implicit caching が既定（H#C18）。手元の agy は、新しい会話が文脈 約 1.6 万〜2.1 万トークンを越えるまで当たらない（M-01、P-021）。

### 2-4. リセットか継続かは、モデルと仕事の長さで決まる

- Sonnet 4.5 は文脈が満ちると早く切り上げる（context anxiety）ので、リセットが要った（H#C5）。Opus 4.5 ではその振る舞いが消え、リセットを外して 1 本の続くセッションにした（H#C6）。
- 毎回新しい文脈で回す Ralph も、仕様の読み直しは無駄と承知のうえ（H#C28）。

### 2-5. 部品は「モデルの弱さの仮定」として外す条件を付ける

- ハーネスの部品は、モデルが単独でできないことの仮定（H#C7）。1 つずつ外して確かめ、新しいモデルで見直す。
- 評価役は、課題がモデルの単独で確実にできる範囲の外にあるときだけ費用に見合う（H#C8）。

### 2-6. 書き手は 1 本、検証は文脈を分ける

- 多役は、書き込みを 1 本の流れに保ち、ほかの役が知恵を足すときに最もよく効く（H#C24）。検証役は書き手と文脈を共有しないときに最もよく効いた（H#C25）。
- 多役は約 15 倍のトークンを使う（H#C13）。

### 2-7. 費用の構造

- トークンの量が性能を大きく左右し、エージェントはチャットの約 4 倍、多役は約 15 倍のトークンを使う（H#C13）。
- 公式の長い課題は 1 課題で 100 万を超える入力トークン（B#C14）。3 役のハーネスは単独の 20 倍超の費用で、出来の差は大きかった（H#C9、1 例）。

## 3. 手元の実測（数は[実験と計画](experiments.md)の M-01〜M-04）

- 1 ターンのキャッシュでない入力は、約 2,800〜2,900 トークンの基礎の分に、前の道具の出力が乗る。利用枠はターンの数にほぼ比例し、時間は出力（思考）の量で決まる。
- agy の新しい会話は、文脈が約 1.6 万〜2.1 万トークンを越えるまでキャッシュが当たらない（25 回の会話の始まりで例外なし、5〜12 応答）。1 回の始まりで、キャッシュでない入力が約 5.6 万〜13.6 万トークン（中央 約 8.5 万。M-01、P-021）。
- 同じ 6 ステージの課題で、1 つの会話を続けた A はキャッシュでない分（入力＋出力）が 67.7 万、ステージごとに新しい会話にした B は 136.8 万（M-02、P-022）。差の約半分が立ち上がりの冷え、残りがターンの多さ（向き直りの読み直しと試しのやり直し）。
- 手元の環境は、FeatureBench の Fast（CPU で走る 100 課題）を回せる。Lite の 19 課題は GPU を求め、手元の Docker では走らない（M-04、P-033）。

## 4. 実戦の想定と、ハーネスの責務

### 4-1. 想定：賢いモデル × 中くらいの仕事の一括

- 実戦（実際のゲーム開発。Unity などでの実開発）では、その時点で最も賢いモデルに、1 つの機能・1 つのまとまりの単位で仕事を一括で任せる（P-030）。
- 公開する比べと証明（校正 X-01 → 開発 X-02 → held-out での証明 X-03 と公開資料）は、agy の Gemini のモデル 1 つで完結させる。Claude の枠で公式のベンチは回さない（P-030）。
- 標準のモデルは Gemini 4 Hydrogen（medium）。X-01 の 1 課題目で、週の目盛りの減りが 2 ポイント未満だったので、数の線（3 ポイント以下）により標準にした（2026-11-14、P-032）。3.8 Flash は、要るときに少数の課題で比べる候補。
  - 理由：公式のベンチは強いモデルでも難しく、天井には張り付きにくい（SWE-EVO の最高 25%、FeatureBench の Claude 4.5 Opus 11.0%、Lite の Gemini-3-Pro-Preview と Gemini CLI で解決 10%。B#C2・B#C10・B#C17）。
  - 逆に 3.8 Flash では、力の不足で 0% に張り付くおそれがある。そのうえ、実戦の賢いモデルでは要らない「弱いモデルの補助輪」の効きを測ってしまうおそれがある。
  - Hydrogen は agy の同じ Gemini Models の週の枠で動き、Argon の枠と Claude の枠を使わない（操縦士、2026-11-14）。
- そのため、ハーネスは、実戦で賢いモデルに中くらいの仕事を任せるときにもそのまま通用する共通骨格として設計し、検証用のモデルで確かめる。共通骨格は「要件の台帳・1 つの単位を 1 つの会話で続ける・機械の背圧」に限り、細かいリセットに頼らない（4-2・4-4、H5）。
- 弱いモデルのために仕事を細かく刻み、毎回文脈を消して面倒を見る形は採らない。agy では細かいリセットのたびに約 5.6 万〜13.6 万トークン（中央 約 8.5 万）の立ち上がりがかかり（P-021）、強いモデルは続くセッションで足りる（H#C6）。

### 4-2. ハーネスの責務：ベンチで確かめる共通骨格

どの賢いモデルでも残る失敗（仕様の読み飛ばし・完了の早合点・退行。B#C4・B#C12・H#C3・H#C15）を抑える、最小の骨格だけをベンチで確かめる。

| 所 | 責務 | 狙う落ち方 |
|:--|:--|:--|
| 入口 | 要件の台帳：仕様（課題の文・リリースノート・企画書）から、要件と確認の項目を JSON で切り出す。実装役が変えてよいのは状態の欄だけ。台帳を作る役と実装役を分け、台帳が仕様を覆うかを別の文脈で確かめる | 読み飛ばし・完了の早合点 |
| 内部 | 1 つの単位を 1 つの会話で続ける（細かいリセットをしない）。頼みの先頭を固定して追記だけにする（キャッシュを効かせる）。調べ・実装・その場の確かめまで一気に走り切らせる。道具の出力は要約の行にし、詳細はファイルに置く | 向き直りの費用・文脈の汚れ |
| 出口 | 機械の背圧の関門：手番の後に、見えるテスト（C1。ベンチでは白箱の F2P のテストのファイル）と静的解析（C2。pyflakes の undefined name と構文の誤り）を走らせ、通るまで同じ会話に押し返す。データの P2P の一覧は A に見えないので使わない（既存のテストの退行は、採点の P2P で測る）。合格した仕事だけを確定し、台帳で次の単位へ機械的に引き継ぐ。エージェントが自分で書いたテストは手がかりに使うが、合否の根拠にしない（P-016） | 完了の早合点・参照の崩れ・推測の実装 |

- 正解の受け入れテストの扱い：FeatureBench の通常の実行（Level 1）は、初期化のときに F2P のテストのファイルを消して隠す。白箱の設定（fb infer の --white）は、ファイルを残し、頼みにそのパスの注記を足す。評価はどちらも、エージェントが変えた F2P のファイルを消し、公式のテストに戻してから走らせる（featurebench/infer/runtime.py と featurebench/harness/runtime.py。コミット 08b25d9 を 2026-11-14 に読んだ）。表 7 の 10% → 60%（B#C11）は、正解のテストを見せた条件の数。
- 隠したままの X-01 の 5 課題では、落ちの大半が、課題の文に無い文言・書式を隠しテストが確かめることによるもので、どの手順でも届かなかった。同じ 5 課題を白箱で走らせると 4 つが解け、残った落ちは手順の型（早合点）だった（[実験と計画](experiments.md)の §3）。X-01 の続きとして、白箱で Fast の大きい層の 5 課題を校正すると、3 つが解け、落ちた 2 つはどちらも手順の型（早合点）だった。判定の線（操縦士の ok、2026-11-14）により、X-02 は白箱の Fast の大きい層で進める。
  - 白箱は課題の条件で、ハーネスの部品ではない。素の A にもハーネスにも同じテストを見せるので、比べは公平なまま。実戦の受け入れテストの事前の提示（4-4 の ①）に近い。
  - 白箱の数は、公式の順位表の数（隠した条件）とは比べられない。
- FeatureBench の 1 課題は、はじめから 1 つの機能。複数の機能を台帳で引き継ぐ効きは、大きい課題と SWE-EVO の複数 PR の課題で確かめる（実験と計画の X-02）。

### 4-3. 人の手動の /clear と何が違うか

- 引き継ぎを、人の記憶やメモでなく、機械が作って機械が確かめる成果物（台帳の状態はテストの結果で決まる）で行う。
- 完了は、モデルの宣言でなく、外の検証で決まる。
- 人が画面の前にいなくても回る。操縦士を上流に戻すことが目的。
- 区切りの粒度と検証の頻度を、勘でなく実測の損益で決める。
- 限界：モデルを賢くはしない。モデルが単独で確実にできる仕事では、上乗せの費用でしかない（M-02・H#C8）。

### 4-4. 共通骨格と、実戦で専用化する部分

ハーネスを 2 つの層に分ける。ベンチで確かめるのは共通骨格（4-2）だけで、実戦の専用化はベンチの形に縛られずに作る。

- 共通骨格は、モデルが賢くなっても要る理由が消えにくいと見るもの（設計の判断）に限る。
  - 要件の台帳と機械の背圧：検証器がほぼ完璧でないと、エージェントは違う問題を解く。H#C14・H#C29。
  - 1 つの会話の継続：強いモデルが向かう側にある。Opus 4.5 でリセットを外した。H#C6。
  - モデルの弱さを補う仕掛け（細かいリセット・独立の検証役）は既定で使わず（§5・§6）、賢いモデルに替えるときに外す部品が無い形にしておく。
- 実戦（Unity × その時点で最も賢いモデル。今なら Opus 5.5）では、次のように専用化する。
  - ① 正解の受け入れテストと合格の条件を、はじめから実装役に見せる。見せると解決が大きく上がる（B#C11）。受け入れの基準は人が決める（憲章 §6）。ベンチの通常の実行では隠されているが、X-02 からは白箱で回し、素の A にもハーネスにも見せる（4-2）。
  - ② 1 つの会話に任せる仕事の粒度を、モデルの推論の力に合わせて大きくする。
  - ③ 背圧のアダプタを、Unity 専用の多段の関門に作り替える（§9）。
- 専用化は、台帳の中身（受け入れテストを持つか）・周回の粒度の設定・アダプタで行い、制御核は替えない（§5-1）。
- 検証用のモデルで確かめるのは、ハーネスの効きが共通骨格から出ること（H5）。賢いモデルでの効きの大きさと、実戦の専用化の効きは、このベンチの計画では測らない（§12）。公開資料には、数は検証用のモデルでの共通骨格の結果だけを書き、持ち越しは、測っていない構造の理由として書く。

## 5. 構成

### 5-1. 制御核と実行環境のアダプタ

ハーネスを、制御核・実行環境のアダプタ・エージェントの実行口の 3 つに分ける。制御核は、どの実行環境で、どのモデルが動くかを知らない。ベンチで確かめた制御核（共通骨格。4-2）を、後から書き直さずに Unity の実開発へ持ち込むため（操縦士、2026-11-13）。

| 層 | 中身 | ベンチ（X-01〜X-03） | Unity の実開発 |
|:--|:--|:--|:--|
| 制御核 | 要件の台帳（JSON。要件と確認の項目、あれば受け入れテスト。実装役は状態の欄だけ変える）・検証の手順の形（汎用のスキーマ）・1 つの単位を 1 つの会話で進める周回（粒度は設定）・検証の背圧の関門（合否の決定と押し返し） | 同じ。白箱で回す（4-2）。見えるテスト（F2P）を台帳と背圧の関門にどう入れるかは、X-02 の前に決める | 同じ。台帳に受け入れテストを入れ、粒度を大きくする（4-4） |
| 実行環境のアダプタ | 検証の手順を実際に走らせ、結果を決まった形で返す。ファイルの受け渡しと閉じ込め | FeatureBench の課題の箱（harness/fb_core.py）。見えるテスト（C1）と静的解析（C2。pyflakes）を走らせる | Unity 専用の多段の関門（§9） |
| エージェントの実行口 | 会話を始める・続ける、利用量と使ったモデルの記録、利用枠切れの検出 | agy の Gemini（標準は gemini-4-hydrogen-medium。P-032。harness/agy_stream.py・fb_agy.py・fb_core.py） | その時点で最も賢いモデルの CLI |

- 制御核とアダプタのあいだは、検証の手順の形（どの確かめを・どの順で・何をもって合格とするか）と、結果の形（確かめごとの合否・通ったテストと落ちたテストの名・時間・生の出力の置き場）だけで繋ぐ。制御核は、コマンドの文字列・パスの形・OS を持たない。
- 制御核とエージェントの実行口のあいだは、会話の操作（始める・送る・続ける）と、手番ごとの利用量とモデルの記録だけで繋ぐ。
- 制御核は harness/core.py（台帳・確かめの手順と結果の形・合否・押し返しの文・1 つの単位を 1 つの会話で進める周回）。FeatureBench の箱との繋ぎは harness/fb_core.py：
  - 実行環境のアダプタ：見えるテストのファイルを pytest で走らせ、項目ごとの合否を読む（C1）。見えるテストのファイルを、隠しのパッチが消した import の足し戻しを超えて書き換えていたら、C1 を落とす（テストの書き換えで関門を通さない）。変えた .py に pyflakes をかけ、undefined name と構文の誤りを落ちに数える（C2）。道具が無いときは合格にせず、走りごと止める。
  - エージェントの実行口：箱の中の agy の会話を始め、押し返しは --conversation で同じ会話に送る。手番ごとに、送った文・利用量・報告されたモデルを残す。
  - 腕は config/fb_core.json で、部品を 1 つずつ足し外しする（台帳を添える・関門で押し返す・静的解析）。全部切った腕は素の A と同じ形。2026-11-14 に作り、偽物の agy で端から端まで確かめた（利用枠 0）。
- 腕の公平の決まり：ハーネスが使うのは、A にも見えるもの（リポジトリ・課題の文・見えるテスト）だけで、データの P2P の一覧は使わない。押し返しの文は、落ちた確かめの名と 1 行の要約を機械的に並べるだけにし、お願いを足さない（憲章 §5）。時間の上限は、押し返しと確かめを含めて A と同じ（1 課題 60 分）。

### 5-2. 部品ごとの「補う弱さ」と「外す条件」

| 部品 | 補うモデルの弱さ（仮定） | 外す条件 |
|:--|:--|:--|
| 要件の台帳（入口） | 仕様の読み飛ばし・完了の早合点 | 台帳なしの A と比べて、読み飛ばしと早合点の失敗が減らない |
| 台帳の網羅の確かめ（別の文脈） | 台帳の作り手の見落とし | 網羅の指摘が開発用で 0 件、または指摘を入れても解決が変わらない |
| 見えるテストの関門（C1。押し返し） | 完了の早合点 | 関門ありとなしで、早合点の落ちの数も解決も変わらない |
| 静的解析の関門（C2。pyflakes） | 参照の崩れ・推測の実装 | 開発用で、C2 が単独で落ちを拾った手番（C1 が通り C2 が落ちた手番）が 0 件、または拾っても解決が変わらない（core_record.json から数える） |
| 既存のテストの回帰（作らない） | 退行 | 外す条件に当たった：X-01 の 15 回の走りで退行は 0 件。退行は採点の P2P で測り続け、出たら作り直す |
| 区切りでの新しい会話＋機械の引き継ぎ | 長い文脈での劣化・context anxiety | 続く会話のほうが、同じ費用で解決が下がらない |
| 独立の検証役（既定は切る） | 自分の仕事への甘い評価 | 課題がモデルの単独の範囲の内（指摘が解決を変えない） |

## 6. 採らないもの

- 小さい段ごとのリセット（毎ステージ・毎ターンの新しい会話）。agy の立ち上がりの費用（P-021）と、続く会話の安さ（P-022）による。
- 並列の書き手（多役の群れ）。書き込みが割れる（H#C24）。
- 学習を前提にした文脈の畳み（P-028）。
- 思考の強さを下げて費用を削ること。手戻りで枠をかえって使う（操縦士、2026-11-08）。
- 頼みの文面のお願いを効きに数えること（憲章 §5）。
- 素の A が落ちない自作の小さい課題での比べ（M-03、P-018）。

## 8. 反証から入れる条件

調べで見つかった不利な証拠は、方向を止めず、条件として入れる。

- 課題が小さいと差は出ない（B#C7）→ 課題は、素の A が落ちることを校正で確かめてから使う（憲章 §5）。
- 強いモデルは続くセッションで足りる（H#C6）→ リセットは既定にせず、測って決めるつまみにする（§5）。
- 学習なしの文脈の管理は弱い（H#C30）→ 学習の効きを当てにしない。
- 多役は高く壊れやすい（H#C13・H#C24）→ 書き手は 1 本。検証役は既定で切る。
- 公式のベンチにも限界がある。SWE-EVO は 48 課題で 1 課題が 2.08 ポイント（B#C5）、分布は dvc に偏る（B#C6）。どちらのベンチも Python のライブラリで、ゲームの好みは測れない（H#C26）→ 主張には区間と限界を書く。ゲームの質は Unity の実戦で別に見る。
- 規則の反証の段（別の会社のモデル Argon）はまだ行っていない。行ったら、この節に足すか書き直す。

## 9. Unity への接続の方針

- 要件の台帳の源は、操縦士の企画書。人は企画と「何ができれば完了か」（受け入れテストと合格の条件）を決め、はじめから実装役に見せる（4-4 の ①）。実装と検証はハーネスに任せる（憲章 §1・§6）。
- 出口の背圧は、Unity 専用の多段の関門にする（4-4 の ③）：速い C# のコンパイルと、.meta・Prefab の参照の検査 → 対象の EditMode テスト → 区切りでの PlayMode テストと画面の確かめ（Unity Test Framework のバッチモード、結果は XML。H#C19）。コンパイルが遅いので、速い段を先に作る。
- 見た目と遊び心地は、画面の写しと状態の読みを使う評価役で確かめる。好みの判断は人に残す。モデルは音を聞けない。
- 持ち込みは、台帳の中身・周回の粒度・実行環境のアダプタ・エージェントの実行口を替えて行う。制御核は替えない（§5-1）。1 つの会話に任せる粒度は、実戦のモデルの推論の力に合わせて大きくする（4-4 の ②）。
- 接続の下見で最初に確かめること：Unity の公式の MCP の今の状態、ネイティブの Windows ではエージェントを閉じ込められないこと（P-017）。リポジトリの C# の読み書きを拒む設定は、2026-11-13 に外した。
