## 1. 問題の見立て：素のチャットは、大きい仕事でどう落ちるか

先人の記録と公式のベンチが示す落ち方は、次の 4 つにまとまる。

| 落ち方 | 出どころ |
|:--|:--|
| 仕様の読み違いと、完了の早合点。一気に作ろうとして途中で文脈が尽き、半端で記録の無い状態を残す。後のセッションが進みを見て「完了」と言う | H#C1・H#C3（Anthropic）。SWE-EVO では gpt-5 の失敗の 6 割超が指示の読み違い（B#C4） |
| 多ファイルの整合の崩れ。別のファイルの部品を読まずに推測し、参照を壊す | FeatureBench の失敗の最多は NameError、次が推測の怠け（B#C12・B#C13） |
| 退行。新しい機能のたびに既存の機能を壊す | 大きいプロジェクトの終盤（H#C15） |
| 長い文脈での劣化。入力が長くなるほど、情報を正しく引き出す力が一様でなく落ちる | H#C10・H#C27 |

- 規模の差：公式の長い課題では、強いモデルでも解決は 1〜2 割台（SWE-EVO の最高 25%、FeatureBench の Claude 4.5 Opus 11.0%。B#C2・B#C10）。単発の課題（SWE-bench）は飽和に近い（B#C7）。
- 手元の課題では落ちなかった：v3 の自作の鎖の課題（6 ステージ）では、素の A が 6/6 を 1 回で完了し、B のゲートは 42 ステージすべてで 1 回目に合格した（[実験と計画](experiments.md)の M-03、P-023）。課題がモデルの単独の範囲の内にあると、ハーネスの価値は原理的に測れない。

## 2. 先人の知見の要点

### 2-1. 状態は外に、構造化して置く

- 長く走るエージェントの核の課題は、セッションが記憶なしに始まること（H#C1）。Anthropic は、初期化役が機能の一覧（JSON。全部「未達」から）・進捗のファイル・最初のコミット・起動の手順を作り、実装役が 1 回に 1 機能を進める形にした（H#C2・H#C3）。
- JSON にしたのは、モデルが Markdown より書き換えにくいから（H#C2）。2 つの役の違いは最初の頼みだけで、ハーネスは同じ（H#C4）。価値は仕掛けではなく、環境（ファイル・テスト・起動の手順）の設計にある。
- 新しい文脈に入るエージェントは向き直りに時間を使う（H#C16）。引き継ぎのファイルは、それを短くするためにある。

### 2-2. 検証の背圧

- 検証器がほぼ完璧でないと、違う問題を解く（H#C14）。テスト・型・静的解析など、何でも背圧として配線して不正な生成を拒む（H#C29）。
- FeatureBench では、正解の単体テストを見せると解決率が大きく上がった（B#C11。表 7 で Lite の Gemini 3 Pro が 10% → 60%）。何をもって完了かが分かることの効きが最大。
- ただし、エージェントが自分で書いたテストは合否の根拠として弱い（P-016）。受け入れの確かめは、実装役と別の役か人が先に決める。

### 2-3. 文脈とキャッシュ

- 1 つの仕事の中は、頼みの先頭を固定して追記だけにし、キャッシュの当たりを守る（H#C20・H#C21）。本番のエージェントでは入力が出力の約 100 倍（H#C22）。
- 圧縮は戻せる形にする（パスや URL を残す。H#C23）。最も安全で軽い圧縮は、古い道具の結果を消すこと（H#C11）。古い観測を伏せるだけで、費用は半分、解決率は要約と同じかやや上だった（H#C31）。
- 学習で畳む方式（Context-Folding）は RL で学ばせることが前提（H#C30）。手元では学習できないので、学習の効きを当てにしない（P-028）。
- キャッシュの値段は提供元で違う。Claude は先頭の一致で会話をまたいで当たり、読みは 0.1 倍（H#C17）。Gemini API は 2.5 以降で implicit caching が既定（H#C18）。手元の agy は、新しい会話が文脈 約 1.6 万〜2.1 万トークンを越えるまで当たらない（M-01、P-021）。

### 2-4. リセットか継続かは、モデルと仕事の長さで決まる

- Sonnet 4.5 は文脈が満ちると早く切り上げる（context anxiety）ので、リセットが要った（H#C5）。Opus 4.5 ではその振る舞いが消え、リセットを外して 1 本の続くセッションにした（H#C6）。
- 毎回新しい文脈で回す Ralph も、仕様の読み直しは無駄と承知のうえ（H#C28）。

### 2-5. 部品は「モデルの弱さの仮定」として外す条件を付ける

- ハーネスの部品は、モデルが単独でできないことの仮定（H#C7）。1 つずつ外して確かめ、新しいモデルで見直す。
- 評価役は、課題がモデルの単独で確実にできる範囲の外にあるときだけ費用に見合う（H#C8）。

### 2-6. 書き手は 1 本、検証は文脈を分ける

- 多役は、書き込みを 1 本の流れに保ち、ほかの役が知恵を足すときに最もよく効く（H#C24）。検証役は書き手と文脈を共有しないときに最もよく効いた（H#C25）。
- 多役は約 15 倍のトークンを使う（H#C13）。

### 2-7. 費用の構造

- トークンの量が性能を大きく左右し、エージェントはチャットの約 4 倍、多役は約 15 倍のトークンを使う（H#C13）。
- 公式の長い課題は 1 課題で 100 万を超える入力トークン（B#C14）。3 役のハーネスは単独の 20 倍超の費用で、出来の差は大きかった（H#C9、1 例）。

## 3. 手元の実測（数は[実験と計画](experiments.md)の M-01〜M-04）

- 1 ターンのキャッシュでない入力は、約 2,800〜2,900 トークンの基礎の分に、前の道具の出力が乗る。利用枠はターンの数にほぼ比例し、時間は出力（思考）の量で決まる。
- agy の新しい会話は、文脈が約 1.6 万〜2.1 万トークンを越えるまでキャッシュが当たらない（25 回の会話の始まりで例外なし、5〜12 応答）。1 回の始まりで、キャッシュでない入力が約 5.6 万〜13.6 万トークン（中央 約 8.5 万。M-01、P-021）。
- 同じ 6 ステージの課題で、1 つの会話を続けた A はキャッシュでない分（入力＋出力）が 67.7 万、ステージごとに新しい会話にした B は 136.8 万（M-02、P-022）。差の約半分が立ち上がりの冷え、残りがターンの多さ（向き直りの読み直しと試しのやり直し）。
- 手元の環境は公式のベンチを回せる（M-04）。

## 4. 実戦の想定と、ハーネスの責務

### 4-1. 想定：賢いモデル × 中くらいの仕事の一括

- 実戦では、その時点で最も賢いモデルに、1 つの機能・1 つのまとまりの単位で仕事を一括で任せる（P-030）。
- 今の検証で Gemini 3.8 Flash（agy）を使うのは、Claude の枠を温存しながら仕組みの効き目を確かめるための仮の選択で、実戦の前提ではない。仕組みの結論は、実戦のモデルで確かめ直す。
- 弱いモデルのために仕事を細かく刻み、毎回文脈を消して面倒を見る形は採らない。agy では細かいリセットのたびに約 5.6 万〜13.6 万トークン（中央 約 8.5 万）の立ち上がりがかかり（P-021）、強いモデルは続くセッションで足りる（H#C6）。

### 4-2. ハーネスの責務（中くらいの仕事の入口・内部・出口）

| 所 | 責務 | 狙う落ち方 |
|:--|:--|:--|
| 入口 | 企画書・仕様・リリースノートから、受け入れの確かめ（テスト）付きの機能の台帳（JSON）を切り出す。実装役が変えてよいのは状態の欄だけ。台帳を作る役と実装役を分け、台帳が仕様を覆うかを別の文脈で確かめる。創作の受け入れの基準は人が決める | 読み違い・完了の早合点 |
| 内部 | 1 つの会話を続け、頼みの先頭を固定して追記だけにする（キャッシュを効かせる）。賢いモデルに、調べ・実装・その場のテストまで一気に走り切らせる。道具の出力は要約の行にし、詳細はファイルに置く | 向き直りの費用・文脈の汚れ |
| 出口 | 決まった検証（対象のテスト・型と静的解析・既存の回帰のテスト、Unity ならバッチモードの EditMode と PlayMode のテスト）で未完成と退行を押し返す。合格した仕事だけを確定し（コミット）、台帳と進捗で次の仕事へ機械的に引き継ぐ | 退行・多ファイルの崩れ・偽の完了 |

### 4-3. 人の手動の /clear と何が違うか

- 引き継ぎを、人の記憶やメモでなく、機械が作って機械が確かめる成果物（台帳の状態はテストの結果で決まる）で行う。
- 完了は、モデルの宣言でなく、外の検証で決まる。
- 人が画面の前にいなくても回る。操縦士を上流に戻すことが目的。
- 区切りの粒度と検証の頻度を、勘でなく実測の損益で決める。
- 限界：モデルを賢くはしない。モデルが単独で確実にできる仕事では、上乗せの費用でしかない（M-02・H#C8）。

## 5. 構成（部品ごとの「補う弱さ」と「外す条件」）

| 部品 | 補うモデルの弱さ（仮定） | 外す条件 |
|:--|:--|:--|
| 機能の台帳（入口） | 仕様の読み違い・完了の早合点 | 台帳なしの A と比べて、読み違いと早合点の失敗が減らない |
| 台帳の網羅の確かめ（別の文脈） | 台帳の作り手の見落とし | 網羅の指摘が開発用で 0 件、または指摘を入れても解決が変わらない |
| 速い確かめ（対象のテスト・型・静的解析） | 推測の実装・参照の崩れ | 失敗の型に参照の誤りと推測が出ない |
| 回帰の確かめ（区切りごと） | 退行 | 開発用で退行が 0 件 |
| 区切りでの新しい会話＋機械の引き継ぎ | 長い文脈での劣化・context anxiety | 続く会話のほうが、同じ費用で解決が下がらない |
| 独立の検証役（既定は切る） | 自分の仕事への甘い評価 | 課題がモデルの単独の範囲の内（指摘が解決を変えない） |

## 6. 採らないもの

- 小さい段ごとのリセット（毎ステージ・毎ターンの新しい会話）。agy の立ち上がりの費用（P-021）と、続く会話の安さ（P-022）による。
- 並列の書き手（多役の群れ）。書き込みが割れる（H#C24）。
- 学習を前提にした文脈の畳み（P-028）。
- 思考の強さを下げて費用を削ること。手戻りで枠をかえって使う（操縦士、2026-11-08）。
- 頼みの文面のお願いを効きに数えること（憲章 §5）。
- 素の A が落ちない自作の小さい課題での比べ（M-03、P-018）。

## 8. 反証から入れる条件

調べで見つかった不利な証拠は、方向を止めず、条件として入れる。

- 課題が小さいと差は出ない（B#C7）→ 課題は、素の A が落ちることを校正で確かめてから使う（憲章 §5）。
- 強いモデルは続くセッションで足りる（H#C6）→ リセットは既定にせず、測って決めるつまみにする（§5）。
- 学習なしの文脈の管理は弱い（H#C30）→ 学習の効きを当てにしない。
- 多役は高く壊れやすい（H#C13・H#C24）→ 書き手は 1 本。検証役は既定で切る。
- 公式のベンチにも限界がある。SWE-EVO は 48 課題で 1 課題が 2.08 ポイント（B#C5）、分布は dvc に偏る（B#C6）。どちらのベンチも Python のライブラリで、ゲームの好みは測れない（H#C26）→ 主張には区間と限界を書く。ゲームの質は Unity の実戦で別に見る。
- 規則の反証の段（別の会社のモデル Argon）はまだ行っていない。行ったら、この節に足すか書き直す。

## 9. Unity への接続の方針

- 機能の台帳の源は、操縦士の企画書。人は企画と「何ができれば完了か」を決め、実装と検証はハーネスに任せる（憲章 §1・§6）。
- 出口の背圧は、コンパイルの確かめと Unity Test Framework のテスト（バッチモードの EditMode・PlayMode、結果は XML。H#C19）。コンパイルが遅いので、速い抜き取りの道を先に作る。
- 見た目と遊び心地は、画面の写しと状態の読みを使う評価役で確かめる。好みの判断は人に残す。モデルは音を聞けない。
- 接続の下見で最初に確かめること：Unity の公式の MCP の今の状態、ネイティブの Windows ではエージェントを閉じ込められないこと（P-017）、リポジトリの C# の読みを拒む設定（[整理の計画](cleanup_plan.md)の 6）。
