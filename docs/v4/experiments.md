### 5-2. 公式のテストの項目の根拠の分け（静的な規則。パッチの結果を見ずに、走らせる前に決めた）

- 使うもの：課題の文・隠しのパッチ（データの patch。実装を消すパッチ）・公式のテストのファイル（データの test_patch から戻した元の中身）・課題の始まりの状態（隠しのパッチを当てた後）のソース（テストのファイルを除く）。A のパッチと、評価の結果は使わない。
- A の課題ごとの解決と、落ちた項目の数の一部（§3・§4）は、規則を書く前から分かっている。規則はそれに合わせて作らず、決めた後は変えない。計算は道具（harness/fb_ground.py）が機械で行う。
- 規則：
  1. 消された名：隠しのパッチが消した行（テストのファイルを除く）の、`def 名`・`async def 名`・`class 名` と、字下げの無い代入 `名 =` の名。前後が `__` の名は除く。
  2. テストの範囲：公式のテストのファイルのテストの関数ごとに、関数の本体・同じクラスの準備のメソッド（setup_method・setup_class・setup・setUp）・引数の名と同じ名の、同じファイルの fixture の本体・本体から名で直に呼ぶ、同じファイルの関数の本体（1 段まで）。
  3. 範囲の中の名：Name の名と、属性の名（Attribute の attr）。
  4. 範囲の中の文言：
     - match= の文字列：pytest.raises・pytest.warns・pytest.deprecated_call と、名が assert_produces_warning の呼び出し。
     - assert の文の比べ（==・!=・in・not in）の文字列の定数と、名が assert で始まる呼び出しの文字列の定数のうち、12 字以上か、空白か `<>:%{}[]=` のどれかを含むもの。
  5. 項目の分け（上から、最初に当たったもの）：
     - 隠し：文言 — 4 の文言のうち、課題の文にも、始まりの状態のソースにも無いものがある。空白を 1 つに詰め、大文字と小文字を区別せずに比べる。match= は、正規表現の `\` と、先頭の `^` と末尾の `$` を外して比べる。
     - 隠し：名 — 3 の名のうち、消された名で、課題の文に無く、始まりの状態のソースにも名として出てこないものがある。
     - 根拠：参照 — 3 の名のうち、消された名で、課題の文に無く、始まりの状態のソースには名として出てくる（残ったコードが呼んでいる）ものがある。
     - 根拠：文 — 上のどれでもない（課題の文の名か、消されていない既存の口だけを使う）。
  6. 公式の項目（パラメータの付いた 1 つずつ）は、テストの関数の分けを受け継ぐ。項目の名は正解の評価の記録から取り、pytest の項目の ID（path.py::…）の部分で突き合わせる。同じファイルの基底のクラスから受け継いだテストの関数は、子のクラスの名前の項目として扱い、準備のメソッドと fixture は子から基底の順に辿る。
- 段 b 以降の物差し（根拠のある項目の通過率など）は、この分けで数える。「根拠」は「根拠：文」と「根拠：参照」の 2 つで、分けて出す。

### 6-2. 母集団と dev・held-out（2026-11-20 に分けて封をした）

- 規則（操縦士が承認した。2026-11-20）：
  - 単位を途中で切らない。SlopCodeBench は問題を丸ごと（チェックポイント 1 から最後まで）、Mode 4 はゲーム（同じゲームのケースは同じ側）。
  - 母集団は 0b の事実と公開の issue だけで決め、エージェントの結果は見ない。
  - 層ごとに、ID を整列して非公開の乱数の種で混ぜ、先頭の round(n/3)（四捨五入）を dev、残りを held-out にする。層は SlopCodeBench が難しさ（易・中・難）、Mode 4 が視点（2D・3D）。
  - held-out は、層ごとの混ぜた順を保ったまま、層の中の位置の割合（(i+0.5)/n）で織り交ぜた順に並べて封をする（どこで切っても層の割合が崩れにくい）。
  - held-out の使い方（憲章 §5）：開発用で十分に磨き上げてから開ける。並びの先頭から区画（ブロック）に切り、区画ごとに 1 回だけ使う。区画の大きさは Gate ② で決める。一度開けた区画の課題は、やり直して証明に使い回さない。開けた結果は勝敗によらず全件を記録し、公開資料に含める。

### 6-3. 走らせ方の境界と採点の再現性（利用枠 0 で決めた。2026-11-20）

- ネットワーク（実装役のコンテナ）：
  - Docker の内部のネットワーク（`--internal`。外への経路が無い）だけにつなぎ、外への道は許可リストのプロキシ（tinyproxy 1.11.0 を別のコンテナで立てる）だけにする。許可は CONNECT の 443 で、agy の 3 つの宛先（daily-cloudcode-pa.googleapis.com・oauth2.googleapis.com・www.googleapis.com）と、依存を入れるための PyPI（pypi.org・files.pythonhosted.org）だけ。
  - 確認（実装役と同じイメージ・uid 1000 のコンテナから。宛先ごとの結果）の全文は [archive/phase1_checks.md](archive/phase1_checks.md) にある。
  - PyPI に SlopCodeBench の問題やテストを含むパッケージが無いことを確認した（作者の scb-check は品質の指標の道具）。
- agy の Web の道具と下位エージェント：
  - agy 1.5.3 の道具のうち、外から取るものは `search_web`（検索と要約をサーバーの側で行うので、コンテナのネットワークでは止まらない）・`read_url_content`・ブラウザの `webview_browser` で、下位エージェントの口は `invoke_subagent`（実行ファイルの中の道具の実装の名前と文言で確かめた。利用枠 0）。下位エージェントは親と違うモデルを選べ（`inherit` か `named_model`）、その道具の手番は親の stream-json に出ないので、モデルの照合（model_pin）と走りの後の検査のどちらも及ばない。
  - 公式のフック（`~/.gemini/config/hooks.json` の `PreToolUse` で `"decision": "deny"`）で、Web の道具（`search_web`・`read_url_content`・`read_url`・`open_browser_url`・`browser_subagent`・`webview_browser`）と `invoke_subagent` を止める。止めたときの文は、Web の道具が「Web access is not available in this environment.」、`invoke_subagent` が「Subagents are not available in this environment.」で、どの比較条件でも同じ。この土俵の素の A は、Web の道具と下位エージェントを使わない agy になる。
  - フックのファイルとスクリプトは root の持ち物で書き換え不可、置き場のフォルダは root の 1777（sticky）にする。uid 1000 からの書き換え・消し・移しはどれも拒まれた。agy は uid 1000 で起動して、フックを読み込んだ（ログに `loaded 1 named hooks`）。走りの後にフックのファイルの SHA-256 を照らす。
  - 走りの後の検査：止めた道具の手番が DONE で終わった走り（道具が走った）は無効にする。agy は deny を手番のエラー（`state: ERROR`、`tool_info.error` の文に「denied by pre-tool hook」）で返すと見込む（実行ファイルの文言と、ほかの道具がエラーで終わった手番の形から）。`deny` が実際に道具を止めるかと、見込みどおりの形で返るかは、モデルが道具を呼ぶまで観測できないので、Stage 1 の最初の軌跡で確かめる。
  - agy のエージェントの定義で道具の一覧そのものを絞る形は採らない（系統のプロンプトが替わり、素の A が変わる）。
- 実装役は非 root（イメージの agent ユーザー、uid 1000）で走らせる。公式の SlopCodeBench の走らせ方と同じ。
- 採点：
  - 公式の `slop-code eval-snapshot` を、実装役の作業場の写しに当てる。非 root（`HUID`・`HGID`）、基本のイメージは ID を記録して作り直さない。
  - 公式の採点は、基本のイメージに、環境の設定の environment.env から描いた Dockerfile のハッシュのラベルを付け、合わなければ作り直して同じ名前に付け替える（そのときの最新の道具が入る）。採点ごとに environment.env を変える形は、イメージの固定とぶつかる（確認の採点で実際に作り直しが起き、公式の設定の採点がビルドのキャッシュから同じ ID を作り直して名前を戻した）。
  - そこで、環境の設定は公式の値のまま `environment.include_os_env: true`（採点を起動したホストの環境変数を採点のコマンドに写す公式の口。ハッシュに入らない）だけを足し、`UV_EXCLUDE_NEWER`（uv が、その日時より後に公開された配布物を候補から外す）を採点の時刻にして、ホストの最小の環境（PATH・HOME=/tmp/agent_home・問題の置き場・HUID・HGID）で渡す。時刻を記録し、採り直すときは同じ時刻を与える。
  - 確認（3 回の採点でイメージが作り直されないこと・時刻を変えたときと同じ時刻の 2 回の比べ・HOME の写し）の全文は [archive/phase1_checks.md](archive/phase1_checks.md) にある。
  - 実行口は、採点の前に基本のイメージの ID を固定の値と照らし、違えば採点しない（偽物の通しで、確認の採点が付け替えた名前を、この照らし合わせが採点の前に止めた）。
- 採点の抜け道（scb-problems#39 の影響）：
  - #39 は Harbor 版を読んだ指摘。Harbor の走らせ方に固有の項目（`python -m pytest` での入れ替え・報酬のスクリプトの書き換え・root の共有コンテナ・品質の履歴・全チェックポイントのテストの写し）は、eval-snapshot には当たらない。eval-snapshot は、提出物を一時のフォルダに写して採点し、pytest を uvx の分けた環境で走らせ、報告をホストで読み、写すテストは今と前のチェックポイントのものだけ。
  - eval-snapshot の抜け道（#39 に無い。コードで確認した）：提出物にすでに `.evaluation_tests/` があると、公式のテストを写さず、テストの一覧づくりも本番もそのフォルダのテストで行う。実行口は、このフォルダのある提出物を採点せず、無効として記録する（正直な実装役は作らない名前）。
  - 実装役が作業場の根に置いた conftest.py は、公式の直し（slop-code-bench#16、使った版に入っている）で採点に読まれない。
  - テストの弱さ（#39 の問題のロジックの項目。eval-snapshot にも当たる）：母集団の 31 問・166 チェックポイントのそれぞれに、空の提出物を 2 種（入口のファイルが無いもの・何もせず終わりの符号 0 で終わるもの。どちらも requirements.txt は空）、公式の採点に通した（利用枠 0。公式の設定、uid 1000）。
    - どちらかで通るテストは、採点したテストの延べ 19,416 のうち 1,518（7.8%）。166 チェックポイントのうち 98、31 問のうち 22 にあった。
    - 群ごとには、Core 51/1,088・Error 174/982・Functionality 192/3,831・Regression 1,101/13,515。問題ごとの割合の上位 6 問は 20.6〜53.4%（dev は recli の 53.4% の 1 問。残りの 5 問は held-out で 20.6〜25.1%。held-out の問題の名前は公開に書かない）。scb-problems#39 が、空の作業場でチェックポイント 1 の 11 項目のうち 5 に通ると報告した問題は、手元でも 5/11 だった。
    - 空の提出物が strict や core を満たしたチェックポイントは 0。弱さはテストごとの通過率を押し上げるが、strict・isolated・core の判定は動かさない。
    - 項目の一覧は Gate ② の材料にする。テストごとの通過率を読むときに、これらの項目を外した値を並べるかは Gate ② で決める。
- 依存：実装役は PyPI から依存を入れられる（公式の走らせ方もネットワークあり）。採点は提出物の requirements.txt を、上の時刻の固定の下で入れる。

### 6-4. 比較条件の基本形（操縦士の決め、2026-11-20）

- そろえるもの：モデル（agy の gemini-4-hydrogen-medium）・思考の強さ・問題の文（公式の just-solve のひな形で、チェックポイントの仕様をそのまま渡す）・環境（6-3）・時間と利用枠の上限・採点（公式の eval-snapshot）。プロンプトの直しは効きに数えない。

- 隠しテストの出力は、どの比較条件でも実装役に返さない。
- Mode 4 は 1 回の修理なので、H0 だけを基本にする（関門の比べは 6-7）。
- H_stack と、それに入れる部品は Gate ② で決める（6-7）。

### 6-7. E-2・E-3：H_stack の比べ

- 比較条件：
  1. H0・H0_fresh：6-4。
  2. H_stack：次の要素を組み合わせる。どれを入れるかは Gate ② で決める。
     - 1 つのチェックポイントを 1 つの素直な続く会話で進める（憲章 §2。細かいリセットはしない）。
     - E-2 の要件の台帳で、チェックポイントの仕様を検証できる項目にする。
     - 第 1 関門（設計 §4-2 の 1〜4：pyflakes の差・台帳の口・群 1 と非退行の関門・守るテストのファイルの改変の押し返し。モジュールの import の検査と群 2・3 は使わない。P-038・P-042）と、通った検査を積む非退行の関門を当てる。
     - H_stop_1 の安全停止を入れる。
  3. H_ind（必要なときだけ）：候補のコードを見る前に、台帳から受け入れの確認の手順を作って凍結し、文脈を分けた検証で当てる。足す前に、各チェックポイントの正解（Mode 4 では reference）に当てて、正解を落とす項目の割合を測る。線は足す前に書く。
  - 外すもの：H_ctx_1（古い観測の伏せ）。agy に会話の履歴を伏せる口が無いため。
- E-2（上流）：
  - 問い：チェックポイントの仕様から、系が検証できる要件の台帳（公開の口の約束と、完了を判定する振る舞いの項目）を作れるか。テストのコードは作らない。
  - 質は 2 つで読む。台帳の項目が公式のテストの根拠のある項目をどれだけ覆うか（§5-2 の分けを SlopCodeBench のテストに当てる）と、H_stack の結果への効き。
  - 測れないもの：粗い企画（企画書の粒度）からの仕事の分解。SlopCodeBench のチェックポイントの仕様は、すでに 1 つの仕事の細かさで書かれている。
- 時間の予算（設計 §5-1 の契約）：毎ターンの軽い段は、変えたファイルの pyflakes と群 1（数十秒を上限）。区切りの段で非退行の関門。公式のテストは使わない。
- H_stop_1 の発火の条件（客観のものだけ）：同じ差分（SHA-256）が続く・明示の断念・測定系の異常（設計 §5-1 の infra）・前進が無い・警告の後のテストの改変や -k の絞りの繰り返し・通った検査を続けて壊す。停止のときは、変更の範囲・未達とその根拠・人に渡す選択肢の要約を決まった形で残す。
- 評価（取れない値は 0 と混ぜず、null と理由で残す）：
  - 成果：strict・isolated・core（問題ごとの割合の平均と、チェックポイントの和の両方）。
  - 害：前のチェックポイントで通っていたテストの退行・H0 が通した単位を壊したか（番兵）・規範の違反（テストの改変・-k の絞り）。
  - 費用と時間：キャッシュしない入力と出力のトークン・Gemini の週の利用枠の減り・壁時計。
  - 安全：停止の誤りと漏れ、測定系の故障と実装の失敗の分け。
- 判定：3 軸の AND（害の上限・ノイズを超える効果・採算）の枠だけを先に決め、数は Gate ② で凍結する。
- 進め方：H_stack の先読み（2〜3 問）で共通の無駄を削ってから、残りの dev を走らせる。開発の改善は、周回の数を決めずに、素のチャット（H0）と戦える算段がつくまで dev で積み上げる。軌道修正のサイン（ベンチの欠陥や環境の待ちが失敗と時間の大半を占める、改善が頭打ちになり H0 とノイズ未満の差しか出ないままになる）が出たら撤退し、「H0 で足りる」と記録を確定する。
- 前に作るもの（利用枠 0。Gate ② で要ると決めたものだけ）：制御核の積み重ねの周回・設計 §5-1 の契約・H_stop_1 の検知。

### 6-8. 外側：失敗の型の台帳

- 走りごとに、軌跡から失敗の型を付けて台帳に足し、繰り返す型から 1 つずつ直す。
  - 直し先は、第 1 関門の機械の検査・要件の台帳のひな形・仕事の粒度・ハーネスの設定のどれか（設計 §4-2）。
  - 直した効きは、その型が出た単位の走らせ直しと、節目の held-out での非劣性で検証する。開発用の点の上下だけでは決めない（憲章 §5）。

### 6-9. 証明

- SlopCodeBench の held-out（20 問）と Mode 4 の held-out（23 ゲーム）は、開発用で十分に磨き上げ、6-7 の判定に届いた形だけを、未開封の区画に送る（憲章 §5）。区画は 6-2 の並びの先頭から切り、1 つの区画は 1 回だけ使う。線は開発用の結果の後、走らせる前に書く。
  - 一発の 0/1 にしない：1 つ目の区画で届かなかったら、その区画の結果を全件記録したうえで dev でさらに改善し、同じ課題は使い回さずに、別の未開封の区画で確かめ直す。
  - 開けた区画の結果は、勝敗によらず全件を記録して公開資料に含める。
  - 改善が頭打ちになったとき（6-7 の撤退）か、未開封の区画が尽きたときは、開けた全区画の結果とともに「H0 で足りる（損益の分かれ目の手前）」として公開する。
- 限界：ゲームの領域での積み上げは測らない。SlopCodeBench は Python の CLI を空の作業場から作る問題で、成熟した大きなコードベースの保守ではない。
- FeatureBench の held-out（14 課題）と SWE-EVO の held-out（10 課題）は、封を開けずに終える。
