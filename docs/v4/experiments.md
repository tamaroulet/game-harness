### M-01 agy の新しい会話のキャッシュの立ち上がり（2026-11-13）

- 材料：箱の中の実装役（agy 1.5.3、gemini-3.8-flash-medium）の stream-json の記録。3 本のラン（A の会話の形の 1 ステージ目 1 回、B の 6 ステージ、前の A の 18 ステージ）で、新しい会話の始まりが計 25 回。
- 読み方：応答ごとの `cache_read_tokens` と `input_tokens`。キャッシュの読みが 0 でなくなる最初の応答と、その手前の文脈の長さ（入力＋キャッシュの読み）を見た。
- 結果：
  - 25 回とも、最初の 5〜12 応答はキャッシュの読みが 0。当たり始めるのは、手前の文脈が約 1.6 万〜2.1 万トークンを越えた所（最初の当たりの読みは 1.5 万〜2.1 万。1 回だけ 4,681 で当たり、次の応答で 0 に戻った）。
  - 1 回の始まりの、キャッシュの読みが 0 の応答の入力の計：5.6 万〜13.6 万トークン（中央 約 8.5 万）。
  - 会話を続けた A は、2 ステージ目以降、最初の応答から前の会話のキャッシュに当たった（読み 63,654 → 183,605）。
- 公開の文書との差：Gemini API の文書は、3.8 Flash の implicit caching の最低を 4,096 トークンとする。agy の経路はこれと合わない。仕組みは公開されていないので、実測で扱う。
- 前提：P-021。

### M-02 同じ課題での、続く会話と毎ステージの新しい会話の費用（2026-11-13）

### M-05 Gemini の利用枠の目盛り（2026-11-08〜13）

- 目盛りの減りは、キャッシュでない分（入力＋出力）100 万トークンあたり約 2.1〜2.3 ポイント（11-08 の基準のランと 11-13 のランから）。
- キャッシュの読みを数えるかは、まだ分からない。これまでのランはキャッシュの読みがキャッシュでない分の 10〜13 倍で、どちらの数え方でも見込みが同じ幅に入った。キャッシュの読みが入力の 97% を占める A の長い会話の前後で目盛りを読めば分かる。
- 枠の分かれ方（操縦士の読み、2026-11-13 の夜）：Gemini Models の週の枠（残り 21%。リセットは土曜 10:35）と 5 時間の枠（残り 96%）、Gemini 4 Argon の週の枠（残り 15%）が別にある。gemini-4-hydrogen と 3.8 Flash は Gemini Models の枠を使う。
- 11-13 は朝の残り 34% から夜の 21% まで 13 ポイント減った。B07 の 2 本のランの見込みは 5〜6 ポイントだったが、副操縦士の Gemini の利用とキャッシュの読みの数え方が混ざっていて、分けられない。X-01 では、走りの直前と直後に、ほかの Gemini の利用を挟まずに目盛りを読む。

## 3. X-01 校正（素の A、FeatureBench の Fast）

- 目的：仮説 H1（素の A が、手順の型で落ちるか）と、X-01〜X-03 の標準のモデルを決めること（1 課題あたりの利用枠の減りと、解決の余地）。
- 課題：4 つの像の 63 課題（Fast v1.1）を、課題の ID の順に並べ、種 20261114 の乱数（Python の random.Random(20261114).shuffle）で並べ替える。1 課題目は、並べ替えた順で最初の seaborn の課題（取ってある像で燃費を測るため）。残りの 4 課題は、それを除いた順の先頭から取る。結果を見て差し替えない。選んだ 5 課題（2026-11-14 に選んだ）：
  1. mwaskom__seaborn.7001ebe7.test_statistics.0f2ae277.lv1
  2. astropy__astropy.b0db0daa.test_basic_rgb.067e927c.lv1
  3. astropy__astropy.b0db0daa.test_functions.40530bf7.lv1
  4. mwaskom__seaborn.7001ebe7.test_plot.b645d353.lv1
  5. pandas-dev__pandas.82fa2715.test_iceberg.85771c70.lv1
  - 1 課題目の正解のパッチは 0-a で評価した（エージェントには何も渡らない）。2〜5 課題目の像（astropy・pandas）は、1 課題目の燃費を見てから取る。
- 設定：agy 1.5.3・gemini-4-hydrogen-medium、1 課題 1 つの会話、時間の上限は 1 課題 60 分（目安）。燃費が分からないので、まず 1 課題を走らせて目盛りを読み、残りを走らせるかを決める。3.8 Flash（medium）は、同じ課題のうち少数で比べる（要るときだけ）。
- 物差し：解決（全テストが通る）・通った F2P のテストの割合・P2P の退行・キャッシュでない分と読み・時間・ターン。軌跡を読んで、失敗の型を 1 つずつ付ける（早合点・退行・読み違い・推測と参照の崩れ・能力の不足・環境の不具合）。
- 判定の線：
  - A が 5 のうち 4 以上を解く → 課題が易しすぎる。Full の大きい課題か、SWE-EVO の複数 PR の課題に移る（Full のうち GPU を求める課題は、手元では走らない。M-04）。
  - A が 0 で、通ったテストの割合が 2 割未満、失敗がほぼ能力の不足 → そのモデルには難しすぎる。易しい課題の組に移る（選び方は走らせる前にここに書く）。
  - それ以外で、失敗のうち 2 つ以上が手順の型 → X-02 に進む。
  - 標準のモデル：Hydrogen の燃費が、X-02・X-03 の規模を週の枠で回せる範囲なら、Hydrogen を標準にする。範囲を外れるなら、3.8 Flash の比べ（解決の余地と燃費）を見て決め直す。数の線（1 課題あたりの上限のポイント）は、0-a〜0-c の後、走らせる前にここに書く。
- 費用の見込み（推測）：3.8 Flash なら 1 課題 約 0.2〜0.7 ポイント（FeatureBench の Gemini CLI は 1 課題で入力 約 260 万トークン。M-02 のキャッシュでない割合を当てた）。目盛りがキャッシュの読みを 1 割数えるなら、1 課題 約 0.6 ポイント足す。Hydrogen の減りは分からない（1 課題目で測る）。走りの前後で操縦士が目盛りを読む。
- 状態：計画。走らせる前に、順 0-a〜0-c を済ませ、利用枠の確認を取る。

## 4. X-02 開発（部品を 1 つずつ）

- 目的：仮説 H2〜H5。共通骨格の 3 つ（入口の要件の台帳・1 つの単位を 1 つの会話で続ける・出口の機械の背圧＝既存のテストの回帰と型・参照・静的解析）を、1 つずつ足し、外して確かめる（[設計と仮説](design.md)の §4-2）。正解の受け入れテストは使わない（ベンチの通常の実行では隠されている）。H5 は、効きが共通骨格から出るか（細かいリセットや独立の検証役を足さないと出ない形でないか）を見る。
- 課題：X-01 で使った課題と、4 つの像の残りの課題のうち held-out に入れないもの。長い課題の確かめに、SWE-EVO の複数 PR の課題を少し足す。どれも held-out に入れない。
- FeatureBench の 1 課題は、はじめから 1 つの機能。複数の機能を台帳で引き継ぐ効きは、大きい課題と SWE-EVO の複数 PR の課題で確かめる。
- 物差しと線：X-01 の結果を見てから、走らせる前にここに書く。

## 5. X-03 証明（封をした held-out）

- 目的：仮説 H5・H6 と、公開の主張。証明に使う構成は、共通骨格（要件の台帳・1 つの単位を 1 つの会話で続ける・機械の背圧）に限る。実戦の専用化（受け入れテストの事前の提示・大きい粒度・Unity の多段の関門）は、ベンチで証明しない。
- 課題：X-02 を始める前に、4 つの像の課題から X-01 の 5 課題を除いた残りの中から、開発に使わない組を、種を書いた乱数で、像ごとに同じ割合で選んで封をする（ID の並びだけを手元の非公開の所に残す）。
- 物差し・判定の線・回数は、走らせる前にここに書く（軽い事前登録）。結果は、区間・限界・負けた所も含めて、リポジトリの中の技術レポートにする。数は検証用のモデルでの結果で、賢いモデルへの持ち越しは測っていない構造の理由として書く（[設計と仮説](design.md)の §4-4）。
