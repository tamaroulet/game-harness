### 5-2. 公式のテストの項目の根拠の分け（静的な規則。パッチの結果を見ずに、走らせる前に決めた）

- 使うもの：課題の文・隠しのパッチ（データの patch。実装を消すパッチ）・公式のテストのファイル（データの test_patch から戻した元の中身）・課題の始まりの状態（隠しのパッチを当てた後）のソース（テストのファイルを除く）。A のパッチと、評価の結果は使わない。
- A の課題ごとの解決と、落ちた項目の数の一部（§3・§4）は、規則を書く前から分かっている。規則はそれに合わせて作らず、決めた後は変えない。計算は道具（harness/fb_ground.py）が機械で行う。
- 規則：
  1. 消された名：隠しのパッチが消した行（テストのファイルを除く）の、`def 名`・`async def 名`・`class 名` と、字下げの無い代入 `名 =` の名。前後が `__` の名は除く。
  2. テストの範囲：公式のテストのファイルのテストの関数ごとに、関数の本体・同じクラスの準備のメソッド（setup_method・setup_class・setup・setUp）・引数の名と同じ名の、同じファイルの fixture の本体・本体から名で直に呼ぶ、同じファイルの関数の本体（1 段まで）。
  3. 範囲の中の名：Name の名と、属性の名（Attribute の attr）。
  4. 範囲の中の文言：
     - match= の文字列：pytest.raises・pytest.warns・pytest.deprecated_call と、名が assert_produces_warning の呼び出し。
     - assert の文の比べ（==・!=・in・not in）の文字列の定数と、名が assert で始まる呼び出しの文字列の定数のうち、12 字以上か、空白か `<>:%{}[]=` のどれかを含むもの。
  5. 項目の分け（上から、最初に当たったもの）：
     - 隠し：文言 — 4 の文言のうち、課題の文にも、始まりの状態のソースにも無いものがある。空白を 1 つに詰め、大文字と小文字を区別せずに比べる。match= は、正規表現の `\` と、先頭の `^` と末尾の `$` を外して比べる。
     - 隠し：名 — 3 の名のうち、消された名で、課題の文に無く、始まりの状態のソースにも名として出てこないものがある。
     - 根拠：参照 — 3 の名のうち、消された名で、課題の文に無く、始まりの状態のソースには名として出てくる（残ったコードが呼んでいる）ものがある。
     - 根拠：文 — 上のどれでもない（課題の文の名か、消されていない既存の口だけを使う）。
  6. 公式の項目（パラメータの付いた 1 つずつ）は、テストの関数の分けを受け継ぐ。項目の名は正解の評価の記録から取り、pytest の項目の ID（path.py::…）の部分で突き合わせる。同じファイルの基底のクラスから受け継いだテストの関数は、子のクラスの名前の項目として扱い、準備のメソッドと fixture は子から基底の順に辿る。
- 段 b 以降の物差し（根拠のある項目の通過率など）は、この分けで数える。「根拠」は「根拠：文」と「根拠：参照」の 2 つで、分けて出す。

  - フックのファイルとスクリプトは root の持ち物で書き換え不可、置き場のフォルダは root の 1777（sticky）にする（確認は [archive/phase1_checks.md](archive/phase1_checks.md) の §6-3）。走りの後にフックのファイルの SHA-256 を照らす。
  - 走りの後の検査：止めた道具のステップが DONE で終わった走り（道具が走った）は無効にする（本物の agy での止まり方は [archive/phase1_checks.md](archive/phase1_checks.md) の §6-3）。
  - agy のエージェントの定義で道具の一覧そのものを絞る形は採らない（系統のプロンプトが替わり、素の A が変わる）。
- 実装役は非 root（イメージの agent ユーザー、uid 1000）で走らせる。公式の SlopCodeBench の走らせ方と同じ。
- 採点：
  - 公式の `slop-code eval-snapshot` を、実装役の作業場の写しに当てる。非 root（`HUID`・`HGID`）、基本のイメージは ID を記録して作り直さない。
  - 公式の採点は、基本のイメージに、環境の設定の environment.env から描いた Dockerfile のハッシュのラベルを付け、合わなければ作り直して同じ名前に付け替える（そのときの最新の道具が入る）。採点ごとに environment.env を変える形は、イメージの固定とぶつかる。
  - そこで、環境の設定は公式の値のまま `environment.include_os_env: true`（採点を起動したホストの環境変数を採点のコマンドに写す公式の口。ハッシュに入らない）だけを足し、`UV_EXCLUDE_NEWER`（uv が、その日時より後に公開された配布物を候補から外す）を採点の時刻にして、ホストの最小の環境（PATH・HOME=/tmp/agent_home・問題の置き場・HUID・HGID）で渡す。時刻を記録し、採り直すときは同じ時刻を与える。
  - 確認（作り直しが起きた確認の採点・3 回の採点でイメージが作り直されないこと・時刻を変えたときと同じ時刻の 2 回の比べ・HOME の写し・下の照らし合わせの偽物の通し）の全文は [archive/phase1_checks.md](archive/phase1_checks.md) にある。
  - 実行口は、採点の前に基本のイメージの ID を固定の値と照らし、違えば採点しない。
- 採点の抜け道（scb-problems#39 の影響）：
  - #39 は Harbor 版を読んだ指摘で、Harbor の走らせ方に固有の項目は eval-snapshot には当たらない（読みは [archive/phase1_checks.md](archive/phase1_checks.md) の §6-3）。
  - eval-snapshot の抜け道（#39 に無い。コードで確認した）：提出物にすでに `.evaluation_tests/` があると、公式のテストを写さず、テストの一覧づくりも本番もそのフォルダのテストで行う。実行口は、このフォルダのある提出物を採点せず、無効として記録する（正直な実装役は作らない名前）。
  - 実装役が作業場の根に置いた conftest.py は、公式の直し（slop-code-bench#16、使った版に入っている）で採点に読まれない。
  - テストの弱さ（#39 の問題のロジックの項目。eval-snapshot にも当たる）：空の提出物 2 種を母集団の全チェックポイントの公式の採点に通すと、どちらかで通るテストは延べの 7.8%（P-047）で、strict・core を満たしたチェックポイントは 0。弱さは strict・isolated・core の判定を動かさない（通過率の扱いは 6-6）。
- 依存：実装役は PyPI から依存を入れられる（公式の走らせ方もネットワークあり）。採点は提出物の requirements.txt を、上の時刻の固定の下で入れる。

### 6-7. E-2・E-3：H_stack の比べ

- H_stack（Gate ② で凍結）は H0 に次を足す。どの部品も A にも見えるもの（課題の文・始まりの状態・系が作った検査）だけを使い、正解と公式のテストは使わない（設計 §5-1）。
  1. E-2 の台帳（U3）：チェックポイントごとに新しい会話で、仕様の文と例（Mode 4 は BUG_REPORT.md・BUGFIX_TASK.md・GAMEPLAY_REQUIREMENTS）から、仕様が明示した公開の口の約束と完了を判定する項目を作り、根拠の文をそのまま引く（仕様に無い文を引いた項目は捨てる。内部のファイルや関数の名は載せない）。実装役には作業場の外に読み取り専用で置き、置き場の 1 行だけを文面に足す。
  2. 第 1 関門（設計 §4-2 の 1〜4）：毎ターンは pyflakes の差と群 1（60 秒まで。Mode 4 は GDScript の構文と、変えた場面のヘッドレスの読み込み）、区切りは非退行の関門と台帳の口（300 秒まで）。口は仕様が明示した公開の口だけ（指定された CLI の入口・サブコマンド・フラグ、Mode 4 は既存の場面とスクリプトの公開の口）で、内部のファイルの分け方や関数の名は縛らない。
  3. H_ind（設計 §4-2 の第 2 関門）：チェックポイントごとに 1 回、別の新しい会話と別のコンテナで、台帳・公開の口の約束・始まりの状態の写し（前のチェックポイントの終わりの作業場、Mode 4 は壊れた状態のプロジェクト）だけから作り、渡したファイルの一覧と SHA-256 を記録する。実装役の始まりと同時に作ってハッシュで固める。SlopCodeBench は CLI を呼ぶ pytest、Mode 4 は Godot をヘッドレスで動かす GDScript。壊れた検査は捨てる。誤った押し返しの防止は次の 2 つだけで、正解に当てて検査を選ぶことはしない（比較条件に正解の情報が入るため）。
     - (a) 静的な根拠の規則：知らせるだけにするのは、仕様の文・台帳・始まりの状態のどれにも無い名（結果の JSON の鍵・CLI のサブコマンドとオプション・ノードや場面や公開のメソッドの名）か、例外やエラーの固定の文言を求める検査だけ。仕様の規則から計算して決まる値（数・リストの要素・JSON の記号や空白を含む出力）は、全体が仕様に無いことを理由に隠しにしない。検査の中のローカル変数や補助の関数の名は数えない。
     - (b) dev での較正（§5-6）：正解の状態で押し返しの検査がすべて通る単位が 8 割以上なら押し返しに使い、届かなければ知らせるだけにする。根拠のある落ちがあった H0 の提出物で押し返しの検査が 1 つ以上落ちる割合が 4 分の 1 に届かなければ外す（設計 §5-2）。較正は生成器の版の採否にだけ使う。held-out の正解には採点のほかで触れない。
  4. 積み重ね：確定したチェックポイントで通っていた H_ind の押し返しの検査と群 1 を、次からの非退行の関門に積む。確定できなかったもの（押し返しの上限・H_stop_1・時間の上限）は、H0 と同じく終わりの状態を採点して次へ進む。Mode 4 は残りが 600 秒を切ったら押し返さない（時間切れは提出物を残さない）。
  5. 部品ごとの観測（設計 §5-2。利用枠 0）：実装役の初めの終わり（台帳だけが効いた状態）・押し返しの前後・終わりの写しを、走りの後に公式の採点に通し、押し返しごとに引き金の部品と公式のテストの変わりを数える。帰属があいまいな部品は、held-out の前に dev で外して比べる。
- E-2 の問い：仕様から系が検証できる台帳を作れるか。質は、公式のテストの根拠のある項目の覆い（6-6 の規則）と結果への効きで読む。
- H_stop_1 の発火の条件（客観のものだけ）：同じ差分（SHA-256）が続く・明示の断念・測定系の異常（設計 §5-1 の infra）・前進が無い・警告の後のテストの改変や -k の絞りの繰り返し・通った検査を続けて壊す。停止のときは、変更の範囲・未達とその根拠・人に渡す選択肢の要約を決まった形で残す。
- 評価：取れない値は 0 と混ぜず、null と理由で残す。安全（停止の誤りと漏れ、測定系の故障と実装の失敗の分け）も並べる。
- 段と線（走らせる前に書いた）：
  - Step A（利用枠 0）：部品・制御核の積み重ねの周回・設計 §5-1 の契約・写しの事後の採点・費用の集計・較正の道具を作り、単体の試験と偽物の agy で確かめ、H0 の走らせ方が変わらないことを照らす。etl_pipeline の 2 チェックポイントを `--ttl 120` で 1 回走らせ、時間切れの形と止める線 8 を見る（比べに入れない）。
  - Step B-0（較正。生成だけ）：SlopCodeBench は Stage 1 の 16 チェックポイントで H0 の始まりの状態から作り、正解で精度を、根拠のある落ちがあった H0 の 5 チェックポイントの提出物で見抜く力を測る。Mode 4 は pixel_platformer の 2 ケースで、もとのゲーム・壊れた状態・1d の提出物に当てる。写しの疑い（§5-6）と、台帳の ① の根拠の文の引きも出す。線は、精度 16 中 13 以上かつ見抜く力 5 中 2 以上、Mode 4 は 2 ケースとも正解で全部通り、壊れた状態と 1d の提出物で 1 つ以上落ちること。届かない系統は、生成器を問題に依らない形で 1 回だけ直し、未見の dev（migrate_configs で、始まりの状態は渡さない。Mode 4 は ballast_yard の 1 つ目のケース）を足して、足した単位を含む精度 8 割以上を確かめる（足した単位だけの値も並べる）。それでも届かなければ、その系統の B-1 は走らせず、軌道修正を諮る。
  - Step B-1（先読み）：file_query_tool・sith・1d のケースを H_stack で 1 回ずつ（H0 は Stage 1）。線は、害（真の退行・規範の違反・無効な走りが 0、Mode 4 のもとから通る道筋 2/2）、仕組み（file_query_tool と sith で、Stage 1 に ④ と承認した 20 テストの外で落ちたテストが、初めて落ちたチェックポイントで数えて 5 以下。H0 は 14・H0_fresh は 11。Mode 4 は目当ての道筋が 0/3 より増えるか resolved）、採算（6-6）。主指標は、上限が走りの食い違いの中なので並べるだけ。採算だけ外れたら無駄を 1 問で削って測り直し、仕組みが 6〜10 なら直しを入れるかを操縦士が決め、11 以上か害なら軌道修正を諮る。
  - Step C（届いた系統だけ）：残りの dev の H0 と、dev の全部の H_stack（同じ版で）。6-6 の線に届いた形だけを held-out に送る（6-9）。dev の全部と、Step B で使った単位を除いた未見の dev だけ（足さなければ 8 問・51 チェックポイントと 21 ケース）の両方を集計し、食い違えば held-out の前に諮る。dev の残りの H0 は Step B の後まで走らせない。
- 開発の改善は、周回の数を決めずに、H0 と戦える算段がつくまで dev で積み上げる。軌道修正のサイン（ベンチの欠陥や環境の待ちが失敗と時間の大半を占める、改善が頭打ちで H0 とノイズ未満の差しか出ない）が出たら撤退し、「H0 で足りる」と記録を確定する。


### 6-8. 外側：失敗の型の台帳

- 走りごとに、軌跡から失敗の型を付けて台帳に足し、繰り返す型から 1 つずつ直す。
  - 直し先は、第 1 関門の機械の検査・要件の台帳のひな形・仕事の粒度・ハーネスの設定のどれか（設計 §4-2）。
  - 直した効きは、その型が出た単位の走らせ直しと、節目の held-out での非劣性で検証する。開発用の点の上下だけでは決めない（憲章 §5）。
- 1c からの区分（操縦士の承認、2026-11-22）：① 仕様の文か例が名指ししている場合を取りこぼした（台帳の的）、② 一般の規則から組み合わせ・境界・エラーの道で落ちた（関門の的）、③ 前のチェックポイントで通っていたテストを壊した（非退行の関門の的）、④ 仕様が決めていないか、仕様と食い違うテスト（届かない）。
- 今の台帳（X-01・X-02 の段 1・Stage 1 の 1b と 1c の、素の A の走り。1b・1c は H0 と H0_fresh）：

| 型 | 数 | 出た所 |
|:--|:--|:--|

### 6-9. 証明

- SlopCodeBench の held-out（20 問）と Mode 4 の held-out（23 ゲーム）は、開発用で十分に磨き上げ、6-7 の判定に届いた形だけを、未開封の区画に送る（憲章 §5）。区画は 6-2 の並びの先頭から切り、1 つの区画は 1 回だけ使う。線は開発用の結果の後、走らせる前に書く。
  - 一発の 0/1 にしない：1 つ目の区画で届かなかったら、その区画の結果を全件記録したうえで dev でさらに改善し、同じ課題は使い回さずに、別の未開封の区画で確かめ直す。
  - 開けた区画の結果は、勝敗によらず全件を記録して公開資料に含める。
  - 改善が頭打ちになったとき（6-7 の撤退）か、未開封の区画が尽きたときは、開けた全区画の結果とともに「H0 で足りる（損益の分かれ目の手前）」として公開する。
- 限界は設計 §7 の注（ゲームの領域での積み上げと、成熟した大きなコードベースの保守は測らない）。
- FeatureBench の held-out（14 課題）と SWE-EVO の held-out（10 課題）は、封を開けずに終える。
