## 1. 測った記録

### M-01 agy の新しい会話のキャッシュの立ち上がり（2026-11-13）

- 材料：箱の中の実装役（agy 1.5.3、gemini-3.8-flash-medium）の stream-json の記録。3 本のラン（A の会話の形の 1 ステージ目 1 回、B の 6 ステージ、前の A の 18 ステージ）で、新しい会話の始まりが計 25 回。
- 読み方：応答ごとの `cache_read_tokens` と `input_tokens`。キャッシュの読みが 0 でなくなる最初の応答と、その手前の文脈の長さ（入力＋キャッシュの読み）を見た。
- 結果：
  - 25 回とも、最初の 5〜12 応答はキャッシュの読みが 0。当たり始めるのは、手前の文脈が約 1.6 万〜2.1 万トークンを越えた所（最初の当たりの読みは 1.5 万〜2.1 万。1 回だけ 4,681 で当たり、次の応答で 0 に戻った）。
  - 1 回の始まりの、キャッシュの読みが 0 の応答の入力の計：5.6 万〜13.6 万トークン（中央 約 8.5 万）。
  - 会話を続けた A は、2 ステージ目以降、最初の応答から前の会話のキャッシュに当たった（読み 63,654 → 183,605）。
- 公開の文書との差：Gemini API の文書は、3.8 Flash の implicit caching の最低を 4,096 トークンとする。agy の経路はこれと合わない。仕組みは公開されていないので、実測で扱う。
- 前提：P-021。

### M-02 同じ課題での、続く会話と毎ステージの新しい会話の費用（2026-11-13）

- 材料：自作の鎖の課題 B07（6 ステージ）を 1 回ずつ。A は 1 つの会話と 1 つの作業の場所を続けた。B はステージごとに新しい会話で、作業の場所を課題の範囲に絞った。モデル・箱・上限・採点は同じ。
- 結果（6 ステージの計、トークン）：

| | A（続く会話） | B（毎ステージ新しい会話） |
|:--|--:|--:|
| キャッシュでない入力 | 510,953 | 1,107,545 |
| 出力 | 166,118 | 260,741 |
| キャッシュでない分（入力＋出力） | 677,071 | 1,368,286 |
| キャッシュの読み | 17,399,084 | 10,234,262 |
| 入力のうちキャッシュでない割合 | 2.9% | 9.8% |
| 1 ステージ平均の秒・応答 | 262 秒・24.7 | 421 秒・40.8 |

- 2〜6 ステージの 1 ステージ平均のキャッシュでない分は、A 8.8 万・B 23.6 万（2.7 倍）。1 ステージ目だけは B が安い（19.0 万と 23.6 万）。
- B のキャッシュでない入力の 46% が、立ち上がり（M-01）の応答だった。2〜6 ステージの差の約半分が立ち上がり、残りがターンの多さ（前の仕様・本体・テストの読み直しと、試しのやり直し）。
- 1 ターンのキャッシュでない入力は、約 2,800〜2,900 トークンの基礎の分に、前の道具の出力が乗る（A 2,874・B 2,815）。時間は出力（思考）の量で決まる。並べて呼ぶ道具は 0 回（1 応答に道具 1 つ）。
- 限界：課題 1 つ・1 回ずつ。品質は両方とも満点で、品質の差は見えない（M-03）。
- 前提：P-022。

### M-03 自作の課題の天井（2026-11-13）

- 鎖の課題 B07 で、A は 6 ステージすべてを 1 回で完了し、新しいテストも前のテストも全部通った。B のゲートは、11-08〜11-12 の 2 回（36 ステージ）と 11-13 の 1 回（6 ステージ）の計 42 ステージで、すべて 1 回目に合格し、差し戻しも延長も 0。
- 前の世代の凍結の 10 本も、単一の文脈の形が 10 本と 4 つの型のすべてで満点だった（v3 §2）。同じ失敗の 2 回目。
- 前提：P-023（と P-018）。

### M-04 手元の環境（2026-11-13）

- WSL2 の Ubuntu、Docker 29.1.3（linux/amd64）、20 コア、WSL のメモリ 15GB。C ドライブの空き 466GB。
- SWE-EVO のイメージは課題ごと（Docker Hub の 42 個で圧縮 70.9GB、中央 1.37GB、最大 3.01GB。ほかに ghcr.io の 6 個）。FeatureBench のイメージはリポジトリごと（24 個。大きさは問い合わせの上限で数えていない）。
- SWE-EVO のデータセット：48 課題（dvc 26・dask 8・requests 4・pydantic 3・modin 3・conan 2・scikit-learn 2）。パッチの行の中央 392（四分位 153・392・1,200）。リリースノートだけの語数の中央 75.5（リンクの PR と課題の文を足すと、論文の平均 2,390 語）。

### M-05 Gemini の利用枠の目盛り（2026-11-08〜13）

- 目盛りの減りは、キャッシュでない分（入力＋出力）100 万トークンあたり約 2.1〜2.3 ポイント（11-08 の基準のランと 11-13 のランから）。
- キャッシュの読みを数えるかは、まだ分からない。これまでのランはキャッシュの読みがキャッシュでない分の 10〜13 倍で、どちらの数え方でも見込みが同じ幅に入った。キャッシュの読みが入力の 97% を占める A の長い会話の前後で目盛りを読めば分かる。

## 2. 土俵の移行の手順（FeatureBench を先に、SWE-EVO を長い課題に）

| 順 | すること | 利用枠 |
|:--|:--|:--|
| 0-a | FeatureBench を入れ（版を固定）、Lite の 1〜2 課題を正解のパッチで評価して、評価の道が手元で通ることを確かめる | 0 |
| 0-b | agy の実行口を足す（FeatureBench の Gemini CLI の実行口の形をまねる。agy の版と SHA の固定は箱の設定を使う）。偽物の agy で空の 1 回を通し、頼みと記録の形を確かめる | 0 |
| 0-c | 外への通信を、モデルの API だけに絞る（箱の proxy の形を使う。未来の版の取り寄せを防ぐ） | 0 |
| 1 | 校正 X-01 | 小 |
| 2 | 開発 X-02（FeatureBench の開発用の課題、SWE-EVO の複数 PR の課題を少し） | 中 |
| 3 | 証明 X-03（封をした held-out） | 中〜大 |

- 使うモデル：X-01〜X-03 は、すべて agy の Gemini 3.8 Flash で行う。Claude の枠で公式のベンチは回さない（[設計と仮説](design.md)の §4-1、P-030）。
- 使い回す：箱（コンテナ・外への通信の制御・agy の版の固定）、利用量の読み（stream-json）、モデルの固定の検査、記録の読みの道具。
- 使わない：v3 の鎖のベンチの経路（H ラインの流用・鎖の採点・腕の走らせ役）。整理の計画の 2 で退ける。
- 公平の設定：両方の腕で、同じイメージ・同じモデルと思考の強さ・同じ時間とトークンの上限・同じ採点（ベンチの公式の評価）。素の A は、agy の 1 つの会話に課題の全文を渡すだけ。

## 3. X-01 校正（素の A、FeatureBench の Lite）

- 目的：仮説 H1。素の A が、手順の型で落ちるかを確かめる。
- 課題：Lite（V1.1）から 5 課題。選び方は走らせる前に決めて、ここに書く（課題の ID の並びの決まった位置か、種を書いた乱数）。結果を見て差し替えない。
- 設定：agy 1.5.3・gemini-3.8-flash-medium、1 課題 1 つの会話、時間の上限は 1 課題 60 分（目安）。
- 物差し：解決（全テストが通る）・通った F2P のテストの割合・P2P の退行・キャッシュでない分と読み・時間・ターン。軌跡を読んで、失敗の型を 1 つずつ付ける（早合点・退行・読み違い・推測と参照の崩れ・能力の不足・環境の不具合）。
- 判定の線：
  - A が 5 のうち 4 以上を解く → 課題が易しすぎる。Full の大きい課題か、SWE-EVO の複数 PR の課題に移る。
  - A が 0 で、通ったテストの割合が 2 割未満、失敗がほぼ能力の不足 → Flash には難しすぎる。易しい課題の組に移る（選び方は走らせる前にここに書く）。
  - それ以外で、失敗のうち 2 つ以上が手順の型 → X-02 に進む。
- 費用の見込み（推測）：1 課題 約 0.2〜0.7 ポイント（FeatureBench の Gemini CLI は 1 課題で入力 約 260 万トークン。M-02 のキャッシュでない割合を当てた）。5 課題で約 1〜4 ポイント。目盛りがキャッシュの読みを 1 割数えるなら、1 課題 約 0.6 ポイント足す。走りの前後で操縦士が目盛りを読む。
- 状態：計画。走らせる前に、順 0-a〜0-c を済ませ、利用枠の確認を取る。

## 4. X-02 開発（部品を 1 つずつ）

- 目的：仮説 H2〜H5。台帳・速い確かめ・回帰の確かめ・区切りの戦略を、1 つずつ足し、外して確かめる。H5 は、効きが 1 つの機能を 1 つの会話で続けたままの台帳と背圧から出るか（細かいリセットや独立の検証役を足さないと出ない形でないか）を見る。
- 課題：X-01 で使った課題と、FeatureBench の開発用の課題（Lite の残り、または Fast の一部）。長い課題の確かめに、SWE-EVO の複数 PR の課題を少し足す。どれも held-out に入れない。
- 物差しと線：X-01 の結果を見てから、走らせる前にここに書く。

## 5. X-03 証明（封をした held-out）

- 目的：仮説 H5・H6 と、公開の主張。証明に使う構成は、賢いモデルにそのまま持ち越せる構造（1 つの機能を 1 つの会話で続け、入口の台帳と出口の背圧で挟む）に限る。
- 課題：X-02 を始める前に、開発に使わない課題の組を、種を書いた乱数で選んで封をする（ID の並びだけを手元の非公開の所に残す）。
- 物差し・判定の線・回数は、走らせる前にここに書く（軽い事前登録）。結果は、区間・限界・負けた所も含めて、リポジトリの中の技術レポートにする。数は Flash での結果で、賢いモデルへの持ち越しは測っていない構造の理由として書く（[設計と仮説](design.md)の §4-4）。
