# 立て直しの意図・問題・計画

## 0. この文書の役

- 立て直しの意図・今の問題・今の計画を、今の形だけで書く。新しいセッション・総監督・評価者が最初に読む
- 計画を変えるときは、この文書を直す PR で変える。操縦士の追記・削除の指示も、この文書の PR で入れる。過去の形は、この文書の Git の履歴で見る
- 同じ中身を写さない。ほかのものは次の置き場に置き、ここからは指すだけにする

| 残すもの | 置き場 |
|:--|:--|
| 何をしたか・なぜその変更か | commit と PR の本文 |
| 決めたこと（会話で決めたことを含む） | `docs/design/decision_log.md`。決めたその場で 1 行足す |
| 問題 | この文書の §3。解けたら状態の欄を直し、`decision_log.md` に 1 行足す |
| ゴールの木 | `docs/tree/`（W-149）。総監督が作る（W-153） |
| 実行するタスクと依存 | 進捗の台帳 `docs/progress.yaml` |

## 0.5 指揮系統（今までのまま変えない）

- 総監督が、抽象度の高い計画とゴールの木を作る。そのために、リポジトリを読み、外の情報を調べられる
- 分解役が、木からセクターとタスクに分ける。タスクは台帳に載り、実行役が作って試験を通す
- 確かめは、試験と評価者（Argon。リポジトリを自分で読む）がする
- 会話の席は、立て直しの間だけの臨時の席。問題と計画を書き、総監督が木を作れるようにするタスクを台帳に載せるところまでを行う。木は書かない。会話の席が抜けても回る形にする（操縦士、2026-10-24）

## 2. 意図

**方向（操縦士、2026-10-24）**

1. 適切に検索できる土壌を作る
2. 大局観を持ったプロジェクトの進め方を考え直す

この 2 つができれば、あとは直しながら進められる。

**進め方の原則**

- **ゴールの木**：最終ゴールから、深さの決まっていない木で分ける。節は、目的・届いた状態・仮定を持つ。最初は決め打ちで仮の木を作り、外の情報と評価で直していく。仮に置いた節には印を付ける
- **確実なものと仮説を分ける**：実行するタスクと、確かめる仮説を分けて持つ。仮説も木の節にし、確かめたら木に返す
- **評価**：事前（子の節で親に届くか）と事後（届いたか）の評価は、状態を持たない別の AI がする。進みは数ではなく評価で判じる。数は、無駄が無いかを評価するときの証拠に限る
- **改善と実装を分ける**：改善（木を直す）は議論と評価の場でだけ行う。実装は、木のタスクを 1 つずつこなすだけにする
- **作業の実行**：状態を持たない別の起動で、1 つずつ行う。台帳（DAG）に載せることと、誰が実行するかは別
- **外の知識**：問い → 収集 → 出典の照合 → 当てはめと暫定の案 → 評価者の批評 → 操縦士の確認 → 溜める、の流れで行う。問いは、方向と現状の資料を添え、仮説と確かめの聞き方を入れずに書き、投げる前に操縦士に見せる
- **無駄が無いこと**：トークン・人の待ち時間・AI の作業時間に無駄が無いことも、ゴールに含める
