- 状態: 見解と提案（コードは変えていない）
- 前提: v2-smoke-01（game-harness#85、`experiments/v2/results/smoke/notes.md`）
- 諮問（2026-09-25）: ① 再試行の知らせの品質の格差、② 単一チャットの累積が藁人形になっていないか、③ B4 との環境の剥奪の差
- 結論:
  1. **諮問 ① の前提は半分違う**。A は B と同じ 1 行の反例を受け取っている。違うのは、A だけが**それに加えて**生の出力の末尾 40 行を受け取っていること。対等化には賛成で、A から末尾 40 行を外し、ビルドが通らない回は B と同じ診断の射影を渡す（§1）
  2. **それより先に直すべき欠陥が見つかった**。T5 のキックの性質（P-T5-01〜03）は、公開シード 5 本では、正しい実装でも前提が 1 回も成り立たない（PROPERTY_VACUOUS）見込みが大きい。v2-smoke-01 の A は T5 の 4 回の呼び出しすべてでこれに当たった。**T5 は A にも B にも通せない受入になっている可能性が高い**（§4）
  3. 諮問 ② は、A の定義（未圧縮の単一会話）の範囲で主張すれば藁人形にはならない。ただし v2-smoke-01 の A の費用の爆発は、主に ④ の欠陥（通せない T5 で再試行が重なった）とパスの漏れ（game-harness#85 で塞いだ）による。会話の累積だけの効果として数えない（§2）
  4. 諮問 ③ の剥奪は A だけでなく B にもかかっている（両方ともテストを見ない）。v2 では両条件とも性質の宣言をプロンプトで受け取る。非対称なのは B の門（非公開シード・P2P・内側ループ）で、それが処置そのもの（§3）

## 1. 再試行の知らせ（諮問 ①）

### 1.1 事実（コードと v2-smoke-01 のプロンプト）

| | 条件 A（`harness/ab/driver.py` の `run_task_a`） | 条件 B（`harness/pipeline.py` の内側ループ） |
|:--|:--|:--|
| 性質テストが落ちた | 「落ちたテスト」＝ `failure_list` → `dotnet.property_lines(trx)`（PROPERTY_FAIL・PROPERTY_VACUOUS の 1 行、最大 5 行）。**B と同じ関数** | `dotnet.failure_detail` → `property_lines(trx)`。同じ 1 行、最大 5 行 |
| それに加えて | 「失敗の出力（末尾 40 行）」＝ dotnet の生の出力の末尾 | なし |
| ビルドが通らない | 落ちたテストは「（ビルドが通らず…）」、末尾 40 行 | 生のエラーの末尾 40 行を、診断の射影（`diagnose_build`、interface の識別子に写す）で置き換える |

v2-smoke-01 の A の T5 の再試行のプロンプト（a2〜a4）の「落ちたテスト」には、`PROPERTY_VACUOUS id=P-T5-01 rule=RL-39 given=0` など 3 行が入っていた。B と同じ形の 1 行の知らせは届いている。

### 1.2 見解

- 「A に生のスタックトレースだけを投げている」は事実と違う。A は同じ 1 行を受け取っている
- それでも、**末尾 40 行は A だけが受け取るノイズで、実際に害があった**（作業ツリーのパスが入っていて、A はそれをたどって外に出た。game-harness#85 でパスは置き換えたが、ノイズとしては残る）。B に無い情報を A にだけ渡すのは、有利にも不利にもなりうる非対称で、処置（契約駆動の防壁）とは関係がない
- **対等化に賛成**。A の再試行の知らせを B と同じものにする：
  - 性質テストが落ちた：`property_lines` の 1 行だけ（末尾 40 行を外す）
  - ビルドが通らない：B と同じ `diagnose_build` の射影
  - v1 の固定テンプレート（再試行の文面）は、v2 では A・B の知らせの形をそろえるために作り直す

## 2. 単一チャットの累積（諮問 ②）

### 2.1 事実

- A の定義は、2026-09-24 以前からの実験計画（`docs/design/b4_ab_experiment.md`）どおり「1 つの会話（agy の `--conversation`）に積む」。圧縮や要約はハーネスは挟まない（agy が内部で圧縮しているかは確かめていない）
- 呼び出し 1 回の入力は T1 の 95,671 から T4 の 711,954 へ伸びた。ただし T1〜T4 は 1〜2 回の呼び出しで受入まで通り、費用は合わせて 2.82 USD
- 費用 10.13 USD のうち 7.31 USD は T5 の 4 回。T5 の再試行が重なった原因は、§4 の欠陥（受入に届けない）と、パスの漏れで外に出たこと（a3・a4 で手番 38・27）

### 2.2 見解

- 「未圧縮の単一会話」は、実際にエージェントを 1 つの会話で長く使うときの素直な形で、それ自体は藁人形ではない。**主張はその範囲に限る**（「要約を挟む単一チャット」には一般化しない）
- 要約を挟む A'（タスクの境目で会話を切り、前のタスクの要約を渡す）は、別の条件として意味がある。ただしそれは「会話を切って前提を渡し直す」点で B に近づき、A と B の差（門と反例のループ）を測る目的からは外れる。**v2-smoke-02 では A の定義を変えない**ことを推奨し、A' は本走の後の追加の条件の候補として記録する
- v2-smoke-01 の A の費用の爆発を「会話の累積の効果」として報告しない。§4 と game-harness#85 の欠陥を直した走行で測り直す

## 3. B4 との差（諮問 ③）

- B4（v1）では、A も B もテストのファイルにアクセスできた。v2 では、細い作業場所で**両条件とも**テストを見ない（2026-09-25 の裁定 2）。代わりに、両条件とも性質の宣言（前提と帰結の式）をプロンプトで受け取る。A だけが剥奪されたのではない
- 非対称なのは、B の門（非公開シード・P2P・内側ループでの反例の返し方・whitelist）で、これが処置そのもの。A に門が無いので、A は受入（公開シード）が通れば止まる。T1 の P2P の破壊（5 件）は、A に門が無いことの帰結（裁定 3 で「実験結果としてそのまま記録」）
- B4 の A（b4-smoke-01 で 4.81 USD、T1〜T5 を 1 回ずつで通過）は、受入が例示テストで、テストのファイルを読めた。v2 の A と直接は比べられない

## 4. 新しく見つかった欠陥：T5 の受入が通せない見込み

### 4.1 事実

- v2-smoke-01 の A の T5 の 4 回の呼び出しは、どれも P-T5-01・02・03 の `PROPERTY_VACUOUS … given=0` で落ちた（P-T5-04 は落ちていない）。VACUOUS は「ランダムな系列の中で前提が 1 回も成り立たなかった」ときの失敗で、実装が正しくても起きうる
- P-T5-01・03 の前提は「その手の入力が RotateCw（または RotateCcw）だけ」かつ「そのまま回すと置けない」かつ「キックで置ける」。P-T5-02 はさらに「向きが Spawn」
- 公開シードは 5 本、系列の長さは 50（`properties.json`）。シードは固定なので、VACUOUS になるかどうかはシードでほぼ決まり、実装を直しても変わらない見込みが大きい

### 4.2 見積もり（`experiments/v2/tools/vacuity_mc.py`。近似のモンテカルロ、2,000〜4,000 系列）

| 系列の長さ | 1 系列で前提が 0 回の確率 | 5 系列（公開）で 0 回 | 20 系列（非公開）で 0 回 |
|:--|:--|:--|:--|
| 50 | 0.84〜0.85 | **0.41〜0.43** | 0.029〜0.035 |
| 100 | 0.73〜0.74 | 0.20〜0.23 | 0.002〜0.003 |
| 200 | 0.67 | 0.13 | 0.0003 |

近似（重力とロック猶予を無視、乱数は C# と違う）なので桁の目安。P-T5-02 は向きの条件が加わるので、これより成り立ちにくい。系列を長くしても頭打ちになる（ミノが固定されて盤面が埋まる）ので、効くのは公開シードの本数（0.845^n < 0.01 には n ≈ 27）。

### 4.3 見解

- **T5 の受入（公開シード）は、A にも B にも通せない見込みが大きい**。A が T5 で迷走したのは、知らせの形よりも、この欠陥で「直しようのない失敗」を返され続けたことが大きい。B は非公開シードの門（20 本）も持つが、公開シードの受入で止まるのは同じ
- 直し方の候補（どれも受入の定義＝性質の宣言を変えるので、**別の PR で独立のレビュー**を受ける）：
  1. 公開シードを 5 → 30 本にする（VACUOUS の確率を 1% 未満に）。実行時間は性質テストの分だけ伸びる
  2. VACUOUS の判定を、公開と非公開を合わせた本数で行う（公開だけで 0 でも失敗にしない）。ただし B の内側ループと A の再試行が「公開で 0」を知る手段が無くなる
  3. 前提が成り立つ状況を作る開始状態（壁際と回転を組み合わせた置き方）を増やす
- 推奨は 1。加えて、生成の時点で、各性質の前提が公開シードの中で成り立つことを確かめる検査を足す（参照モデルで走らせる。VACUOUS は実装に依らず先に分かる）
