## 2. 根本の原因：前提が実装の結果を条件にしている

性質は「前提（given）が成り立つ Tick で、then が成り立つ」と書く。**前提に after（実装が Tick を進めた後の状態）が入っている**と、性質は「実装がその出来事を起こしたなら、その結果はこうである」になる。

- 実装が出来事を起こさなければ、前提は成り立たず、性質は空虚になる。空虚の原因が「実装の欠陥（消去しない）」なのか「系列の運（無作為な 60 手で行が揃わない）」なのかを、測定器は見分けられない
- 空虚を失敗にすると、測定器の運が実装の欠陥として数えられる（v2r-dry-01 の T6・T7）。空虚を合格にすると、出来事を起こさない実装が通る（オラクルが弱い）
- 変異の死滅率 71.9%（U2、タスク前の main）も、この弱さと矛盾しない：出来事を起こさなくする変異は、前提ごと消えるので殺せない

実測（`python -m harness.propaudit`、2026-09-27）：

| 宣言 | 性質 | 前提に after を使う（P1 に反する） | after は無いが開始状態だけでは決まらない | 開始状態だけで決まる |
|:--|:--|:--|:--|:--|
| experiments/v2r/properties.json | 34 | **30** | 2 | 2 |
| experiments/v2/properties.json（V2-RUN） | 20 | **17** | 3 | 0 |

V2-RUN の宣言も同じ形だった。v2r の不具合ではなく、性質の書き方そのものの欠陥である。

## 3. 自己批判：確率を上げる継ぎ当てを重ねてきた

空虚が出るたびに、前提を**起こりやすくする**仕組みを足してきた。どれも確率を上げるだけで、前提が成り立つことを保証しない。

| 時期 | 継ぎ当て | していること | 保証しないこと |
|:--|:--|:--|:--|
| v2.1e | 前提の探索（`propgen.directed`） | 開始状態だけで評価できる前提を満たす系列を探す | after を含む前提（30 件）は探索から外している |
| v2.1f | 前提を狙う抽出（`sampling`） | 開始状態の領域と入力の分布を絞る | 絞っても出来事が起きるかは運 |
| v2r | 局面の食い違い（`_phase_conflict`） | 開始状態で成り立たない局面の前提を探索から外す | 外した前提が系列の途中で成り立つかは運 |
| v2r | 穴の行（`start.gap_rows`） | 下の行を 1 マスの穴だけ残して埋める | 穴にミノが入るかは運（v2r-dry-02 の B で 0 回） |

「テトリスの T6 を通す」ことを目的にして、目の前の空虚を減らす調整を続けた。Phase 4 の連続系（接触・衝突・転倒）では、希な出来事は落ちものパズルの行消去よりはるかに起きにくいので、この方式は通用しない。

同じ形の失敗が、ほかにもある：

- **直せない知らせを実装役に渡していた**：`PROPERTY_VACUOUS` は、前提が作れないという測定器の側の事実で、実装役に知らせても直せない。v2r-dry-02 の B は、この知らせで 2 回呼び直し、思考だけで 11 万トークンを使った
- **変化の無い呼び直しを止めなかった**：何も書かない試行の後に同じ門で測り直しても、知らせは変わらない
- **走行の前に測定器を検定していなかった**：前提が作れるかどうかは、実装を呼ぶ前にお金をかけずに確かめられるのに、有料の走行で初めて分かった
- **ファイルの削除が再試行を通っていなかった**：`fileops.retry_os` はあるのに、作業場所・最初の提出・不変条件の作業ディレクトリの削除は `shutil.rmtree` を直に呼んでいた

## 4. 原則（Phase 4 でもそのまま使う）

**P1 Given は構成する。観測しない。** 前提は、テストが実装を動かす前に作れる状態（before）と入力（input）だけで書く。実装の結果は then に書く。希な状態は、無作為な系列で起きるのを待たず、証拠の状態（witness）として注入する。証拠の状態で前提が成り立つことは、参照モデルで実装に依らず確かめる（成り立たなければ生成の時点で止める）。無作為な系列は、証拠に加える網として残す。Phase 4 の「状態の貯蔵庫（State Reservoir）からの状態の注入」と同じ考え方で、接触の直前・転倒の直前の状態を作って注入する。

**P2 測定器の故障と実装の失敗を分ける。** 実装に依らず決まる事実（前提が作れない・空虚・生成できない）は測定器の故障で、実装役に知らせず、欠陥としても数えず、走行を止める。実装役に渡すのは、実装を変えれば変わる事実だけ。

**P3 走行の前に、お金をかけずに測定器を検定する。** 宣言の監査（P1）、生成、証拠の状態の前提の確認、生成したテストのビルドを、実装役を呼ぶ前に通す。通らなければドライバは起動しない。

**P4 進まない試行を打ち切る。** 思考の量は CLI では制限できない（§6.2 の実測。モデル名で重さを選ぶだけ）。暴走の引き金（直せない知らせ）を P2 で断ち、変化の無い試行（2 回続けて何も書かない）の後は呼び直さない。

**P5 走行を環境の揺らぎで落とさない。** Windows のファイルロックのような一時的な失敗は再試行し、それでも駄目なら理由を添えて止める。落ちたときは、どこで何が起きたかを記録に残す（突然死にしない）。

## 8. 証拠の状態の注入の実装（§6 の 1、2026-09-27）

- 宣言：性質の任意のキー `witness`（1〜10 個）。`board`（一番下の行から上へ、幅ちょうどの `#`・`.`）、`mino`（型・x・y・向き、または null）、`input`（押すキー）、`phase`（省略時は `start.phase`）。書き方と検査は `harness/witness.py`
- 生成の時点（実装に依らない）：前提を Python の参照モデル（`witness.Evaluator`。C# の `PropertyModel` と同じ定義）で証拠の状態と入力について評価し、成り立たなければ生成しない。証拠を書く性質の前提は after を使えない（P1）。before の数（得点・固定の数など）も、今の契約の復元用コンストラクタ（GamePhase, ActiveMino?, IReadOnlyList<Cell>）が受け取らないので使えない。`counters` を書くと生成を止める。数を前提に使う性質は、契約の復元用コンストラクタを広げる PR（系列の変更）の後で書く
- テストの時点：`PropertyRunner.Run` が、無作為な系列の前に証拠を流す（`RunWitnesses`）。復元した状態（局面・ミノ・盤面）が証拠と違えば `PROPERTY_WITNESS_RESTORE`（実装の失敗。実装役に知らせる）、前提が成り立たなければ `PROPERTY_WITNESS_INVALID`（評価の食い違い。測定器の故障で、ドライバが走行を止める）、then が破れれば `PROPERTY_FAIL`（ops は `witness<k>:<入力>`）。証拠で前提が成り立った回数は given に数えるので、証拠のある性質は空虚にならない
- 証拠を書いた性質が 1 つも無い宣言の生成物は、前と同じバイト列（v2r のマニフェストの生成物 12 件の sha256 と一致を確かめた）
- **確かめていないこと**：生成した C# のコンパイルと実行（総監督は dotnet のビルドとテストを走らせない）。操縦士が `python -m harness.witness_selftest <一時ディレクトリ>` の後に `dotnet test <一時ディレクトリ>/W.csproj --filter "FullyQualifiedName~P_T5_02"` を一度走らせる（期待：`P_T5_02_Public` が合格、`P_T5_02_Hidden` は Ignore）

## 9. 宣言 T1〜T10 の書き直し（§6 の 2、最初の段、2026-09-27）

**方針**：前提（given）には、その Tick で何が起きるかを**前の状態と入力だけで決める**条件を書く。起きたかどうか（after）で絞らない。

- **固定しないこと**：前は `after.LockedMinoCount == before.LockedMinoCount` で絞っていた。これを「空中にある」（`fits(moved(before.ActiveMino, 0, -1))`、直下が空き）と「ハードドロップが無い」に替えた。前の Tick の ④ で直下が空きならロック猶予タイマーは 30 に戻っているので、この Tick で満了して固定することは無い（RL-26・RL-28・RL-43）
- **前提にした事実（要確認）**：「空中なら固定しない」は、無作為な系列の最初の Tick では、復元したときのタイマーの値に依る。今の契約はそれを決めていない。次の段で契約に書く復元の意味（タイマー 30）が入って、はじめて実装に依らず成り立つ
- **消去の有無と行数**：関数 `full_rows(m)`（前の盤面に m の 4 マスを足したとき横がすべて埋まる行の数）を足した。ハードドロップ（移動・回転なし）の固定位置は `drop(before.ActiveMino)` で決まるので、消去の行数は前の状態で決まる（RL-30・RL-44）
- **ゲームオーバー**：出現向きの I を Y = 19 で固定すると、4 マスがすべて Y ≥ 20 になる（ST-02、LP-05）
- **希な事象には証拠の状態を付けた**：ライン消去（T6・T7）、接地したままのハードドロップ（T7・T8）、ゲームオーバー（T10）、1 マスだけの落下（T3）。証拠のある性質は空虚にならない
- **then を強めたもの**：P-T2-02（空中なら固定の数も変わらない）、P-T6-01（2 行の消去）、P-T7-03（落下 2 マス＋1 行で、得点をちょうど +104）、P-T8-04（ソフトドロップの得点は、落下したマスの数とちょうど等しい。落ちた Tick も落ちない Tick も確かめる）、P-T10-03（局面が GameOver になることも確かめる）
- **弱めたもの**：P-T8-02（接地してのソフトドロップ）は、隠れたタイマーで固定が起きうるので、then を「得点は不変、かつ（固定したか、Y が変わらない）」にした。固定の有無は後の段の複数ティックの証拠で確かめる

## 10. 走行の前の検定（§6 の 3、原則 P3、2026-09-27）

`python -m harness.ab.v2r_preflight`（`harness/ab/v2r_preflight.py`）。実装役を呼ばずに次の 7 項目を確かめ、`<out-root>/preflight/<マニフェストの sha256>.json` に記録する。ドライバ（`run`・`run-all`）は、v2r のマニフェストについて、同じ sha256 で合格した記録が無ければ起動しない（`v2r_preflight.require`）。

1. マニフェストの凍結した入力が sha256 と一致する
2. 前提に after を使う項が無い（P1）
3. 性質の宣言が、base commit の構造化仕様・GDD で検査を通る（証拠の状態の前提を含む）
4. 生成物を作り直すと、マニフェストの generated_sha256 と一致する
5. 描画器の語彙が全単射で、契約を覆う
6. タスクごとに、自然言語の仕様が描けて検査を通り、形式の prompt の語彙が閉じている
7. 実装役のモデルが明示され、使ったモデルを記録できる

今のマニフェスト（sha256 `4c27213b…`）で 7 項目とも合格した。参考として、証拠が無く無作為な系列で前提が起きるのを待つ性質が 21 件ある（よく起きる事象。成立回数は走行の `property_hits` で見る。判定には入れない）。

**しないこと**：生成したテストのビルドと実行（dotnet）。総監督は走らせないので、ドライバの baseline の測定（走行の最初）で確かめる。

## 11. 落ちた走行の記録と再開（§6 の 4、原則 P5、2026-09-27）

- **記録**：`driver.record_fault` が `fault.json`（タスク・番号・段・例外・トレースバック・再開のコマンド）を、`guard.record_stop` が `guard_stops.jsonl`（STOP の行）を、走行の出力先に残す
- **再開**（`driver run --resume`、v2r だけ）：metrics の各行に `resume`（終わりのコミット・通っていたテスト・落ちていたテスト）を足した。`resume_point` が行の並びを確かめ、作業ツリーを最後の行の終わりのコミットに戻し（`git reset --hard`・`git clean -fd`）、`set_aside` が途中のタスクの出力を `aborted/` に移して、次のタスクから続ける。v2r は呼び出しごとに新しい会話なので、途中から続けても実装役に渡るものは同じ
- **guard**：途中のタスクの呼び出しのログを `aborted/` に移しても費用に数えるように、実装役のログを `rglob` で探す
- **しないこと**：`run-all`（4 条件の繰り返し）の再開。止まった条件の `run --resume` を手で呼び、残りの条件は `run` で続ける
