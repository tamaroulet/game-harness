# V2-6：試験制度の対称化（v2-smoke-02 の前）

- 状態: 見解と修正案（コードは変えていない）
- 前提: game-harness#86（公平性の見直し）。2026-09-25 の裁定：T5 は公開シード 30 本＋生成の時点の前提の検査、A の再試行の知らせを B と同じにする、A の定義（未圧縮の単一会話）は変えない
- 諮問（2026-09-25）: B は非公開シード・不変条件・P2P で落ちても再試行できるが、A は公開シードが通った時点で終わり、事後の測定で落ちる。この非対称をどう正すか
- 結論: **諮問の指摘は事実で、同意する**。いまの B の優位は「門（検査と再試行）」と「文脈の持ち方（会話を積まない）」が混ざっていて、どちらの効果か分けられない。**A にも B と同じ検査の順と同じ知らせと同じ呼び出しの上限を与える（試験制度を同じにする）**ことを推奨する。そのうえで、両条件とも「最初の提出」の成績も同じ測定器で記録し、門の効果は B の中の比較（最初の提出 → 最終）として別に示す

## 1. 事実（コード）

### 1.1 B が 1 回の実装役の呼び出しの後に受ける検査（`harness/pipeline.py` の `attempt`）

| 順 | 検査 | 落ちたとき | 実装役に返る知らせ |
|:--|:--|:--|:--|
| 内側 | whitelist の内側の検査 | 内側ループの次のターン | 変更を取り消した旨と書き換えてよいファイル |
| 内側 | 高速検査（**全テスト**：公開シードの性質テストと、前のタスクまでのテスト＝P2P を含む） | 内側ループの次のターン（最大 3） | 性質テストなら 1 行の反例（最大 5 行）、例示テストなら名前と期待値の不一致。ビルドが通らなければ診断の射影 |
| 外側 | whitelist・静的・差分の行数 | 次の試行（最大 3） | 門の知らせ |
| 外側 | 受入（開示）と P2P（`check_p2p`） | 次の試行 | 「先祖返り（P2P 破壊）n 件: 名前…」 |
| 外側 | 性質テスト（**非公開シード**） | 次の試行 | 「非公開シードで性質が破れました（反例は開示しません）」。件数も名前も返さない |
| 外側 | 不変条件（Outer） | 次の試行 | 反例の行 |

呼び出しの上限は 3 試行 × 3 ターン = 9 回。試行の境目でサンドボックスを base に戻す。

### 1.2 A（`harness/ab/driver.py` の `run_task_a`）

- 呼び出しの上限は 9 回（`call_budget`。B の最大にそろえてある）
- 呼び出しの後の検査は、**そのタスクの受入の公開シードだけ**（`measure.acceptance(..., public_only=True)`）。P2P（前のタスクまでのテスト）、非公開シード、不変条件、whitelist、差分の行数は見ない
- 公開シードの受入が通れば、その場でタスクを終える。非公開シード・不変条件・P2P はタスクの後の測定器で初めて測られ、A には知らされない

### 1.3 実際に効いた例

- v2-dry-04 の A は、公開シード 4/4 で止まり、測定の非公開シードで 1 件落ちた（受入 7/8）。以前の記録（`notes.md`）で「非公開シードが A の合わせ込みを捕まえた」と書いたが、**B は同じ状況なら門で知らされて直せた**。A だけの弱さとして書いたのは不正確だった
- v2-dry-05b・v2-dry-06・v2-smoke-01 の A は、T1 で Issue17Cases の 5 件（P2P）を壊した。B は高速検査で全テストを見るので、内側ループで知らされる（v2-dry-05b の B の 2 回目の呼び出しの「前回の失敗」に、同じ Issue17Cases の期待値の不一致が入っていた）

## 2. 何を比べる実験か

A と B の差は、いま次の 3 つが重なっている。

| # | 差 | 性質 |
|:--|:--|:--|
| 1 | 文脈の持ち方：A は 1 つの会話に積む。B は呼び出しごとに新しく始め、試行ごとにサンドボックスを戻す | 比べたいもの（単一チャット vs ステートレス） |
| 2 | 試験制度：B は全テスト・非公開シード・不変条件・P2P で検査され、落ちれば知らされて再試行する。A は公開シードだけ | 諮問の指摘 |
| 3 | 知らせの形：A は末尾 40 行が余分 | game-harness#86 で是正を裁定済み |

v2 の主張（型・コンパイラ・性質テストの反例で、長期にわたり仕様ドリフトを起こさずに作り続ける）の中心は、契約と門と反例のループにある。門を B から外すと、B は「会話を積まない A」になり、v2 の仕組みの効果を測れない。逆に、門を B だけに与えると、2 の差が 1 の差に見えてしまう。

## 3. 修正案

### 3.1 推奨：試験制度を両条件で同じにする（A にも門を与える）

- **A にも、B と同じ検査を同じ順で、呼び出しの後に行う**。落ちたら B と同じ文面の知らせを、A の会話の次の入力として渡す
  - 全テストの高速検査（公開シードの性質テスト＋前のタスクまでのテスト）→ whitelist・静的・差分の行数 → P2P → 非公開シード（反例は開示しない）→ 不変条件
  - 非公開シードは、B の門と同じく「単位・試行・差分から決める」（`pipeline.hidden_seeds`）。**測定器の非公開シード（走行とタスクから決める）とは別の系列**のまま
- 呼び出しの上限は同じ 9 回。**違いとして残すのは文脈の持ち方だけ**：A は会話を積み、作業ツリーを戻さない。B は呼び出しごとに新しく始め、試行ごとにサンドボックスを戻す
- 実装は、B の検査の列を 1 つの判定関数に切り出し（`pipeline.attempt` の検査の部分）、A と B が同じものを呼ぶ。同じコードを通るので、知らせの形も同じになる（#86 の対等化もここで満たす）
- これで主張できること：「同じ契約・同じ性質・同じ門・同じ知らせ・同じ上限のもとで、会話を積む単一チャットと、呼び出しごとに新しく始める防壁型を比べた」

### 3.2 門の効果は、両条件の「最初の提出」で別に示す

門そのものの価値（知らされて直せること）は、A と B の比較ではなく、**各条件の中の比較**として記録する。

- 両条件とも、最初の実装役の呼び出しの直後の状態を、最後の測定器と同じ測定器（公開＋非公開シード・不変条件・P2P）で測って残す（「最初の提出」）
- 最終の成績（門を通った後）と並べれば、門で何件直ったかが条件ごとに分かる
- 測定は実装役に知らせない（測定器の非公開シードは門の非公開シードと別の系列なので、門の再試行の情報にもならない）

### 3.3 採らない案：B の門を外に出す（非公開シード・P2P を再試行なしの測定にする）

- 両条件とも公開シードだけで止まる実験になり、公平ではあるが、v2 の仕組み（門と反例のループ）を測らなくなる。v2 の本走の目的から外れる
- 3.2 の「最初の提出」の記録で、門の無い状態の比較は同じデータから取れる。わざわざ門を外した走行をする必要は無い

## 5. 裁定が要ること

1. **試験制度の対称化の方式**：3.1（A にも門を与える、推奨）か、3.3（B の門を外す）か
2. **「最初の提出」の記録（3.2）を足すか**（推奨：足す。門の効果を条件の中で示す唯一の方法）
3. **A の作業ツリーの扱い**：B は試行の境目でサンドボックスを base に戻す。A は戻さない（会話と同じく積む）。推奨：戻さない（単一チャットで人がファイルを戻さないのと同じ。これも文脈の持ち方の一部として扱う）
4. 過去の記録の訂正：v2-dry-04 の A の 7/8 を「A の合わせ込み」と書いた箇所に、試験制度の差があったことを注記する（推奨：注記する。この PR の後の記録の PR で行う）
