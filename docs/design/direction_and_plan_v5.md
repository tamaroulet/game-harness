# 方向と計画 v5 —— 入口の検査を 1〜3 週で終え、Unity の実開発へ

- 版：v5（2026-11-05）。v4（game-harness#345 の最初のコミット）を置き換える。v3 は記録として残す。
- 決めるのは操縦士と総監督。日数・費用・確率は、どれも推測。
- 鎖の段の中身は書かない。件数と種類だけ。

## 1. 目標

**最終の目標**
- Unity のゲーム開発を、ハーネスに任せる。
- ハーネスは、その開発で出た問題から、自分を直し続ける。
- 内容が大きくなっても崩れない。

**今の段の着地点**
- GitHub で公開したとき、第三者が「素のエージェントで作るより、ハーネスを通すほうが有効だ」と納得できる、測りの結果を出す。
- 出たら、トイ課題（MuJoCo の鎖）の周回と作り込みはせず、Unity の実開発に移る。
- ハーネスの改善は、Unity の実開発で出た問題に対して行う。鎖は、改善の的にしない。

**v4 の誤り**
- v4 は、Unity の前に「外側の改善の輪（周期）が鎖で効くことの確かめ」と自動化を置いた。v3 の L6〜L8 の筋を、そのまま引き継いだため。
  - 最終の目標から見ると回り道で、主（Unity の実開発）と従（鎖での確かめ）が逆になっていた。
  - 3〜4 か月の見込みの大半は、ここから来ていた。
- v4 の「両方にコマンドを許してそろえる比べ」は、「ハーネスの作りのどこが効くか」を切り分ける問いに答えるもの。今の着地点には要らない。そのための箱づくり（2〜3 週）も要らない。

## 2. 鎖の比べで言えること・言えないこと

- 鎖の段の走りで呼ばれるのは、実装役（agy の gemini-3.8-flash-medium）だけ。
  - held-v0 の 34,361,580 トークンは、28 回の呼び出しのすべてが実装役だった（数えた）。開発の組の 2 回も同じ。
  - 計画役と監修役（Sonnet）は、鎖では呼ばれない。走らせ役が固定の計画を書き、監修の「通った」の印を先に置くため（bench_chain の write_plan、bench_run の seed_reviews。Argon も確かめた）。
- だから鎖の比べが測るのは、ハーネスの内側の輪の値打ち。内側の輪とは、頼みの作り・門が回す試験・落ちたテストを渡す試し直し・変えてよい場所の守り。
- **言えること：** 同じモデルで、6 段の積み上げの変更を、内側の輪を通すほうがよく通すか。
- **言えないこと：** 大きな内容を、計画と分解で崩さずに作れるか。これは Unity の実開発の記録で示すしかない。鎖に長く掛けても示せない。
- だから鎖の比べは、小さく速く済ませる。

## 3. 入口の検査（Unity に入る前に済ませる 3 つ）

### 3-1 比べ（R1）

**腕**
- **H：** 今のハーネス（v0、rev 38d61e0）。実装役にコマンドは無く、門が試験を回す。設計のままの形。
- **P：** 素のエージェント。同じ agy（版の固定も同じ）・同じモデルを、段ごとに新しく起動し、段の仕様を渡す。コマンドを含む道具を、ふだんどおり使える（`--sandbox` を付けない）。

**道具をそろえない訳**
- 第三者の問いは「ふだん使う素のエージェントより、ハーネスを通すほうがよいか」。
- ふだんの素のエージェントは、コマンドで自分で試験を回す。ハーネスは、実装役にコマンドを持たせず、門で試験を回すのが設計。どちらも、使う形のまま比べる。
- 10-30 の「道具を両方でそろえる」決まりは、この段では外す（§9 の決め 2）。

**材料**
- H は、もうある 3 回の走りを使う。走らせ直さない（3 回で 94,621,484 トークン。約 9,500 万を省く）。
  - 開発の組の 1 回目・2 回目（13/18・16/18）と、保留の組の held-v0（12/18）。
- P は、同じ組を同じ回数だけ走らせる。開発の組 2 回・保留の組 1 回（54 段）。
- 対は、H の開発の 1 回目と P の 1 回目、H の 2 回目と P の 2 回目、H の held-v0 と P の保留の 1 回。段ごとに 54 の対になる。
- P の始めの木は、H と同じ段 0 のコミット（基のテストを含む）。段 k の仕様は、H と同じく作業ツリーの中に置く。
- H の走りは 10-31〜11-05、P は 11-11 ごろから。
  - agy の版は、ハッシュの照合で同じものに固定する（agy_pinned）。モデルの ID は、CLI の報告で照合する（採点の道具の bad_models）。
  - モデルの提供元の側の変化は抑えられないので、結論に日付を書く。
  - 同じ時期に H を 1 本だけ走らせ直す確かめは、しない。6 段では、同じ版の 2 回の差（3 段）と見分けられず、1 本で約 1,000 万掛かる。

**判じ方（走る前に登録する）**
- **主：** 54 の対のうち、片方だけが通った段を数える（H だけが通った段を a、P だけを b）。
  - 片側の正確な符号検定で p ≤ 0.05 なら、勝ったほうの優位が示せたとする。
  - 要る数の例：a + b が 8 なら 7 以上、10 なら 9 以上、15 なら 12 以上、20 なら 15 以上。
  - あわせて、次の 2 つも同じ向きであること。
    - 保留の組だけでも a ≥ b（開発の組だけの差でないことの確かめ）。
    - 9 本の鎖の走り（開発 3 本 × 2 回・保留 3 本 × 1 回）で、通った段の多い鎖の数も、勝ったほうが多い（引き分けの鎖は数えない）。段は前の段の上に積むので、同じ鎖の中の対は独立でない。その確かめ（Argon）。
- **副：**
  - 通った段あたりのトークンと時間（ROI）。
  - 新しい隠しテストだけで見た通過（前の段の保ちを外す）。1 つの落ちが後の段に響く分を、分けて見せる（Argon）。
- **公開：** 腕ごとの合計・a と b・p・鎖ごとの勝ち越し・トークン。保留の組の段ごとの結果は、この段の終わりまで公開しない（§3-3）。
- **数える道具：** 今の対の道具（bench_pair の compare）は公開の記録を読むが、保留の組の公開の記録には合計しか無い（段ごとは非公開の置き場）。比べは、非公開の段ごとの記録を読む小さな道具で数える（Argon）。

**公平の決まり**
- 採点は、両方の腕に、同じ隠しテストと同じ採点の道具（chain_score）を使う。
- P は、段の終わりに、変えてよい場所の外の変更を戻してから記録する。散らかしのファイルで 0 点にしないため。
  - H の開発の組の 2 回は、外の変更のあった段が 0 だった（数えた）。保留の組は合計で無効 0。この決まりで H の点は変わらない見込み。保留の組の段ごとは、採点の前に確かめる。
- 道の検め（作業の場所の外を指す道具の呼び出しで、段を無効にする）は、P のコマンドにもそのまま掛かる。
  - P の無効の段は、H の優位を言うときは P の点のまま数え、P の優位を言うときは P の落ちとして数える。どちらの向きでも厳しい側に倒す。
- P の段の時間の上限は 60 分。H の実装役の上限（1 回 30 分 × 試行 2 回）に合わせる。上限に当たった段の数も出す。
  - ターンの上限は、どちらにも掛けない（H の agy の実装役にも `--max-turns` は付いていない）。トークンの上限も掛けず、記録する。
  - H の門は、段のテストのほかに大きさの決まりのテストも回す。これは H の設計の一部として、そのまま比べる。
- P への頼みは、段の仕様に、H と同じ作業の決まりだけを足す。
  - 作業の決まり：テストを tests/ に書く・git を触らない・進捗のファイルを変えない・CLAUDE.md の進捗と報告の規約は適用しない。
  - ハーネスの指示（目次・試験を走らせない・あきらめの書き方）は入れない。
  - 頼みの全文と走らせ役を、登録の文書に載せる。
- 作業場の根には、エージェント向けの指示のファイルが CLAUDE.md しか無い（GEMINI.md・AGENTS.md は無い。見た）。bench の agy の大域の設定が P のふるまいを縛らないことは、探りの 1 段で確かめる（P が実際にコマンドを使うか）。

**閉じ込めと検め**
- P は、bench のアカウントでコマンドを使う。今の形のままだと、走らせ役と同じアカウントなので、次が読める。
  - 先の段の仕様：段の写し（操縦士のアカウントの stage が、走りの前に段 1〜6 をまとめて置く）。置き場の名前は当てられない 16 桁だが、コマンドがあれば一覧で見つかる。
  - 前の走り：H の作業ツリーと記録、前の走りの段の写し。
- 読めることは P に有利な向きにしか働かない。それでも、次の 2 つの害がある（Argon）。だから読めなくしてから走らせる。
  - 結果が「示せない」に寄る。そうなると R2 の費用を招く。
  - P が勝ったときに、勝ちを確かめられない。道の検めは、コマンドの引数に出たパスしか見ないので、漏れを見落とすことも、正当なコマンドを誤って当てることもある。
- 箱は作らない。代わりに、P の走りの前に次の 3 つをする。
  1. **配り役。** 操縦士のアカウントで動く小さな道具。段の写しを 1 段ずつ置き、段 k が済んでから段 k+1 を置く。走らせ役の側は、次の段の仕様が置かれるのを待つ形に変える。仕様のハッシュは、初めから記録に書いてよい（中身は漏れない）。1 日（推測）。
  2. **前の走りを移す。** H の作業ツリーと記録、前の走りの段の写しを、bench の読めない所に移す。
  3. **bench の拒みを効かせる（§3-2）。**
- 道の検めは、P にもそのまま掛ける。漏れの守りの主は、配り役と移しのほうで、道の検めは補い。

### 3-2 任せて走らせる前の安全

- **bench の拒みを効かせる。** 11-05 に、次の 2 つを見つけた。
  - 拒みが無い：総監督の読む main と枝の写し・機械の設定・席の置き場は、bench が書ける。候補選びの隠しテストの置き場（試しの土台のもの）は、bench が読める。
  - 拒みが下まで届いていない：拒んでいる置き場の下で、自分の許しを持つ子がある（受信箱の下に 5 つ、out の下に 52。out のほうは試験の一時の置き場など）。Windows は、子が自分で持つ許しを、上から受け継いだ拒みより先に見る。だから、上の階の拒みは、その子には効かない（使い捨ての置き場で確かめた）。写しと席の置き場の下にも、自分の許しを持つ子が多い。
  - 隠しテストの置き場（oracles）の下には、自分の許しを持つ子は無かった。そこの拒みは効いている。
  - 直し：足りない拒みを上の階に足し、下の子の許しを外して、上の階を受け継がせる。前の状態を写してから行い、戻せる形にする。会話の席が手順を出し、操縦士が流す。
  - 拒みの検め（bench_guard）は、上の階だけを見ていた。下の子の自分の許しも数えるように広げる。
  - bench の走りは、写しの同期を呼ばない（同期は受信箱に書く処理の中にあり、操縦士の側で動く）。写しを書きの拒みにしても、bench の走りは止まらない見込み。拒んだ後に、探りの 1 段で確かめる。
- **H ラインの監修役の起動の旗。** `--permission-mode` を足し、PowerShell も拒む。Unity で計画役と監修役を使うので、Unity の前に直す。
- **提案役の道具の直し（game-harness#344）。** マージし、1 回起こして、使える道具が 3 つだけで、読む根の外に当たらないことを確かめる。出た提案は記録だけにし、鎖では取り込まない。
- **版の固定。** v0 の rev（38d61e0）に GitHub の札を付ける。枝が消えているので、第三者が同じ版を取れるようにするため。

### 3-3 Unity に持っていく回帰の確かめ

- 鎖は、改善の的にしない。役を次の 2 つに替える。
  1. ハーネスの内側の輪を変えたときの回帰の確かめ（開発の組を 1 回、1 夜）。
  2. 公開の物差し。
- 保留の組の段ごとの結果と、鎖の中身を公開するかは、この段の終わりに決める。
  - 公開すれば、第三者が走らせ直せる。
  - 置き場は別のリポジトリにし、実装役の作業場（main の写し）には入れない。

## 5. Unity の段

**入るとき（R1 で決まれば 11 月の半ばすぎ、R2 まで行っても 11 月の終わり）**
- 操縦士のゲームの設計を受け取る。
- 門を Unity につなぐ。
  - ロジックを Assets の外の素の C# に分け、Unity を起こさずに試験を回す形を先にする（falling-blocks の作業場に例がある）。
  - Unity の起動が要る試験は、batchmode で少なく。
- 実装役は、R1・R2 で良かった形にする。

**改善の回し方**
- 提案役に、Unity の作業の記録（試行・門の結果・人の手・費用）を読ませる。
- 直しを取り込むかは、Unity の次の作業の記録の前後で決める。内側の輪を変えたときは、鎖の回帰の確かめ（1 夜）も通す。
- 自動化（L7・L8 の形）は、Unity で直しが取り込まれ始めてから、要る分だけ作る。

**並べ方**
- Unity の準備（門のつなぎ・作業場の形）は、R1 の夜の走りと並べて進める。
- 夜の走りは Gemini の枠を使い、会話の席の作業は Claude の枠を使うので、取り合わない。

## 8. やめること・後へ回すこと（v4 から）

- **鎖ではやらない：** 周期（L6 の周回）・自動化（L7・L8）・G2・取っておく組・保留の組を見る回数の上限。周期と自動化は、Unity で要る分だけ作る。
- **作らない：** 箱（WSL2）。配り役と前の走りの移しで代える。
- **やらない：** 両方にコマンドを許す比べ（v4 の B0′）。R2 の H′ はそれに近いが、目的は作りの直し 1 つの確かめ。
- **後へ回す：** Sonnet の単体の腕（10-30 の「枠があれば足す」）。今の着地点の問い（同じモデルで、ハーネスを通すか）には要らない。

## 9. 操縦士に決めてほしいこと

1. 目標と着地点を、§1 の言葉で置く。木の目的も、総監督に頼んでこれに替える。
2. 比べは、使う形のままにする（H は設計どおりコマンド無し、P はコマンドあり）。10-30 の「道具をそろえる」決まりは、この段では外す。
3. R1 で示せなければ、R2 を 1 回だけ試す。R2 の後は、結果によらず Unity へ入り、結果はそのまま公開する。
4. P の走りの前に、bench の拒みを効かせ（足りない拒みを足し、下の子の許しを外す）、前の走りを移す。会話の席が手順を出し、操縦士が流す。
5. v0 の rev に GitHub の札を付ける（外に出る操作）。
