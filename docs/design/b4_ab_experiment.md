# B4-RUN：単一チャット型とステートレス防壁型の A/B 実験の構成

- 状態: 方針のみ。コードは変更していない
- 前提: B3（ADR-003）と B4-PREP が完了。falling-blocks は GDD v9、main に falling-blocks#12（初期状態）と falling-blocks#17（出現と 1 段の自然落下）が入っている
- 決定（2026-09-24、オーナー指示）: B4-RUN を、5 機能の直列実装による 2 条件の A/B 比較として無人で走らせる。Task 3・5 は各タスクの前に GDD を改訂する。Task 1 の前に harness を拡張する（given に構造体のリテラルを書けるようにする）

## 1. 目的と測るもの

相互に干渉しやすい 5 機能を直列に実装させ、次の 2 条件がどれだけ壊れにくいかを数字で比べる。

| 条件 | 中身 |
|:--|:--|
| A（対照群）：単一チャット型 | 1 つの会話に、タスク・差分・テストの結果を積み続ける。作業ツリーはリセットしない。門は無い |
| B（本基盤）：ステートレス＋決定論的防壁型 | タスクごとに作業ツリーをリセットし、pipeline.py の門（スキーマ門・差分バジェット・P2P・不変条件・診断の射影）の下で走らせる |

5 機能は次の順に固定する。

| # | 機能 | GDD |
|:--|:--|:--|
| T1 | 左右移動（壁・盤面外の判定） | v9 §4・§8-4 にある |
| T2 | 自然落下と接地判定（ロック猶予・固定） | v9 §4 ③④⑤ にある |
| T3 | ハードドロップ（即時固定） | **無い**。§5 で GDD を改訂する |
| T4 | 回転（壁キックなし） | v9 §4 にある |
| T5 | 壁キック回転（SRS） | **無い**。v9 は「壁蹴り等の補正移動は一切行わない」。§5 で GDD を改訂する |

## 2. 公平性の原則（交絡を消す）

2 条件で違ってよいのは「会話を積むか・門の下で走るか」だけにする。それ以外はすべてそろえる。

1. **同じ入力**：各タスクの入力は、マニフェスト（§4）の固定テンプレートから機械的に作る。人間はプロンプトを書かない
2. **同じ情報**：どちらの条件も、同じ要求文・同じ interface（`testgen.render_interface`）・同じ生成テスト（Generated/）を見られる。不変条件のテストは、どちらにも見せない
3. **同じ受入基準**：単位定義は実験の前に 1 回だけ作って凍結し（§4.2）、sha256 で固定する。分解役の揺らぎを実験に持ち込まない。判定は両条件とも同じ測定器（§6）で行う
4. **同じ実装役**：同じ CLI・同じモデル・同じ温度。モデル名はテレメトリで確かめ、違えばその回を無効にする
5. **同じ試行の予算**：1 タスクあたり、実装役を呼べるのは最大 3 回（B の `max_retry: 2` と同じ）。A で 2 回目以降に渡すのは、固定テンプレートに埋めた失敗の要約（§3.2）
6. **同じ出発点**：両条件とも、同じ base commit（GDD 改訂の後の falling-blocks main の SHA）から始める
7. **繰り返し**：LLM の揺らぎがあるので、各条件を N 回（まず 3 回）走らせる。A と B は交互に走らせ、時間帯の偏り（API の混み具合）を散らす

## 3. 自動ドライバ

### 3.1 置き場所と起動

```
harness/ab/driver.py      実験の駆動（条件 A・B、1 回の走行）
harness/ab/measure.py     測定器（両条件に共通。読み取りだけ）
harness/ab/report.py      集計（metrics.jsonl → summary.md）
experiments/b4_ab/tasks.json          タスクのマニフェスト
experiments/b4_ab/templates/*.md      固定テンプレート（初回・再試行）
experiments/b4_ab/units/T1..T5.json   凍結した単位定義 v2
experiments/b4_ab/tests/T1..T5/       凍結した生成テスト（testgen の出力）
```

起動は 1 行で、人間が打つのはこれだけにする。

```
python -m harness.ab.driver run --manifest experiments/b4_ab/tasks.json --condition A --run-id ab-01
python -m harness.ab.driver run --manifest experiments/b4_ab/tasks.json --condition B --run-id ab-01
python -m harness.ab.report --run-id ab-01
```

`run-all --repeat 3` で、A・B を交互に 3 回ずつ無人で回す。

### 3.2 1 回の走行の流れ

```
準備：base commit から専用の worktree と枝を作る（§3.3）
for T in T1..T5:
    タスク開始の commit を記録する
    凍結した生成テスト（T までのもの）を worktree の Generated/ に置く
    条件 A：
        同じ会話に初回テンプレートを送る
        実装役が worktree を書き換える
        測定器（§6）で受入を見る。落ちたら、再試行テンプレートを同じ会話に送る（最大 3 回）
        作業ツリーはリセットしない
    条件 B：
        pipeline.py --unit experiments/b4_ab/units/T.json --repo-dir <worktree-B> --local-only
        （試行ごとのリセット・門・診断の射影・Outer 段は pipeline のまま）
    測定器（§6）で T の終わりを測り、metrics.jsonl に 1 行を足す
    worktree の状態を枝に commit する（あとから差分を再現できるように）
```

- **A の会話の持ち方**：実装役の CLI が会話の再開（resume）に対応していれば、それを使う。対応していなければ、ドライバが会話の全文を持ち、毎回すべてを送り直す。どちらでも「会話を積む」ことに変わりはない。後者は、トークンの伸びが測定そのものになる
- **A の再試行テンプレート**：落ちた生成テストの名前と、失敗の本文の末尾 40 行を埋める。これは単一チャットで人が普通に貼るものの代わりで、B の診断の射影は入れない（射影は B の処置の一部）
- **B の `--local-only`**：pipeline.py に足すフラグ。push と CI の待ち（[6]〜[8]）を行わず、持ち出しを worktree-B の中の commit で終える。A は CI を通らないので、CI の有無を条件の差に混ぜない。CI の代わりは測定器が務める

### 3.3 物理的な隔離

| もの | A | B |
|:--|:--|:--|
| worktree | `C:\src\.local\wt\ab\<run-id>-A` | `C:\src\.local\wt\ab\<run-id>-B`（pipeline のサンドボックスもこの下に別に切る） |
| 枝 | `ab/<run-id>/A` | `ab/<run-id>/B` |
| 出力・ログ | `C:\src\.local\out\ab\<run-id>\A` | `C:\src\.local\out\ab\<run-id>\B` |
| ビルドの中間物 | worktree ごとの `obj/`・`bin/` | 同じ |
| 実装役の会話 | 走行ごとに新しく 1 つ | タスクの試行ごとに新しく |

- 枝は push しない。GitHub を汚さず、互いの CI も起こさない
- NuGet のグローバルキャッシュだけは共有する（中身はパッケージの版で決まり、成果物が混ざらない）
- 走行が終わったら、worktree は消し、枝は残す（差分の再現用）。`driver cleanup --run-id` で消す

## 4. タスクのマニフェスト

### 4.1 形（`experiments/b4_ab/tasks.json`）

```json
{
  "schema": 1,
  "experiment": "b4_ab",
  "base_commit": "<GDD 改訂後の falling-blocks main の SHA>",
  "gdd_sha256": "<その版の GDD の sha256>",
  "implementer": {"cli": "agy", "model": "<固定するモデル名>"},
  "max_attempts": 3,
  "invariant_seeds": [11, 22, 33],
  "tasks": [
    {
      "id": "T1",
      "title": "左右移動（壁・盤面外の判定）",
      "requirement": "要求文（自然言語。GDD の節と構造化仕様の ID で根拠を示す）",
      "gdd_refs": ["§4 基本操作と衝突判定", "§8-4"],
      "unit": "units/T1.json",
      "unit_sha256": "<凍結した単位定義の sha256>",
      "tests": "tests/T1/",
      "tests_sha256": "<生成テストの sha256>",
      "superseded_tests": []
    }
  ]
}
```

- `requirement` は、実験の前に人間が 1 回だけ書いて凍結する。両条件の初回テンプレートは `{requirement}`・`{interface}`・`{whitelist}` を埋めるだけ
- `superseded_tests`：後のタスクが**仕様どおりに**振る舞いを変えるため、通らなくなって正しいテストの一覧。P2P の破壊の数から除く（両条件とも同じ一覧）。§5 の設計により、いまの 5 機能では空にできる見込み

### 4.2 凍結の手順

1. GDD を改訂し、構造化仕様を再生成して main に入れる（§5）
2. タスクごとに分解役（`decompose.py`）で単位定義を 1 回作り、スキーマ門と生成テストを通す
3. 人間が単位定義を読み、要求文と食い違っていないかを確かめてから凍結する（sha256 をマニフェストに書く）
4. 生成テストも凍結する。実験中に単位定義も生成テストも作り直さない

## 5. GDD の改訂（T3・T5）

v9 では T3・T5 の受入基準を書けない。**推測で埋めず**、実験の前に GDD を 1 回だけ版上げする（v10）。実験中に仕様を変えると、それ自体が交絡になるからである。

- **ハードドロップ（T3）**：GDD の本文として足す。足すのは、入力の定義（1 ティック分の離散入力）、処理順序での位置（②と③の間など）、落下距離、即時固定の扱い、得点の有無（ソフトドロップの 1 点／マスに合わせるか）
- **SRS（T5）**：キックの候補表（JLSTZ 用と I 用、向きの組ごとに 5 候補）を §5 の外部パラメーター（PR-xx）として足す。候補を順に試し、最初に置けた位置を採る規則を本文に足す
- **回転の行の書き換え**：v9 の「壁蹴り等の補正移動は一切行わない」を「SRS の候補表に従う」に改める
- **T4 と T5 の切り分け**：GDD は v10 の最終形（SRS あり）だけを持つ。T4 の受入データには「キックが要らない回転」（開けた場所での 90 度回転。候補 1 のオフセットは (0, 0)）だけを入れ、壁際の回転は T5 に入れる。こうすれば T5 が T4 のテストを壊すことはなく、`superseded_tests` は空のまま、両条件に同じ基準を当てられる
- キック表の値は、外部の標準をそのまま写す。写したことを人間が確かめてから main に入れる（2026-09-17 に、外部 AI が一般的なテトリス仕様を書き足して実験の前提を壊した前例がある。メモリの記録）

## 6. 測定器と指標

### 6.1 測定器（`harness/ab/measure.py`、両条件に共通）

タスクの終わりごとに、worktree を読み取りだけで測る。実装役にも総監督にも生ログは渡さず、数だけを残す。

1. ビルドと高速検査：凍結した生成テストのうち、T1〜T の全部を実行する
2. 受入（F2P）：T の生成テストの合格数・総数
3. **P2P の破壊**：T より前のタスクの生成テストのうち、前のタスクの終わりには通っていて、今は通らない数（消えたものも破壊。`superseded_tests` は除く）
4. **保存則の違反（Outer）**：`invgen` の宣言を、マニフェストの固定シードで回し、破れた不変条件の数と反例の向き（dir）
5. 差分：タスク開始の commit からの追加行・削除行（B の予算を A にも当てはめ、超過したかを記録する。A では拒絶しない）
6. トークン：実装役の呼び出しごとの入力・出力トークン（`telemetry.USAGE_FORMATS` で読む）。A は会話の累積、B は試行ごと
7. 時間：実装役・測定・合計の秒

### 6.2 出力

- `C:\src\.local\out\ab\<run-id>\metrics.jsonl`：1 行 = 1 条件 × 1 タスク
- `experiments/b4_ab/results/<run-id>/summary.md`：`report.py` が作る表
  - タスクごとの P2P の破壊数・保存則の違反数・受入の合否（A と B を並べる）
  - トークンの推移：タスク番号 N に対する累積の入力トークン。A は N² に、B は N に比例するかを、両対数の傾きで示す（傾き 2 と 1 が仮説）
  - N 回の繰り返しの中央値と最小・最大

### 6.3 判定しないこと

実験は測るだけで、どちらが勝ったかを門にしない。B の門が A の実装を拒絶することも無い（A は門を通らない）。

## 7. 実装の順序と PR の分け方

| 順 | 内容 | リポジトリ | 門・指標に触れるか |
|:--|:--|:--|:--|
| E1 | GDD v10（ハードドロップと SRS）と構造化仕様の再生成。キック表は人間が確かめる | falling-blocks | 触れない（仕様） |
| E2 | given に構造体のリテラル（復元用コンストラクタで作る）と、入れ子の基準（`{"given": "GameState.ActiveMino.X", "add": -1}`）を足す（2026-09-24 オーナー裁定） | game-harness | 触れる |
| E3 | マニフェスト・固定テンプレート・凍結した単位定義と生成テスト | game-harness | 触れない |
| E4 | ドライバ・測定器・集計と、pipeline.py の `--local-only` | game-harness | 触れない（B の門はそのまま。push と CI を省くだけ） |
| E5 | 乾式の走行（T1 だけを A・B で 1 回ずつ）で配管を確かめる | — | — |
| E6 | 本走（T1〜T5 × A・B × 3 回） | — | — |

E2 は、T1 の受入データ（壁際の状態を given で作る）を書くのに要る。実装（2026-09-24）：given と op.args に構造体のリテラル、±1 の基準に構造体の成分。入力は `Tick(TickInput input)` の 1 操作にまとめ、1 行 1 操作は守る。GDD と同じく、実験の前に入れておかないと B だけが有利・不利になる。

## 8. 未決事項（人間の裁定待ち）

1. **実装役の会話の再開**：agy が resume に対応しているかは未確認。対応していなければ、A はドライバが全文を送り直す方式にする（§3.2）。どちらを使ったかは結果に明記する
2. **繰り返しの回数と費用**：1 走行は 5 タスク × 最大 3 試行。A は会話が伸びるので、後半のタスクほど高くつく。まず 3 回で見積もり、ばらつきを見て増やすか決める
3. **A の試行の打ち切り**：A が 3 回とも受入に落ちたとき、次のタスクへ進むか（壊れたまま積む）、止めるか。単一チャット型の実態に合わせ、**進む**を推す。B も 3 回とも落ちたら、そのタスクの実装を入れずに次へ進む（どちらも同じ扱い）
4. **E1 の GDD の書き手**：ハードドロップの規則とキック表は、人間が書くか、総監督が下書きして人間が確かめるか

## 9. やらないこと

- 実験中の GDD・単位定義・生成テスト・テンプレートの変更
- 人間によるプロンプトの手入力、途中での介入
- 実験の結果を門の判定に使うこと
