# 調べ方の規則（段 A の A1、W-141）

- 状態：採択（2026-10-23）。操縦士の指摘（「語が一致する質の低い記事と、自分の前提に合う結果しか集めていない。分野を分け、最先端の企業で何が使われているかの俯瞰から攻めないと、良い方針にまとまらない」）を受けた
- 道具：`harness/research.py`（調べる・照合する・記録する・索引を引く）、`harness/premises.py`（前提の根拠の強さ）

## 1. なぜ要るか

game-harness#272（W-124 の 1 回目）の照合は、出典が本物かどうかは確かめたが、何をどう集めるかが決まっていなかった。そのため、次のことが起きた。

- 問いに自分の案を入れていた（「OS アカウントと ACL は妥当か」）。そのため、その案に合うか合わないかの記事しか探さず、ほかの手法の系統を見ていない
- 語の一致で探したので、質の低い記事と売り手の宣伝が混ざった
- 根拠の強さに下限が無かった。2 社の自社の報告（P-002）や、単著のプレプリント 1 本（P-003）を「支持された」とした
- 調べ役が浅かった（小さいモデルで 12 ターン）

## 2. 段：俯瞰 → 比較 → 反証 → 照合

方向を決める調べものは、この順に行う。前の段の記録が無いまま、後の段の問いを立てない。

| 段 | 問うこと | 書かないこと | 調べ役 |
|:--|:--|:--|:--|
| map（俯瞰） | その領域で、いまどんな手法の系統があるか。系統ごとの代表例。分野ごとに巡回する | 自分の案。勧め。良し悪し | 深く読むモデル（`claude-deep`）か agy |
| compare（比較） | 俯瞰で出た系統ごとの、採用例・実測・失敗例・反対意見。自分の案は候補の 1 行として並べる | 勧め | 深く読むモデル |
| refute（反証） | 採ろうとする案に反する証拠だけ | 案を支える証拠 | 小さいモデルでよい |
| verify（照合） | 特定の主張・数字が、出典の本文にあるか | — | 小さいモデルでよい |

## 3. 分野（俯瞰の段は、問いに挙げた分野をすべて巡回する）

巡回しても一次か二次の出典が取れなかった分野は、記録の unknowns に、その分野の名前（下の表の英字の名前）を書いて理由を残す。`tests/test_research_coverage.py` が、`docs/research/` の俯瞰の記録について、挙げた分野ごとに主張か unknowns の名指しがあることを確かめる。

| 分野 | 中身 |
|:--|:--|
| frontier_labs | 最前線の AI 企業の、公式の技術ブログ・文書・研究（Anthropic・OpenAI・Google DeepMind・Microsoft と GitHub・Meta） |
| practitioners_at_scale | エージェントを大規模に運用している企業の、当事者の技術ブログ・事後検証 |
| academia | サーベイ論文、主要な学会（ICSE・FSE・NeurIPS・ICLR など）、arXiv |
| standards_tools | 標準と道具の公式の文書（OpenSSF・GitHub の文書・主要な OSS の設計文書） |
| practitioners | 名の通った実務家の記事・講演（当人の一次のもの） |

## 4. 問いのファイルの形

`python -m harness.research ask` は、この形でない問いを、調べ役を呼ぶ前に拒む（利用枠を使わない）。

```
# 題
## 段
map | compare | refute | verify
## 決めたい判断
（この調べものの結果で、何を決めるか。決めたい判断の無い調べものはしない）
## 判断を変えうるもの
（どんな事実が出れば、判断が変わるか）
## 分野
（map のとき必須。3 節の名前を 1 行に 1 つ）
## 候補
（compare・refute のとき必須。map では書かない）
## 問い
（本文）
```

## 5. 出典の格

調べ役は、主張ごとに出典の格を付ける。

| 格 | 例 |
|:--|:--|
| primary | 公式の文書、論文、当事者の技術ブログ・事後検証、標準 |
| secondary | 学会の講演、名の通った実務家の記事、査読の無いプレプリントの紹介 |
| marketing | 製品の売り手の宣伝、まとめ記事、SEO の記事 |

## 6. 根拠の強さ（`python -m harness.premises check` が判じる）

前提の台帳で `kind: research` の前提は、次のものを満たすときだけ「強い」とする。満たさないものは「弱い」と表示する。`--strict` では、弱い前提があれば不合格にする。

- 引いた主張が、`docs/research/` の記録に実在する
- 照合が verified で、格が primary か secondary で、種類が vendor_claim でない主張が、**2 つ以上の別のドメイン**から出ている

方向を決める判断（ADR の裁定）は、弱い前提だけを根拠にしない。

## 7. 記録と索引（知識の台帳）

- 記録には、主張・出典・格・分野・系統・照合の印に加えて、調べ役が使った検索語を残す。後から探し方の偏りを点検するためである
- `python -m harness.research index` が、記録の置き場（Git の外）と `docs/research/` の記録から、索引（`<local>/research/index.json` と `INDEX.md`）を作る
  - 主張ごとに、話題・段・分野・系統・格・照合の印・公開日・見直しの期限を持つ
- `python -m harness.research search <語>`：索引を引く。`--stale` で、見直しの期限を過ぎた記録を挙げる
- 見直しの期限は、調べた日から 30 日とする。期限を過ぎた記録に依る前提は、調べ直す
- 公開してよい記録（内部の事情を含まないもの）だけを、`docs/research/` に PR で写す

## 8. 調べ役のモデル

- `claude-deep`（claude-sonnet-5-5、ターン数を多く）：俯瞰と比較。Claude の利用枠を使う
- `agy`（gemini-3.8-flash-medium）：俯瞰の代わり。agy の利用枠があるときに使う
- `claude`（claude-haiku-5-5）：反証と照合
- 段ごとの既定は `config/research.json` の `stages` に置く。`--backend` で替えられる
