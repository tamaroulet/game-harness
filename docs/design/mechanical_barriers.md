# 紳士協定を機械的な拒絶に置き換える 3 つの防壁（ADR-002）

- 状態: 防壁①は配置済み（`.claude/settings.json`）。防壁②③は方針のみで、コードは変更していない
- 前提: Issue 12 カナリアが 1 回で合格（`docs/design/canary_issue12.md`）。再現性の検証は打ち切り
- 決定（2026-09-21、人間の指示）: これ以降の要件は、文章による注意ではなく、機械が拒絶する形で実装する

## 1. 目的

過去の 2 回の破綻は、どちらも「書いてある規約を守る」という前提が崩れて起きた。そこで次の 3 つを、書いてあるだけの規約から、機械が拒否する仕組みへ置き換える。

| 防壁 | 守るもの | 拒絶する主体 |
|:--|:--|:--|
| ① 総監督の視界 | 総監督がコード・テスト・生ログを見ないこと | Claude Code の権限設定 |
| ② 単位定義の形 | 分解役（Layer 2）が手計算の式や C# を書かないこと | ハーネスのスキーマ門 |
| ③ テストの階層 | 実装役（Inner Loop）が不変条件テストに触れず、見もしないこと | ディレクトリとプロジェクトの物理分割、ハーネスの配線 |

## 2. 防壁①：総監督の deny ルール（配置済み）

`game-harness/.claude/settings.json` に置いた。拒否する範囲は次のとおり。

- `Read` / `Edit` で拒否するもの
  - `C:\src` 以下のすべての `*.cs`
  - falling-blocks と unity-2d の `Game/Assets/Core/**`・`tests/**`
  - worktree 置き場 `C:\src\.local\wt/**`
- `Bash` / `PowerShell` で拒否するもの
  - `dotnet test` を含むコマンド
  - `.cs` のファイル名を含むコマンド
  - `Assets/Core` / `Core.Tests` / `*/tests` を含むコマンド

**配置後に確認した結果：** ダミーの `.cs` を使い、`Read`、`cat`、`dotnet test` を含むコマンドの 3 通りを試した。3 つとも権限設定で拒否された。

**影響範囲：** このリポジトリで起動するすべてのセッションに効く。ハーネスは Python なので、ハーネス改修の作業は妨げない。

**残る穴（正直に書く）：** 権限ルールはコマンドの文字列で照合する。そのため次の 2 つは塞げない。
- ファイル名を文字列に書かずに参照する方法。グロブ（`*.c[s]`）、変数、`python -c` などで回避できる。確認用のダミーファイルを消すときに、実際にグロブで通ってしまった
- ディレクトリ単位の再帰検索。`grep -r` をリポジトリの根に向けて使う場合

完全に塞ぐには、OS レベルのサンドボックス（`sandbox.filesystem.denyRead`）が要る。ただしサンドボックスは総監督のすべてのシェルコマンドを閉じ込める。パイプラインの起動、git push、実装役（agy）の呼び出しまで閉じ込めるので、今回は有効にしない。穴を突いた事例が 1 件でも観測されたら、サンドボックスを有効にする。

## 3. 防壁②：単位定義のスキーマ門

### 3.1 何を拒絶するか

「C# 構文が混ざっていたら REJECT」を文字どおり実装すると、今の `issue_12.json` が通らない。`prompt` に型名とメンバーのシグネチャが書かれているからである。そこで次の 2 つを区別し、拒絶するのは後者だけにする。

- **インターフェース宣言**：作るものの形。型名、種類、メンバー名、型。単位の契約そのものなので残す
- **オラクル**：期待値と、それを導く計算。ここに手計算が入り込む

### 3.2 単位定義 v2 の形

- `schema: 2`
- `interface`：型の一覧。各型は `name`、`kind`（enum / struct / class）、`members[]` を持つ。メンバーは `name`、`type`、`kind`、`params[]`、`static` を持つ。値はすべて列挙値か識別子で、C# の文字列は置かない（2026-09-21 裁定：C# 構文の生文字列は許さず、構造化フィールドだけで表す）
  - 型の表記は「識別子」「識別子<識別子>」と、それぞれの末尾に `?` を付けた形だけを受理する。式、本体、属性、修飾子の並びは書けない
- `acceptance.cases`：受入条件の表。1 行が 1 回の状態遷移に対応する
  - `given`：事前状態。公開状態のフィールドをリテラルで書く
  - `op`：操作 1 つ。公開操作の列挙値から選ぶ
  - `expect`：事後状態。リテラルで書く
- `prompt`：自然言語だけ

### 3.3 バリデータ門の規則（機械判定のみ）

1. JSON Schema に適合すること。未知のキーがあれば拒絶する
2. `given` / `expect` の値はリテラルだけ。使えるのは整数、真偽、列挙のメンバー名、盤面の行を表す固定長の文字列。演算子・括弧・関数呼び出し・変数参照を含む文字列は拒絶する
3. 1 行に置ける `op` は 1 つだけ。複数ステップの列は拒絶する（horizon = 1）
4. `prompt` の中のコード表記（バッククォート）は、`interface` で宣言した識別子と、whitelist にあるパスだけを許す。コードフェンス、`;`、`{`、`=>` は拒絶する
5. **期待値は GDD に拘束する**（2026-09-21 裁定）。`expect` の各値は次のどれかでなければならない
   - `{"same": true}`：`given` から変えない
   - `{"param": "PR-xx"}`（座標などの成分なら `"index"` を付ける）：構造化仕様 §5 の外部パラメーターから引く。構造化仕様の `gdd-sha256` が今の GDD と一致しない場合は、引いた値を信用せずに拒絶する
   - `{"given": "<フィールド>", "add": 1}` または `"add": -1`：1 回の遷移で起きる 1 単位の増減だけ
   - 自明なリテラル：`0`、`1`、`true`、`false`、`null`、空の列、列挙のメンバー名

   上のどれにも当たらない数値のリテラル（分解役が独自に計算した値）は拒絶する。あわせて、各行の `rule` には構造化仕様の ID（LP / ST / RL / IF / PR）を必須とし、仕様に存在しない ID は拒絶する
6. 門に落ちた単位は、パイプラインを起動しない。終了コードは 2 とし、スケジューラを止める。壊れた単位のまま Issue を回し続けないためである

### 3.4 テストコードは誰が書くか

C# のテストコードは、ハーネスの決定論的な生成器が `acceptance.cases` から出力する。分解役は C# を 1 行も書かない。

**このスキーマで手計算そのものは消せない**ことは明記しておく。期待値のリテラルは、依然として誰かが計算したものである。スキーマが保証するのは次の 2 点までである。
- 期待値は、GDD の文言だけで 1 ステップ分を確かめられる大きさに収まる（horizon = 1）
- 複数ステップにわたる正しさは、期待値を持たない不変条件テスト（防壁③）に任せる

### 3.5 手順 3 で決めたこと（2026-09-21）

- **事前状態は「復元用のコンストラクタ」で作る。** 公開 API には状態を書き換える入口が無い。そのため given は、引数が given のフィールドとちょうど一致するコンストラクタで作る。そのようなコンストラクタが interface に無い単位では、生成を拒絶する。horizon = 1 の表駆動テストを成り立たせるには、ドメインモデルがこの入口を持つ必要がある。分解役は、given を使う単位で、このコンストラクタを interface に宣言しなければならない
- **same・±1 は、操作前の値との比較で出力する。** given に書いたリテラルは C# に写さない
- **Invariants の生成は手順 5 に移す。** Invariants には次の 3 つが同時に要る。これらは手順 5 の範囲なので、生成器もそちらでまとめて作る（1 PR 1 責務）
  - 宣言データのスキーマ
  - 操作列を回す駆動部
  - 反例を返す仕組み
- **手順 6 の前に塞ぐべき穴が 1 つある。** v2 の期待値は、状態（property / field / const）に対してしか書けない。そのため、引数付きの問い合わせを受入データで表せない。例は Issue 12 の `Board.InBounds(x, y)` や `Board.IsOccupied(x, y)` である。このままでは、`issue_12.json` を v2 に移すときに受入テストの一部が失われる。手順 6 の前に、スキーマ門へ「問い合わせの期待値」を足す小さな PR が要る

### 3.6 手順 5.5 で決めたこと（2026-09-23）

- **受入データに query の行を足した。** 形は `{"query": "型.メソッド", "args": {...}}` で、戻り値のあるメソッドだけに使える。期待値は `{"return": 値}` だけを書き、値の決まりは expect と同じ（GDD に拘束）。static な query の行は given を持てない
- **生成テストは、query の行ごとに次の 2 つを必ず検査する**（2026-09-23 裁定）。分解役はこれを書かないし、外すこともできない
  - 冪等：同じ引数で 2 回呼び、2 回目の戻り値が 1 回目と等しい
  - 状態の不変（CQS）：呼ぶ前に、対象の型が interface で公開している状態（property / field。static な query なら static なもの）をすべて控え、呼んだ後に等しいことを確かめる。列の状態は、参照ではなく中身を写し取って比べる
- **検査が効くことは、実物で確かめた。** 次の 2 つの合成の実装を dotnet test まで通し、どちらも落ちることを確認した
  - 問い合わせの中で公開している列を書き換える実装
  - 呼ぶたびに戻り値が変わる実装
- **残る限界**：CQS で見るのは、問い合わせ先の型が公開している状態だけである。公開していない内部状態や、公開状態が指す別のオブジェクトの中身までは追わない。追うには状態の深い比較が要り、そのためにはテンプレートが型の中身を知る必要がある

## 4. 防壁③：テストの物理的な階層分離

### 4.1 分け方

| 層 | 置き場所 | 中身 | 実行する者 |
|:--|:--|:--|:--|
| Unit | ゲームのリポジトリの `<test_dir>/Generated/`（既存の高速検査の csproj に入る） | 防壁②の生成器が出力する、1 回の遷移ごとの表駆動テスト | 実装役の Inner Loop、CI |
| Invariants | **ゲームのリポジトリには置かない。** 宣言は harness の `projects/<id>/invariants.json`、テストと csproj は Outer 段のたびに pipeline の出力先へ生成する（2026-09-21 改定、§4.4） | GDD の保存則・状態遷移の包括規約を、シード付きランダム操作列で検査する性質テスト | パイプラインの Outer 段だけ |

### 4.2 規則

1. **Invariants は、実装役のサンドボックスに置かない。** フィルタで実行対象から外すのではなく、ファイルそのものを持ち込まない。見えないテストに合わせて書くことはできない
2. Inner Loop の高速検査は `tests/Unit` の csproj だけを実行する
3. Invariants が失敗したとき、実装役に返すのは次の 3 つだけ。値、スタックトレース、テストコードは返さない（2026-09-21 改定：反例を返す）
   - 不変条件の ID
   - GDD の節番号
   - 破綻に至った最小の操作列（反例）。公開操作の列挙値とシードだけで表す

   反例だけを特別扱いする実装で通ることを防ぐため、Outer 段が検査に使うシードの集合は、報告した反例のシードとは別にする。シードは commit の SHA から決定論的に導く。同じ commit なら同じ判定になり、試行が変わればシードも変わる
4. Invariants は期待値を持たない。宣言データ（ID、GDD の節、公開状態のフィールドに対する等式）から生成器が出力する。等式の文法は、公開フィールド名・整数・`+ - * =` に限る
5. Invariants の変更は、GDD の版が上がる PR でだけ許す。Core の実装と同じ PR で変えることは、門で拒絶する

### 4.3 手順 5 で決めたこと（2026-09-21）

- **手順 5 を 5a・5b・5c の 3 つに分けた**（1 PR 1 責務）。生成器、ハーネスの配線、ゲーム側の配置は、検証の仕方も触る場所も違う
- **宣言は `tools/invariants.json` に置く。** 中身は次のとおり。検査はスキーマ門と同じ部品で行う
  - 対象の作り方（`subject`）
  - ランダムに選ぶ操作とその引数の候補（`ops`）
  - 操作列の長さとシードの本数
  - 等式の列
- **反例は、破綻した時点までの操作列（最短の接頭辞）とする。** 1 行の書式は `INVARIANT_FAIL id=… rule=… seed=… ops=…` で、値は出さない。操作列そのものを縮める処理（delta debugging）はしない。長い反例が実装役を迷わせると観測されたら、そのとき足す
- **「GDD の節番号」は構造化仕様の ID（`rule`）で表す。** 仕様の ID は GDD の行番号を根拠に持つので、節番号より細かい
- **観測できない量は等式に書けない。** GDD §5 の保存則は「消去ライン数 × 10 ＋ 盤面ブロック数 ＝ 4 × ロックしたミノ数」だが、次の 2 つは GDD §6 の公開状態に無い
  - 盤面ブロック数
  - ロックしたミノ数

  等式の文法を集計関数で広げると、そこに手計算が戻ってくる。そこで文法は広げない。公開状態を足すかどうかは GDD の改定として B3 で扱う（falling-blocks の凍結は手順 6 まで続く）
- **5c は総監督が行わない。** deny 設定（防壁①）が、総監督によるゲームのテスト置き場の編集を拒否する。スクリプトを使えば迂回できるが、迂回すれば防壁①の意味が無くなる。そこで 5c は人間か現場（Layer 3）の作業とし、総監督は結果の報告（csproj の分割と CI の緑）だけを受け取る

### 4.4 手順 5b で決めたこと（2026-09-21）

- **Invariants はゲームのリポジトリに置かない。** 当初はゲーム側に `tests/Invariants` を作る案だったが、それでは次の 3 つが同時には成り立たなかった
  - サンドボックスに持ち込まない（§4.2 の 1）
  - 人間が手作業をしない
  - 総監督がゲームのテスト置き場を触らない（防壁①）

  そこでハーネスが、Outer 段のたびに自分の出力先（`out_dir/invariants/`）へ csproj と生成テストを置く。サンドボックスの実装は外から `Compile Include` で参照してビルドする。生成器は、置き場所がサンドボックスの内側なら拒否する
- **宣言は harness の `projects/<id>/invariants.json` に置く。** 実装役の作業ツリーには現れない。宣言は書いたときの GDD の sha256（`gdd_sha256`）を持ち、GDD が変われば見直すまで ABORT になる。これで §4.2 の 5（GDD の版上げと連動させる）を機械で強制する。宣言を変えるには harness への PR（人間のレビュー）が要る
- **シードは、候補の差分（whitelist の `git diff`）の sha256 から決める。** 当初は commit の SHA としていたが、Outer 段は commit の前に走る。差分が同じなら同じ判定、試行で差分が変われば別のシードになる性質は変わらない
- **失敗の分類**
  - 反例の行が出た：REJECT。実装役に返すのは反例の行だけ
  - 行が出ないのに失敗した（ビルド不能など）：ABORT。実装役には直せない
  - 宣言が無い：この段を飛ばし、テレメトリに `declared: false` を残す。いまの falling-blocks には宣言が無いので、カナリアには影響しない
- **Inner Loop の分離は今のままで成り立つ。** Unit は既存の高速検査の csproj に入り、Invariants は最初からサンドボックスに存在しない。ゲーム側の csproj を分ける必要は無い

## 5. 実装の順序と PR の分け方

防壁②と③は門の挙動を変える。そのため、それぞれを独立した PR にして人間のレビューを受ける。**1 PR に 1 つの責務だけを持たせ、前の PR が main に入ってから次に着手する**（2026-09-21 改定）。

| 順 | PR | 内容 | 門に触れるか |
|:--|:--|:--|:--|
| 1 | 本ブランチ | 防壁① の設定と本文書 | 触れない |
| 2 | 単位スキーマ v2（game-harness PR 20） | スキーマ門 | 触れる |
| 3 | テスト生成器 | 固定テンプレートに表を埋め込むだけの生成器。`cases` から Unit テストを出力する（Invariants の生成は手順 5 へ移した。§3.5）。**生成器の自己テストを必須にする**：出力した C# が `dotnet build` を通ることを、ハーネスの Python テストで保証する。保証できるまで次に進まない | 触れない |
| 4 | 分解役の改修 | `decompose.py` に v2 の単位定義を出力させ、書き出す前にスキーマ門で自己検査させる。この PR が入るまで、新しい単位定義はすべて門で止まる | 触れない |
| 5a | Invariants の生成器 | 宣言（`tools/invariants.json`）の検査と、NUnit テストの生成。自己テストで `dotnet build` まで通す（§4.3） | 触れない |
| 5b | ハーネスの配線 | Outer 段で Invariants を生成・配置・実行する。シードは候補の差分から決め、返すのは反例の 1 行だけ。宣言は GDD の sha256 に縛る（§4.4） | 触れる |
| 5c | ゲーム側の配置 | **不要になった**（§4.4）。Invariants はハーネスが自分の出力先に置くので、ゲームのリポジトリの csproj・テスト置き場・CI は変えない | — |
| 5.5 | 問い合わせの期待値 | スキーマ門と生成器に、引数付きの問い合わせ（例：`Board.InBounds(x, y)`）の期待値を足す。生成テストは冪等と状態の不変（CQS）を必ず検査する（§3.6） | 触れる |
| 6 | 移行 | `issue_12.json` を v2 に書き換え、カナリアを 1 回走らせる | — |

6 のカナリアは、防壁を入れた後もループが壊れていないかの 0/1 判定である。ばらつきの調査はしない。

**トラックの分離**：6 が終わるまで、falling-blocks（ゲーム側）は完全に凍結する。GDD の改定も Issue 15 以降の着手もしない。game-harness の改修だけを進める。

## 5.1 用語

| 用語 | 意味 | 使わない言い方 |
|:--|:--|:--|
| 受入データ | 単位定義の `acceptance.cases`。1 回の遷移ごとの事前状態・操作・期待値 | 「オラクル」 |
| 不変条件 | `tests/Invariants` が検査する、期待値を持たない性質（GDD §5 の保存則など） | 「オラクル」 |
| 門番判定 | パイプラインと CI が下す PASS / REJECT / DISPUTE / ABORT | 「オラクル」 |
| リポジトリ付きの番号 | Issue と PR は `falling-blocks#15`・`game-harness#34` のように書く | 「Issue 15」だけ |
