## 1. 要旨

1. **v3 の筋は残す。** 物差しを作り、外側の周期で直し、最後に比べる筋は変えない。直すのは、比べの道具の形と、順番の 2 つ。
2. **比べの道具：両方にコマンドを許し、箱の中で走らせる。**
   - 今の形（両方ともコマンド無し）では、試験の結果を受け取るのはハーネスの側だけ。門が試験を回し、落ちた出力を次の試行に渡す。素のエージェントは、試験を 1 度も走らせずに書くことになる。
   - これでは、勝っても「試験の結果を見られるか」の差で、実戦でどちらを使うかの判断に使えない。10-30 の決め「比べる相手は強い方」とも逆になる。
   - コマンドが無いことは、開発の組の落ちの原因の 1 つでもある（F2）。Unity の実開発でも要る見込み。
   - ただし、今の bench では走らせ役と実装役が同じアカウントで動く。コマンドを許すと、実装役が先の段の仕様や前の走りの記録を読める（§3-1）。だから、実装役を別の利用者として閉じ込める箱（WSL2）を先に作る。
   - L6 の後は環境を変えないので、今決める。
3. **順番：優位の確かめを、周期の前に置く（関所 G1）。**
   - 周期に掛ける値打ち（数週と数億トークン）は、元のハーネスが素のエージェントより勝つかで決まる。今は一度も測っていない。
   - 先に、開発の組と保留の組で、コマンドありの v0 と素のエージェントを、事前に登録した決まりで比べる。比べは段ごとの対で判じる。
4. **周期は、G1 で素のエージェントに負けなかったときだけ回す。人が運ぶ形のまま回す。**
   - 自動化（v3 の L7・L8 の「人の手なし」）は、周期が取り込みを 2 件出してから作る。
   - 止めの決まりを先に置く。
5. **保留の組は評価にだけ使い、G2 までに見るのは 3 回まで。**
   - 毎周の回帰の守りは、開発の組だけにする。
   - これで、取っておく組（24 段）を新しく作らずに済む見込み。
6. **L6 の配線の確かめは、今、いちばん小さく行う。** 提案役・面の検査・対の走り 1 段まで。今の形（コマンド無し）での取り込みと回帰の守りは行わない。
7. **Unity は 3〜4 か月目から、比べの実験はしない（10-30 の操縦士の決め）。** Unity の門（凍結中の道具の EditMode の試験）を繋ぎ、そのまま実開発に入る。調べは周期と並べてよい。
8. **費用（推測）。** 関所ごとに次に掛けるかを決めるので、上限まで使うとは限らない。
   - G1 まで：Gemini 約 1.5 億〜2.1 億トークン、約 4〜6 週。
   - G2（周期の後の比べ）まで：約 2.5 億〜6.5 億、約 3〜4 か月。

## 3. v3 の筋で直す所（4 つ）

### 3-1. 比べの道具の形

- **v3 §8：** B が周期で「コマンドを許す」を取り込んでいれば両方あり、取り込んでいなければ両方なし。
- **問題：**
  - v0 の実装役にはコマンドが無い。それでも門（Gate 1）が試験を回し、落ちた出力を次の試行に渡す（v3 §7-4、試行は 2 回まで）。
  - 素のエージェントにコマンドが無ければ、試験を 1 度も走らせずに書く。だから「両方なし」の比べは、ハーネスの作りよりも「試験の結果を見られるか」を測り、ハーネスに有利に偏る。
  - ふだんの使い方の素のエージェント（Claude Code や agy の CLI）は、自分で試験を走らせる。試験を走らせられない相手は、10-30 の操縦士の決め「比べる相手は強い方」の強い相手と言えない。
  - 反論：門が試験を回すことは、ハーネスの作りの一部だ。ただし、素のエージェントもふだんは同じことを自分でする。ハーネスにしか無い値打ちを測るには、相手にも同じことをさせる。
  - 実装役のコマンド無しは、F2 の原因になっている。
  - Unity の実開発では、コンパイル・試験・数値の調整にコマンドが要る見込み（推測）。
- **直し：** 比べも周期も、両方コマンドありにする（A の文書の (c)）。L6〜比べの間は環境を変えないので、周期の前に決める。
- **閉じ込め（Argon の指摘を実物で確かめた）：**
  - 今の鎖の走りは、走らせ役も実装役も bench のアカウントで動く。
    - 走らせ役は、全段の仕様を先に写しの置き場へ置く（`harness/bench_chain.py:74,95`）。
    - 前の走りの作業場と記録も、bench の置き場にある。
  - コマンドが無い今は、読む道具の引数を道の検めで見て、外を読んだ段を無効にしている。コマンドを許すと、命令の中で道を組み立てられ、検めは後から見つけるだけで、見落としうる。道の検めは、`${local}` の下で作業場の外を指す道しか見ない（`harness/chain_score.py:207-209`）。
  - 同じアカウントのままでは、拒みの設定（ACL）でも閉じられない。走らせ役が読めるものは、実装役も読める。
  - だから、実装役を別の利用者として走らせ、自分の作業場しか見えない箱を先に作る（§4 の P1）。
- **費用の違い：**
  - コマンドありで基準を取り直す（§4 の P2 に入れた）。
  - 箱づくり。A の文書は (c) の準備に 1〜3 週以上と見た（箱・WSL2 の中の認証・agy の版の固定・規約の書き直し・基準の取り直し）。この見込みを使う。
- **実物で確かめたこと（この文書のとき）：**
  - 鎖の実装役の agy には、ハーネスがいつも `--sandbox` を付け、頼みの頭に「命令の実行の道具は使えません」と足している（`harness/hline_agy.py:21,72-74`）。
  - 命令を実行した試行は、門の前に打ち切られる（REQ-09、`harness/hline_abort.py:53-68`、`harness/hline_task.py:67`）。

### 3-2. 順番

- **v3：** 周期（L6〜L8）の後に比べる。木も、比べを自己改善の後に置く。
- **問題：**
  - 周期の値打ちは、元のハーネスが素のエージェントより勝つかで決まる。
  - 勝たないなら、面（指示の文とつまみ）の直しを重ねるより、作りを見直すほうが効く。
  - 測らずに周期に掛けると、ROI を確かめないまま、数週と数億トークンを掛けることになる。
- **直し：**
  - 優位の確かめ（G1）を周期の前に置く。
  - 周期の後の比べ（G2）も残す。自己改善の効きは G2 で測る。
- **損得（推測）：**
  - G1 の費用は約 1.3 億〜1.9 億。
  - G1 で「素のエージェントが勝つ」と出れば、周期の約 0.3 億〜3 億と、その後の比べを掛けずに済む。
  - G1 でハーネスが勝てば、G1 の分だけ余計にかかる。そのぶんは、§3-4 で取っておく組を作らずに済む分と、毎周の保留の組を省く分で埋まる。
- **G1 を Unity でなく MuJoCo の鎖で測る訳：**
  - 隠しテストの物差しが、もう 36 段ある（開発の組と保留の組）。試験は Python で、1 段の必須の試験は数秒〜90 秒。
  - Unity で同じ確からしさの物差しを作るには、C# の隠しテストと参照の実装を作り直す要がある。試験も batchmode で重い。
  - 操縦士の 10-30 の決めも「比べはずっと Python と MuJoCo。Unity は比べに使わない」（v3 §2-1）。

### 3-3. 自動化の時期

- **v3 の L7・L8：**
  - 周期の起動を Git に置く。予定のタスクに bench の密語を保存する。総監督を無人で起こす。実行役の身元を操縦士と分ける。
  - 確立の条件は「2 周を続けて人の手なしで」。
- **問題：**
  - 周期が取り込みを出すかは分からない（§2 の判定の鈍さ）。出す前に自動化を作ると、使わない仕組みに手を掛ける。
  - 11-01 の操縦士の教訓「自律化を自己目的にしない」。
- **直し：**
  - 周期は、1 周を 1 本の命令にまとめた台本で、人が運ぶ。
  - 自動化（L7）は、取り込みが 2 件出てから作る。L8 の条件は、そのときに決め直す。
  - P1 の箱があれば、bench の密語の保存は要らない（箱の中で、密語なしで別の利用者として起こせる。v3 §15 の 10-31 その 2）。

### 3-4. 組の使い方

- **v3：**
  - 保留の組を、取り込む周ごとの回帰の守りに使う（§7-7 の 4）。
  - 比べの本番のために、取っておく組（4 本・24 段）を作る。
- **問題：**
  - 保留の組を見るたびに、比べに使える組が減る。
  - 取っておく組の 24 段は、会話の席の手で 2.5〜3 日かかる（CD の見込み）。
- **直し：**
  - 毎周の回帰の守りは開発の組だけにする（基準の先端から、2 回とも通った段）。
  - 保留の組は、これから G2 までに 3 回まで見る（G1・周期の途中の 1 回・G2）。
  - 取っておく組は、保留の組が使えなくなったときか、長い鎖が要るとき（G1 の「両方が天井」）だけ作る。

## 4. 推す流れ

```
P0 L6 の配線の確かめ（1 段の対まで）──┐
P1 箱とコマンドの道（探り・箱・直し・素のエージェントの走らせ方・探りの鎖）──┤
                                     └→ P2 優位の確かめ ─ G1 ─┬→ P3 周期（人が運ぶ）─ G2
                                                              ├→（素のエージェントが勝つ）作りを見直して G1 をやり直す
                                                              └→（両方が天井）長い鎖を作るかを操縦士が決める
P4 Unity の口（調べは P3 と並べる）→ P5 実開発
```

### P0 L6 の配線の確かめ（今。いちばん小さく）

- **中身：**
  1. 提案役 1 回。道の当たりが 0 で、決まった見出しの提案が出るか。
  2. 提案の直しを書いて、面の検査（`harness/surface.py check`）に掛ける（0 トークン）。
  3. 狙いの段のうち 1 段で、旧版と新版の対を 1 回走らせ、採点と比べ（finish・compare）まで通す。
- **行わないこと：**
  - 取り込み（main へのマージ）と、開発の組の回帰の守り（約 1,760 万）。
  - 理由：P1 でコマンドを許すと、実装役への指示を書き換え、実装役のふるまいも変わる。コマンド無しの形に合わせた直しを入れると、手戻りになり、コマンドありの基準（B0′）も濁る（Argon）。
- **費用：** Gemini 約 300 万〜400 万、1 日。
- **出口：** 提案役・面の検査・対の走り・採点の道具が通しで動く。提案の質の見当が付く。

### P1 箱とコマンドの道（会話の席の作業が主。2〜3 週、推測）

0. **今すぐの守り（コマンドの有無に依らない）。**
   - 実物で確かめたこと：bench のアカウントは、次の 3 つを書き換えられる。
     - 総監督が読む main と枝の写し。
     - 操縦士のアカウントで読まれる機械の設定。
     - 会話の席の非公開の置き場（読むこともできる）。
   - 受信箱・H ラインの out・oracles は、読みも書きも拒んでいる。場所は非公開の手順書に書く。
   - 足すこと：bench の書きと読みを拒む設定。bench_guard の check に、その場所を足す。
1. **探り（1 日）。** 次の 3 つを、小さく 1 回ずつ確かめる。
   - WSL2 の中で、agy が定額の認証で窓なしに動き、命令を走らせるか。
   - 別の Linux の利用者として、密語なしで起こせるか。
   - 版を固定して入れられるか（Windows の凍結の版は 1.2.14、Linux は 10-30 の時点で 1.4.11）。
2. **箱（1〜2 週）。**
   - 箱専用の distro にする。自動のマウントと Windows との相互運用を切る。WSL の既定では、/mnt/c から操縦士の権限で Windows のファイルに届き、Windows の実行ファイルも呼べるため。
   - 利用者を分ける。走らせ役は材料と記録を持つ。実装役は、自分の段の作業場しか読み書きできない。門の試験も、実装役の側の利用者で回す（実装役の書いたコードを、強い権限で走らせない）。
   - ネットは、API と依存の導入だけにする。
   - 採点（finish）と隠しテストは箱の外に置く。
3. **ハーネスの直し（高リスクの PR と、規約の PR）。** ここまでで、B0′ の形を決める。
   - コマンドの切り替え：`--sandbox` と前置きの文（`harness/hline_agy.py:21,72-74`）、命令で試行を打ち切る決まり（`harness/hline_abort.py:53-68`）、指示の「テストは走らせない」（`harness/hline_prompt.py:27`）。それを固める既存の試験の直し。
   - 作業場を、課題だけの決まった木にする。今は版の木まるごと（docs と記録を含む）から作る（CD の G6、`harness/bench_chain.py:131-133`）。
   - 実装役の頼みから、課題と関係の無いハーネスの目次と、「game-harness の実装役です」の名乗りを外す（`harness/hline_prompt.py:23,64`。v3 §15 の 10-31 その 3 で、目次は約 2,100 字）。
   - 許した場所の外のファイル（一時の台本・試験のキャッシュ）が、段の差分に入らないようにする。採点は、許した場所の外を 1 つでも変えた段を 0 点にする（`harness/chain_score.py:417-424`、`harness/bench_run.py:762-764`）。今の無視の設定は `__pycache__/`・`*.pyc`・`*.log` だけ。
   - 規約の REQ-09（道具）の書き直し。保護パスなので操縦士の PR で、P2 の登録と一緒にする。
4. **素のエージェントの走らせ方（E5。低リスクの PR 1 本）。**
   - 段ごとに新しく起動し、自分の前の段の先端を作業場として引き継ぐ。
   - 同じモデル・同じ道具・同じ箱・同じ時間の上限で走らせる。門と試行の繰り返しは無く、試験は自分で回す。
   - 段の終わりの作業場を、そのまま段の先端にする。ハーネスは、門で落ちた段の変更を入れずに前の先端を保つ。この違いはハーネスの作りの一部として残し、登録に書く（Argon）。
   - 採点は同じ finish で行う。
5. **探りの鎖。** 開発の組の B08（6 段。コマンドが効くはずの F2 の段 4 を含む）を、B0′ と A で 1 回ずつ走らせる（約 2,000 万）。
   - 見ること：トークンと時間がどれだけ増えるか、箱とハーネスの継ぎ目、両方のふるまい。G1 の数には入れない。

- **箱が作れないとき：** Windows の bench のまま、同じアカウントでコマンドを許す。その場合は、次の 2 つで補う。
  - 道の検めを強める：作業場の外を指す道と `..` を、置き場によらず全部当たりにする。
  - 先の段の仕様を、段ごとに置く形にする。
  - それでも後から見つけるだけなので、G1 の結論に「閉じ込めは検めだけ」と書く。

### P2 優位の確かめ（関所 G1）

- **事前の登録。** 規約の PR で行う。保護パスなので操縦士の PR。Argon の事前の評価に掛ける。登録すること：
  - 腕：B0′（v0 にコマンドを許し、P1 の直しを入れた形）と A（素のエージェント）。

## 5. 運用の決まり（ROI と確からしさの両立）

1. **走る前に札を書く。** bench の 1 夜（約 3,000 万トークン）を超える走りには、走る前に、目的・予想・止める条件を書く（v2 の 5 欄の札）。

   - 結果を見てから決まりを変えない。

   - 実開発は、固定した版のハーネスで走らせる。9〜10 月に崩れたのは、改善と開発を同時に進めたため。
6. **安い道を選ぶ。** 人を 1 手挟むほうが安く確かなら、人が運ぶ（11-01）。
7. **結果を残す。** 結果は、この文書の §12 に差分で足す。
8. **Claude の枠で区切る。** 会話の席の作業（PR・登録・分析）が Claude の枠の大半を使う。一段落ごとに、札・実装・試験・コミット・push を済ませる。
