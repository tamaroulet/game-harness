## 0. 結論（先に）

1. 方向（根絶 → 自己回復 → 人間は非同期の最小）は理念と整合する。ただし案の中には、**それ自体が次の Harness Rot になる要素**（agy.exe の ACL ロック、思考役の工具の物理剥奪、未達のスキップ受領、機能合格のみの受領）が混ざっている。
2. 11 課題の多くは、ひとつの未決の問いから派生している：**このハーネスは「実験の測定器」なのか「製造ライン」なのか**。Phase 3（v2r 2×2）は因果実験だったので、版の固定・非公開シード・base の厳密な健全性・測定器故障の分離が「正しく」必要だった。製造ラインにはその多くが要らない。課題 4・2・10 は、実験用の厳密さを製造ラインにも適用し続けたことの症状と見るのが最も単純な説明。
3. したがって最初の一手は「足す」ではなく「**分ける**」：実験の測定器（`harness/ab/`・版の照合・天井・変異の記録）を v2r の版で凍結し、製造ラインの門から外す。これだけで課題 2・4・10 の大半が消える。
4. 基盤改修は Phase 4 の前に「一気に」ではなく、**無人の 1 晩走行を止める原因だけ**を先に潰す（下の §2 の 5 件）。残りは Phase 4 の最初の実タスクで必要になってから入れる。そうしないと「Phase 3.5：足場の作り直し」が新しい玩具タスクになる（課題 9 の再演）。
5. v3.1（並列 1,000 ワーカー・Δt/100 参照・OpenAI 調停・3 段の門）は、P4-01 の時点では過剰。最初の Phase 4 タスクは「MuJoCo を 1 本だけ結合して、1 つの不変量を 1 つの門で判定する」まで縮める。

## 1. 要素ごとの評価

記号：◎ そのまま採る／○ 形を変えて採る／△ 後回し／× 採らない（代案あり）

### 原理 1：根絶

| 要素 | 評価 | 理由と代案 |
|:--|:--|:--|
| 思考役の工具剥奪 | ○ | 工具を剥ぐと、ハーネス自体の開発（このリポジトリの PR）も止まる。問題は「走行中に、走っている配管を書き換える」ことなので、**走行は固定したコミット（タグか、読み取り専用の展開）から実行する**ことで根絶できる。リポジトリを編集しても走行中のラインには届かない。変更は PR → main → 次の走行で入る。既存の防壁①（deny）はそのまま |
| UUID の使い捨てサンドボックス＋Detach＋非同期 GC | ◎ | 安くて効く。名前の衝突も、同期削除の `WinError 32` も構造的に消える。GC は「起動時に、作成から N 時間以上の `wt/*` を消せるものだけ消す、失敗は無視」で十分（常駐の掃除屋は要らない） |
| Job Object（KILL_ON_JOB_CLOSE） | ○ | 正しいが、先に**常駐を作らせない**方が安い：`MSBUILDDISABLENODEREUSE=1`、`DOTNET_CLI_USE_MSBUILD_SERVER=0`、`UseSharedCompilation=false`（VBCSCompiler を作らない）を子プロセスの環境に入れる。これで残るものがあれば Job Object（ctypes で数十行）を足す |
| Base 検査のホワイトリスト化 | ○ | 方向は正しい。ただし「合格したタスク番号を列挙する」も手で保つ表になる。**直前に受理したコミットで実際に通ったテスト名の集合**を受理時に保存し、次のタスクの base はその集合だけを「通るべき」とする（P2P の基準を測り直さず引き継ぐ）。集合に無いテストは、通っても落ちても base の判定に使わない。これで `_Hidden` の除外・クラス単位の除外（`pipeline.py` の `task_test_classes`）・除外 JSON がすべて不要になる。さらに根本的には、**将来のタスクのテストをリポジトリに置かない**（タスクの開始時にハーネスが注入する）。存在しないテストは base を壊せない |
| agy.exe の ACL ロック | × | ホストのセキュリティ設定をいじる運用は、更新器の挙動の変化（別名で置き換える、失敗を繰り返す）に対して壊れやすく、別マシンへ移すときの手順も増える。課題 4 の要求どおり、**版は門ではなくテレメトリ**にする（記録して進む）。照合して止めるのは、実験（比較の走行）を回すときだけ。game-harness#134・game-harness#135 の照合は v2r の実験用として凍結する |
| アーキ制約のコンパイル化 | ○ | 小さく始める：`.editorconfig` の重大度と `TreatWarningsAsErrors`、組み込みのアナライザ（CA 系）を数件。ArchUnitNET の層の規則は、Phase 4 でセクターの境界が実在してから。「1 クラス 300 行」のような数値は根拠が無いので入れない |

### 原理 2：自己回復

| 要素 | 評価 | 理由と代案 |
|:--|:--|:--|
| インフラ例外の Outer-Loop | ◎ | 最も効果が大きい。前提は**例外の分類が閉じていること**：終了コードとタイムアウトとプロセスの起動失敗だけで分け、ログの正規表現で分類しない（課題 2 の再発を防ぐ）。再試行は新しい UUID のサンドボックスで、上限つき（例：2 回）。上限を超えたら停止して人間へ |
| 3 回のサーキットブレーカー | ◎ | 打ち切りは採る |
| 未達のスキップ＋TODO.md／機能合格のみ受領 | × | 直列積層では、スキップしたタスクに依存する後続が必ず壊れ、その壊れ方が「後続の実装役の失敗」に見えて原因が遠くなる。「機能合格のみ受領」は門を弱めるので公理に反する。代案：未収束のタスクは **BLOCKED** にして証拠を残し、**依存しないタスクだけ**進める（依存は分解役の出力にある）。依存するものが残っていなければ走行を止め、人間のバッチレビューに回す |
| Tech Debt GC（リファクタ専用エージェント） | △ | 有効だが、安全条件（テストが振る舞いを十分に縛っていること）が変異の死滅率で示せてから。Phase 4 のマイルストーン 2 つめ以降 |
| コンテキストの完全リセット | ◎ | 既に事実上そう（タスクごとに CLI を新しく呼ぶ）。明文化だけでよい |

## 2. Phase 4 の前に外せない最小（5 件）

選ぶ基準は 1 つ：**無人の 1 晩走行を、コードの不合格以外の理由で止めるもの**。

1. **製造ラインと実験の分離**：`harness/ab/` と版の照合・天井の検査を v2r の版でタグ止めし、製造ラインの経路から外す。版はテレメトリへ。
2. **base の基準を引き継ぐ**：受理時に通ったテストの集合を保存し、次の base はそれだけを見る。除外 JSON・`_Hidden` の特別扱いを削除。
3. **使い捨てサンドボックス**：UUID のパス、同期削除しない、起動時の掃除は失敗を無視。あわせて MSBuild／Roslyn の常駐を環境変数で止める。
4. **Outer-Loop**：インフラ例外（終了コード・タイムアウト・起動失敗）だけ新しいサンドボックスで上限つき再試行。コードの不合格は今の試行ループのまま。
5. **UTF-8／LF の強制**。

走行は固定したコミットから実行する（§1 の工具剥奪の代案）は、1 と同じ PR に含められる。

後へ回すもの：Job Object（3 で残りが出たら）、ArchUnitNET、Tech Debt GC、Zero Allocation の門、OpenAI 調停、並列ロールアウト。

## 3. 凍結と剪定の規則（課題 9・10 への答え）

足すたびに減らす規則が無いと、上の 5 件もまた積み増しになる。

- **予算**：製造ラインの経路（`scheduler.py`・`pipeline.py`・門）の行数に上限を置き、検証コマンドで測る。基盤刷新の段では「17,167 行から増やさない」を合格条件の 1 つにする（減らす変更と足す変更を同じ段に入れる）。
- **門の追加は、消す門とセットで**：新しい検査を足す PR は、どの障害を、どの既存の検査の代わりに防ぐかを本文に書く。
- **凍結**：段が完了したら、その段のための検査は「次の段で同じ障害が再発するまで」触らない。再発しなければ次の段の終わりに削除の候補にする。
- **剪定の候補**（読んだ範囲で）：
  - `pipeline.py` の `establish_base` の、受入テストを消してビルドし直す経路と `task_test_classes`（§2 の 2 で不要になる）
  - `envcheck.py` の版の照合（テレメトリに格下げ）
  - `harness/ab/`（3,153 行）の製造ラインからの切り離し
  - 中身を読んでいないので行数だけ挙げる：`propgen.py`（1,224 行）と `scheduler.py`（2,433 行）は、Phase 3 の離散系に特化した部分がどれだけあるかを先に棚卸しする（棚卸し自体を 1 タスクにする）

## 4. タスクの切り方と検証コマンド

原則：1 タスク＝1 つの障害の型を構造で消す。検証コマンドは**障害を再現する注入テスト**（その障害を人工的に起こし、ラインが止まらない／正しく止まることを `pytest` の終了コードで見る）。ログの文字列は見ない。

| ID（案） | 中身 | 検証コマンドの形 |
|:--|:--|:--|
| F-0 | 製造ラインと実験の分離・固定したコミットからの実行 | 実験のモジュールを import せずに製造ラインのテストが通る。走行中にリポジトリを書き換えても走行の挙動が変わらない（`pytest tests/test_line_isolation.py`） |
| F-1 | base の基準の引き継ぎ・除外の撤去 | 将来のタスクのテストが落ちる状態を作っても base が ABORT しない／引き継いだ集合の 1 件を壊すと ABORT する（両方向） |
| F-2 | 使い捨てサンドボックス | ロックを掴んだままのプロセスを残した状態で、次のタスクが始まり完了する |
| F-3 | Outer-Loop | 1 回目だけタイムアウトする偽の実装役で、タスクが完了する／毎回タイムアウトすると上限で止まり、実装役の試行回数は消費されない |
| F-4 | UTF-8／LF | CP932 の出力と CRLF のファイルを注入しても通る |
| F-5 | 剪定と行数の予算 | 製造ラインの経路の行数が予算以下（行数を数えるスクリプトの終了コード） |

各タスクは `docs/progress.yaml` の検証コマンドとして main への PR で定める（作業規約どおり）。F-0 を最初に置くのは、後の F-1〜F-5 を「実験の厳密さ」と切り離して判断できるようにするため。

## 5. v3.1（phase4_v3_architecture.md）への注記

- Phase 4-1 の検証コマンドは未定義（`harness.progress anchor` の出力）。v3.1 の M1 の合格条件「スナップショット 1,000 件・VACUOUS 0%」は、まだ不変量が 1 つも無い段階で測定器を先に作る順序になっている。Phase 3 で起きた「測定器の自爆」と同じ形。
- 最初の実タスクの案：MuJoCo の 1 つのモデル（落下する剛体 1 個と床）を結合し、1 つの不変量（非貫通、または外力なしの運動量）を 1 つの門で判定する。述語のトリガーは 1 つ、ワーカーは 1 つ。これが無人で 1 晩回ってから、並列化と包絡線を足す。
- OpenAI 調停（Level 2）は、Level 1 と人間の間に確率的な判定者を置く。判定が割れたときの扱いが決まるまで入れない方が、フェイルクローズドの公理と矛盾しない。
