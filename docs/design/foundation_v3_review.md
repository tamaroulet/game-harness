## 3. 段 0：最速の無菌化（総監督が道具を使う最後の作業）

ねらい：H ラインを「完全な工廠」ではなく、**受信箱のファイル 1 件を PR 1 件に変える最小の自律ループ**として作り、それが動いた時点で総監督の道具を剥ぐ。残りの改修はすべてこのループに流す。

### 段 0 の中身（1 つの PR）

| 部品 | 中身 |
|:--|:--|
| 受信箱 | Git の外のディレクトリ `C:\src\.local\inbox\`。総監督が What（タスクの説明と合格条件）を 1 ファイルずつ置く |
| H ラインのスクリプト（300 行以内） | 受信箱の 1 件を取り → main から UUID の作業ツリーを作り → 実装役（CLI、モデル固定）を作業ツリーの中だけで動かし → `python -m unittest discover -s tests` で判定 → 通ればブランチを push して PR を作り、`harness.progress review` で記録し → report をファイルに書き出す。落ちれば最大 3 回やり直し、未収束なら §5 に従う |
| 起動 | Windows のタスク スケジューラで 15 分ごとにスクリプトを 1 回起動（常駐しない。前回が走っていれば何もしない） |
| 総監督の部屋 | 総監督のセッションは受信箱のディレクトリで起動し、その設定で：Bash・PowerShell・NotebookEdit を無効、受信箱の外への Edit・Write を deny（ハーネス・ゲーム・発注窓口・`.local` のほかの場所、および**総監督の部屋の `.claude/` 自身**）、生ログと作業ツリーの Read を deny。この設定は総監督のセッションにだけ効き、H ラインが呼ぶ CLI には効かない |
| report | H ラインが状態の変わるたびに `harness.progress report` の出力を受信箱の `report.md` に書く。総監督はそれを Read して貼る |

### 段 0 で意図的に入れないもの

- 分解役・受入テストの隠蔽（防壁③）：段 0 では実装役がコードとテストを両方書く。自分で採点する弱さは、main へのマージを人間が非同期に承認することで当面受け止める。段 3 で、受入テストを別の役が書き、実装の後に注入する形にする
- Job Object・UUID の Detach の作り込み・ACL：段 1 で H ラインに流す
- 性質テスト：§2 の ③

### 段 0 の合格条件（What）

1. 受信箱に置いたカナリア（ハーネスに小さな関数とそのテストを足す What）が、人間と総監督の操作なしに PR になり、進捗に REVIEW_REQUIRED として記録される
2. 既存のテストを壊す実装では PR が作られない
3. H ラインのスクリプトは 300 行以内で、実装役の設定に `model_flag` と正確なモデルの ID があり、`python -m harness.model_pin` が通る
4. 総監督の部屋で起動したセッションは、シェルを実行できず、受信箱の外と自分の設定に書き込めない
5. `report.md` が `harness.progress report` と同じ内容で更新される

### 段 0 の後の人間の作業（1 回だけ・非同期）

段 0 の PR のマージ、タスク スケジューラへの登録、総監督のセッションの起動場所の切り替え。以後、人間の定常作業は PR の非同期の承認だけ。

## 4. 段 1 以降：すべて受信箱から H ラインに流す

総監督は各段を What として受信箱に置くだけ。順序は「無菌室を固める → 自己回復 → 門の純化 → 保守」。

| 段 | 中身 | 合格条件（What） |
|:--|:--|:--|
| 1 実行基盤 | UUID の作業ツリーと Detach（同期削除しない、起動時に消せるものだけ消す）。すべての子プロセスを Job Object（KILL_ON_JOB_CLOSE）の配下で起動。agy を呼ぶ前の SHA-256 照合と、ACL の手順書 | 同じタスクの作業ツリーのパスが重ならない／途中で落ちた走行の残骸が次の走行に影響しない／タスクの終わりとハーネスの強制終了のときに子孫のプロセスが残らない／agy の中身が変わっていれば呼ぶ前に止まる |
| 2 自己回復と門の純化 | インフラ例外の Outer-Loop。Gate 2 の廃止。Base 検査を合格済みタスクの `--filter` に一本化（除外の JSON を全廃）。新規ファイルの作成の許可と、§1 の規模の制約 | 1 回目だけタイムアウトする状況でタスクが完了し、実装役の試行回数を消費しない／未実装のタスクのテストが落ちても Base は通り、合格済みのテストが 1 件落ちると止まる／タスクの ID の指定が別の ID に部分一致しない／門の判定に LLM の呼び出しが無い／規模の制約を超える差分は落ちる |
| 3 役の分離 | 分解役（推論特化）が受入テストを書き、実装役（高速軽量）には見せず、実装の後に注入する。H ラインとゲームのラインの両方 | 実装役が受入テストを読めない／受入テストを満たさない実装は通らない |
| 4 保守層 | Refactorer（非同期 GC）を 10 タスクごと、またはマイルストーンの完了時に起動。既存の超過ファイルの分割を最初の仕事にする | Refactorer の変更は Gate 1 が 100% 通るときだけ受理される |
| 5 Phase 4 | MuJoCo の剛体 1 個・不変量 1 つから | — |

ACL は段 1 の PR に手順を書き、人間が 1 回だけ実行する。実行されるまでは SHA-256 照合が単独で働く（改変は検知して止まる）ので、人間を待ってラインが止まることはない。

検証門の言語：ゲームのラインの Gate 1 は確定仕様のとおり（Roslyn・ArchUnitNET・FsCheck・受入テスト）。H ラインの Gate 1 は、バイトコンパイルと import、`unittest` の回帰と受入、§1 の規模の制約。

## 5. 未収束のタスクの扱い（両方のライン共通）

| 状況 | 動作 |
|:--|:--|
| 修正 3 回で未収束 | パッチを捨てる。分解役がその MUC（契約違反の ID と最小の反例）を受け取り、そのタスクを**自動で 1 回だけ**分解し直して再実行する（段 3 より前は、分解し直しの代わりに同じ What での新しい作業ツリーからの再実行 1 回） |
| 再実行でも未収束・下流が無い | `TODO.md` に記録して次へ |
| 再実行でも未収束・下流がある | そのタスクと**下流だけを凍結**し、独立したタスクは進める。下流のタスクには実装役を呼ばない（中身の無い走行をしない） |
| 進めるタスクが無くなった、または同じマイルストーンで凍結が 2 件に達した | ラインを止める（2 件目は仕様の誤りの兆候と見る） |
| インフラ例外が上限を超えて続く | ラインを止める |

- 通知：凍結とラインの停止は report の人間の作業欄に出し、まとめて 1 日 1 回知らせる。止まっても壊れるものは無いので、即時の対応は求めない
- 再開：総監督が受信箱に直した What を置くと、H ラインが取り込んで凍結を解く。人間の操作は要らない

## 6. 人間に決めてほしいこと

1. 段 0 の構成（受信箱 `C:\src\.local\inbox\`・15 分ごとの起動・総監督の部屋の設定）でよいか
2. モデルの ID：H ラインの実装役（推奨：Claude CLI の `claude-sonnet-5-5`。agy はリポジトリ外の `~/.gemini/GEMINI.md` に挙動が左右されるため、ハーネス自身の改修には使わない）、分解役（推奨：`claude-opus-5-5`）、Refactorer
3. 凍結が何件でラインを止めるか（推奨：同じマイルストーンで 2 件）
4. 規模の制約の値（差分・モジュールの行数・複雑度）と、複雑度を測る道具（`ruff` の版を固定して入れるか、標準ライブラリで数えるか）
5. 段 0 の実装を総監督が直接行うことを認めるか（H ラインが無いので、これだけは避けられない）
