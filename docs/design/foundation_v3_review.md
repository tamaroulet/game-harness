## 2. 役と書き込み先（人間を作業主体にしない）

| 役 | 書いてよい場所 | できないこと |
|:--|:--|:--|
| 人間 | 自由（ただし同期的な作業を求められない） | — |
| 総監督（Claude IDE） | 発注窓口の `C:\src\dispatch\spec\**` だけ | シェルの実行（Bash・PowerShell）、ハーネス・ゲーム・作業ツリーへの書き込み、生ログの読み取り |
| Layer 2（`driver.py`／H ライン） | 作業ツリー、ブランチ、PR、`docs/progress.yaml`（`harness.progress` 経由）、report のファイル | main へのマージの承認 |
| 実装役・分解役・Refactorer | 割り当てられた作業ツリーの中だけ | 受入テストの閲覧、他タスク |

- 総監督の書き込みを `spec/` に限定するのは、クライアント設定の範囲でできる最大の剥奪：シェルの道具は無効、書き込みは `spec/` の外をすべて deny（ハーネス・ゲーム・`.local` のリポジトリの根を丸ごと）。総監督のセッションは発注窓口のディレクトリで起動し、その設定にだけ置く（同じ制限が Layer 2〜5 のエージェントに及ばないように）
- `spec/` の変更は Layer 2 が検知し、様式の検査（既存の発注窓口の様式検査）を通したうえで、自動でコミットし、H ラインまたはゲームのラインのタスクとして取り込む。人間のコミットは要らない
- 総監督は report を Layer 2 が書き出したファイルで読む。CLAUDE.md の「毎ターン anchor／report を実行」は、「report のファイルを読む」に置き換える（この改訂自体も H ラインのタスクにする）
- main へのマージの承認は人間が非同期に行う（エージェントは承認しない、の規則を維持）。人間がするのは承認だけで、コミット・PR の作成・記録はしない

## 3. ロードマップ（段 0 を追加）

| 順 | 段 | 中身 | 実行者 | 終わりの条件 |
|:--|:--|:--|:--|:--|
| 0 | H ラインの設立 | ハーネス自身を改修する自律ライン：`spec/` の取り込み → 分解 → 使い捨て作業ツリー → 実装 → Python の門（§4）→ PR の作成 → 進捗の記録。あわせて report のファイル出力 | **総監督（道具を使う最後の作業）**。PR は人間が非同期に承認 | カナリアのタスク（§6 段 0）が、人間・総監督の手を介さずに PR まで到達する |
| 1 | 統治層の無菌化 | 総監督のセッションの道具の無効化と書き込み先の限定、CLAUDE.md の改訂 | H ライン（設定ファイルと規約の変更を PR にする）。人間は承認だけ | 総監督が `spec/` 以外に書けず、シェルを実行できない |
| 2 | 実行基盤 | UUID の作業ツリーと Detach、Job Object、agy の ACL | H ライン（ACL の適用は §7 の 3） | §6 段 2 |
| 3 | 検証門 | `--filter` のホワイトリスト、Gate 2 の廃止、新規ファイルの許可、3 回の打ち切りと停止の規則（§5） | H ライン | §6 段 3 |
| 4 | 自己回復 | インフラ例外の Outer-Loop | H ライン | §6 段 4 |
| 5 | 保守層 | Refactorer の非同期起動（両方のライン） | H ライン | §6 段 5 |
| 6 | Phase 4 | MuJoCo の剛体 1 個・不変量 1 つから | ゲームのライン | — |

- 段 0 は H ラインがまだ無いので、総監督が直接作る。これは避けられない一度きりの例外で、段 0 の PR がマージされ、カナリアが通った時点で終わる
- 段 1 より後、総監督は `spec/` に What を書くだけになる
- H ラインは自分自身の門を改修しうる。門・指標・承認の機構に触れるタスクの PR は、独立した PR にして本文にその旨を書く（既存の規則「独立レビューが要る変更だけ別 PR」）。走行中の H ラインは、マージ済みの main の版で動き、作業中の変更の影響を受けない

## 4. 検証門：2 本のライン

確定仕様の Layer 4（Roslyn・ArchUnitNET・FsCheck・受入テスト）は**ゲームのライン**の門で、これは変えない。ハーネス（Python）の改修には別の門が要る。

### H ライン（ハーネス改修）の Gate 1

判定は終了コードだけ。LLM は使わない。ハーネスの今の依存（標準ライブラリと `pyyaml`）を増やさない範囲で定める。

| 確定仕様の要素 | H ラインでの対応 |
|:--|:--|
| ビルド（Roslyn） | ハーネスの全モジュールがバイトコンパイルでき、import できる |
| アーキ制約（ArchUnitNET） | モジュール間の禁止の参照が無い（製造ラインの経路が実験のモジュールに依存しない、など）。ファイルの行数は、上限を超えているファイルを今より増やさない（増やさない方向の歯止め。値は §7 の 4） |
| 性質テスト（FsCheck） | 性質は `unittest` の中で、固定のシードの乱数による入力の生成で書く（新しい依存を入れない）。外部のライブラリを入れるかは §7 の 5 |
| 受入テスト | そのタスクの受入テストを、実装の後に作業ツリーへ注入して実行する。実装役には見せない（防壁③） |
| 回帰 | 既存のテスト（`python -m unittest discover -s tests`）が全部通る |

- 新規のファイル：実装役に新しい `.py` モジュールの作成を許可する（ゲームのラインの新規 `.cs` の許可に対応）。`tests/` への書き込みは拒否する
- Base 検査（`--filter` の対応）：H ラインでは、合格済みタスクの受入テストだけを指定して実行する。指定はタスクの ID で、別の ID に部分一致しない形にする

### ゲームのラインの Gate 1

確定仕様のとおり（Roslyn・ArchUnitNET・FsCheck PBT・受入テストの exit 0、Gate 2 の廃止、新規 `.cs` の許可、`--filter` のホワイトリスト）。改訂 3 の §3 の 3（`T1` が `T10` に当たらないこと、`_Hidden` を含めないこと）を合格条件に含める。

## 5. 未収束のタスクの扱い（両方のライン共通）

修正ループは最大 3 回。収束しないときは、パッチを捨てる（マージしない）。そのあとは依存関係で分ける：

| 状況 | ラインの動作 |
|:--|:--|
| 未収束のタスクに、後続で依存するタスクが**無い** | `TODO.md` に記録して次のタスクへ進む |
| 未収束のタスクに、依存する後続タスクが**ある** | **ラインを止める**。依存しないタスクも含めて、それ以上は着手しない。状態を BLOCKED にし、MUC（契約違反の ID と最小の反例）を添えて通知する。人間の作業欄に BLOCKED が出る |
| インフラ例外が上限を超えて続く | 同じく止めて通知する |

- 依存しないタスクも止めるのは、未収束の原因が仕様（分解）の誤りである可能性があり、同じ仕様から作った他のタスクも同じ誤りを積む恐れがあるため
- 止まったラインを再開するのは、総監督が `spec/` を直して Layer 2 が取り込んだとき、または人間が非同期に再開を指示したとき。人間に同期的な対応は求めない（止まっていても他に壊れるものが無い）
- 通知の手段は §7 の 6

## 6. 各段の合格条件（What のみ）

各段の検証コマンドは H ラインが書き、main への PR で `docs/progress.yaml` に定める。どれも障害を人工的に起こして両方向で確かめる。

### 段 0 H ラインの設立

1. `spec/` に置いたカナリアのタスク（ハーネスに小さな関数とその受入テストを足す What）が、人間と総監督の操作なしに、取り込み → 実装 → 門 → PR の作成 → 進捗の記録まで到達する
2. 受入テストを満たさない実装では、PR が作られない（門が実際に効いている）
3. 実装役は受入テストを読めない
4. report のファイルが、`harness.progress report` と同じ内容で、状態が変わるたびに更新される
5. H ラインの呼ぶすべてのエージェントの設定に `model_flag` と正確なモデルの ID があり、`python -m harness.model_pin` が通る

### 段 1 統治層

1. 総監督のセッションでは、シェルの実行ができない
2. 総監督のセッションでは、`spec/` の外に書き込めない
3. 総監督のセッションからは、生ログ・作業ツリーが読めない
4. 1〜3 の制限が、Layer 2〜5 のエージェントに及ばない
5. 総監督が `spec/` に書いた変更が、人間の操作なしに取り込まれる

### 段 2 実行基盤

1. 同じタスクを何度始めても、作業ツリーのパスが重ならない
2. 走行が途中で落ちても、次の走行は前回の残骸に影響されずに完了する
3. タスクの終わり、およびハーネス自体の強制終了のとき、起動したプロセスの子孫が残らない
4. 作業ツリーの削除の失敗が、タスクの結果に影響しない
5. agy の導入先が書き換えられない。書き換わっていた場合は、agy を呼ぶ前に止まる

### 段 3 検証門

1. 未実装のタスクのテストが落ちても、Base 検査は通る
2. 合格済みのタスクのテストが 1 件でも落ちると、Base 検査は止まる
3. タスクの ID の指定が、別のタスクの ID に部分一致しない
4. 除外の JSON を読む経路が無い
5. 門の判定に LLM の呼び出しが無い
6. 実装役が新規のソースファイルを作っても拒否されない。テストのパスへの書き込みは拒否される
7. 依存先を持たない未収束タスクは `TODO.md` に記録されてラインが進む。依存先を持つ未収束タスクではラインが止まり、BLOCKED と MUC が通知される

### 段 4 自己回復

1. 1 回目だけタイムアウトする状況で、タスクは新しい作業ツリーで完了する
2. インフラ例外は実装役の試行回数を消費せず、実装役に見せない
3. インフラ例外が上限を超えて続くと、ラインは止まり通知される

### 段 5 保守層

1. 10 タスクごと、またはマイルストーンの完了時に Refactorer が起動する
2. Refactorer の変更は、そのラインの Gate 1 が 100% 通るときだけ受理される

## 7. 人間に決めてほしいこと

1. 総監督の書き込み先を `C:\src\dispatch\spec\` に限定する案でよいか（発注窓口のリポジトリに置く）
2. H ラインの実装役と分解役のエージェントとモデルの ID（ゲームのラインは agy `gemini-3.8-flash-medium`）。Refactorer のモデルの ID
3. agy の ACL の適用：ホストのセキュリティ設定の変更はエージェントが実行できないため、段 2 の PR に手順を書き、人間が 1 回だけ実行する（同期的な待機は不要。適用されるまで段 2 の合格条件 5 が通らないだけ）
4. 行数の上限の値（ゲームのラインの ArchUnitNET、H ラインの歯止め）
5. H ラインの性質テストに外部のライブラリを入れるか（入れない場合は `unittest` と固定シードで書く）
6. BLOCKED の通知の手段（report の人間の作業欄だけでよいか、プッシュ通知も要るか）
7. Gate 2 の廃止の範囲（分解役の出力への監査を含めるか）
