## 1. 要旨

1. **線を 2 本に分ける。**
   - 線 1 は、外側の周期への最短の道。今の Windows の道具（工廠の走らせ役・制限した OS のアカウント・判定と漏れの検め）を使い回し、実装役はコマンド無しのまま回す。
   - 線 2 は、環境の分離と、単一コンテキスト型との比較の本番。線 1 と並べて進め、周期を止めない。
2. **物差しを作り直す。**
   - 10 本の独立した課題（単一コンテキスト型が全部満点）を、段を積む筋書きに替える。前の段の自分の出力の上に、次の段を積む。
   - 凍結の 10 本を「開発 3・保留 3・取っておく 4」に分ける。開発の組は周期が改善を選ぶのに使い、保留の組は合わせ込みの守り、取っておく組は比較の本番だけに使う。
   - 題材は、ずっと Python と MuJoCo（操縦士の決め、10-30）。
3. **外側の周期の形。**
   - 提案役が、開発の組の走りの全文の記録を読み、狙う失敗の型を 1 つ選んで直す。直してよいのは、最初に 1 回だけ承認した「最適化の面」だけ。
   - 取り込むかは、合計の点では決めない。狙った失敗が出た段で旧版と新版を対で走らせて直りを見て、さらに開発の組と保留の組で回帰を見る。
   - 確立の条件：2 周を続けて人の手なしで回し、取り込んだ改善のうち 1 件以上が保留の組でも悪くしていない。
4. **比べるハーネスの実体（v0）。**
   - 凍結の工廠の道具（走らせ役・実装役・Gate 1）を、計画役なしで使う形。段ごとに 1 件の What。
   - 実装役は agy の gemini-3.8-flash-medium（凍結の記録と同じ）。比べる相手 A も同じモデルの素のエージェント。
5. **費用の見込み。**
   - 確立までに段の走りが約 90 回、合わせて約 1.4 億〜2.7 億トークン（大半はキャッシュの読み出しで、主に Gemini の枠）。
   - 凍結の 10 本の工廠の記録（1 本で 132 万〜914 万トークン）から見込んだ。L1 と L4 で実測して直す。日数は 3〜5 週の見込み。
6. **作り方を批判で 7 回直した（§13）。** 自己批判 3 回、外部の AI（Gemini 3.8 Flash High）の批判 4 回。最後の自己批判で順番と決めが変わらなくなったので止めた。

## 5. 推す流れ

```
線 1（外側の周期への最短の道。Windows のまま、実装役はコマンド無し）
  段 0 足場 ─┐
  L1 煙の試し ┼→ L2 開発の組の筋書き → L3 筋書きの走らせ方 → L4 v0 の基準 → L5 保留の組
             ┘   → L6 1 周目（会話の席が回す）→ L7 起動を Git に → L8 2 周以上を人の手なしで

線 2（環境の分離と比較の本番。並べて進め、周期を止めない）
  E1 安い確かめ → E2 置き場を選ぶ → E3 Linux の CI → E4 箱の中の走り
  → E5 A の走らせ方 → 「実装役にコマンドを許す」を周期の候補に → 比較の本番（保留と取っておく組で）
```

**枠の使い方**
- A も B も、実装は同じモデルなので、走りはどちらも Gemini の枠を使う。
- Claude の枠を使うのは、提案役・総監督・会話の席。会話の席の作業も同じ Claude の枠を使うので、読む量を絞り、区切りで新しい起動にする。
- 線 2 の A の走りは、線 1 と Gemini の枠を取り合う。だから A の走りは、周期が確立した後か、Gemini の枠が空いているときに回す。
- 線 2 の E1〜E4 は、走りをほとんど使わない。

**費用の総額の見込み**
- 確立（L8）までに、段の走りは約 90 回（L4 の 18・L5 の 9・L6 の約 22・L8 の約 44）。
- 1 段は 1〜2 件の What ぶんと見て、1 回 150 万〜300 万トークン。合わせて約 1.4 億〜2.7 億トークン。
- 枠に収まらなければ、組を 2 本ずつに減らす。保留の組での確かめも、取り込み 2 回に 1 回にする。

## 7. 線 1：外側の周期への最短の道

### 7-1. L1 煙の試し（確かめる単位）

### 7-2. L2 開発の組の筋書き（作る単位）

- **組の分け方：** 凍結の 10 本を、開発 3・保留 3・取っておく 4 に分ける。物理の種類が散るように選ぶ（選ぶのは会話の席。理由を書く）。
- **段の形：**
  - 段 0 は、凍結の課題を満点で解いた実装（参照の実装）から始める。過去の満点の出力があれば使い、無ければ Flash に書かせて、凍結の判定役で満点を確かめる。
  - 段 1〜3 は、機能を足す・振る舞いを改める・不具合の報告を直す、を混ぜる。どの段も物理を使う。
  - 骨組み（各段の「足すもの」と「保つべき前の振る舞い」を 1 段落ずつ）は会話の席が書く。
- **仕様・隠しテスト・参照の実装の書き方（Gemini 3.8 Flash High、別々の文脈で）：**
  1. 段の仕様（公開）を先に書く。物理の判定は、許す誤差と見る時間の幅で書く（W-160 の中身。凍結の B01 の仕様の REQ-05 の帯の書き方が手本）。
  2. 隠しテストを、仕様だけを見て書く。必須の試験の組は「その段の新しい試験＋前から保つ試験（置き換えた試験を除く）」。置き換えた試験の名前も書く。
  3. 参照の実装を、仕様だけを見て、試験を見ずに書く。
- **確かめ（段ごとに、走らせる前に必ず）：**
  - 参照の実装が、必須の試験を全部通す。互いを見ずに書いたものが一致するので、満たせることと、仕様の読みが揃っていることが分かる。
  - 前の段の参照のまま変えないもの（何もしない実装）は、その段の新しい試験に落ちる。
  - 主な物理の計算を外した変異を、最低 1 つ落とす。変異の死滅率の全体は測るだけ（関門にしない）。
  - 外れたら、Flash に 2 回まで直させる。それでも駄目な段は、易しくするか捨てる。
- **置き場：**
  - 段の仕様（公開）は `docs/bench/` の下の新しい置き場。これは保護パスで、H ラインの実装役は変えられない。
  - 隠しテストと参照の実装は、制限のアカウントから読めない置き場（`config/hline.json` の oracles、今は `C:\src\.local\oracles`）。Git には入れない。
  - **10-30 に直した（§15 の「10-30 その 2」）：** 段の仕様も骨組みも、リポジトリに置かない。すべて非公開の置き場（`C:\src\.local\oracles\chains`）に置き、段 k を走らせるときに、走らせ役が段 0〜k の仕様だけを作業場に入れる。

### 7-3. L3 筋書きの走らせ方（作る単位。低リスクの PR）

- 工廠の走らせ役に、鎖の形を足す。
  - 段 k は、その走りの段 k−1 の枝の先から始める。
  - 前の段で落ちても、次の段は巻き戻さずに走らせる（FeatureArc と同じ）。
- どちらの条件でも、作業場の docs に、全部の段の公開の仕様を積む。差は構造だけにする。
- 判定は、段 k の必須の試験を名前ごとに見る（回帰の判定 `harness/oracle.py` の F2P と P2P を使い回す）。
  - 段ごとに、新しい試験だけの点（孤立）と、前の試験を保つ率（回帰）を分けて記録する。
- 実装役の全文の記録（agy の stream-json の出力）を、呼び出しごとに走りの記録に残す。
- 落ちた試験の名前・例外・直前の数ターンをそのまま抜いた索引を、機械で作る。言い換えの要約は作らない。
- 試験ごとの記録は公開の Git に置かない（集計の点だけを置く）。公開のリポジトリから、ネットを使えるエージェントが読めないように。
- 段ごとに、時間・ターン・トークンの上限を置く（担当の無かった「収束しないタスクの上限」）。
- 新しい試験のファイルを足すだけの PR にする（既存の試験は変えない）。

### 7-4. L4 v0 の基準（確かめる単位）

- **v0 の形：** 凍結の工廠の道具（走らせ役・実装役・Gate 1）を、計画役なしで使う。段ごとに 1 件の What にし、監修役も置かない（非劣性の走りと同じ）。実装役は agy の Flash で、Gate 1 が試験を回して、落ちた出力を次の試行に渡す。
- **中身：** 開発の組（3 本×3 段）を 2 回走らせる。
- **予想：**
  - 点が天井にも床にも張り付かない。2 回の走りの揺れの幅が分かる。
  - 1 周の費用の見積もりが立つ。
- **外れたら：**
  - 天井（全部の土台で 3 段を保つ）なら、段を足すか難しくする。
  - 床（段 1 の新しい試験が 2 回とも半分未満）なら、v0′ を基準にする。v0′ は凍結の工廠と同じく、計画役が段ごとに 1 回だけ計画を作り、固定する形。
- **予算：** 段の走り 18 回。枠の目盛りを、走りの前後で操縦士が見る（1 分）。

### 7-5. L5 保留の組（作る単位）

- 提案役には、保留の組の集計の点しか見せない。隠しテストと詳しい結果は、OS の権限と許しの設定の両方で読めないようにする。

### 7-6. L6 1 周目（会話の席が手で回す）

- **始める前：** 最適化の面（§7-8）と、戻せない操作の一覧を、操縦士に 1 回だけ承認してもらう。
- **中身：** §7-7 の周期の形を、手で 1 回通す。この回の取り込みの検めは、信書で総監督に頼む（人の運び 1 回）。
- **予想：** 取り込みが 1 件、または「取り込まない」の理由つきの判定が出る。
- **外れたら：** 詰まった所を直してから L7 へ。

**木の依存の組み替え（総監督への提案）**

- 人の手なしで回す前には、守り（物差しに届かない・走りの上限・実行役の身元）だけを先に満たす。

### 7-7. 周期の形（L6 以降）

1. **提案役が生の記録を読む。**
   - 提案役は別の起動の Claude Code（claude-sonnet-5-5。提案の質が低ければ Opus に替える）で、使うのは Read・Grep・Glob・Edit だけ。
   - 読むのは、開発の組の走りの全文の記録と判定の結果。Meta-Harness では、生の記録を読めると点が上がり（中央値 34.6 → 50.0）、要約を足しても戻らなかった（34.9）。
   - 入口は、L3 の失敗の所の索引。1 回の起動には、ターンと時間の上限を置く。
   - 提案役への指示で、特定の課題の式や変数名に依る直しを禁じる。一般の手順の直しだけを出させる。
2. **改善を 1 つ選ぶ。**
   - 狙う失敗の型と、その型が出た段を名指しする。予想・補う弱さ・外す条件（v2 の H2）も書く。
   - 面の外を差分のパスの検査で落とす（`harness/hline_protect.py` の形を使い回す）。
   - 面の差分に、開発の組の試験の名前や文字列が入っていないかも、機械で見る（Meta-Harness の、課題に特有の文字列の漏れの検め）。
3. **狙いの直りを見る。**
   - 狙った失敗の型が出た段（基準の 2 回の走りのどちらかで出た段）のすべてで、旧版と新版を同時に 1 回ずつ、対で走らせる。該当が 1 段しか無いときは 2 回ずつ。
   - 対にするのは、同じ ID のままモデルの中身が変わるのを相殺するため。
   - 始める作業場は、失敗の型で選ぶ。段の中の誤りなら、前の段の参照の実装の写しから。受け継いだ欠陥や回帰なら、基準の走りの前の段の作業場の写しから。
   - 新版が直した段の数が、壊した段の数より多ければ、次へ進む。
4. **回帰を守る。**
   - 開発の組の全体を新版で 1 回、保留の組を 1 回走らせる。
   - 保つ率と通過率が、L4 の揺れの幅を超えて下がらないこと。
   - 費用は基準の 1.5 倍以内。費用は通過率と並べて見る守りの値として扱う。
5. **取り込む。**
   - 総監督は、検めの結果を受信箱のファイルに書くだけ（シェルが無い）。マージは、周期の走らせ役がそのファイルを読んで行う。
   - 決定の記録と前提の台帳に、外れた予想も書く。
   - 「この周期で使わなかった規則・部品」を問う（v2 の H8）。

**最初の候補になりそうなもの（決め打ちせず、記録を見て選ぶ）**
- 計画役を足す（v0′）。
- 受入の試験を別の役が先に書く（W-134。物差しの隠しテストとは別物）。
- AGENTS.md を実装役に渡す（W-108）。
- ターン切れの手当て（deferred の X-32：W42 の 96 試行のうち 22 回）。
- 黙る故障の止め方（空の差分で rc=0）。
- 線 2 の後なら、実装役にコマンドを許す。

### 7-8. 最適化の面（周期が自分で変えてよい所）

- **面の 1 つ目：** 実装役への指示と、それを組むコード（`harness/hline_prompt.py` など）。
- **面の 2 つ目：** 面の設定のファイル 1 つ。実装役のターンの上限・試行の回数・役の有無の切り替えを書く。
  - 走らせ役は、ベンチの走りでだけ、ここを読む。
  - 高リスクの設定（`config/hline.json`）の値を、範囲つきで写す。範囲と面の外枠は、走らせ役のコードの側に置いて、周期からは変えられないようにする。
  - 範囲を広げるのは、高リスクの変更として扱う。
- **面の外：**
  - 役そのものを足すコード（例：受入の試験を先に書く役）。面の外の普通の PR で入れ、入った後は切り替えで面の中から試す。
  - 実装役にコマンドを許すこと。権限の層なので、線 2 の後に操縦士の承認で入れる。
  - 高リスクの設定・既存の試験・CI・物差し（隠しテスト・判定役・規約・筋書き）。
- 面と外枠は、L6 の前に操縦士が 1 回だけ承認する。

### 7-9. L7 起動を Git に

- 周期の起こし方を Git の中に置く。今の `hline_cron.py` の登録の形を使い回し、H ラインの常駐の代わりに周期の走らせ役を登録する。高リスクの層の「常駐ワーカー」に当たるので、単独の PR にする。
- bench で走る予定のタスクを、操縦士が 1 回だけ登録する（密語を保存。§7-1 の後の手当て）。
- 取り込みの検めは、総監督の無人の起動（`director_launch`）で行う。その指示（`docs/prompts/director_weekly.md`、保護パス）の書き換えは、操縦士の PR で 1 回だけ入れる。
- 人の手なしでマージするなら、実行役の身元を操縦士と分ける（専用のアカウントか GitHub App。取り下げた W-131 と K-9 の中身）。
- 周期は PC が点いている間だけ回る。CI の上に移すかは、線 2 の E2 で決める。

### 7-10. L8 確立の条件

- 2 周を続けて人の手なしで回し、取り込んだ改善のうち 1 件以上が、保留の組でも悪くしていない。
- W-25 の「4 周」から下げる案。1 周の費用を測ってから、総監督と操縦士で決め直す。

  - B09 の仕様：不具合の報告の段に、原因と直し方（積分の方式）を 3 か所で書いていた。期待の振る舞いだけを残した。再現の手順の歩の数を直した。
- **会話の席の道具の誤り：** 確かめの走らせ役が、subTest の失敗を拾っていなかった。落ちた試験が結果から抜け、何もしない実装と変異が落ちていないように見えた。直して、段 0 と段 1 を確かめ直した（上の数は、直した後のもの）。
- **費用：** Flash（gemini-3.8-flash-high）の呼び出しは 12 回で 501,026 トークン、合わせて約 33 分。ほかに、道具を使おうとして空の答えで終わった呼び出しが 3 回あった（頼みに「道具を使わない」と書いて直した）。
