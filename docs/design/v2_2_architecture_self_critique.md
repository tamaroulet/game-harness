# v2 の自己批判：防壁と贅肉の峻別、実装役とのインターフェース、狭い文脈の原則

- 状態: 起草（2026-09-26）。**スモーク（v2-smoke-05）と本走は、この文書を人間と副操縦士が精査・合意するまで走らせない**
- 前提: game-harness#97（`docs/design/v2_b_efficiency.md`）、game-harness#98（v2.2 の 4 点）
- 測り方: 単位定義（`experiments/v2/units/T*.json`）・性質の宣言（`experiments/v2/properties.json`）・マニフェスト・v2-smoke-04 の `prompt_chars` から字数と件数を数えた。Core の中身・テストコードは見ていない

## 0. 目的の再確認と、前の姿勢の誤り

本基盤の目的は、長期・大規模のドメイン（ゲーム開発、Phase 4 の 3D 物理・連続力学系）で、人間の介入なしに開発を回し続けるときの**コスト効率（トークン・時間）**と**頑健性（仕様ドリフトの阻止・先祖返りゼロ）**を、構造で担保することにある。falling-blocks の 5 タスクは、その構造を測る台にすぎない。

game-harness#97 で、私は「A も同じ大きさのプロンプトを受け取る」「長考は条件によらず出る」ことを根拠に、B の過密なプロンプトという病因を「実測で支持されない」とした。これは **A/B の対称性という問いにすり替えた**判断だった。問うべきは「B の 1 呼び出しの文脈が、ドメインの規模とタスクの数に対して増えないか」で、その答えは下のとおり「増える」。A が同じ無駄を抱えていることは、B の無駄を正当化しない。

**本文書の主張**：v2 の B は、門（型・コンパイラ・性質テスト・P2P）は決定論的だが、実装役に渡す文脈は決定論的に絞られていない。**B の 1 呼び出しの文脈は、いまタスク数 N とコードの大きさに比例して伸びる**（§1.3）。これは B の存在理由（長期でも O(1) の文脈で回る）と矛盾する。

## 1. 防壁の本質と、実装上の贅肉

### 1.1 防壁の本質（削らないもの）

| 防壁 | 実体 | 実装役のプロンプトに要るもの |
|:--|:--|:--|
| 型拘束 | 契約の生成物（IGameState・TickInput・Cell）、interface の宣言、`required_symbols` の門 | 編集する境界の型の宣言 |
| コンパイラ主権 | サンドボックスでのビルド。whitelist・`forbidden_patterns`・差分の上限の門 | 書き換えてよいファイルの一覧と、門の閾値（差分の上限） |
| 性質テスト（PBT） | 性質の宣言 → 生成テスト。非公開シード、Targeted State Sampling（game-harness#94） | **このタスクの**性質（前提と帰結） |
| 先祖返りの阻止 | P2P の門（前のタスクのテスト）、大域の不変条件 | 破れたときの反例（門が返す） |
| 視界の制限 | 細い作業場所（`narrow_dir`）、テスト・仕様書を置かない | 作業場所のパス |

防壁は**門の側**にある。プロンプトは防壁ではなく、門を通る実装を 1 回で書かせるためのインターフェースにすぎない。したがって、プロンプトの要素は「門を通るために実装役が知る必要があるか」だけで評価できる。

### 1.3 B の文脈は N に比例して伸びている

v2-smoke-04 の B の最初の呼び出しの `prompt_chars`：T1 31,640 → T2 35,704 → T3 40,342 → T4 42,955 → T5 45,282（+13,642）。

| 伸びた分 | 字数 | 伸び方 |
|:--|:--|:--|
| 単位定義の prompt（ほぼ e） | +4,443 | 性質 4 件・約 1,000 字 / タスク。O(N) |
| 残り（書き換えてよいファイルの実装の伸びと埋め込みの見出し。差し引き） | +9,199 | コードの大きさに比例 |
| 契約・interface・決まり | 0 | 一定 |

5 タスクでは目立たないが、性質が数百件、実装が数千行になる規模（ゲーム開発・Phase 4）では、**B の 1 呼び出しが A の会話の累積と同じ速さで伸びる**。しかも B はステートレスで、agy では会話をまたいだキャッシュが効かない（#97 §1.4）ので、伸びた分を毎回全額払う。B の優位は「文脈が O(1)」にしか無く、いまの実装はそれを満たしていない。

### 1.4 プロンプト以外の贅肉と構造の制約

| 項目 | 見立て |
|:--|:--|
| DISPUTE_TEST の読み取り（One-Strike） | 指示を外したので死んだ経路。残すなら、出たことを異常として数えるだけにする |
| 再試行で全部を渡し直す（v2-smoke-04 の T3 の 2 回目 41,627 字） | ステートレスの定義上は避けられない。**文脈を絞れば再試行の費用も同じ比で縮む**ので、対策は §3 に一本化する |

| 思考の重さ（`gemini-3.8-flash-medium`） | 共有の設定。費用の最大の項（B の 57%）に直接効くつまみだが、プロンプトとは別の実験になる |

## 2. 実装役とのインターフェースの客観視

型と性質で縛るはずの環境で、ハーネス自身が「読み解き・すり合わせ・深読み」を要する文面を作っていた。見つかったもの：

| # | 所見 | 件数（実測） | 実装役に起きうること |
|:--|:--|:--|:--|
| F1 | 自然言語の要求が、見せていない性質の ID を名指す。`tool_policy` は「ID の意味は書いてある性質がすべて」と言うのに、その性質が無い | 名指しの ID 56 のうち 13（T1 4/7、T2 3/10、T3 3/12、T4 2/13、T5 1/14）。T1 は「保存則（RL-36）が常に成り立つこと」と求めるが、RL-36 の性質（P-T2-04）は T2 から | 定義の無い義務の意味を推測する。指示どうしの矛盾を解こうとする |
| F2 | 性質の「前提」に実行後の状態（`after.`）が入る。テストの側の絞り込み（固定が起きたティックを除く）を、実装役には「前提」として見せている | 20 件中 17 件。うち 14 件が `after.LockedMinoCount == before.LockedMinoCount` | 「自分の出力が前提を左右する」含意を解こうとする。固定の時機を別タスクの性質と突き合わせる |
| F3 | 性質が使う関数（`fits`・`moved`・`rotated`・`kick`）の定義を実装役に渡していない。定義は `propgen` の説明と、テスト側の参照モデルにしか無い | 4 種。T5 の `kick` は SRS の手順そのもの | 関数の意味を性質の文面から逆算する |
| F4 | interface の描画が、既存の型と契約を「作る型とメンバー」として並べ、触らないメンバーまで毎回出す | 毎回 1,790 字。埋め込み（i1・i3）と重複 | 既存の型を作り直すべきか迷う |
| F5 | 同じ趣旨の指示が 4 か所（a・b・f・h）に別の言い回しで散る。報告の形も「何をしたかだけ」（b）と「変更したファイルの一覧だけ」（A のテンプレート）で揺れる | 4 か所 | 文面の差に意味を探す |
| F6 | 自然言語の要求（c）と性質（d）の二重の経路 | 全タスク | 二つを突き合わせ、食い違いを探す |

**言えること・言えないこと**：これらは長考の引き金になりうる要素で、ハーネスが作ったものだ。ただし、どれが長考を招いたかは実測では切り分けられていない（同じプロンプトで最初の手番の思考が 2,773〜37,547 トークンと揺れる。#97 §1.1）。除去の根拠は「長考の原因と証明された」ではなく、**「門を通るために要らず、曖昧さを足すだけ」**である。この基準は決定論的に判定でき、実験を待たずに適用できる。

## 3. 狭い文脈（Narrow Context）の設計原則

ドメインが大きくなっても、実装役の 1 呼び出しの文脈を**タスクの境界の大きさ**で抑える。原則と、それを機械で守らせる検査：

| # | 原則 | 機械の検査（v2prep・単位定義の門で落とす） |
|:--|:--|:--|
| N1 | **事実は一か所**。仕様は型（契約）・性質・参照データの定数だけで渡す。自然言語の要求は実装役に渡さない（題名 1 行まで） | 実装役の prompt に自然言語の要求の節が無い |
| N2 | **語彙の閉包**。プロンプトに出る ID・関数・定数は、すべてプロンプトの中で定義されている | 性質の無い仕様 ID が 0、定義の無い関数が 0、契約に無い PR が 0（PR は v2prep で検査済み） |
| N3 | **足跡で絞る**。性質ごとに読み書きするメンバー（`after.ActiveMino.X` → `ActiveMino.X`）を宣言から機械で抜き、このタスクの編集の足跡と交わる性質だけを見せる。交わらない性質は P2P の門が守り、破れたときだけ反例で見せる | 見せる性質の数が、タスク数ではなく足跡で決まる |
| N4 | **本体でなく境界**。読むだけの依存は宣言（シグネチャ）だけを埋め込む。interface の描画と契約の全文を二重に出さない。書き換えてよいファイルは、関心ごとに分けて小さく保つ（1 タスクが触る whitelist を小さくするのは、ゲームの側の設計の責務でもある） | 同じ型の宣言が二度出ない。書き換えてよいファイルの字数に上限 |
| N5 | **参照データは需要で**（v2.2 で導入）。性質と既存のコードが使う定数と表だけ | 済み（`prune_reference`） |
| N6 | **実装役の見る性質と、判定器の見る性質を分ける**。実行後の状態に依る絞り込み（F2）は判定器の側に置き、実装役には「前提（実行前と入力）→ 帰結」の形で見せる | 実装役に見せる前提に `after.` が無い |
| N7 | **文脈の予算を門にする**。要素ごとの字数を記録し（`prompt_chars` を節ごとに）、タスクをまたいで一定を超えて伸びたら止める | 予算超過で ABORT |

**Phase 4 への写し**：MuJoCo のような物理系では、境界は「状態・行動 → 次の状態」の 1 ステップと観測の型で、エンジンの本体は決して埋め込まない。物理定数は GddReference と同じく契約の定数にし、需要で絞る（N5）。性質（エネルギーの保存・接触の非貫通など）は許容誤差と地平（horizon）を仕様に持たせ（連続系の判定の破綻のリスク）、足跡（N3）で絞る。N1〜N7 はドメインに依らない。

### 4.2 仮説と指標

### 4.3 停止条件

- 走行中（`harness/ab/guard.py` の監視）：P2P の破壊、テストの改ざん、ABORT のどれかが出たら、その走行を止め、本走に進まない
- 1 条件の費用が v2-smoke-04 の B（1.0660 USD）の 2 倍を超えたら止める
- 本走（V2-RUN、N=4）へ進む条件：H0・H1・H2 がすべて成り立ち、結果の記録を人間と副操縦士が確認したこと

## 5. 合意が要ること

1. §0 の主張（B の文脈は N とコードの大きさに比例して伸びており、B の存在理由と矛盾する）を前提にしてよいか

4. §1.4 のキャッシュ（agy の制約）を、Phase 4 の設計で再検討する課題として残すか
