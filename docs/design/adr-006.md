# ADR-006 決定の権限と役の分け方（暫定の枠組み）

- 状態：提案（2026-10-23）。権限の決め直しで、実行役の利害が絡むので、操縦士がこの文書と根拠の記録を読んで決める。別系統のモデル（agy）の反論は、利用枠が戻ったら回して 6 節に足す
- 順序：ADR-005（部品の取捨、game-harness#276）より先に入れる。部品を選ぶ枠組みのほうが壊れていたため
- 書いた者：実行役。本来は 3 節の形で総監督が書くべき種類の文書だが、枠組みがまだ無いので、実行役が書いて操縦士が決める（この 1 回だけの例外）

## 1. 何が壊れていたか（2026-10-23 の操縦士の指摘）

| # | 症状 | 今日の実例 |
|:--|:--|:--|
| 1 | 判断の材料が人に見えない | 調べものの記録は Git の外（`C:\src\.local`）と未マージのブランチにあり、引継ぎも Git の外。チャットは `CLAUDE.md` の規則で進捗ツリーと 1 行の要約だけに絞られ、何を見て何を捨てたかが届く経路が無い |
| 2 | 人の承認が儀式になっている | 承認は「PR の番号を言う → 実行役がラベルを付ける」。中身と根拠を読んだかは、どこでも確かめていない |
| 3 | 判断・実行・検証を 1 つの役が握る | 実行役が ADR を書き、調べものの問いと候補を立て、同じ系統のモデルに調べさせ、その ADR を確かめる試験を書き、自分で完了にする。総監督には一度も回していない |
| 4 | 権限を「AI か人か」の二択で切っている | ADR-005 の「人の出番」も二択のまま書いた |

## 2. 調べたこと

俯瞰 2 件・比較 1 件・反証 1 件（`docs/research/R-20261023-g1`〜`g4`）。前提は P-023〜P-027（P-026 だけ弱い）。

- 承認は数が多いほど形だけになる。Claude Code の許可の確認は 93〜97% が承認され、監督の要点は全部を承認することでなく、介入できる位置にいること（P-023）
- LLM は自分の出力を高く評価し、外からの帰還が無いと誤りを直せない（P-024）
- 作る役と承認する役を分けるのが、規格と道具の標準。GitHub は、エージェントに PR を作らせた本人の承認を数えない（P-025）
- 書き込みは 1 か所に集め、他の役は助言だけを出す形が、今は最もうまくいく。役の並列はトークンが約 15 倍かかり、コーディングには向かない（P-027）
- 別系統のモデルの検めも誤りを共有する（弱い前提 P-026）。だから、検め役の助言だけを独立の検証とみなさない

## 3. 暫定の枠組み

### 3.1 役

| 役 | 中身 | しないこと |
|:--|:--|:--|
| 操縦士（人） | 目的を決める。下の「重い決定」を、記録を読んで決める。いつでも止められる | 機械的な操作と調べもの |
| 総監督（別の文脈のエージェント） | 方向の案（ADR）と改善の案を出す。読むのは決定の記録・実測の表・調べものの索引だけ | 書き込み（コードと台帳）。実行の細部を読むこと |
| 実行役（このセッション） | 唯一の書き込み役。案を実装し、戻せる小さな決定を自分で決めて記録する | 自分の採点・検証・物差しに関わる決定を確定すること。方向の ADR を自分で書いて自分で進めること |
| 検め役（別系統のモデル、実行役と文脈を共有しない） | 決定の記録と高い層の差分に、反論と助言を出す | 書き込み。合否を決めること |
| 機械（試験・出典の照合・必須チェック） | 合否を決める。検め役の誤りの共有（P-026）を補う | — |

### 3.2 決定の重さと、決める者

二択ではなく、次の 3 つの軸で分ける：戻せるか、目的や物差しを変えるか、実行役の利害が絡むか。

| 段 | 当てはまる決定 | 決める者 | 検める者 |
|:--|:--|:--|:--|
| 軽い | 戻せて、物差しにも実行役の利害にも触れない（PR を閉じる、ブランチの扱い、文書の整理） | 実行役 | 事後の抜き取り（操縦士が記録を読む） |
| 利害が絡む | 実行役の検証・試験・完了の条件・記憶を変える | 実行役は案まで | 検め役の助言と機械の照合を経て、操縦士が決める |
| 重い | 戻せない、または目的・物差し・権限を変える（ADR の採択、R4 の定義、門と計器の変更） | 操縦士 | 総監督の案、検め役の反論、根拠の記録を読んでから |

### 3.3 決定の記録

- すべての決定（軽いものも）を `docs/design/decision_log.md` に 1 行で残す。列は、日付・決定・段・見た資料（リンク）・決めた者・戻せるか
- 重い決定と利害が絡む決定は、調べものの記録を `docs/research/` に入れ、Git の中で辿れるようにする。Git の外の記録は根拠に使わない
- 操縦士への報告は、進捗ツリーに加えて「前回からの決定の記録の新しい行」を出す。チャットで判断の説明を禁じる今の規則は外す（`CLAUDE.md` の変更は、この ADR の採択の後に行う）

### 3.4 承認

- 人の承認は「重い」と「利害が絡む」だけに絞る（P-023）
- 承認は、記録と根拠を読んだうえで、何を決めたかを一文で書く形にする。番号を言うだけの承認は受けない
- 実行役が作った PR を、実行役が承認の代わりに扱うことはしない（P-025）

## 4. 1〜4 への対応

| # | 対応 |
|:--|:--|
| 1 | 3.3 の決定の記録と、根拠を Git に入れる規則 |
| 2 | 3.4 の、承認を絞り、読んだうえでの承認に替える規則 |
| 3 | 3.1 の役の分離。実行役は書き込みだけを握り、方向と検証を握らない |
| 4 | 3.2 の 3 つの軸による段 |

## 7. 崩れたら直す前提

- P-027 は、コーディングで書き込みを 1 か所に集める形の、1 人での運用の実測が無い。総監督と実行役の食い違いが記録に 2 回出たら、役の境目を見直す
- 1 人の運用での人の時間を測った出典が無い。操縦士が記録を読む時間が週に 1 時間を超えたら、「軽い」の段を広げる
