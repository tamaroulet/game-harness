## 1. 目的と原則

後続の A/B 比較実験（Step 11）で、外部から反論の余地がない客観的なデータを残す。そのために、仕様の決定をすべて機械で追える形にする。

1. **決定は GDD とコミット履歴にだけ残す。** 構造化仕様に「仮」の値か質問が 1 つでも残っていれば、機械的にマージできない。人間がその値のまま承認する道は無い。値を決めたいときは、人間が GDD に書き足して版を上げ、再送する
2. **構造化役は推測で値を埋めない。** 一般的な落ちものパズルの常識で仕様を補わない（ハードドロップ・ゴースト・ホールド・SRS は Step 11 で後から足す実験用の機能で、ベースラインに入れてはならない）
3. **検査は決定論的に行う。** 網羅・参照・書式・禁止語の判定に LLM を使わない
4. **機械で判定できるものは人間に回さない（H1 と H2 の分離）。** パズルの論理・得点・ライン消去・勝敗は Pure C# のテスト（H1）で判定する。人間確認（HC）は演出と手触りだけ
5. **読めなければ止まる。** 書式が崩れている・根拠が無い・参照先が無いときは、既定値で補わず NG にする
6. **承認は人間だけが行う。** エージェント（Claude・スケジューラ）は `ms4:approved` を付けず、`dispatch --approve` も実行しない（§11.5）

```
            head の docs/gdd/source.md の sha256 に処理済みのマーカー（ms4:gdd-processed:<sha256>）の
            コメントがあれば触らない（再処理しない。自分の push で head が変わっても同じ GDD なら飛ばす）
            錨の事前検査（gdd_check.precheck。LLM を呼ばない）→ 足りなければマーカーつきで一覧をコメントし ms4:questions

            それ以外が変わっていれば ABORT。§11.4）。worktree と作業用のローカルブランチは消す
            マーカーつきで検査結果（仮・質問・錨の欠落・HC・候補語・ID の変化）をコメントする

```

## 3. 入力: GDD

- 置き場: ゲームのリポジトリの `docs/gdd/source.md`（dispatch が下書きとバイト単位で同じものを置く。LF、末尾の改行 1 つ）
- 先頭 2 行: `<!-- project: <id> -->` と `<!-- version: <正の整数> -->`
- **行番号の基準はこのファイル**（メタデータの 2 行を含む。1 始まり）。spec の根拠列はこの行番号を書く
- **書き方の制約（S11）**: dispatch の禁止規則（`.cs`・`Assets/`・CamelCase に `State` `Rules` `Controller` などが付いた語・テスト件数・`golden` `受入条件` など）は GDD にも当たる。錨（§5）は、コード上の名前を書かず、日本語の名前と数値の表で書く
- **錨の事前検査に通る書き方（B-2d）**: 語「ティック」「XorShift32」「シード」「不変条件」をそのまま書く。形状の座標は `(x, y)` の形（整数）で、7 種 × 4 方向 × 4 ブロック = 112 組以上を書く（`config/gdd_check.json` の `precheck`）。事前検査に通らない GDD では構造化役（LLM）を呼ばない

## 4. 出力: 構造化仕様

### 4.1 `docs/spec/spec.md`

先頭に次のメタデータを置き、どの GDD から作ったかを残す。

```
<!-- project: falling-blocks -->
<!-- gdd-version: 1 -->
<!-- gdd-sha256: <source.md の sha256> -->
```

節の見出し・順序・表の列は固定する（崩れていれば NG）。どの行にも根拠列を置く。

| 節（見出し） | ID | 列 |
|:--|:--|:--|
| `## 1. ループと終了条件` | `LP-nn` | ID / 内容 / 根拠 |
| `## 2. 状態遷移` | `ST-nn` | ID / 状態 / 契機 / 遷移先 / 根拠 |
| `## 3. 規則と計算式` | `RL-nn` | ID / 規則・式 / 境界値 / 参照パラメーター / 根拠 |
| `## 4. 公開インターフェース` | `IF-nn` | ID / 公開する状態・操作 / 型・範囲 / 根拠 |
| `## 5. 外部パラメーター` | `PR-nn` | ID / 名前 / 値 / 区分 / 根拠 |
| `## 6. 人間確認・演出` | `HC-nn` | ID / 内容 / 根拠 |

- `nn` は 2 桁以上の数字。ID は文書の中で重複しない
- 根拠: `L<行>` または `L<行>-L<行>` を `, ` で区切って並べる（例 `L26, L34-L35`）
- 区分: `確定` か `仮` のどちらか。`仮` は「GDD に値が無く、構造化役が既定値を置いた」ことを表す
- 行が 1 つも無い節は、表に `| （該当なし） | … |` の 1 行だけを置く（節そのものは省略しない）
- 参照パラメーター: `PR-nn` を `, ` で区切って並べる。無ければ `-`

### 4.2 `docs/spec/questions.md`

同じメタデータ 3 行と、見出し `## 質問` の下に 1 つの表。

| 列 | 内容 |
|:--|:--|
| ID | `Q-nn` |
| 質問 | GDD から決められないこと。選択肢を並べてもよいが、推奨を書かない |
| 根拠 | 疑問の元になった GDD の行（§4.1 と同じ形） |
| 推測で決めない理由 | なぜ既定値を置かなかったか |

質問が無ければ `| （該当なし） | … |` の 1 行。

## 5. 基盤ゲームモデル（spec に必ず含める定量的な錨）

A/B 実験で、マシンの負荷や環境によるぶれと、実装役とオラクル（テスト）の解釈のずれによる偽陽性を排除するため、spec は次を必ず含む。
**spec の行はすべて GDD に根拠を持つ（§1-2）。したがって錨は人間が GDD に書く（S1）。** harness 側に共通の錨を置いて GDD を経由せずに注入することはしない（決定が GDD の外に出るため）。GDD に錨が無ければ、spec では `仮` か質問になり、§7 によってマージできない。

**検査器での扱いは 2 種類に分ける（B-2b で確定）。** 錨が見当たらないことは spec の不備ではなく GDD の不足なので、**合格のまま `mergeable` を偽にする**（要約の `anchors_missing`。構造化役に作り直させても直らない）。錨の書き方の誤りは spec の不備なので **NG**（構造化役に作り直させる）。

| # | 錨 | spec での置き場（検査器が読む書き方） | 欠落（mergeable を偽に） | 誤り（NG） |
|:--|:--|:--|:--|:--|
| A1 | **時間は整数ティック。** 1 ティック = 1/60 秒。ロジックは実時間（秒・`Time.deltaTime`・時計）に依存しない。**外から時間を進める操作は「n ティック進める（n は非負の整数）」だけを公開し、秒（浮動小数）での注入は設けない（S8）**。落下・ロック猶予・ソフトドロップ・計時はすべてティック数で表す。テストは実時間の待機をしない | RL（各規則はティック数で書く）、IF（ティックを進める操作）、PR（各間隔のティック数） | RL か IF に「ティック」を含む行が無い | IF の「公開する状態・操作」「型・範囲」に `秒`・`浮動小数`・`float`・`double` がある |
| A2 | **幾何の一意固定。** 7 種類（I, O, T, S, Z, J, L）それぞれの 4 ブロックの初期相対座標、回転原点、4 方向の回転後の相対座標を数値の表で固定する | PR の行。名前は `形状 <種類> 向き <0/R/2/L>`（値は異なる 4 組の整数の `(x, y)` を空白で区切る）と `形状 <種類> 回転原点`（値は `(x, y)` 1 組。x, y は整数か .5） | 7 種類のどれかで、4 方向か回転原点の行が無い | 名前の種類・向きが不正、座標が 4 組でない・重複・整数でない・余計な文字、回転原点の形が不正 |
| A3 | **乱数の決定論性（S4）。** 7-Bag は 32 ビット符号なし整数のシードを外から注入できる。**生成器は XorShift32 に固定し、式（シフト量と順序）、シードが 0 のときの扱い、Fisher-Yates の手順（どの乱数をどの順に何回引き、どう範囲に落とすか）を spec に書く。** .NET の `System.Random` は使わない（dotnet と Unity で数列が一致する保証が無い） | IF（シードの注入）、RL（生成器の式とシャッフルの手順） | IF に「シード」を含む行が無い、または RL に「XorShift32」を含む行が無い | どの行にも `System.Random` がある |
| A4 | **保存則（不変条件のオラクル）。** 例: 消去ライン数 × 10 ＋ 盤面（バッファ行を含む 22 行）のブロック数 ＝ 4 × ロックしたミノの数 | RL の行で、「規則・式」が `不変条件:` で始まるもの | そのような行が 1 つも無い | - |
| A5 | **H1 と H2 の分離。** 論理・得点・ライン消去・勝敗を HC に回さない | HC は演出・手触りだけ | - | §6.8 |

検査器が読む語（`ティック`・`シード`・`XorShift32`・`不変条件:`）と正規表現は `config/gdd_check.json` の `anchors` に置く。「行がある」ことしか機械では確かめられない（式の中身が正しいかは、承認で人間が見る）。

## 6. 検査器 `harness/gdd_check.py`（B-2b）

入力: `source.md`、`spec.md`、`questions.md`、main にある前の版の `spec.md`（あれば）、プロジェクトの禁止語。出力: 合否と、承認コメント用の要約（JSON）。

### 6.1 書式
§4 の見出し・順序・列・ID の形式と重複・メタデータ（`gdd-sha256` が `source.md` と一致すること）

### 6.2 根拠
行番号が GDD の範囲内であること。分母から外した行（§6.4）だけを指す根拠は NG

### 6.3 網羅
GDD の対象行（§6.4 で外した行を除く全行）が、spec・questions のどこかの根拠に必ず現れること。拾い落としは、行番号と本文を並べて NG

### 6.4 分母から外す行
規則は `config/gdd_check.json` の正規表現リストに置き、各規則にテストを付ける。外した行数は規則ごとに出す（分母を黙って減らさない）。

| 規則 | 例 |
|:--|:--|
| 空行・空白だけの行 | |
| 見出し | `^#{1,6}\s` |
| 水平線 | `^\s*([-*_])(\s*\1){2,}\s*$` |
| コードフェンスの行（**中身は外さない**） | `^\s*(```\|~~~)` |
| 表の区切り行 | `^\s*\|?\s*:?-+:?\s*(\|\s*:?-+:?\s*)*\|?\s*$` |
| HTML コメントだけの行（先頭メタデータを含む） | `^\s*<!--.*-->\s*$` |
| 記号だけの行 | `^\s*[-*+]\s*$` |

見出しの文言は網羅の対象にしないが、根拠の行番号から所属する見出しを辿り、承認コメントに表示する。

### 6.5 参照
本文中の `LP-` `ST-` `RL-` `IF-` `PR-` `HC-` `Q-` の ID がすべて実在すること。参照パラメーター列は `PR-` だけ

### 6.6 禁止語（プロジェクトごと。S5）
- 置き場: harness の `projects/<id>/spec_terms.json`（ゲームごとの値なので共通設定に置かない）。ファイルが無いゲームは禁止語なし
- 照合: 大文字小文字を区別しない。英字の語は単語境界で照合する（`threshold` の中の `hold` に当てない）
- falling-blocks の初期一覧（Step 11 の実験用機能）

  | 機能 | 語 |
  |:--|:--|
  | ハードドロップ | ハードドロップ、瞬間落下、即時落下、hard drop、harddrop |
  | ゴースト | ゴースト、着地予測、着地予想、ghost |
  | ホールド | ホールド、ストック、hold |
  | SRS | SRS、スーパーローテーション、Super Rotation System、壁キック、wall kick、T-spin、Tスピン |

- spec.md・questions.md に禁止語が現れたら NG。**例外は、その語が GDD の根拠行にそのまま現れ、かつ spec の行がその根拠行を引いている場合だけ**（GDD 自身が「壁キック等の位置補正は行わない」と否定している語を引くため）
- 質問（questions.md）にも適用する（「ハードドロップを入れますか」という質問で機能を誘導させない）
- **一覧は漏れる前提で扱う。** 要約に「GDD に現れない語で、spec に現れた機能名らしい語」の候補（カタカナ語・英字の語）を並べ、承認コメントに表示して人間の見落としを減らす

### 6.7 「仮」・質問・錨の欠落の数
数えて要約に出す。**合否（書式として正しいか）とは分ける。** 0 件でないことは spec の不備ではなく、GDD の不足を表す（§7）。要約の `passed`（合否）と `mergeable`（合格かつ「仮」・質問・錨の欠落がすべて 0）を別々に出す。終了コードは合否だけで決める（0 合格 / 1 不合格 / 2 環境異常）

### 6.8 HC の近似検査（S6）
HC の行の「内容」に、数字・比較演算子（`<` `>` `=` `≤` `≥`）・ID 参照（`PR-` など）・ティックの語があれば NG。HC にロジックが無いことを完全には判定できないので、承認コメントに HC の全行を表示する。GDD v1 には演出の行が無いので、HC は `（該当なし）` になるはず

### 6.9 ID の継続性（S3）
- main に前の版の `spec.md` があれば、ID の集合を比べる
- **消えた ID は再利用しない。** 機械で確かめられる形にするため、**新しく現れた ID の番号は、前の版にあった同じ接頭辞の最大番号より大きくなければ NG** とする（前の版だけを見ても、それより昔に消えた番号の再利用を防げるように、番号は増える一方にする）
- 同じ ID の行の本文（根拠の列を除く）が変わったものは「変わった ID」として要約に出す。根拠の行番号だけがずれたものは変わっていないとみなす（版上げで行番号はずれるため）
- 要約に「残った ID・変わった ID・消えた ID・新しい ID」を出す。構造化役には前の版の spec を渡し、変わらない行の ID を保たせる（§2）。前の版の spec が読めなければ環境異常（終了コード 2）

## 7. マージの条件

GDD の PR は、次がすべて成り立つときだけマージできる。

1. 検査器が合格（§6.1〜6.6、§6.8、§6.9）
2. questions.md の質問が 0 件
3. spec.md の区分 `仮` が 0 件
4. 錨の欠落（§5、要約の `anchors_missing`）が 0 件
5. 人間の承認と `test` が緑

**2・3 は必須チェック `approval` の中で機械的に判定する（S2）。** 4 の錨の欠落をゲートでどう判定するか（ゲートが検査器を実行するのか、検査器の要約を信用するのか）は B-2d で決める（要約は PR の head に置かれ、PR の中で書き換えうるため、そのまま信用はできない）。 承認ゲート（`harness/templates/game-repo/.github/scripts/ms4_approval_gate.py`）は、PR が `docs/spec/**` を変えるとき、PR の head の `questions.md` と `spec.md` を API で読み、質問と `仮` が 1 つでもあれば、承認ラベルがあっても赤にする。ゲートは base 側の定義で動くので、PR の中から判定を外せない。ルールセットは変えない。

- スケジューラは、2・3 が満たされない PR には `ms4:questions` を付け、承認依頼を出さない。dispatch の `--approve` は今の head への承認依頼が無いと拒否する
- **ゲートの変更は、各ゲームのリポジトリの main に配備されて初めて効く（S15）。** 配備は各リポジトリへの PR で行い、B-2d の完了条件に含める。テンプレートと各リポジトリの写しが一致することを harness のテストで確かめる（リモートの写しを読む）

## 8. 再現性の記録

LLM の出力は同じ入力でも毎回変わる。再現性は「作り直すと同じものができる」ことではなく、「**何を入力に、何を使って、何ができたかが後から完全に分かる**」ことで担保する。PR のコメントと `runs.jsonl` に次を残す。

- GDD の版・`source.md` の sha256
- harness の SHA（検査器・構造化役・プロンプトの版はこれで決まる）
- 構造化役の CLI のバージョン・**モデル名**（設定で固定する。S7）・プロンプトの sha256
- 試行ごとの検査結果（NG の理由）と試行回数
- 合格した spec.md・questions.md の sha256（コミットそのもの）
- **GDD の再送で古い PR を閉じるとき、閉じる PR の head SHA をコメントに残す（S17）。** dispatch は古い PR のブランチを削除するが、GitHub は `refs/pull/<N>/head` を残すので、その SHA から構造化の試行を辿れる

## 10. 検証（B-2 全体）

- 検査器の変異テスト: 網羅・根拠・参照・書式・禁止語・HC・ID の継続性・「仮」と質問の数え方の各規則を外すと、テストが赤になること
- 構造化役の出力から 1 行消すと網羅検査が NG になること
- 承認ゲート: `ms4:approved` があっても、質問か `仮` が残る spec の PR では赤になること。spec を変えない PR の判定は変わらないこと
- falling-blocks の GDD v1: 構造化まで通り、S9 の曖昧さと錨の欠落が質問か `仮` になり、`ms4:questions` が付いて承認依頼が出ないこと。禁止語が spec に現れないこと
- GDD v2（錨と S9 の値を書いたもの）: 質問 0・`仮` 0 で承認依頼が出て、承認でマージされること

## 11. 実装・運用の制約（S12〜S20 から）

### 11.1 実装役への禁止パターン（S12・S13）
Pure C# の実装（`impl_roots`）に対する禁止パターンを、§5 の錨に合わせて足す。

| 目的 | 禁止するもの |
|:--|:--|
| 乱数は XorShift32 だけ（A3） | `System.Random`・`new Random(`（引数の有無を問わない）・`UnityEngine.Random` |
| 時間は整数ティックだけ（A1） | `Time.`（`deltaTime` 等）・`DateTime.Now` / `UtcNow`・`Stopwatch`・`Environment.TickCount`・`Thread.Sleep`・`Task.Delay` |

テストのコードにも、実時間の待機（`Thread.Sleep`・`Task.Delay`・`WaitForSeconds`）を禁止する。

### 11.2 置き場の制約（S14）
いまの harness は契約（`.harness.toml`）を読まず、禁止パターンは共通設定（`config/decompose.json`）から全ゲームに効く。§11.1 を共通設定に足すと unity-2d の既存コードを壊しうる。
**契約の読み込み（`contract.md` §6.7 の手順 1）を先に入れ、§11.1 は falling-blocks の契約にだけ書く。** 契約の読み込みが入るまで、§11.1 の禁止は効いていない（B-2d の前提条件にする）。

### 11.3 ゲームごとの値の置き場
禁止語（§6.6）はゲームごとの値なので、harness の `projects/<id>/` に置く。契約の読み込みが入ったあとで契約へ移すかは、契約側の改定で決める。

### 11.4 保護するパス（S16）
- 契約の組み込みの禁止（`contract.md` §5.2）に `docs/gdd/**` と `docs/spec/**` を足す（実装役・分解役に GDD と構造化仕様を書き換えさせない）
- B-2d のスケジューラが GDD の PR にコミットしてよいのは `docs/spec/**` だけ。それ以外が変わっていれば ABORT

### 11.5 承認者の識別（S18）
- スケジューラ・dispatch・エージェント（Claude）は同じ GitHub アカウントで動いており、承認ゲートは「誰が」ラベルを付けたかを人とエージェントで区別できない
- **運用: エージェントは `dispatch --approve` を実行せず、`ms4:approved` を付けない。** 人間から承認の実行を頼まれても、人間に実行してもらう
- 恒久策: スケジューラとエージェントに別のアカウント（またはボットのトークン）を割り当て、承認者の一覧（`.github/ms4-approvers`）には人間のアカウントだけを置く。導入の時期は別に決める

### 11.6 スケジューラの同時実行（S19）
ロック（`lock_path`）と停止ファイルはマシンに 1 つで、常駐は 1 つのプロジェクトだけを扱う。**意図として明記する: 1 台で同時に動かすスケジューラは 1 つ**（Unity のバッチ実行を重ねず、計測のぶれを避ける）。複数のゲームを常駐で扱う必要が出たら、1 つのプロセスで順に巡回する設計を別に決める。

### 11.7 C2 への引き継ぎ（S10・S20）
- 分解役の出力（単位定義）に `spec_refs`（spec の行 ID の一覧）を必須にし、存在する ID かを検査する（`config/decompose.json` の `required_keys`）
- GDD の版上げで既存の RL・ST・IF が変わるときは、変わった行を `ms4:spec-change` の Issue に展開する（`spec-change.md` §3.2 に繋ぐ）

## 14. 閉世界仕様化プロトコル（CWA、2026-09-18、人間の決定）

### 14.1 なぜ §1-2 を変えたのか

初版の §1-2 は「構造化役は推測で値を埋めない。GDD から決まらないものは質問にする」だった。falling-blocks の GDD v2〜v7 でこれを実測した結果、**質問は収束しなかった**。

| 版 | 質問 | 内容の性質 |
|:--|:--|:--|
| v2 | 10 | 核心（乱数のシフト量、ティック内順序、シード 0） |
| v3 | 9 | 核心（回転遷移順、GameOver 後の入力） |
| v4 | 4 | 整合性（回転原点と整数座標の矛盾、離散入力と落下間隔の矛盾） |
| v5 | 5 | 境界（同時入力、Ready 時入力、天井、タイマー初期値） |
| v6 | 4 | 微視（消去走査範囲、接地時のカウンタ満了、シード注入可能状態） |
| v7 | 2 | **基盤層**（Ready 時の非存在オブジェクトの表現、複数ティック進行時の入力消費） |

内容は核心から基盤層へ単調に移ったが、件数はゼロにならない。v7 の 2 件は「ゲーム設計者が決めること」ではなく「実行基盤が定めるべき規約」であり、**これを人間に散文で書かせているのはプラットフォームの責任放棄**である。

要求工学の $W, S \vdash R$（Jackson & Zave）では、人間の要求（R）と実行基盤の前提（W）は分離される。W3C SCXML・Erlang/OTP・Microsoft Research の P 言語はいずれも、未規定イベントの破棄・非存在の null 表現といったデフォルト意味論を **基盤側の規約として明文化**して隙間を閉じている。同じ形を採る。

### 14.2 規約（`harness/templates/spec_prompt.md` の第 1 規則）

GDD に明示の記述が無い境界・例外の挙動は、次の決定論的な規約で確定させる。区分は `確定`。

| 対象 | 既定 |
|:--|:--|
| 未規定の操作・非稼働状態での入力 | No-op（状態を変えず、入力を破棄） |
| 初期状態で存在しないオブジェクト | `null` / 未配置 / 空のコレクション |
| 複数ティックをまとめて進めるときの入力 | 先頭のティックにだけ適用、以降は入力なし |
| タイマー・カウンタの未規定の例外 | Hold か 0 リセット（同種のカウンタには同じ扱い） |

**構造化役が規約を自分で増やすことは禁止**（表に無いものを常識で補ってはいけない）。

### 14.3 質問の扱い

**未規定・不完全を理由とする質問を禁止する。** 質問してよいのは、**GDD の 2 つの記述が矛盾していて、どちらが正しいか規約では決められないとき**だけ（未規定ではなく誤りの指摘）。§7 のマージ条件は変えない。

### 14.4 出所の明示（`[Origin: CWA]`）

「AI が仕様を捏造している」という批判に答える唯一の手段は、**人間が決めたことと機械が決めたことの境目を、承認する人間に見せること**である。

- 規約で確定させた行は、根拠列の末尾に `[Origin: CWA]` を付ける（例 `L98-L101 [Origin: CWA]`）
- **行番号は省略できない。** 規約が当てはまる GDD の箇所を必ず指す。`[Origin: CWA]` だけの根拠は不合格（根拠の無い行を作る抜け道を塞ぐ）
- 許す出所の名前は `config/gdd_check.json` の `origins`。コードに直書きしない
- 要約の `derived` に載り、検査結果のコメントに一覧が、承認依頼に件数が出る

**合否には使わない（マージを止めない）。** 門にすると、通すためにタグを付けない／付けるという最適化が起き、Goodhart の法則で信号が消える。**出所は「不在の検出」であって「充足の証明」ではない**（被参照チェックと同じ扱い。§13.1 の 3）。

### 14.5 この決定が変えるもの

実験の記録では、SDD の各行が「人間が GDD に書いた決定」か「基盤の規約から演繹した決定」かを機械的に数えられるようになる。§1-1「決定は GDD とコミット履歴にだけ残す」は、**「決定は GDD か、明文化された基盤規約のどちらかに残り、どちらであるかが行ごとに分かる」**へ広がる。
