# フェーズ B: GDD → 構造化仕様のプロトコル

- 状態: 設計（B-2a）。コードはまだ無い。検査器（B-2b）・構造化役（B-2c）・スケジューラへの接続（B-2d）はこの文書に従って作る
- 前提: harness `a7c2aa0`（ラベル `ms4:gdd`）、dispatch `a0173cc`（`--submit-gdd`）、falling-blocks PR #3（GDD v1、66 行）
- 決定（2026-09-17、人間）: §1 の原則、§4 の書式、§5 の基盤モデル、§6.6 の禁止語、§7 のマージ条件

## 1. 目的と原則

後続の A/B 比較実験（Step 11）で、外部から反論の余地がない客観的なデータを残す。そのために、仕様の決定をすべて機械で追える形にする。

1. **決定は GDD とコミット履歴にだけ残す。** 構造化仕様に「仮」の値か質問が 1 つでも残っていれば、機械的にマージできない。人間がその値のまま承認する道は無い。値を決めたいときは、人間が GDD に書き足して版を上げ、再送する
2. **構造化役は推測で値を埋めない。** 一般的な落ちものパズルの常識で仕様を補わない（ハードドロップ・ゴースト・ホールド・SRS は Step 11 で後から足す実験用の機能で、ベースラインに入れてはならない）
3. **検査は決定論的に行う。** 網羅・参照・書式・禁止語の判定に LLM を使わない
4. **機械で判定できるものは人間に回さない（H1 と H2 の分離）。** パズルの論理・得点・ライン消去・勝敗は Pure C# のテスト（H1）で判定する。人間確認（HC）は演出と手触りだけ
5. **読めなければ止まる。** 書式が崩れている・根拠が無い・参照先が無いときは、既定値で補わず NG にする

## 2. 流れ

```
人間        drafts/gdd/<project>.md を書く（先頭 2 行にメタデータ）
dispatch    --submit-gdd → ブランチ spec/gdd-v<版> に docs/gdd/source.md、PR（ms4:gdd）            [B-1 済み]
scheduler   ms4:gdd の PR を拾う → PR のブランチを取り出す                                         [B-2d]
spec.py     構造化役（Claude CLI）が docs/spec/spec.md と docs/spec/questions.md を作る             [B-2c]
gdd_check   書式・根拠・網羅・参照・禁止語・「仮」と質問の数を検査する                               [B-2b]
            NG（書式や網羅の不備）→ 理由を渡して構造化役に作り直させる（上限あり）→ それでも NG なら PR にコメントして止める
scheduler   合格した spec を PR のブランチにコミットする
            質問 0 件かつ「仮」0 件 → ms4:awaiting-approval と承認依頼
            それ以外                → ms4:questions と質問・「仮」の一覧。承認依頼は出さない
人間        dispatch --approve（questions のときは GDD を直して版を上げ、--submit-gdd で再送。古い PR は閉じられる）
scheduler   承認済み・必須チェック緑 → マージ（C2 で、spec の行からタスク Issue を作る）
```

## 3. 入力: GDD

- 置き場: ゲームのリポジトリの `docs/gdd/source.md`（dispatch が下書きとバイト単位で同じものを置く。LF、末尾の改行 1 つ）
- 先頭 2 行: `<!-- project: <id> -->` と `<!-- version: <正の整数> -->`
- **行番号の基準はこのファイル**（メタデータの 2 行を含む。1 始まり）。spec の根拠列はこの行番号を書く

## 4. 出力: 構造化仕様

### 4.1 `docs/spec/spec.md`

先頭に同じ形のメタデータを置き、どの GDD から作ったかを残す。

```
<!-- project: falling-blocks -->
<!-- gdd-version: 1 -->
<!-- gdd-sha256: <source.md の sha256> -->
```

節の見出し・順序・表の列は固定する（崩れていれば NG）。どの行にも根拠列を置く。

| 節（見出し） | ID | 列 |
|:--|:--|:--|
| `## 1. ループと終了条件` | `LP-nn` | ID / 内容 / 根拠 |
| `## 2. 状態遷移` | `ST-nn` | ID / 状態 / 契機 / 遷移先 / 根拠 |
| `## 3. 規則と計算式` | `RL-nn` | ID / 規則・式 / 境界値 / 参照パラメーター / 根拠 |
| `## 4. 公開インターフェース` | `IF-nn` | ID / 公開する状態・操作 / 型・範囲 / 根拠 |
| `## 5. 外部パラメーター` | `PR-nn` | ID / 名前 / 値 / 区分 / 根拠 |
| `## 6. 人間確認・演出` | `HC-nn` | ID / 内容 / 根拠 |

- `nn` は 2 桁以上の数字。ID は文書の中で重複しない
- 根拠: `L<行>` または `L<行>-L<行>` を `, ` で区切って並べる（例 `L26, L34-L35`）
- 区分: `確定` か `仮` のどちらか。`仮` は「GDD に値が無く、構造化役が既定値を置いた」ことを表す
- 行が 1 つも無い節は、表に `| （該当なし） | … |` の 1 行だけを置く（節そのものは省略しない）
- 参照パラメーター: `PR-nn` を `, ` で区切って並べる。無ければ `-`

### 4.2 `docs/spec/questions.md`

同じメタデータ 3 行と、1 つの表。

| 列 | 内容 |
|:--|:--|
| ID | `Q-nn` |
| 質問 | GDD から決められないこと。選択肢を並べてもよいが、推奨を書かない |
| 根拠 | 疑問の元になった GDD の行（§4.1 と同じ形） |
| 推測で決めない理由 | なぜ既定値を置かなかったか |

質問が無ければ `| （該当なし） | … |` の 1 行。

## 5. 基盤ゲームモデル（spec に必ず含める定量的な錨）

A/B 実験で、マシンの負荷や環境によるぶれと、実装役とオラクル（テスト）の解釈のずれによる偽陽性を排除するため、spec は次を必ず含む。
**ただし、spec の行はすべて GDD に根拠を持たなければならない（§1-2）。GDD に無い錨は、`仮` か質問になり、§7 によってマージできない。** したがって、これらは人間が GDD に書く（§10 の S1）。

| # | 錨 | spec での置き場 | 検査器での扱い |
|:--|:--|:--|:--|
| A1 | **時間は離散ステップ。** ロジックは実時間（秒・`Time.deltaTime`）に依存しない。1 ティック = 1/60 秒の整数ティックで進める。外部から時間を進める操作（例: n ティック進める）を持つ。テストは実時間の待機をしない | RL（落下・ロック猶予・ソフトドロップの間隔はティック数）、IF（時間を進める操作）、PR（各間隔のティック数） | RL・IF に「ティック」を単位とする行が無ければ NG |
| A2 | **幾何の一意固定。** 7 種類（I, O, T, S, Z, J, L）それぞれの 4 ブロックの初期相対座標、回転原点、4 方向の回転後の相対座標を数値の表で固定する | PR（形状ごとの座標表）、RL（回転の規則は表を参照する） | 7 種類 × 4 方向の座標が揃っていなければ NG |
| A3 | **乱数の決定論性。** 7-Bag は整数のシードを外から注入できる。**生成器のアルゴリズムと、シャッフルの手順（どの乱数をどの順に何回引くか）も固定する**（§10 の S4） | IF（シードの注入）、RL（生成器とシャッフル） | IF にシードの行が無い、または RL に生成器の式が無ければ NG |
| A4 | **保存則（不変条件のオラクル）。** 例: 消去ライン数 × 10 ＋ 盤面（バッファ行を含む 22 行）のブロック数 ＝ 4 × ロックしたミノの数 | RL（不変条件と明記した行） | 不変条件の行が 1 つも無ければ NG |
| A5 | **H1 と H2 の分離。** 論理・得点・ライン消去・勝敗を HC に回さない | HC は演出・手触りだけ | HC の行に数値・比較・ID 参照（`PR-` など）があれば NG（§10 の S6） |

## 6. 検査器 `harness/gdd_check.py`（B-2b）

入力: `source.md`、`spec.md`、`questions.md`、プロジェクトの禁止語。出力: 合否と、承認コメント用の要約（JSON）。

### 6.1 書式
§4 の見出し・順序・列・ID の形式と重複・メタデータ（`gdd-sha256` が `source.md` と一致すること）

### 6.2 根拠
行番号が GDD の範囲内であること。分母から外した行（§6.4）だけを指す根拠は NG

### 6.3 網羅
GDD の対象行（§6.4 で外した行を除く全行）が、spec・questions のどこかの根拠に必ず現れること。拾い落としは、行番号と本文を並べて NG

### 6.4 分母から外す行
規則は `config/gdd_check.json` の正規表現リストに置き、各規則にテストを付ける。外した行数は規則ごとに出す（分母を黙って減らさない）。

| 規則 | 例 |
|:--|:--|
| 空行・空白だけの行 | |
| 見出し | `^#{1,6}\s` |
| 水平線 | `^\s*([-*_])(\s*\1){2,}\s*$` |
| コードフェンスの行（**中身は外さない**） | `^\s*(```\|~~~)` |
| 表の区切り行 | `^\s*\|?\s*:?-+:?\s*(\|\s*:?-+:?\s*)*\|?\s*$` |
| HTML コメントだけの行（先頭メタデータを含む） | `^\s*<!--.*-->\s*$` |
| 記号だけの行 | `^\s*[-*+]\s*$` |

見出しの文言は網羅の対象にしないが、根拠の行番号から所属する見出しを辿り、承認コメントに表示する。

### 6.5 参照
本文中の `LP-` `ST-` `RL-` `IF-` `PR-` `HC-` `Q-` の ID がすべて実在すること。参照パラメーター列は `PR-` だけ

### 6.6 禁止語（プロジェクトごと）
- 置き場: harness の `projects/<id>/`（falling-blocks: ハードドロップ・ゴースト・ホールド・SRS。§10 の S5 で英語表記と言い換えを足す）
- spec.md・questions.md に禁止語が現れたら NG。**例外は、その語が GDD の根拠行にそのまま現れ、かつ spec の行がその根拠行を引いている場合だけ**（GDD 自身が「行わない」と否定している語を引くため）
- 質問（questions.md）にも適用する（「ハードドロップを入れますか」という質問で機能を誘導させない）

### 6.7 「仮」と質問の数
数えて要約に出す。**合否（書式として正しいか）とは分ける。** 0 件でないことは spec の不備ではなく、GDD の不足を表す（§7）

## 7. マージの条件

GDD の PR は、次がすべて成り立つときだけマージできる。

1. 検査器が合格（§6.1〜6.6）
2. questions.md の質問が 0 件
3. spec.md の区分 `仮` が 0 件
4. 人間の承認（必須チェック `approval`）と `test` が緑

2・3 が満たされない PR には `ms4:questions` を付け、承認依頼を出さない。dispatch の `--approve` は今の head への承認依頼が無いと拒否するので、dispatch からは承認できない。
**GitHub の画面から `ms4:approved` を付けた場合の扱いは §10 の S2 で決める**（現状の必須チェックは spec を見ていない）。

## 8. 再現性の記録

LLM の出力は同じ入力でも毎回変わる。再現性は「作り直すと同じものができる」ことではなく、「**何を入力に、何を使って、何ができたかが後から完全に分かる**」ことで担保する。PR のコメントと `runs.jsonl` に次を残す。

- GDD の版・`source.md` の sha256
- harness の SHA（検査器・構造化役・プロンプトの版はこれで決まる）
- 構造化役の CLI のバージョン・**モデル名**（§10 の S7）・プロンプトの sha256
- 試行ごとの検査結果（NG の理由）と試行回数
- 合格した spec.md・questions.md の sha256（コミットそのもの）

## 10. 構造的な問題と未決事項（B-2b の着手前に決める）

| # | 問題 | 何が起きるか | 推奨 |
|:--|:--|:--|:--|
| S1 | **§5 の錨と §1-2（根拠の無い値は置かない）が衝突する** | GDD v1 には、ティック・7 種×4 方向の座標表・シードと生成器・保存則が書かれていない。錨を spec に入れると根拠が無く、入れないと §5 を満たさない。v1 は必ず `ms4:questions` になる | 人間が GDD v2 に錨を書く（座標表を含む）。§7 の原則（決定は GDD にだけ残す）と一致する。harness 側に「共通の錨」を置いて GDD を経由せず注入する案は、決定が GDD の外に出るので採らない |
| S2 | **「仮・質問が残ればマージ不可」を機械で強制する場所が無い** | 必須チェック `approval` は、ラベルと承認者と head SHA しか見ない。スケジューラが承認依頼を出さないだけでは、GitHub の画面から承認ラベルを付ければ通る（プレイ確認と同じ穴） | 必須チェックの中で spec を検査する。候補: (a) 承認ゲートが `docs/spec/**` を変える PR で questions.md と `仮` を数える、(b) 新しい必須チェック `spec`（ルールセットの変更が要る）。**(a) を推奨**（ルールセットを変えず、base 側の定義で動くので PR から骨抜きにできない） |
| S3 | **版を上げると spec の ID が振り直される** | C2 以降、タスクとテストは `RL-07` のような ID を参照する。v2 で構造化役が作り直すと番号がずれ、追跡が切れる | 構造化役に main の spec を渡し、変わらない行の ID を保つ。消えた ID は再利用しない。検査器は main の spec と比べ、消えた ID と新しい ID を要約に出す |
| S4 | **シードを固定しても、乱数列が環境で変わりうる** | `System.Random(seed)` の数列は .NET の実装に依存し、dotnet（net8）と Unity（Mono / IL2CPP）で一致する保証が無い。一致しなければ、dotnet で緑・Unity で赤の偽陽性が出る | 生成器を式で固定する（例: xorshift32 の式と初期化）。シャッフルの手順（Fisher-Yates、引く順と回数）も spec に書く |
| S5 | **禁止語の一覧は漏れる** | 「hard drop」「瞬間落下」「wall kick」「T-spin」「ghost piece」のような英語表記・言い換えは、日本語 4 語の一覧では止まらない | 英語表記と言い換えを一覧に足す。一覧は漏れる前提で、承認コメントに「GDD に無い語で、機能名らしいもの」の候補を並べ、人間の見落としを減らす |
| S6 | **HC に論理を回していないことは、機械で完全には判定できない** | 「ライン消去の手触りが良い」のように、ロジックを含む行が HC に入りうる | 近似で検査する（数値・比較演算子・ID 参照があれば NG）。GDD v1 には演出の行が無いので、HC は `（該当なし）` になるはず |
| S7 | **構造化役のモデルが固定されていない** | `config/decompose.json` は Claude CLI の既定モデルで動く。時期によってモデルが変わり、実験の条件がずれる | モデル名を設定で固定し、§8 に記録する |
| S8 | **浮動小数の時間注入は、ティックへの変換でずれる** | 外から秒（float）で時間を注入すると、丸めと累積誤差で環境ごとにティック数が変わりうる | 公開する時間の操作は整数ティックだけにする（秒での注入は設けない） |
| S9 | **GDD v1 は錨以外にも決まっていない値が多い** | ソフトドロップ（「10 倍またはフレーム毎」）、レベルごとの落下間隔、ネクストの表示数（「1〜5 個」）、偶数幅のミノの出現列、レベルが上がった回のスコアの倍率（消去前か後か）、Lock Out の「ブロック」は 1 つでもか全部か、40 ライン達成の時間の単位 | これらは質問になる。§7 により v1 はマージされない（設計どおり）。v2 で一括して決める |
| S10 | **仕様変更 Issue のプロトコル（`spec-change.md`）と、GDD の版上げが繋がっていない** | GDD v2 で既存の規則を変えると、C2 で作られたテストが P2P で先祖返りとして落ちる | C2 の設計で、GDD の版上げによる RL の変更を `ms4:spec-change` の Issue に展開する規則を決める（B-2 の範囲外。ここに残す） |

## 11. 検証（B-2 全体）

- 検査器の変異テスト: 網羅・根拠・参照・書式・禁止語・「仮」と質問の数え方の各規則を外すと、テストが赤になること
- 構造化役の出力から 1 行消すと網羅検査が NG になること
- falling-blocks の GDD v1: 構造化まで通り、S9 の曖昧さが質問か `仮` になり、`ms4:questions` が付いて承認依頼が出ないこと。禁止語が spec に現れないこと
- GDD v2（錨と S9 の値を書いたもの）: 質問 0・`仮` 0 で承認依頼が出て、承認でマージされること
