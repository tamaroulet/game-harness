- 結論:
  1. **①は同意する。ただし「Directed を入れる」だけでは直らない**。Directed は game-harness#88 で全性質に入っているが、P-T2-02〜04 の前提は「固定が起きた（after）」で、開始状態と最初の手では決まらないので、いまの Directed は何もしていない。**接地した開始状態から、何もしない手をロック猶予の分だけ続ける系列**を、性質の宣言で指定できるように Directed を広げる

  3. **②の「ステートレスの弱点」は当たらない**。T1 は最初のタスクで、A も B も会話の履歴を持たない同じ状態から始まる。これまでの A（v2-dry-05b・v2-dry-06・v2-smoke-01）も T1 で同じ 5 件を壊していた。原因は両条件に共通の情報の欠け：前のタスク（falling-blocks#12・#17）の振る舞い（Ready から Playing への遷移と出現、自然落下）は、性質の宣言にもプロンプトにも無く、base のコードとテストにしか無い
  4. ②の対策は、自然言語の注意書き（「既存の遷移を壊さない」）ではなく、**base の振る舞いを性質（T0）として宣言し、前のタスクの性質と同じく全タスクの単位定義に入れる**。v2 の原則（言葉ではなく性質で示す）に沿う
  5. ③：game-harness#92（記録と生ログの修正）はこのままでよい（受入の定義に触れない）。①と④は受入の定義を変えるので単独の PR で入れ、**v2-smoke-04 を走らせてから本走に進む**

## 1. T2 の固定の性質（諮問 ①）

### 1.1 事実

| 性質 | 前提（given） | Directed で開始状態に当てられる部分 |
|:--|:--|:--|
| P-T2-02（RL-43） | `before.Phase == Playing && after.LockedMinoCount != before.LockedMinoCount` | `before.Phase == Playing` だけ（常に真） |
| P-T2-03（RL-32） | 同上＋`after.Phase == Playing && after.ActiveMino != null` | 同上 |
| P-T2-04（RL-36） | 同上＋`after.LinesCleared == before.LinesCleared` | 同上 |

- 前提の中心は「このティックで固定が起きた」で、after にしか現れない。いまの Directed（開始状態の前提＋最初の手）では狙えない
- v2-smoke-03 の T2 の知らせ：A は 2〜7 回目の呼び出しの前（6 回）、B は試行 1 の 2・3 回目と試行 2 の 1・2 回目（4 回）が、3 件とも `PROPERTY_VACUOUS … given=0`。反例（`PROPERTY_FAIL id=P-T2-04`）が出たのは、A の 8 回目の前と B の試行 2 の 3 回目の前からで、その手順には `HardDrop` が入っていた（A・B で同じ反例の行）
- 費用：T2 は A 2.56 USD（全体の 83%）、B 1.83 USD（79%）

### 1.2 見積もり（`experiments/v2/tools/lock_mc.py`、近似のモンテカルロ 20,000 系列）

盤面は空、横棒のミノ、重力 60 ティック・ソフトドロップ 3 ティック・ロック猶予 30 ティック・リセット 15 回、開始の Y は一様。

| 実装 | 1 系列（50 手）で固定が起きる確率 | 33 系列（公開 30＋探索 3）で 0 回 |
|:--|:--|:--|
| T2 だけ（ハードドロップ無し） | 0.0087 | **0.75** |
| ハードドロップも実装 | 0.9987 | 0.0000 |

近似なので桁の目安。**T2 だけを正しく実装すると、4 回に 3 回は VACUOUS で落ちる**。ハードドロップを先に実装すれば通る。

- 諮問の「上空にあると 50 ティックでは接地すら不可能」は言い過ぎ（開始の Y は 0〜21 の一様で、ソフトドロップもある）。ただし、接地してからロック猶予の 30 ティックを、25% ずつの左右・回転の入力（成功すると猶予が戻る）をかわして続けるのが難しい、という点で結論は同じ

### 1.3 修正方針

性質の宣言に、任意で「前提を起こす系列」を書けるようにする（Claude が宣言を書く。決定 2 の範囲）。

```json
{"id": "P-T2-02", "task": "T2", "rule": "RL-43", "given": "…", "then": "…",
 "directed": {"pre": "before.ActiveMino != null && !fits(moved(before.ActiveMino, 0, -1))",
              "idle": {"param": "PR-03", "add": 1}}}
```

- `pre`：開始状態で評価する前提（before と after を使わない関数だけ。いまの Directed と同じ検査）。ここでは「接地している」
- `idle`：最初の手から、何も押さない手を N 回続ける。N は構造化仕様から引く（`PR-03`＝ロック猶予 30 ＋ 1）。数値を宣言に書き写さない
- 残りは乱数の手（系列の長さは 50 のまま）
- 正しい T2 の実装なら、`idle` の間に必ず固定が起きる。起きなければ `PROPERTY_FAIL`（反例の 1 行）が出るので、VACUOUS の手探りが無くなる
- 探索が 1 本も見つからなければ、いまと同じく `PROPERTY_UNSATISFIABLE`（実装に依らない）
- 生成器（propgen）と宣言の検査を広げる。P-T2-02〜04 に `directed` を足す

乱数の手に HardDrop が入ること自体は変えない。T2 の実装がハードドロップを持たなければその入力は無視されるだけで、先に実装する必要は無くなる。

## 2. T1 の P2P の破壊（諮問 ②）

### 2.1 事実

- v2-smoke-03 の B の T1：最初の提出で Issue17Cases の 5 件を壊し、試行 1 の 3 回目の呼び出しで 0 に戻した（知らせは全テストの高速検査の失敗）
- 同じ 5 件を、試験制度を揃える前の A も T1 で壊していた（v2-dry-05b・v2-dry-06・v2-smoke-01。いずれも T1 は A の最初の呼び出し）。v2-smoke-03 の A は T1 で壊さなかった
- 諮問の「Tick の冒頭に Phase の検査を書いて Ready の遷移を消した」は、総監督は実装のコードを見ないので確かめていない

### 2.2 見解

- **T1 は最初のタスクで、A も B も会話の履歴を持たない**。ステートレスかどうかの差は T1 には無い。壊れやすさは、両条件に共通の「base の振る舞いが実装役に見えない」ことから来ている（base のコードは埋め込まれているが、どの振る舞いが守るべき仕様かは示していない）
- B の T1 の 3 回は、上限（3 試行 × 3 ターン = 9 回）の中の試行 1 の終わりで、「ギリギリ」ではない。ただし、呼び出しと費用は増える
- 「既存のフェーズ遷移を壊さない」を指示の文に足すのは、言葉で導く形で、v2 の原則（性質で示す）から外れる。どの遷移を守るかも、文では曖昧

### 2.3 修正方針

- **base の振る舞いを性質として宣言する（T0）**：Ready から最初のティックで Playing になりミノが出現位置（PR-09）に出る、自然落下の間隔（PR-01）など、falling-blocks#12・#17 で入った振る舞いを、構造化仕様の規則 ID を根拠に Claude が宣言する（テストのコードは見ない）
- T0 の性質は、全タスクの単位定義の「前のタスクの性質（守り続ける）」に入れ、性質テストも T1 から置く（受入の判定には使わず、P2P と同じく守らせる）
- これで、壊したときの知らせが「Issue17Cases の期待値の不一致」から「性質の 1 行の反例」になり、最初の提出の前から守るべき振る舞いが見える
