## 1. 評価の仕方

### 1-1. 4 つの判定

| 判定 | 意味 | 何で決めたか |
|:--|:--|:--|
| keep（残す） | 外の実践か、今の最終目的に照らして要る | 補う弱さが今も残っている。入口から届くか、残すと決めた線（ベンチ）が使う |
| remove_now（今捨てる） | 今消しても、ほかの確かめが止まらない | 入口から届かない。ほかの部品も、ほかの部品の試験も依っていない。設計がもう使われていない |
| remove_later（この後捨てる） | 捨てる向きだが、条件がそろってから | 決める台帳のタスク（`decide_task`）と条件（`decide_when`）を書く |
| hypothesis（仮説として一回走らせる） | 要るかがまだ分からない。または、消すとほかの確かめが止まる | 走らせる場（台帳のタスク）と、残す・外すの分かれ目を書く |

### 1-2. 「使われている」の数え方（再現できる形）

- 入口は 2 組（`config/arch_components.json` の `entrypoints`）
  - core：規約の命令（CLAUDE.md の progress・pilot_brief・model_pin）、フック（progress の hook）、必須の CI（fastsuite）
  - rebuild：立て直しの道具（木・止まっている間の report・調べもの・前提の台帳・評価役・main の写し・部品の数え上げ）
- 入口から、import の文（ast）を辿って届くモジュールを数える（`arch_inventory.reach`）
- 限界：文字列の中の名前は辿らない。なので「届かない」は「消してよい」の必要条件で、十分条件ではない。消す前に、そのモジュールの名前と、その試験の名前の両方で、試験・設定・保護パスの一覧を探す（10-28 の U1 は、試験の名前を文字列で持つ一覧を見落として外れた）。受信箱や操縦士の手元の手順から起こす命令も辿らないので、rebuild の入口に、規約・引き継ぎ・計画の文書に名前が出る命令を入れて補っている
- 残すものが依るもの：`--reach` の最後の行は、keep のモジュールから import の文と、子プロセスで起こす命令（`["-m", "harness.x"]` の形）で辿って届くのに keep でないもの。捨てる前に依り先を移すものの一覧になる
- 決まり（`tests/test_arch_verdicts.py`）：core から届くモジュールは keep。remove_later と hypothesis には、取り下げられていない台帳のタスクがある。消したもの（`removed`）はどこからも import されない

## 4. 確かでないこと

- 判定は書き手（Claude）が自分たちの作ったものにした。受入の条件と試験（`tests/test_arch_verdicts.py`）は別のモデル（Gemini 3.8 Flash High）が書いたが、判定の中身（どれを残すか）は書き手の読み。Argon の事後の検め（10-28、game-harness#315）で、書き手が見落とした依り方（ベンチと H ライン）と、現状を残したがる偏り（実験の道具）が見つかり、直した。Argon は書き手と別の作り手のモデルだが、強いモデルどうしは誤りが重なりうる（Kim ほか）ので、残った判定にも同じ型の見落としがありうる
- Argon の CLI（agy）は、リポジトリの外の `~/.gemini/GEMINI.md`（副操縦士の決まりと教訓）を毎回読む。評価役の読みに、その文が混ざっている
- **仮説の置き場を 1 つ増やした。** 計画の文書 §3.2 は「仮説は新しい番号体系を作らず、木の要件の属性（検証の状態）にして単一の DAG に統合する」と決めている。部品の判定（hypothesis と決めるタスク）は木の要件ではなく部品の扱いで、決めるタスクは台帳を指すだけにした。ただ、計画の層の書き手と置き場が増えると、正本が食い違う（v2 の H3）。木に寄せるかは総監督が決める
- 外の出典はどれも要約で読んだ。OpenAI の記事は本体が読めなかった
- 走行の記録の数（H ラインの 134 件など）は、`arch_inventory` が手元の out から数えたもの。CI の上では「記録なし」になる
