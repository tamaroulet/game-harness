### 0.3 新しく測ったこと（agy の stream-json）

最小のプロンプト（「OK とだけ返す」）を、空の作業場所で agy に 1 回だけ渡した（`--output-format stream-json`、`gemini-3.8-flash-high`）。

- 9.2 秒。手番（step）1 つで、**入力 12,775・出力 123（うち思考 122）**
- stream-json は、手番が終わるたびに `step_update`（`state: DONE`）の中に**その手番の利用量**（input・output・thinking・cache_read）を出し、最後に `result` で合計を出す
- `init` には、使える道具の一覧が出る（ブラウザ操作などを含む）

ここから言えること：

1. **12,775 トークンは、何もしない手番 1 つの下限**（agy のシステムプロンプトと道具の定義）。「入力を 1 万〜2 万トークンに」は、agy を使う限り、手番 1 つでほぼ使い切る
2. 入力 30 万〜70 万トークンは、1 回の呼び出しの中で agy が**何十手番も回り、毎回それまでの文脈を送り直した合計**と読める（手番ごとの内訳は、今のテレメトリが `result` しか読まないので記録されていない）。「サンドボックスの巨大なディレクトリを無差別に吸い上げている」かどうかは、まだ確かめていない（§1 の 1 で確かめる）
3. 打ち切られても、**終わった手番までの利用量は stream-json から取り出せる**

## 1. 所見と対策

### 1.1 入力トークンの肥大と遅さ（諮問 ①）

**真因の仮説**：agy は、プロンプトだけで編集を終えず、ファイルを読み、編集し、確かめる手番を重ねている。手番ごとに文脈（システムプロンプト 1.3 万＋それまでの読み取りと思考）を送り直すので、入力が手番の数の 2 乗に近い形で増える。v2 §7 の「編集だけ」は**プロンプトで頼んでいるだけ**で、道具は全部開いている。

| # | 対策 | 効き目 | 区分 |
|:--|:--|:--|:--|
| 1 | **まず測る**：実装役を `--output-format stream-json` で呼び、手番ごとの種類（道具の名前）・利用量・秒をテレメトリに残す。どの道具で何手番使ったかが分かる（ファイルの中身は残さない） | 真因の確定 | v2.1 |
| 2 | **読む手番をなくす**：whitelist のファイルと契約のファイルの今の中身を、ハーネスがプロンプトに埋め込んで渡す（総監督は中身を見ない。ハーネスが機械的に埋める）。実装役はファイルを読まずに編集できる | 読み取りの手番がなくなる | v2.1 |
| 3 | **道具を機械で絞る**：`--sandbox`（端末の操作を制限）で、ビルド・テスト・探索のコマンドを使えなくする。「編集だけ」をプロンプトの頼みから、仕組みに変える | 確認の手番がなくなる | v2.1 |
| 4 | **思考を軽くする**：`--effort`（low / medium / high）。いまは `-high` のモデルで、出力の大半が思考（最小の呼び出しでも出力 123 のうち思考 122）。medium で受入が落ちないかを T1 で測ってから決める | 1 手番の秒 | v2.1（測ってから） |
| 5 | **作業場所を細くする**：サンドボックス全体（Unity のプロジェクトを含む）ではなく、whitelist のファイルと契約だけを置いた専用のディレクトリで agy を動かし、終わったらハーネスが書き戻す | 探索の手番と、読める範囲 | v2.2 |
| 6 | **agent をやめる**：実装役を、モデルの API を 1 回呼んで「新しいファイルの全文」を返させる形にする（手番 1 つ、下限はプロンプトの大きさだけ）。ハーネスが書き込む | 入力 1 万〜2 万に届く唯一の方法 | v2.2（裁定が要る） |

**現実的な目標**（agy を使い続ける場合）：手番を 2〜3 つ（編集の道具を 1〜2 回呼んで終わる）に抑えて、入力 3 万〜8 万トークン、1 回 30〜90 秒。1 万〜2 万トークンは、#6 でなければ届かない。

**公平性**：#1〜#6 は、実装役の呼び出し方の変更なので、**A と B の両方に同じものを当てる**（A だけ全リポジトリを探索できると、処置以外の差が混ざる）。A の「会話を積む」と B の「試行ごとに新しく始めて門の下で走る」という違いは変えない。#6 を選ぶ場合、A は API の会話履歴を積み、B は毎回新しく呼ぶ形になる。

### 1.2 TTL で打ち切ったときの利用量の消失（諮問 ②）

**真因**：実装役を `--output-format json` で呼んでいて、利用量は最後の 1 行（`result`）にしか出ない。TTL でプロセスを止めると、その行が出ないので、利用量が丸ごと失われる。

| # | 対策 | 区分 |
|:--|:--|:--|
| 1 | **stream-json に切り替え、手番ごとの利用量を足し込む**。打ち切られても、終わった手番までの利用量は残る。失うのは、打ち切りの時点で進んでいた手番 1 つ分だけ。記録には「打ち切りで失った手番があるか」を残し、合計は下限として扱う（推測で埋めない） | v2.1 |
| 2 | **agy に先に止まらせる**：`--print-timeout` を TTL より短く（例：TTL 300 秒に対して 280 秒）して、agy が自分で止まって `result` を出す。ハーネスの TTL は安全弁に戻す | v2.1 |
| 3 | テレメトリの合計と集計（report.py）で、「打ち切りを含むので下限」の印を付ける。費用の比較の表で、不明を 0 と扱わない | v2.1 |

### 1.3 whitelist と実装役の考えの食い違い（諮問 ③）

**真因**：base（falling-blocks#12 の後）の `Board` クラスは、すでに `IsOccupied(int, int)`・`InBounds(int, int)` を持っている（`tools/units/issue_12.json` の interface）。盤面の占有を `Board` に置くのは、既存の設計に沿った自然な判断で、実装役の誤りとは言いにくい。一方、単位定義の whitelist は `GameState.cs` だけで、プロンプトはそのことを「書き換えてよいファイル」として並べるだけだった。

| # | 対策 | 区分 |
|:--|:--|:--|
| 1 | **whitelist に `Board.cs` を足す**（推奨）。`Board` は base からある振る舞いの型で、v2 §3.1 の「実装役が書くのは振る舞いの型だけ」とも食い違わない。契約（`IGameState`）は変えない | v2.1（裁定が要る） |
| 2 | 足さないなら、プロンプトに「`Board.cs` は読み取り専用。盤面の状態は `GameState` の中で持つ」と明記する。単位定義のプロンプトは機械的に作っているので（`v2prep.py`）、whitelist の外で触りそうな既存のファイルを列挙して書き足す | v2.1 |
| 3 | **whitelist の門を内側ループにも置く**：実装役の呼び出しの直後に whitelist を検査し、外れていれば、その試行を捨てずに内側ループの次のターンへ「`Board.cs` は変更できません」と返す。いまは外側の門でしか見ないので、試行 1 回（v2-dry-02 では 248.5 秒）を丸ごと失う | v2.1（門の変更） |
| 4 | 1.1 の #5（作業場所を細くする）を入れれば、whitelist の外のファイルは作業場所に無いので、そもそも書けない | v2.2 |

1. **whitelist**：`Board.cs` を足すか（推奨）、`GameState.cs` だけのまま、プロンプトで読み取り専用と明記するか

4. **`--sandbox` の範囲**：端末の制限で、agy が編集の道具まで使えなくならないかは、まだ試していない。v2.1 の 5 で確かめる前提でよいか
