- 前提: ADR-002（`docs/design/mechanical_barriers.md`）の手順 1〜6 が完了。v2 カナリアの 2 回目が PASS（rc=0、229 秒、1 回目の試行で CI まで完走。CI run 35855044626）

## 1. 目的

ADR-002 で入れた防壁は、falling-blocks#12（静的な盤面と初期状態）という「時間の進まない」単位でだけ実証された。本格開発では、次の 2 つが同時に要る。

- 時間が進む単位（落下・接地・固定）を、防壁を緩めずに通す
- 実測で過剰だった防壁を、外部の工学規範に沿って適正化する

会議で受け入れた必須要件は次の 4 群である。

| 群 | 要件 |
|:--|:--|
| R1 既存契約の移行 | v2 の `issue_12.json` と旧手書きテスト 3 本の退役を falling-blocks の main に反映する。未定義のパラメーターを GDD に定義する |
| R2 未踏領域への対策 | falling-blocks#17 を最小スライスに限る。Outer Gate が 3 ターンで回復しなければ DISPUTE。破壊率 0.0% の定義。`.meta` 破損防止の時限制約 |
| R3 過剰防壁の適正化 | Feature/Refactor 分離型の差分バジェット。共通数学型。ティック進行の述語。反例情報の制限 |
| R4 報告 | 進捗は簡素なツリーで報告する（本文書の範囲外） |

## 2. 前提の検証：要件と実物の食い違い

要件を制約に落とす前に、リポジトリの実物と照合した。食い違いが 6 件あったので、先に書く。**要件の意図は変えず、書き方だけを実物に合わせる。**

| # | 要件の前提 | 実物 | 本文書での扱い |
|:--|:--|:--|:--|
| G1 | バッファ行数（2）は GDD に未定義 | **定義済み。** GDD §1 L9「上側に 2 行分のバッファ領域（Y=20..21）」、構造化仕様 RL-02、PR-08（内部行数 22） | 追記しない。二重定義は将来の矛盾の種になる。本当に未定義なのは保存則の 2 量（§3.2） |
| G2 | 差分の門は単純 net diff | net ではない。`gate_diff_lines` は whitelist の追加行と削除行の**合計**を数え、上限は `max_impl_lines = 250` | 「net を却下」ではなく「合計を add / del の別枠に分ける」と読む（§3.7） |
| G3 | Google 規範に add ≤ 250・del ≤ 100 がある | Google の eng-practices（*Small CLs*）が定めるのは「小さく保つ」「リファクタリングを機能変更から分ける」という原則で、**行数の閾値は無い** | 分離の原則は Google に拠る。250 / 100 という数値は本プロジェクトの設定値として扱い、出典を Google にしない |
| G4 | 破壊率 0.0% を「公開 API の後方互換」と定義 | 現行の P2P は「base で通った全テストが今も通る（消えたものも破壊）」。API の互換だけでは、振る舞いの破壊を見逃す | **置き換えではなく追加**として定義する（§3.5）。置き換えると門が弱くなる |
| G5 | Outer Gate の「3 ターン」 | 1 回のパイプラインの試行は `max_retry: 2` で 3 回。いまは 3 回とも落ちると「不合格」（rc=1）で終わり、DISPUTE とは区別されない | 3 は独立した設定値にし、試行回数と矛盾すれば起動時に止める（§3.4） |
| G6 | falling-blocks#17 は「出現＋1 段自然落下」 | 自然落下は 60 ティックに 1 回（PR-01）。スキーマ門は 1 行 1 操作（horizon = 1）で、自然落下カウンタは GDD §6 の公開状態に無い。**いまの受入データでは 1 段の落下を書けない** | ティック進行の述語（§3.9）が falling-blocks#17 の前提条件になる |

## 3. 決定

### 3.1 既存契約の正式移行（R1-1）

- v2 の `issue_12.json`、その生成テスト、旧手書きテスト 3 本（InitialStateTests・BoardGeometryTests・CoreContractTests）の退役を、falling-blocks の main に 1 本の PR で入れる
- 変換は `canary.py migrate` で行う。手で書き直さない。カナリアの `prepare` は単位定義の実装ファイルを消すので、main 向けには使わない（2026-09-23 訂正）。v2 の単位定義の原本は `projects/falling-blocks/units/issue_12.json` に置く
- 完了の判定は `canary.py check-migrated`（main の単位定義が v2、v1 の受入テストが残っていない、main の先頭で CI が success）
- **総監督は実施しない。** ゲームのテスト置き場への書き込みは防壁①が拒否する。実施者は人間か現場（Layer 3）で、総監督は次の報告だけを受け取る
  - falling-blocks の CI が緑
  - 高速検査の件数がカナリア 2 回目と一致（23 件、失敗 0、skip 0）
- 旧テストの削除は P2P 上「消えたもの」に当たる。これは実装役の差分ではなく、人間が承認する base の変更として入れる。以後の base は移行後の main とする

### 3.2 GDD の改訂（R1-2）

- GDD を 1 版上げ、§6「公開する状態」に次の 2 つを足す。どちらも §5 の保存則に出てくるのに、今は観測できない（ADR-002 §4.3）
  - 盤面ブロック数
  - ロックしたミノの累計数
- これで保存則が等式の文法（公開フィールド名・整数・`+ - * =`）のまま書ける。集計関数を文法に足さずに済む
- 改訂の後に、次をこの順で行う
  1. 構造化仕様の再生成（`gdd-sha256` が変わる）
  2. `projects/falling-blocks/invariants.json` に保存則を宣言する（harness への PR、人間のレビュー）
  3. `issue_12.json` の `rule` 参照を `decompose --from-unit` で再検査する。仕様の ID がずれていればスキーマ門が拒絶するので、ここで直す
- 「未定義のパラメーター」の洗い出しは、目視ではなく構造化仕様の生成器に任せる。GDD に数値の根拠が無い値は `docs/spec/questions.md` に質問として出る。**GDD への追記は、この質問への回答としてだけ行う**

### 3.3 falling-blocks#17 の最小スライス（R2-1）

（2026-09-23：当初は falling-blocks#15 と書いていたが、その番号は移行の PR が取った。スモークの Issue は falling-blocks#17 として立て直した。falling-blocks#14「出現」の範囲を含む）

falling-blocks#17 の受入データに含めてよいのは、次の 2 つだけとする。

| 挙動 | 仕様 | 受入データの形 |
|:--|:--|:--|
| 出現 | ST-01（Ready → Playing）、RL-15、PR-09 | given = Ready、op = ティック 1 回、expect = 基準位置 `{"param": "PR-09"}`・向き 0 |
| 1 段の自然落下 | PR-01、GDD §4 ③ | 空の盤面で、ティックを PR-01 − 1 回進めても Y は変わらず、PR-01 回目で `add: -1`（§3.9） |

- 除外するもの：左右移動、回転、ソフトドロップ、接地、ロック猶予、固定、ライン消去、ゲームオーバー、同一ティックの複合入力
- **interface に必ず含めるもの（B3.1-3 で決定）**：`void GameState.Tick()`（1 ティック進める。複数ティックは受入データの repeat で表す）、`int GameState.BlockCount`、`int GameState.LockedMinoCount`。保存則の宣言（`projects/falling-blocks/invariants.json`）がこの 3 つを参照するので、欠けると Outer 段がビルドできずに ABORT になる。出現と 1 段の落下の範囲では、2 つの数はどちらも 0 のまま
- 門で強制する：falling-blocks#17 の単位定義で使える `op` は「ティックを進める」だけ。それ以外の操作がある行はスキーマ門で拒絶する（時限。falling-blocks#17 がマージされたら外す）
- 実装（B3.1-2）：`config/unit_schema.json` の `timed_constraints`。単位の番号に依らず、免除した既存の単位（issue_12）以外のすべてに効く。使える操作は `GameState.Tick` の call だけ

### 3.4 Outer Gate の回送（R2-2）

- **条件：** 1 回のパイプラインの中で、Outer 段（Invariants）の反例による REJECT が **3 回連続**した
- **判定：** 不合格ではなく DISPUTE とし、実装役ではなく高次のループ（分解役と総監督）へ回送する。回送の中身は、3 回分の反例の行（§3.10）と不変条件 ID の列だけ
- **理由：** 見えない不変条件に 3 回続けて落ちるなら、疑うべきは実装より、単位定義・不変条件の宣言・GDD のほうである。実装役に 4 回目を回しても情報は増えない
- 実装役が出す `DISPUTE_TEST`（One-Strike Rule）とは**別物**として扱う。ハーネスが出す DISPUTE なので、実装役は起こせないし、One-Strike の回数にも数えない
- 3 は `gates.outer_dispute_after` として独立した設定値にする。`max_retry + 1` より大きければ、条件が永久に成立しないので起動時に ABORT する
- 回送先が機械で見分けられるように、テレメトリに `dispute: {kind: "outer", after, counterexamples}` を残す（B3.2 で決定）。終了コードは 1 のまま（0 / 1 / 2 の三値を増やさない）
- 設定は projects/<id>/pipeline.json の `gates.outer_dispute_after`。無ければ回送しない。falling-blocks は 3
- 前提：Outer 段が実際に発火するのは、§3.2 で保存則が宣言されてからである。宣言が無い間は、ADR-002 §4.4 どおり段を飛ばす

### 3.5 破壊率 0.0% の定義（R2-3）

**破壊率 0.0% とは、次の 2 つが同時に成り立つことをいう。**

1. P2P：base で通った全テストが今も通る（現行のまま。消えたものも破壊）
2. 公開契約の後方互換：main に入った単位定義の `interface` で宣言したメンバー（名前・種類・型・引数・static）が、すべて同じ形で残っている。追加は許し、削除と変更は拒絶する

2 を独自の検査器で作らない。テスト生成器が、単位ごとに `interface` の全メンバーを参照する「契約の形テスト」を出力する。これは Generated/ に残るので、以後は 1 の P2P がそのまま 2 を守る。新しい判定器を増やさずに済む。

- 意図して契約を壊す変更は、GDD の版上げを伴う PR で、人間の承認を得たときだけ許す（Invariants の変更と同じ扱い）
- 1 を 2 で置き換える読み方は採らない（G4）

### 3.6 `.meta` の破損防止（R2-4）

- **時限制約（falling-blocks#17 だけ）：** whitelist のパスがすべて base に実在すること。新しいファイルを作る単位はスキーマ門で拒絶する。新規ファイルが無ければ、新しい `.meta`（GUID）も生まれない
- **恒久策：** `.meta` の自動生成機構を harness 側（Unity アダプタ）に置く。GUID はパスから決定論的に導き、Unity を起動せずに作れるようにする。機構は B3.3 で入れ、新しいファイルを伴う最初の単位（B4-RUN）から使う
- 機構が main に入った時点で時限制約を外す。外す PR は機構の PR と別にする（門の緩和なので）
- **実装（B3.3）**：`adapters/unity.py` の `carry_companion`。サンドボックスにも本体にも .meta が無い新しいファイルは、リポジトリからの相対パスの MD5（32 桁の 16 進）を GUID にした .meta を作って持ち出す。オーナー裁定で機構と時限制約の解除を同じ PR に入れた
- **残る穴**：新しい**フォルダ**の .meta は作らない。新しいフォルダを作る単位は、本体で Unity を開いたときにフォルダの .meta が生える。観測されたら足す

### 3.7 差分バジェット（R3-1）

- 単位定義に `task_kind`（`feature` / `refactor`）を足し、分解役が必ず書く。スキーマ門で検査する
- **feature：** whitelist の追加行 ≤ 250 **かつ** 削除行 ≤ 100。数え方は今と同じ（未追跡ファイルを含む `git diff --numstat`）
- **refactor：** 受入データに新しい行を持てない（振る舞いを増やさない）。P2P の全件維持が唯一の合格条件
- 1 つの単位で機能とリファクタリングを混ぜない。feature で削除が 100 行を超えるなら、分解役は先に refactor の単位を切り出す
- **実装（B3.3）**：`task_kind` は分解役に必ず書かせる（decompose の required_keys）。スキーマ門では省略を feature とみなし、既存の単位（issue_12・issue_17）を壊さない。上限は `max_add_lines`・`max_del_lines`（config/decompose.json の defaults）
- **これは緩和である。** 合計の上限は、いまの 250 から最大 350 に上がる。実績（falling-blocks#12 の v1 が 203 行、カナリア 2 回目が 165 行）はどちらの基準でも収まるので、緩和で通るようになる既知の差分は無い。PR の本文にこの事実を書く

### 3.8 共通数学型（R3-2）：削除

2026-09-23 のオーナー裁定で削除した（YAGNI）。座標や盤面の型が複数の単位で重複したと観測されたら、そのとき改めて扱う。

### 3.9 ティック進行の述語（R3-3）

受入データの `op` に、繰り返し回数を 1 つだけ足す。

- `{"op": "<操作>", "repeat": <回数>}`。回数は `{"param": "PR-xx"}`、またはそれに `add: ±1` を付けたものだけ。独自の数値は書けない（期待値と同じく GDD に縛る）
- 期待値に `at_step` を足す：「repeat の途中では given から変わらず、`at_step` 回目で初めて変わる」。1 行で、早すぎる落下と遅すぎる落下の両方を捕まえる
- **horizon の上限を仕様にする：** repeat の上限は 1000 ティックとし、スキーマに書く。整数ティックのパズルでは上限は効かないが、連続系で「長い horizon は必ず誤差を超える」問題（Phase 4-1 の 3D 物理で表に出る既知リスク）を、ここで先に型として持っておく
- 自然落下カウンタを GDD §6 に公開して given に書く案は採らない。公開状態を増やすと、§3.5 でその状態が永久に後方互換の対象になる

### 3.10 反例情報（R3-4）

- Outer 段が実装役に返すのは、次の行だけとする
  `INVARIANT_FAIL id=… rule=… seed=… ops=… dir=DEFICIT|SURPLUS`
- `ops`：破綻した時点までの操作列（最短の接頭辞。今と同じ）
- `dir`：等式の左辺が右辺より小さければ DEFICIT、大きければ SURPLUS。生の値も差の大きさも出さない
- `seed` は残す。seed は再現の鍵で、状態の値ではない。これが無いと 7-Bag の並びが決まらず、操作列を再生できない
- 対象は Outer 段だけとする。Unit の生成テストは実装役のサンドボックスにあり、期待値は元から見えているので、遮断しても意味が無い

### 3.11 最小診断・反例射影（2026-09-23 追加、B3.2）

- オーナー裁定で B3.2 に組み込む。目的は「因果盲目」の防止：実装役が、型や契約の矛盾のどこが原因かを取り違えたまま試行を重ねることを防ぐ
- 方向：Roslyn の診断から、型・契約の矛盾を起こしている最小の不整合集合（MUC）を取り出し、`interface` の識別子に射影して実装役に返す。コンパイラの生のメッセージは返さない
- **決定（B3.2）**：`harness/diagproj.py`。dotnet アダプタの `diagnose_build` から呼び、高速検査のビルドが通らなかった回だけ、実装役へのフィードバックを射影した文章に差し替える
  - 入力：ビルド出力の診断の行（`<ファイル>(<行>,<列>): error CSxxxx: <メッセージ>`）と単位定義の interface
  - 出力（多くても 10 行、同じ行は 1 回）
    - 生成テスト側のエラー：`BUILD_DIAG kind=contract symbol=<型.メンバー> code=<CSxxxx>`。メッセージ中の識別子を interface と突き合わせ、同じメンバーに由来するエラーは 1 行に畳む（最小の不整合集合）
    - 実装側（impl_dir の下）のエラー：`BUILD_DIAG kind=impl file=<パス> line=<行> code=<CSxxxx>`
  - 捨てるもの：コンパイラのメッセージ、サンドボックスの絶対パス、interface の識別子を含まない生成テスト側のエラー（契約の不整合から派生した連鎖とみなす）
  - 見出しで「検査系の故障ではない」と明示する。これまでは TRX が無いと「検査系故障」と書いて渡しており、実装の過失を配管の故障と取り違えさせる形だった
- 判定（合否）には使わない。射影できる診断が無ければ、これまでどおりの文章を渡す

### 3.12 インフラ起因の失敗の扱い（2026-09-23 追加、B3.1-2）

配管や環境の故障を、実装の過失と取り違えないための 3 案を、既存の機構と突き合わせて判断した。

| 案 | 判断 | 理由 |
|:--|:--|:--|
| 終了コードの三値（0 成功 / 1 不合格 / 2 環境異常） | **採用（規約の穴を塞ぐだけ）** | `exitcode.normalized` は既にある。抜けていた入口 5 本（canary・progress・unit_schema・testgen・invgen）に付け、`canary.py` の前提・環境の不備（`CanaryError`、gh に届かない）と `progress` の照合不能を 2 にした。`progress complete` は検証コマンドの rc=2 を不合格ではなく ABORT として返す。付け忘れは `tests/test_exitcode_coverage.py` が拒む |
| 作業ツリーの原子的ロールバック | 不採用（既存で足りる） | パイプラインは試行のたびに最初に `sandbox_reset` し、DISPUTE と試行の使い切りでも戻す。実装役に引き継ぐのは差分ではなくフィードバックの文章なので、rc=1 でロールバックを足しても守るものが無い。スケジューラも固定 worktree を使う前に `reset --hard` と `clean -fdx` で空にする |
| 起動前の自己検証 | 不採用（既存で足りる） | `pipeline.selftest` と `scheduler.preflight` がある。新しい門を足さない |
