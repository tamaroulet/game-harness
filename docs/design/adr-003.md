# 本格開発に向けた防壁適正化と多段遷移設計方針（ADR-003）

- 状態: 方針のみ。コードは変更していない
- 前提: ADR-002（`docs/design/mechanical_barriers.md`）の手順 1〜6 が完了。v2 カナリアの 2 回目が PASS（rc=0、229 秒、1 回目の試行で CI まで完走。CI run 35855044626）
- 決定（2026-09-23、Phase 3 突入判定会議）: 下の必須要件 R1〜R4 を前提条件として受け入れる。本文書はそれを、機械が判定できる制約と、PR の順序に落とす

## 1. 目的

ADR-002 で入れた防壁は、Issue 12（静的な盤面と初期状態）という「時間の進まない」単位でだけ実証された。本格開発では、次の 2 つが同時に要る。

- 時間が進む単位（落下・接地・固定）を、防壁を緩めずに通す
- 実測で過剰だった防壁を、外部の工学規範に沿って適正化する

会議で受け入れた必須要件は次の 4 群である。

| 群 | 要件 |
|:--|:--|
| R1 既存契約の移行 | v2 の `issue_12.json` と旧手書きテスト 3 本の退役を falling-blocks の main に反映する。未定義のパラメーターを GDD に定義する |
| R2 未踏領域への対策 | Issue 15 を最小スライスに限る。Outer Gate が 3 ターンで回復しなければ DISPUTE。破壊率 0.0% の定義。`.meta` 破損防止の時限制約 |
| R3 過剰防壁の適正化 | Feature/Refactor 分離型の差分バジェット。共通数学型。ティック進行の述語。反例情報の制限 |
| R4 報告 | 進捗は簡素なツリーで報告する（本文書の範囲外） |

## 2. 前提の検証：要件と実物の食い違い

要件を制約に落とす前に、リポジトリの実物と照合した。食い違いが 6 件あったので、先に書く。**要件の意図は変えず、書き方だけを実物に合わせる。**

| # | 要件の前提 | 実物 | 本文書での扱い |
|:--|:--|:--|:--|
| G1 | バッファ行数（2）は GDD に未定義 | **定義済み。** GDD §1 L9「上側に 2 行分のバッファ領域（Y=20..21）」、構造化仕様 RL-02、PR-08（内部行数 22） | 追記しない。二重定義は将来の矛盾の種になる。本当に未定義なのは保存則の 2 量（§3.2） |
| G2 | 差分の門は単純 net diff | net ではない。`gate_diff_lines` は whitelist の追加行と削除行の**合計**を数え、上限は `max_impl_lines = 250` | 「net を却下」ではなく「合計を add / del の別枠に分ける」と読む（§3.7） |
| G3 | Google 規範に add ≤ 250・del ≤ 100 がある | Google の eng-practices（*Small CLs*）が定めるのは「小さく保つ」「リファクタリングを機能変更から分ける」という原則で、**行数の閾値は無い** | 分離の原則は Google に拠る。250 / 100 という数値は本プロジェクトの設定値として扱い、出典を Google にしない |
| G4 | 破壊率 0.0% を「公開 API の後方互換」と定義 | 現行の P2P は「base で通った全テストが今も通る（消えたものも破壊）」。API の互換だけでは、振る舞いの破壊を見逃す | **置き換えではなく追加**として定義する（§3.5）。置き換えると門が弱くなる |
| G5 | Outer Gate の「3 ターン」 | 1 回のパイプラインの試行は `max_retry: 2` で 3 回。いまは 3 回とも落ちると「不合格」（rc=1）で終わり、DISPUTE とは区別されない | 3 は独立した設定値にし、試行回数と矛盾すれば起動時に止める（§3.4） |
| G6 | Issue 15 は「出現＋1 段自然落下」 | 自然落下は 60 ティックに 1 回（PR-01）。スキーマ門は 1 行 1 操作（horizon = 1）で、自然落下カウンタは GDD §6 の公開状態に無い。**いまの受入データでは 1 段の落下を書けない** | ティック進行の述語（§3.9）が Issue 15 の前提条件になる |

## 3. 決定

### 3.1 既存契約の正式移行（R1-1）

- v2 の `issue_12.json`、その生成テスト、旧手書きテスト 3 本（InitialStateTests・BoardGeometryTests・CoreContractTests）の退役を、falling-blocks の main に 1 本の PR で入れる
- 変換はカナリア 2 回目と同じもの（`canary.py` の準備処理と `--retire-v1-tests`）を使う。手で書き直さない
- **総監督は実施しない。** ゲームのテスト置き場への書き込みは防壁①が拒否する。実施者は人間か現場（Layer 3）で、総監督は次の報告だけを受け取る
  - falling-blocks の CI が緑
  - 高速検査の件数がカナリア 2 回目と一致（23 件、失敗 0、skip 0）
- 旧テストの削除は P2P 上「消えたもの」に当たる。これは実装役の差分ではなく、人間が承認する base の変更として入れる。以後の base は移行後の main とする

### 3.2 GDD の改訂（R1-2）

- GDD を 1 版上げ、§6「公開する状態」に次の 2 つを足す。どちらも §5 の保存則に出てくるのに、今は観測できない（ADR-002 §4.3）
  - 盤面ブロック数
  - ロックしたミノの累計数
- これで保存則が等式の文法（公開フィールド名・整数・`+ - * =`）のまま書ける。集計関数を文法に足さずに済む
- 改訂の後に、次をこの順で行う
  1. 構造化仕様の再生成（`gdd-sha256` が変わる）
  2. `projects/falling-blocks/invariants.json` に保存則を宣言する（harness への PR、人間のレビュー）
  3. `issue_12.json` の `rule` 参照を `decompose --from-unit` で再検査する。仕様の ID がずれていればスキーマ門が拒絶するので、ここで直す
- 「未定義のパラメーター」の洗い出しは、目視ではなく構造化仕様の生成器に任せる。GDD に数値の根拠が無い値は `docs/spec/questions.md` に質問として出る。**GDD への追記は、この質問への回答としてだけ行う**

### 3.3 Issue 15 の最小スライス（R2-1）

falling-blocks#15 の受入データに含めてよいのは、次の 2 つだけとする。

| 挙動 | 仕様 | 受入データの形 |
|:--|:--|:--|
| 出現 | ST-01（Ready → Playing）、RL-15、PR-09 | given = Ready、op = ティック 1 回、expect = 基準位置 `{"param": "PR-09"}`・向き 0 |
| 1 段の自然落下 | PR-01、GDD §4 ③ | 空の盤面で、ティックを PR-01 − 1 回進めても Y は変わらず、PR-01 回目で `add: -1`（§3.9） |

- 除外するもの：左右移動、回転、ソフトドロップ、接地、ロック猶予、固定、ライン消去、ゲームオーバー、同一ティックの複合入力
- 門で強制する：Issue 15 の単位定義で使える `op` は「ティックを進める」だけ。それ以外の操作がある行はスキーマ門で拒絶する（時限。falling-blocks#15 がマージされたら外す）

### 3.4 Outer Gate の回送（R2-2）

- **条件：** 1 回のパイプラインの中で、Outer 段（Invariants）の反例による REJECT が **3 回連続**した
- **判定：** 不合格ではなく DISPUTE とし、実装役ではなく高次のループ（分解役と総監督）へ回送する。回送の中身は、3 回分の反例の行（§3.10）と不変条件 ID の列だけ
- **理由：** 見えない不変条件に 3 回続けて落ちるなら、疑うべきは実装より、単位定義・不変条件の宣言・GDD のほうである。実装役に 4 回目を回しても情報は増えない
- 実装役が出す `DISPUTE_TEST`（One-Strike Rule）とは**別物**として扱う。ハーネスが出す DISPUTE なので、実装役は起こせないし、One-Strike の回数にも数えない
- 3 は `gates.outer_dispute_after` として独立した設定値にする。`max_retry + 1` より大きければ、条件が永久に成立しないので起動時に ABORT する
- 回送先が機械で見分けられるように、終了コードかテレメトリの判定欄で「不合格」と区別する（どちらにするかは PR で決める）
- 前提：Outer 段が実際に発火するのは、§3.2 で保存則が宣言されてからである。宣言が無い間は、ADR-002 §4.4 どおり段を飛ばす

### 3.5 破壊率 0.0% の定義（R2-3）

**破壊率 0.0% とは、次の 2 つが同時に成り立つことをいう。**

1. P2P：base で通った全テストが今も通る（現行のまま。消えたものも破壊）
2. 公開契約の後方互換：main に入った単位定義の `interface` で宣言したメンバー（名前・種類・型・引数・static）が、すべて同じ形で残っている。追加は許し、削除と変更は拒絶する

2 を独自の検査器で作らない。テスト生成器が、単位ごとに `interface` の全メンバーを参照する「契約の形テスト」を出力する。これは Generated/ に残るので、以後は 1 の P2P がそのまま 2 を守る。新しい判定器を増やさずに済む。

- 意図して契約を壊す変更は、GDD の版上げを伴う PR で、人間の承認を得たときだけ許す（Invariants の変更と同じ扱い）
- 1 を 2 で置き換える読み方は採らない（G4）

### 3.6 `.meta` の破損防止（R2-4）

- **時限制約（falling-blocks#15 だけ）：** whitelist のパスがすべて base に実在すること。新しいファイルを作る単位はスキーマ門で拒絶する。新規ファイルが無ければ、新しい `.meta`（GUID）も生まれない
- **恒久策：** `.meta` の自動生成機構を harness 側（Unity アダプタ）に置く。GUID はパスから決定論的に導き、Unity を起動せずに作れるようにする。falling-blocks#16 はこの機構を使う最初の単位とする
- 機構が main に入った時点で時限制約を外す。外す PR は機構の PR と別にする（門の緩和なので）

### 3.7 差分バジェット（R3-1）

- 単位定義に `task_kind`（`feature` / `refactor`）を足し、分解役が必ず書く。スキーマ門で検査する
- **feature：** whitelist の追加行 ≤ 250 **かつ** 削除行 ≤ 100。数え方は今と同じ（未追跡ファイルを含む `git diff --numstat`）
- **refactor：** 受入データに新しい行を持てない（振る舞いを増やさない）。P2P の全件維持が唯一の合格条件
- 1 つの単位で機能とリファクタリングを混ぜない。feature で削除が 100 行を超えるなら、分解役は先に refactor の単位を切り出す
- **これは緩和である。** 合計の上限は、いまの 250 から最大 350 に上がる。実績（Issue 12 の v1 が 203 行、カナリア 2 回目が 165 行）はどちらの基準でも収まるので、緩和で通るようになる既知の差分は無い。PR の本文にこの事実を書く

### 3.8 共通数学型（R3-2）

- falling-blocks の `Core` 直下に、ゲームに依存しない純粋な型を置く。最初は `Position`（整数の 2 次元座標）と `Grid`（幅・高さ・セル）に限る
- 制約（機械判定）
  - 整数だけ。浮動小数の型を置かない（決定論を保つ。連続系は Phase 3 の別問題で、ここには持ち込まない）
  - ゲームの語彙（ミノ、盤面、ティックなど）を含まない。`projects/falling-blocks/spec_terms.json` の用語が識別子に現れたら拒絶する
  - `UnityEngine` を参照しない（既存の禁止パターンで足りる）
- 車輪の再発明を防ぐ仕組み：分解役の prompt に共通型の一覧を渡す。`interface` で共通型と同名、または同じ形（整数 2 つだけを持つ struct など）の型を宣言したら、スキーマ門で拒絶する
- 導入は refactor の単位として、§3.6 の恒久策の後に行う。新規ファイルなので `.meta` が要る
- 既存の公開契約は §3.5 で守られるので、既存の座標の引数（x, y）は消せない。共通型は追加の多重定義として入れる

### 3.9 ティック進行の述語（R3-3）

受入データの `op` に、繰り返し回数を 1 つだけ足す。

- `{"op": "<操作>", "repeat": <回数>}`。回数は `{"param": "PR-xx"}`、またはそれに `add: ±1` を付けたものだけ。独自の数値は書けない（期待値と同じく GDD に縛る）
- 期待値に `at_step` を足す：「repeat の途中では given から変わらず、`at_step` 回目で初めて変わる」。1 行で、早すぎる落下と遅すぎる落下の両方を捕まえる
- **horizon の上限を仕様にする：** repeat の上限は 1000 ティックとし、スキーマに書く。整数ティックのパズルでは上限は効かないが、連続系で「長い horizon は必ず誤差を超える」問題（Phase 3 の既知リスク）を、ここで先に型として持っておく
- 自然落下カウンタを GDD §6 に公開して given に書く案は採らない。公開状態を増やすと、§3.5 でその状態が永久に後方互換の対象になる

### 3.10 反例情報（R3-4）

- Outer 段が実装役に返すのは、次の行だけとする
  `INVARIANT_FAIL id=… rule=… seed=… ops=… dir=DEFICIT|SURPLUS`
- `ops`：破綻した時点までの操作列（最短の接頭辞。今と同じ）
- `dir`：等式の左辺が右辺より小さければ DEFICIT、大きければ SURPLUS。生の値も差の大きさも出さない
- `seed` は残す。seed は再現の鍵で、状態の値ではない。これが無いと 7-Bag の並びが決まらず、操作列を再生できない
- 対象は Outer 段だけとする。Unit の生成テストは実装役のサンドボックスにあり、期待値は元から見えているので、遮断しても意味が無い

## 4. 多段遷移：順序と PR の分け方

前の段が main に入ってから次の段に進む。門・指標を触る PR は、それぞれ単独で人間のレビューを受ける。

| 段 | 内容 | リポジトリ | 門・指標に触れるか | 実施者 |
|:--|:--|:--|:--|:--|
| 0 | 本文書 | game-harness | 触れない | 総監督 |
| A1 | §3.1 v2 契約の移行 | falling-blocks | 触れない（base の変更） | 人間 / Layer 3 |
| A2 | §3.2 GDD の改訂、仕様の再生成、保存則の宣言 | 両方 | 宣言は触れる | 人間 / Layer 3 |
| A3 | §3.3・§3.6 の時限制約（操作の限定、whitelist の実在） | game-harness | 触れる | 現場 |
| A4 | §3.9 ティック進行の述語 | game-harness | 触れる | 現場 |
| — | **falling-blocks#15**（出現＋1 段の自然落下） | falling-blocks | — | パイプライン |
| B1 | §3.10 反例の `dir` | game-harness | 触れない（返す情報だけ） | 現場（`integration/harness` に積める） |
| B2 | §3.4 Outer Gate の回送 | game-harness | 触れる | 現場 |
| C1 | §3.7 差分バジェット | game-harness | 触れる（緩和） | 現場 |
| C2 | §3.5 契約の形テスト | game-harness | 触れる（指標） | 現場 |
| C3 | §3.6 `.meta` の自動生成 → 時限制約の解除（2 PR） | game-harness | 解除は触れる | 現場 |
| — | **falling-blocks#16** | falling-blocks | — | パイプライン |
| C4 | §3.8 共通数学型（refactor の単位） | falling-blocks | — | パイプライン |

- A 段は falling-blocks#15 の前提、B 段は Outer 段の実働化、C 段は適正化である
- 単独 PR は A3・A4・B2・C1・C2・C3 の 6 本になる。人間の拘束が本数に比例することは承知のうえで、門の変更をまとめない
- falling-blocks の凍結（ADR-002 §5）は、A1・A2・falling-blocks#15 の範囲に限って解く

## 5. 未決事項（人間の裁定待ち）

1. **refactor の予算。** 要件に数値が無い。暫定案は「合計 250（現行と同じ）」で、緩和しない側に倒す
2. **反例の seed。** 要件は「接頭辞の操作列と DEFICIT/SURPLUS のみ」だが、本文書は再現のために seed を残した（§3.10）。seed も落とすなら、反例は再生できなくなる
3. **「Issue 16」の指す先。** 本文書は「機構は harness に置き、falling-blocks#16 が最初の利用者」と解釈した。falling-blocks#16 自体が機構を実装する意味なら、ゲームのリポジトリにツールが入ることになり、§3.6 を書き直す
4. **A1・A2 の実施者。** 防壁①により総監督は実施できない
5. **Outer DISPUTE の見分け方。** 終了コードを新設するか、テレメトリの判定欄で区別するか

## 6. やらないこと

- Issue 15 に 2 つ目以降の挙動を足すこと
- 破壊率の定義から P2P を外すこと
- 浮動小数の共通型、連続系の門の設計（Phase 3 の連続系は別の ADR で、門の判定から先に決める）
- 総監督による falling-blocks のテスト置き場・Core の編集
