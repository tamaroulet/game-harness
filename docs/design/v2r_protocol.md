# 再実験 v2r の設計要項（プロトコル仕様書）

- 状態: 起草（2026-09-26）。**人間（操縦士）と副操縦士の承認まで、乾式の走行も本走も行わない**
- 前提: `docs/design/v2_run_design_critique.md`（game-harness#106）、モデルの固定と記録（game-harness#105、`harness/model_pin.py`）
- 本書の「確定」は、本書の承認で固定する値。「実測」は 2026-09-26 に確かめた事実。「未検証」は乾式の走行の前に確かめる項目で、§13 の一覧に集め、**1 つでも残れば本走に入らない**

## 0. 目的と問い

| 問い | 内容 | 本書の範囲 |
|:--|:--|:--|
| Q1 門の因果 | 門（検査の知らせと再試行）は、先祖返り・仕様のずれを減らすか | **主目的** |
| Q2 仕様の形の効果 | 同じ事実を、自然言語で渡すか、形式（性質の式）で渡すか | 副目的（Q1 と同じ走行で測る） |
| Q3 長期の文脈 | 会話を積む（ステートフル）か、毎回ゼロから（ステートレス）か | **範囲外**。Q1 の後に別の要項で扱う |

## 1. 交絡の排除：2 × 2 の要因計画（項目 1）

### 1.1 統制方針（確定）

**全条件をステートレスにそろえる**。すべての実装役の呼び出しは新しい会話で始め、前の呼び出しの会話を持ち込まない。呼び出しごとのプロンプトは、同じ組み立て手順で作る（§1.3）。

- 理由：V2-RUN では「門の有無」は同じで「文脈の持ち方」だけが違った。v2r で両方を動かすと Q1 が単離できない。ステートレスにそろえると、条件の違いは §1.2 の 2 因子だけになる
- 「全条件に同じ履歴を注入する」案は採らない。履歴の中身（前の呼び出しの応答）が条件ごとに違うので、同じにできない

### 1.2 因子と条件（確定）

| | 門なし（知らせなし・1 回だけ） | 門あり（知らせあり・再試行） |
|:--|:--|:--|
| **自然言語の仕様** | A0 | A1 |
| **形式の仕様（性質の式）** | B−G | B |

- 因子 1「門」：門ありは pipeline の門の列（高速検査・whitelist・静的検査・性質テスト・P2P・不変条件）を通し、落ちたら知らせ（§3）を付けて再試行する。門なしは実装役を 1 回だけ呼び、そのまま測定する
- 因子 2「仕様の形」：自然言語は §2 の機械的な描画、形式は V2-RUN と同じ性質の式と式の読み方
- **全条件で同じもの**：作業場所（細い作業場所）、書き換えてよいファイルの中身、既存の型と契約のファイル（型の境界。コンパイルに要る）、interface の描画、参照データの定数（GddReference の抜粋）、作業場所の決まり（`tool_policy`）、モデル・TTL・CLI の版
- Q1 の効果 ＝ 門の主効果（A1＋B）−（A0＋B−G）、Q2 の効果 ＝ 形の主効果、交互作用も推定する

### 1.3 プロンプトの組み立て（確定）

呼び出しごとに、次の順で連結する（字数は要素ごとに `prompt_parts` に記録）：

1. 作業場所の行（全条件同じ）
2. 仕様（A：自然言語の描画／B：性質の式と式の読み方）
3. interface（全条件同じ）
4. 埋め込み（全条件同じ手順。中身は各条件のそれまでの実装）
5. 門ありの再試行のときだけ：前回の知らせ（§3）
6. 作業場所の決まり（全条件同じ）

## 2. 自然言語の仕様の生成と情報量の対称性（項目 2）

### 2.1 生成の手順（確定）

- **人も LLM も使わない**。性質の宣言（`properties.json` と同じ形）から、決定論的な描画器（新設 `harness/nlgen.py`）が日本語の文を作る
- 描画器は語句の対応表（識別子・演算子・関数 → 決まった語句）と、1 性質 1 文の型紙だけを持つ。対応表は本書の承認とは別の PR で人間が一度だけ査読し、以後は凍結する（sha256 をマニフェストに記録）
- 例（形だけの例）：`input.Left && !input.Right && fits(moved(m, -1, 0))` → 「左の入力があり、右の入力が無く、ミノを 1 マス左に動かした位置に置けるとき」

### 2.2 情報量の対称性の統制（確定）

| 規則 | 機械の検査（描画のたびに実行、破れたら止める） |
|:--|:--|
| 事実の集合は同じ | 形式の性質 1 件に、自然言語の文がちょうど 1 文。性質の ID・出典（rule）を文に付ける |
| 語彙の対応は全単射 | 性質に出る識別子・関数・演算子は、すべて対応表に 1 対 1 で載る。対応表に無いものが出たら止める |
| 定義の閉包 | 形式側の「式の読み方」の関数（fits・moved など）は、自然言語側でも同じ意味の説明文を 1 回だけ出す（`propgen.FUNC_DOCS` から描く） |
| 量の偏りの記録 | 条件ごとに仕様の字数を記録し、報告で並べる（形の違いによる字数の差は、効果の一部として扱う） |

- **採らない案**：v1 の要求文（人が書いた自然言語）を A に渡す案。性質の無い ID を名指し（56 のうち 13）、事実の集合が形式側と違うので、Q2 が「形」ではなく「中身」の差になる。産業の素朴な基準としての意味はあるが、Q1・Q2 の単離を優先する

## 3. 門の知らせ（項目 3）

### 3.1 知らせの中身（確定）

門ありの 2 条件（A1・B）は、**同じ判定器（`pipeline.judge`）の同じ知らせ**を受ける。違いは、性質を指すときの書き方だけ。

| 知らせの種類 | B | A1 |
|:--|:--|:--|
| 性質の破れ（反例） | `PROPERTY_FAIL id=… rule=… ops=[…] expected=… actual=…`（最大 5 行） | 同じ 1 行に、その性質の自然言語の文（§2 の描画）を添える。式は出さない |
| 前提が 1 度も成り立たない | `PROPERTY_VACUOUS id=…` | 同じ行に自然言語の文を添える |
| コンパイルの失敗 | コンパイラの診断の行（パスは作業場所に置き換え、最大 N 行。N は現行と同じ） | 同じ |
| P2P の破壊 | 壊したテストの名前の一覧 | 同じ |
| whitelist・静的検査 | 現行の知らせ | 同じ |

- **両条件とも渡さないもの**：生のテストの出力、スタックトレース、テストのコード、LLM による要約
- 知らせの字数は記録する（`prompt_parts.feedback`）

## 4. 再試行・時間・費用の上限と緊急停止（項目 4）

### 4.1 再試行と時間（確定）

| 項目 | 門あり（A1・B） | 門なし（A0・B−G） |
|:--|:--|:--|
| タスクあたりの実装役の呼び出し | 最大 9（試行 3 × 内側ループ 3。`max_attempts` 3、`pipeline.MAX_INNER_LOOP_TURNS` 3） | ちょうど 1 |
| 1 呼び出しの TTL | 300 秒（`projects/falling-blocks/pipeline.json`）。agy の `--print-timeout` は 280 秒 | 同じ |
| TTL の打ち切り（rc 124） | 1 回の呼び出しとして数える。利用量は下限（partial）の印を付けて記録 | 同じ |

### 4.2 費用の上限（確定）

**最悪の場合の見積もり**（見積もりの根拠：V2-RUN の 1 呼び出しの費用の最大は 0.1213 USD。再試行でプロンプトに知らせが加わることを見込み、1 呼び出しの上限を 0.5 USD とおく）：

- タスク数を T、走行の繰り返しを R とすると、1 繰り返しの最悪 ＝ T ×（9 + 9 + 1 + 1）× 0.5 ＝ 10T USD
- T = 20、R = 4 なら最悪 800 USD。**これを上限にはしない**。上限は下の Hard Cap で、最悪に達する前に止める

| 上限 | 値 | 当たったとき |
|:--|:--|:--|
| 1 呼び出し | 0.5 USD（手番の利用量の和から、§9 の式で数える） | その走行を止める（想定外の暴走。調べてから再開） |
| 1 繰り返し（4 条件 × T タスク） | 15 USD | その繰り返しを止め、人間に報告 |
| 中間の線 | 25 USD（累計） | 止めずに監査。人間の確認で続ける |
| **全体の Hard Cap** | **50 USD（累計）** | **すべてのドライバを自動で止める**（guard） |

- 監視は guard（`harness/ab/guard.py`）を拡張し、1 呼び出しの上限と 1 繰り返しの上限を足す（§12）。費用は実装役のログの手番の利用量から 15 秒ごとに数える

### 4.3 緊急停止の条件（確定）

| 条件 | 扱い |
|:--|:--|
| 作業場所の外のファイルの中身を読む手番、ビルド・テストを走らせる手番 | 止める（現行の guard） |
| モデルが設定と違う・報告が無い（`model_pin`） | 止める（game-harness#105） |
| 実行環境が固定の版と違う（§5） | 起動しない |
| 費用の上限（§4.2） | 止める |
| 通信の失敗が 3 回続く（§10） | その繰り返しを止める |
| 受入の不合格・P2P の破壊・不変条件の違反 | **止めない**（v2r ではこれが測る対象。A0 で起きることを期待している） |

### 6.1 モデル（確定。game-harness#105 を前提にする）

| 役 | CLI | モデル | 思考の重さ |

### 6.2 サンプリングのパラメータ（実測と方針）

- **実測**：agy 1.2.11 と claude 2.1.258 の `--help` に、temperature・top_p・seed を指定する引数は無い（あるのは `--model`・`--effort` など）。**CLI を使う限り、これらは指定も記録もできない**（提供側の既定値で動く）
- **方針（確定）**：
  1. `env.json` に「temperature・top_p・seed：CLI で指定できない（提供側の既定）」と明記する。値を推測で書かない
  2. 非決定性は繰り返し（R）で扱い、すべての出力（§7）を残す。報告は中央値と範囲・四分位で行う
- **人間の判断が要る点**：サンプリングを固定したいなら、実装役を API の直接呼び出し（temperature・seed を指定できる）に替える必要がある。これは 2026-09-25 に却下した「agy を外す案」と同じで、ファイルを編集する道具の層を自前で作ることになる。本書は agy のままを推奨する（V2-RUN と同じ実装役で、門の因果だけを変える）

## 7. プロンプトと生データの保存（項目 7）

### 7.1 保存するもの（確定）

| もの | 中身 |
|:--|:--|
| 実装役に渡したプロンプトの全文 | 標準入力に渡した文字列そのもの（型紙の変数の展開の後）。呼び出しごとに 1 ファイル |
| 実装役の出力の全文 | agy の stream-json の全行（init の tools の一覧・手番・利用量・応答） |
| 判定の記録 | pipeline のテレメトリ（JSON）、metrics.jsonl、測定器の結果（trx） |
| 入力 | 単位定義・性質の宣言・描画器の対応表・型紙・契約の生成物、それぞれの sha256 |
| 環境 | `env.json`（§5）、モデルの記録（§6） |

- **agy のシステムプロンプトは保存できない**。agy が内部で付け、呼び出しごとに変わる（同じプロンプトでも入力のトークン数が 13,285・13,293・13,295 と変わった。`v2_b_efficiency.md` §1.4）。代わりに agy の版と、init が報告する道具の一覧を記録する

### 7.2 置き場所と公開の手順（確定）

1. 走行の後、ハーネスが各繰り返しの出力を 1 つのアーカイブ（`v2r-<run-id>.tar.gz`）にまとめ、中のファイルごとの sha256 を並べたマニフェストを作る（新設 `experiments/v2r/tools/pack.py`）
2. アーカイブは game-harness の GitHub Release の資産として公開する（game-harness と falling-blocks はどちらも公開リポジトリ。プロンプトに含まれるゲームのコードも公開済みのもの）
3. リポジトリには、マニフェストとアーカイブの sha256、Release のタグだけを置く（`experiments/v2r/results/<run-id>/manifest.json`）
4. 第三者は Release から取得し、`experiments/v2r/tools/verify.py` で sha256 を照合してから集計を再現する
5. 集計の道具（report・percall・smoke_gate の後継）は、ローカルの絶対パスではなく、展開したアーカイブのディレクトリを引数に取る

- **防壁①との関係**：アーカイブにはゲームの Core のコードとテストの生成物が入る。総監督はアーカイブを展開して読まない（集計は道具が行い、総監督は道具の出力の数だけを見る）

## 8. テストのオラクルの妥当性（項目 8）

### 8.1 測るもの（確定）

| 指標 | 方法 | 合格の線（本走に入る条件） |
|:--|:--|:--|
| 変異の死滅率 | 門ありの条件で受入に通った実装に、C# の変異の道具（Stryker.NET を第一候補、版は §13 で固定）で変異を入れ、性質テスト（公開＋非公開シード）で殺せた割合をタスクごとに測る。実行と集計はハーネスが行い、総監督は割合と変異の種類の数だけを見る | タスクごとに 80% 以上 |
| 前提の成立回数 | 性質ごとに、前提が成り立ったティックの数（既存の PROPERTY_VACUOUS の検査を数に広げる） | すべての性質で 1 以上（0 の性質は欠陥） |
| 非公開シードでの検出 | 公開シードだけで通り、非公開シードで落ちた回数（V2 の v2-dry-04 の A で 1 件の実例） | 記録のみ |
| 門をすり抜けた欠陥 | 門に無い非公開の検査（不変条件・非公開シード）でだけ見つかった欠陥の数 | 記録のみ（Q1 の副指標） |

- 生き残った変異は、種類と数を報告に載せる。80% に届かないタスクは、性質の宣言を直してから本走に入る（直した版をマニフェストに記録）

## 9. 課金とトークンの集計（項目 9）

### 9.1 式（確定。`harness/ab/report.py` の `call_cost`）

1 回の呼び出しの費用（USD）＝（入力 × 0.75 ＋ 出力 × 3.75 ＋ キャッシュ読み × 0.075）÷ 1,000,000

- 単価の出典：`experiments/v2/cost_model.json`（Gemini API の料金表、Gemini 3.8 Flash の Standard、2026-09-24 に確認）。v2r でも同じ単価を使い、単価の確認日をマニフェストに記録する
- **1 回の呼び出しの利用量は、手番ごとの利用量の和**。agy の result の利用量は会話全体の累計なので使わない（game-harness#91）
- **思考のトークンは出力に含まれ、出力の単価で数えている**。実測：V2-RUN の利用量を持つ 112 手番のすべてで、思考 ≤ 出力（例：出力 8,222 のうち思考 7,180）。v2r でも手番ごとにこの関係を検査し、破れたら止める
- キャッシュ読みは入力に含めない（`cache_read_included_in_input: false`）

### 9.2 キャッシュの記録（確定）

| 事実（実測） | 記録 |
|:--|:--|
| agy では、会話をまたいだプレフィックスキャッシュは効かない（新しい会話で同じプロンプトを 3 回渡し、キャッシュ読みは 3 回とも 0。`v2_b_efficiency.md` §1.4） | 全条件がステートレスなので、最初の手番のキャッシュ読みは 0 が期待値。0 でない最初の手番を数える |
| 1 回の呼び出しの中では、2 手番目以降にキャッシュ読みが出る | 手番ごとの（入力、キャッシュ読み）を残す |
| キャッシュの有効期限（TTL）は agy から観測できない | 「観測できない」と記録する。推測しない |

- キャッシュの失敗（2 手番目以降でキャッシュ読みが 0）を手番ごとに数え、報告に載せる

### 9.3 請求額との照合（確定）

計算の値は請求額ではない。本走の後、人間が Gemini API の請求の記録（走行の時間帯）を取り出し、計算の合計と並べる。差が 10% を超えたら、報告の費用はすべて「計算の値（請求と未照合）」と明記する。

## 10. 通信の失敗とレートリミット（項目 10）

### 10.1 扱い（確定）

| 事象 | 見分け方 | 費用 | 呼び出しの上限に数えるか | 動作 |
|:--|:--|:--|:--|:--|
| レートリミット・一時的な失敗（429・RESOURCE_EXHAUSTED・503 など） | agy の result の status が ERROR で、エラーの先頭の行がレートリミットの文字列に当たる（文字列の一覧は §13 で実測して固定） | 手番の利用量があれば費用に数える（払っているので） | **数えない**（環境の失敗で、モデルの振る舞いではない） | 60 秒・120 秒・240 秒待って、同じプロンプトで呼び直す。3 回続けて失敗したら、その繰り返しを止める（環境の異常。繰り返しごと捨てて、後で走り直す） |
| TTL の打ち切り（rc 124） | 終了コード | 下限として数える（partial の印） | 数える（モデルが時間内に終えなかった） | 通常の再試行の規則（§4.1） |
| その他の ERROR（上限の超過など） | status が ERROR で、上の文字列に当たらない | 数える | 数える | 通常の再試行の規則 |

- 呼び直しの回数・待ち時間・理由はすべて記録し、報告に載せる。捨てた繰り返しも、アーカイブとして保存する

## 11. 測定と解析の計画（事前登録）

### 11.1 主要な指標（確定）

| 指標 | 定義 |
|:--|:--|
| 最終の欠陥 | タスクの終わりの測定で、受入の不合格・P2P の破壊・不変条件の違反のどれかがあるタスクの数 |
| 先祖返り | P2P の破壊の件数（前のタスクのテストで、前のタスクの終わりに通っていたもの） |
| 門の働き | 門ありの条件で、最初の提出が不合格だったタスクの数と、最終で直ったタスクの数 |
| 費用・秒 | §9 の式、条件の仕事の秒 |

### 11.2 仮説と判定（確定）

- H1（Q1）：門ありの条件（A1・B）の最終の欠陥は、門なしの条件（A0・B−G）より少ない
- H2（Q2）：同じ門の水準で、形式の仕様の条件の最終の欠陥は、自然言語の条件より少ない
- 判定：タスク × 繰り返しの単位で、条件間の差の中央値と、ブートストラップ（10,000 回）の 95% 信頼区間を出す。区間が 0 を含むときは「差があるとは言えない」と書く。費用の差も同じ扱い（V2-RUN の「0.89 倍」の誤りを繰り返さない）
- 繰り返し R は 4 から始め、乾式の走行のばらつきから、H1 の差の区間の幅を見積もって決める（本書の承認とは別に、乾式の走行の後で人間の承認を取る）

### 11.3 タスクの系列（方針。系列そのものは別の PR）

- 先祖返りの圧力がある系列にする：同じメンバーを複数のタスクが触る、前の振る舞いを保ったまま内部を変える、横断的な仕様の変更
- **天井の検査**：乾式の走行で A0 を走らせ、最終の欠陥が 1 件以上出ることを確かめる。出なければ系列が易しすぎるので、本走に入らない
- 系列を決めた後は、実装役が通りやすくなる方向の変更（文面の整理、前提の緩和）を入れない。入れてよいのは測定器の欠陥の修正だけで、修正したら乾式の走行からやり直す

### 11.4 会計（確定）

- F_shared（系列の宣言の費用）と F_B_only を分けて測る。F_B_only は、門の実行の秒と費用、宣言の手直しの回数と時間を測る。ハーネスの開発・保守の費用は測れないので、損益分岐は F_B_only を変数とした感度の表で出す（1 つの N* を主張しない）
