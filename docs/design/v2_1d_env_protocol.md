# v2.1d：作業場所の決まりを事実として示し、空回りの手番を削る

- 状態: 方針・実装済み。検証の走行（v2-dry-06）は §4
- 前提: v2-dry-05c（game-harness#82、`experiments/v2/results/dry_run_t1/notes.md`）
- 方針（2026-09-25、オーナー）: 総監督（Claude）× 実装役（agy）の 2 モデル構成を保つ。API 1 回化（v2.1c §5.3 の (c)）は破棄。実装役の道具は取り上げない。空回りは、作業場所の決まりを事実として示して削る。TTL 300 秒は緩めない
- 結論: 空回りの原因は 3 種と特定した（§1）。うち 1 種は**作業場所の仕組みの欠陥**（ほかの走行の作業場所が読めた）で、プロンプトではなくコードで塞いだ。残り 2 種と一覧の取得は、作業場所の決まりをプロンプトに事実として書いて削る。v2-dry-06 で手番と秒を確かめ、基準を満たせば V2-5 を complete する

## 1. 事実：v2-dry-05c の空回りは何だったか

v2.1d で、道具の手番の引数（コマンドの先頭の語・`manage_task` の Action・作業場所の外を指したか）を記録するようにした（§3 の 3）。v2-dry-05c の生の出力から、引数だけを取り出して数えた（ファイルの中身とコマンドの出力は見ていない）。

### 1.1 `manage_task` は作業の管理ではなかった

`manage_task` の 24 回（A 10・B 14）は、すべて `Action: status` で、TaskId は直前の `run_command` の手番を指していた。agy の端末の操作は非同期で走り、`manage_task` はその完了待ち。**`run_command` 1 回ごとに `manage_task` 1 回と約 8.2〜10.3 秒がつく**。`run_command` が無くなれば `manage_task` も無くなる。

### 1.2 `run_command` の中身（A 10・B 14）

| 種類 | A | B | 例 |
|:--|:--|:--|:--|
| 作業場所の一覧・検索 | 5 | 3 | `Get-ChildItem -Recurse <作業場所>`、親の `harness-narrow` の一覧、`-Filter GameState.cs` |
| **ほかの走行の作業場所のファイルを読む** | 0 | 6 | `Get-Content <A の作業場所>\...\GameState.cs`（同じ走行で先に走った A の作業場所）、前の走行の作業場所 |
| 仕様 ID の定義探し | 2 | 1 | `Select-String -Pattern "ST-09\|ST-10"` |
| 検証の道具を探す | 3 | 4 | `*.log`・`*.csproj`・`*Test*.cs` の検索、`git log`・`git status`、`Get-Command dotnet` |
| 作業場所の外を指した手番 | 6 | 10 | |

- **B の実装役は、同じ走行で先に走った A の作業場所に残っていた `GameState.cs` と `Board.cs` を読んでいた**。v2.1c の作業場所は、OS の一時ディレクトリの下の共通の親（`harness-narrow`）に置き、呼び出しの後も消していなかった。**v2-dry-05c の B の結果は A の実装に汚染されている**。A も親を一覧し、前の走行の作業場所を一覧していた
- 仕様 ID を探したのは、単位定義の要求文（v1 から写した文章）が ST-09・ST-10 などを名指しし、その定義がプロンプトに無いから
- 検証の道具を探したのは、ビルドとテストの手段が作業場所に無いことを知らないから
- B の 14 回 × 約 9 秒 ≈ 125 秒が、実装役の 270.3 秒のうち端末の操作の待ちだった（推定。手番の秒の合計ではなく、`run_command` の手番の秒を足した値）

### 1.3 諮問の記述との違い

| 諮問の記述 | 事実 |
|:--|:--|
| 存在しないファイルを探す端末操作 14 回 | 14 回のうち 6 回は、存在する**ほかの走行の**ファイルを読んでいた。探すだけでなく、読めていた |
| 不要なタスク管理ツールの呼び出し 14 回 | 端末の操作の完了待ち。端末の操作を削れば消える |
| 隔離ディレクトリの外に何かあるのではと勘違いした | 勘違いではなく、実際に外（親）にほかの走行の作業場所があった |

## 2. 方針

| 原因 | 手 | 区分 |
|:--|:--|:--|
| ほかの走行の作業場所が読める | **呼び出しの後に作業場所を消す**（書き戻してから）。走行の前に、残っていた作業場所を消した（31 個） | 仕組み（コード） |
| 作業場所に何があるか分からない | 埋め込みの頭に**作業場所のファイル一覧**を置く | 事実の提示 |
| 仕様 ID の定義が無い | 「RL-xx・ST-xx・LP-xx は性質の出典を示すラベルで、この仕事での意味は書いてある性質がすべて。PR-xx は GddReference の定数」と書く | 事実の提示 |
| 検証の道具が無いことを知らない | 「ビルドとテストの道具（dotnet・テストプロジェクト・ログ・git）は作業場所に無い。検証は外側が行い、失敗は反例で返る」と書く | 事実の提示 |
| — | 「ですから、一覧・検索・読み直しのための端末のコマンドも、manage_task・schedule も要らない。編集したら終える」 | 事実からの帰結 |

実装役の道具は取り上げない（agy の設定も変えない）。禁止の言い方（「〜しないでください」）は使わず、作業場所の決まりを事実として書く。A・B に同じ文面を当てる。
