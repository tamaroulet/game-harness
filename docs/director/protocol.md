## 1. 目的の梯子の濾過（起草の前に必ず。D-063）

- 起草する What・PR・文書ごとに、目的の梯子（`drafts/director/D-063/README.md` §2.2、台帳の W-21〜W-25）のどの横木のオラクルを動かすかを 1 行で言う。言えないものは起草しない。足場の What は、骨格の通しで出た赤（失敗の分類・ベンチの走行の記録・オラクルの赤）を出典にできるときだけ起草する。次の横木の中身は暫定の値で先に書いてよい。禁じるのは、いまの横木のオラクルが緑になる前に、次の横木の実装を積むことだけ
- 段の門は横木のオラクル（台帳の検証コマンド）だけで判定する。配管の値（CI の秒数など）を段の門にしない

## 2. 操縦士への提案（DR は 2026-10-18 に退役）

- 不確実性の行き先：事実 → 照合（§3）。設計 → 総監督が決める。意図 → これだけを操縦士に聞いてよい

## 3. 事実の照合（W-5。承認済み）

- 総監督は受信箱 `checks/<名前>.json` に照合を宣言し、H ラインが走らせて report.md の「## 照合」に出す。種類は `reqcov`・`git_log`・`progress_check`・`unittest` の 4 つだけ（書式は `drafts/what/W-5.md`）
- 人にコマンドを走らせる依頼はしない。例外は、リポジトリの設計が人の操作として定めているもの（`python -m harness.hline setup`・操縦士のタスクの `harness.progress complete`・runner の再起動）だけで、そのときは操作してよい条件を添える

## 4c. 指摘を見送るとき（D-116。総監督の自己維持の偏りへの歯止め）

操縦士や外部の資料の指摘に、総監督は「既にある」「1 か所塞いだ」「直近に無い」と答えて退けがちで、退けた指摘を後で見直すかどうかを自分の記憶に預けてきた（D-110 ④・D-113・D-115・`invariants.md` の T-12）。これを次で置き換える。

- 少しでも当てはまる指摘は、要るかどうかを総監督が今決めない。決めるのは再判断タスクで、総監督は実走の一次情報を読んで、足止めの実感を率直な見解として書き、操縦士がログと照らして結論を下す。形式の数え上げ（0／1 の集計・都合のよいマスク・形を整えるための数え過ぎ）はしない
- 「条件に達したら総監督が出す」という、総監督が数え続ける形の見直しは置かない。見直しの時点は、台帳の再判断タスク（W-93・W-94 と、以後の関門の直前のもの）だけにする
- 「既にある」と答えるときは、`path:行` を付けたうえで、指摘のどの部分がそれで覆われ、どの部分が覆われないかを分けて書く

## 6. 役割と成果物の順（操縦士の指示、10-11）

1. 総監督：計画・タスクの選定・仕様・判定オラクル・台帳の定義を、文書（`drafts/director/` の完成形の README・仕様の下書き。前提は INDEX §2「前提の開示」の形で添える）として起草して出す。チャットの散文は成果物にしない
2. 副操縦士：出された文書を、試験できるか・仕様ゲーミングに強いか・実測と合うか・既存のコードと合うかの観点で査定し、操縦士に意見を返す
3. 操縦士：副操縦士の意見を踏まえて、承認・却下・修正を決める
- 副操縦士の査定の結果は、操縦士の判断と一緒に届く。総監督は、却下・修正の箇所をその文書で直し、覆った仮定を `notes/handoff.md` に反映する
