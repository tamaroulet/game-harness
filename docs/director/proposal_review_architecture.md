# レビューパイプラインとタスク木階層の分離設計書
副題: 機械・AI・人間の責務境界と、人間を律速にしない自律開発アーキテクチャ

2026-10-25 会話の席（操縦士・副操縦士）起草

---

## 1. 背景と課題認識（混同の是正）

これまでの議論において、「レビューの 3 層（機械・AI・人間）」という審査の段階と、「タスク木の階層（下層タスク・中層要件・上層マイルストーン）」という仕事の構造が安易に 1 対 1 で対応づけられ、「3 タスクのまとまり」といった人為的な数字に計画を縛る歪みが生じていた。

この混同は、以下の 2 つの現場破綻を招く：
1. **安全網のすり抜け**: 個別タスクであっても保護パス（CI 設定や権限）に触れる高リスク変更が存在する。それを「タスク層だから機械だけで通してよい」とすると、本線を破壊する。
2. **不要な自律停止（人間の律速化）**: 上位の節目であっても、機械テストが全緑で AI の所見にも懸念がなければ自律進行できる。それを「上位階層だから人間が止めなければならない」とすると、夜間自律走行が停止し、開発速度が完全に人間の生活リズムに律速される。
3. **LLM の Gate 化による破綻**: LLM の定性評価を自動マージの合否判定（Gate）に直結させると、誤合格による本線破壊か、過剰警戒による自律停止の二者択一に陥る。

本設計書では、直交する 2 つの軸（審査の深さとタスクの深さ）を完全に分離し、人間を律速にしない自律開発のアーキテクチャを定義する。

---

## 2. 直交する 2 つの軸の定義

### 軸 A: レビューパイプラインの 3 段階（審査フィルタの深さ）
変更の粒度やタスクの階層に関わらず、すべての変更が通過する直列のフィルタである。

```
[変更の発生]
    │
    ▼
【第 1 段階：機械検査 (Deterministic Gate)】 ── FAIL ──→ [差し戻し・修正]
    │ (構文・fastsuite・受入 exit 0・保護パス判定)
    ├─ PASS (Tier 1 低リスク)
    │   │
    │   ▼
    │ 【第 2 段階：AI 審査 (Qualitative Findings)】
    │   │ (Argon / 総監督による 1 ホップ波及・例外・モック乖離の所見)
    │   ├─ 重大リスク (HIGH) 検知 ──┐
    │   │                           ▼
    │   └─ 通常所見 (LOW/MED) ──→ 【副操縦士が自律マージ・同期】
    │                              (※現在フェーズは総監督合格後に自律マージ)
    │
    ▼ PASS (Tier 2 高リスク：保護パス・CI設定・ワーカー変更)
【第 2 段階：AI 審査で所見を生成】
    │ (所見の内容に関わらず、高リスクは必ず第 3 段階へ)
    ▼
【第 3 段階：人間裁定 (Human Decision)】
      (操縦士による判断点 1 行への大局 GO/NO-GO)
```

1. **第 1 段階: 機械検査（決定論的 Gate）**
   - **担当**: GitHub Actions CI、ローカル fastsuite、受入テスト（`exit 0`）、パス検査（`freeze.json`・`config/protected_paths.json`）。
   - **性質**: 100% 再現可能な客観的事実のみで合否を判定する。この門を通過しない変更は、AI や人間のレビューに回すことなく機械的に遮断する。
2. **第 2 段階: AI 審査（定性所見・発見）**
   - **担当**: 独立評価役 Argon、総監督。
   - **性質**: 人間と同様に「方向性のフィードバック」と「機械テストがすり抜けがちな死角（1 ホップ先の未捕捉例外、モック実体署名の乖離、親要件に対する抜け漏れ）」を言語化して所見（Risk Scorecard）として提示する。
   - **重要原則**: AI の所見は**「止める向き（重大リスク HIGH を検知して人間へ回す）」にのみ効かせる**。通す向き（「AI が懸念なしと言ったからマージ」）には使わず、合否の鍵（Gate）は握らせない。
3. **第 3 段階: 人間裁定（大局判断・例外承認）**
   - **担当**: 操縦士。
   - **性質**: 機械が「高リスク（Tier 2）」と判定した変更（所見の内容に関わらず直行）、Argon が「HIGH Risk（重大な破綻リスク）」と診断した例外、または大局的節目においてのみ、提示された判断点に対して裁定（GO/NO-GO）を下す。

---

### 軸 B: タスク木（DAG）の階層構造（仕事の分解の深さ）
総監督が課題の性質に応じて柔軟に設計する依存関係グラフであり、レビューの段数とは無関係である。

- 階層数を「3 段」などに人為的に縛らない。2 階層で済むものもあれば、4 階層に深掘りするものもある。
- 木の親ノード（要件節 `req.*` や大目標）は「満たすべき目的（`achieved_when`）」を持ち、子ノード（タスク `W-*`）は「実現するための実務手順」を持つ。
- タスクの個数や深さでレビューを区切るのではなく、**「リスク」と「自律性」の観点**から動的にレビュー段階が適用される。

## 3. 人間を律速にしない自律走行の動作モデル

操縦士が開発のボトルネックにならないための動作規則を以下の 3 つに集約する。

### 3.1 定常走行と自律マージの移行条件
- **フェーズ 1（現在 〜 パスから層を決める機械検査が CI に入るまで）**:
  - PR を作成した副操縦士自身が層を決める自己検証の穴を防ぐため、**「総監督の検め合格 ＋ CI 全緑」を確認した上で、副操縦士が自律でマージ・ローカル同期を行う**現行運用を継続する（枝の写し直読により検めは軽量化済み）。
- **フェーズ 2（触れたパスから層を決める機械検査が CI に入った後）**:
  - 機械検査で Tier 1（低リスク）と確定し、CI が全緑で、AI 所見に HIGH がない変更は、総監督の検めを挟まずに副操縦士が完全自律マージ・同期へ移行する。
  - 要件節（`req.*`）が完了しても、後続タスクが低リスクで安全基準を満たしていれば、人間を呼び出さずに数珠繋ぎで自律進行する。

### 3.2 例外エスカレーション（人間が呼ばれる条件）
人間が呼び出されるのは、以下のいずれかに該当した時のみとする：
1. **膠着・連続失敗**: 同一タスクでの機械テスト失敗や構文エラーが 3 回連続した時。
2. **物理的高リスク（Tier 2）**: CI ワークフロー、合否判定スクリプト、常駐ワーカー、保護パス（`freeze.json`）に触れる変更の時。
3. **AI による重大破綻検知（HIGH Risk）**: Argon または総監督が、1 ホップ呼び出し元の例外貫通やデータ破壊などの重大リスクを指摘した時。

### 3.3 大局的節目の人間レビュー
- 上位のマイルストーン（親グループ）完了時、または Outer Loop（R4 本番走行）突入時のみ、操縦士が「事前 GO」および「事後成果物」を 5 行要約で確認・承認する。
- 定常時に細切れの承認を求めないことで、操縦士の認知負荷を最小化する。

## 4. 台帳およびタスク木への具体的反映

本設計に基づき、保留されていたタスクおよび台帳の配線を以下のように確定する。

1. **W-172（Argon 評価役）の着手**:
   - 巨大な影響束（Context Bundle）生成器を詰め込んでタスクを肥大化させず、まずは総監督 40 本目の合意どおり**「リポジトリ全体を読める場所で走り、文章の定性評価に構造化された所見（LOW/MED/HIGH と判断点）を添えて費用を記録する」**コンパクトなタスクとして着手する。
   - `depends_on: [W-150, W-152]` とし、W-152 完了直後に着手可能とする。
2. **W-154（操縦士への要約報告）の再定義**:
   - 個別のコード変更を追うのではなく、操縦士が 30 秒で判断できる**「高リスク PR 要約（判断点提示）」および「大局的節目の進捗要約」を機械生成する道具**として再定義する（`depends_on: [W-172]`）。
3. **W-152（知識の正本化）の実装**:
   - 総監督が日々書き換える 3 文書（`notes/handoff.md`、`drafts/director/INDEX.md`、`drafts/tree/tree.yaml`）は受信箱の下書きに残し、台帳や木に触れる PR のついでに正本（`docs/director/`）へ同期する運用とする（写し単独 PR の乱発防止）。
   - 総監督の権限変更（L5）は生じないため、直ちに実装に着手する。
