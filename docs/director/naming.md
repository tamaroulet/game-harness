## 1. 問いの芯への答え

AI と人間で表記を分けない。人間も AI も同じ台帳（`docs/progress.yaml`）の同じ欄を読む。対応表も見え方の変換も持たない。
読みやすさは ID の字面ではなく、決まった 1 つの表示の形（§3）で出す。
人の作業も H ラインの作業も、同じ台帳の同じ ID の列に載せる。違いは執行者の欄だけで表す（D-056）。

## 2. 属性（台帳の欄）

| 属性 | 欄 | 規則 | 機械の強制 |
|---|---|---|---|
| 識別 | `id` | 新しい ID は `W-<n>`。n は台帳の最上位の `next_id` から払い出し、払い出したら `next_id` を 1 増やす。一度払い出した ID は変えない・再利用しない。欠番は埋めない（W-2・W-3・W-6・W-7・W-9 は欠番）。nodes と tasks で 1 つの番号の列を使う | 運用（台帳は人の PR でしか書かれない） |
| 階層 | `parent`（ノード）・`group`（タスク） | いまの欄のまま。ID の字面は親を表さない | 既存（`harness/progress.py:76-90`） |
| 外部の記録 | `pr`（タスク） | 完了の後に、マージした PR を `game-harness#165` の形で残す。名前には使わない | 運用 |

旧 ID（A・B2〜B8・B7.1・S1-2・G0・G0-5・Phase 4-1 など 90 個）は改名しない。字面の数字や字に意味を読まない。これより後に足す ID は `W-<n>` だけ。

## 3. 表示の形と What のファイル

- ツリー・報告：`<id> <title>`。`by: pilot` のタスクには「（操縦士）」を付ける。総監督の文書・操縦士への報告は `W-4（済みにした時刻をキューに残す）` のように id と title。GitHub の PR は `game-harness#165` の形で、名前としては呼ばない
- タスク：確かめられる到達点（検証コマンドで完了が決まるもの）。1 つのタスクの下の What は何件でもよい（D-048）
- What のファイル：タスクを完了にする What は `<タスクの id>.md`（例 `W-4.md`）。それ以外は英数字とハイフンの短い名前。受信箱の番号（870・910 など）の別の列は使わない
- `タスク:`：タスクを完了にする What だけが宣言する
- `依存:`：タスクを持たない What にだけ使う（依存先の What の名前）。タスクの順は台帳の `depends_on` が決め、W-8 が What に引く

## 4. 計画の変更（D-056）

- 方針が変わったら、その時点で台帳の PR を出す（D-062。D-056 ④ の「段の開始の PR にまとめる」はやめた）。人の作業（ワークフロー・保護パス・設定の変更など）も、`by: pilot` のタスクとして登録する
- 操縦士のタスクの完了：その作業の成果が main に入った後、次の操縦士の PR（台帳の PR があればその中）で、操縦士が `python -m harness.progress complete <id>` を走らせる。検証コマンドは origin/main の台帳の版のもので、成果が main に無いと通らない（W-31 で確かめた手順。D-074 ③）

## 5. D-037（`retired/2026-10-15/decisions.md`）の 3 つの歪みへの答え

1. 表記の二重化（タスク ID と受信箱の番号、W-n と PR-N）→ 受信箱の番号を廃止。PR の番号は外部の記録の欄へ。タスクを完了にする What のファイル名＝タスク ID
2. タスクの粒度の不揃い → タスクは確かめられる到達点、What はその下の実装の単位
3. ツリーの表示と実行の順のずれ → ツリーは階層、実行の順は依存の DAG と台帳の並び。依存は台帳にだけ書く

## 6. 規則の改め方（D-046）

- ノードとタスクで番号の列を共用する。種類は欄で表す
- ID の名前空間は台帳 1 つに 1 つ（`W`）
