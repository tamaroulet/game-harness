D-109（10-15）により、段 3 ではチャット型を走らせず、主要な評価項目（§4.1）・段と止め方（§6）は使わない。この規約は、工廠の走行（W-46・W-88・W-89・W-57）の手続き（§1 の工廠の分・§5・§7・§8）として使う。チャット型との比べは R5 の製品の付け足しで行い、そのときにこの規約を改めて事前登録する。

段 4 では、REQ-37 で変えないものを物差しに限る：課題の仕様・非公開オラクル・CLI の版とモデル ID・工廠の 1 走行の上限（REQ-17）・採点（W-34）。工廠の構造（REQ-08 の指示・REQ-09 の道具・REQ-16 の実装役の予算）は、外側の周期の非劣性の検査（W-57）に合格した変更だけを入れてよい。入れたら REQ-39 の表に 1 行足す（D-111）。

# ベンチの比較の規約（チャット型 対 工廠）

凍結（W-23 の `bench/records/freeze.json`）の前に決めて main に入れる、事前登録の規約です。凍結の後は §8 のとおり変えません。要件 ID（`REQ-NN`）は、走らせ役（W-45・W-46）・検め直し（W-47）・判定（W-52）の What の `要件:` の行から参照します。

問い：同じモデル・同じ道具・同じ仕様・同じ出発点で、工廠の構造（計画・監修・Gate 1 による試験の実行と再試行）は、単発の呼び出し（チャット型）より、隠しテストの通過率を上げるか。

## 1. 両条件でそろえるもの

### 1.1 モデルと CLI

- REQ-01：両条件のすべての LLM の呼び出し（チャット型の 1 回、工廠の計画役・監修役・実装役）は、同じ CLI（`claude -p`）と同じモデル ID（凍結の時の `config/hline.json` の `implementer.model`。今は `claude-sonnet-5-5`）で行う。CLI の内部処理のための `claude-haiku-` は両条件で許す
- REQ-02：各呼び出しで CLI が報告したモデル（`modelUsage` の鍵）を記録し、REQ-01 のモデル ID と `claude-haiku-` 以外が 1 つでも現れた走行は無効にする（§5）
- REQ-03：CLI の版（`claude --version`）は凍結の時の値に固定し、走行の環境では自動更新を止める。走行の始めに版を測り、`freeze.json` の値と違えば走行を始めない
- REQ-04：temperature・top_p・seed は CLI に指定する引数が無く（`docs/design/v2r_protocol.md` §6.2 の実測）、指定も記録もできない。記録には「指定できない（提供側の既定）」と書き、値を推測で書かない。非決定性は §6 の段（各段 10 本 × 2 条件 × 1 回）の繰り返しとブートストラップで扱う
- REQ-05：同じモデル ID のまま提供側の中身が変わる恐れに備え、各段の中で、同じ課題の 2 条件を続けて走らせる（§6.3）。どちらかの条件だけが古い時期のモデルに当たらないようにする

### 1.2 仕様・指示・出発点

- REQ-06：両条件に渡す課題の仕様は、凍結の時の `docs/bench/<課題>/spec.md` の同じバイト列とし、走行の記録にその sha256 を書く
- REQ-07：両条件の出発点は、W-44 の開始のコミット（本体・公開の判定役・その試験を除いた、親の無い単独のコミット）の同じ SHA とする。走行の clone はそのコミットだけを持つ
- REQ-08：条件ごとの指示（チャット型の `docs/bench/prompts/chat.md`、工廠の `docs/prompts/planner.md`・`docs/prompts/auditor.md`・実装役への指示を組む `harness/hline_prompt.py`）は凍結の時の版とし、記録に各ファイルの sha256 を書く。実装役と監修役・計画役への入力の全文を、呼び出しごとに保存する（§7）

### 1.3 道具と読めないもの

- REQ-09：LLM に許す道具は、両条件でファイルの読み書きと検索（`Read`・`Grep`・`Glob`・`Edit`・`Write`）だけとする。命令の実行（`Bash`）・ネットワーク（`WebFetch`・`WebSearch`）・下位のエージェント（`Task`）は両条件で許さない。監修役は道具を許さない（工廠の構造の一部）
- REQ-10：両条件の走行は、W-71 の制限の OS アカウントで行い、非公開オラクルの置き場・受信箱・本線の生ログを OS で読めない状態にする。走行の始めに `python -m harness.bench_guard check` が 0 でなければ走行を始めない
- REQ-11：走行の後に `python -m harness.bench_guard scan` を走行のディレクトリ（§7）に掛け、非公開オラクルのパスか canary の文字列が現れた走行は無効にする（§5）

### 1.4 時間・ターン・人

- REQ-12：LLM の 1 回の呼び出しの時間の上限は両条件で同じ 1,800 秒（`config/hline.json` の `ttl_seconds.implementer`）とする
- REQ-13：人は、走らせ役の命令を 1 回打つことのほかに、走行の中身に触れない（プロンプトの打ち直し・エラーの手引き・受信箱やキューや clone の編集・What の置き直し・runner の手での起こし直し）。触れた走行は無効にする（§5）。利用枠の回復待ちを待つことは介入に数えない
- REQ-14：走行は 1 本ずつ順に行い、2 本を同時に走らせない（利用枠と計算機の取り合いを避ける）

## 2. 違えるもの（工廠の構造）

- REQ-15：チャット型は、`chat.md` と仕様の全文を 1 回の呼び出しで渡し、ターンの上限 30 で 1 回だけ呼ぶ（W-45）。試験は走らず、やり直しも無い
- REQ-16：工廠は、計画役（W-42）と計画の監修のループ（W-43）で What と台帳の対を作り、開始のコミットから H ラインで積み切る（W-46）。実装役は 1 試行 15 ターン（続きの試行は 8）・What ごとに 2 試行で、Gate 1 が試験を走らせて落ちた出力を次の試行に渡す
- REQ-17：工廠の 1 走行の上限は、実行の時間 3 時間（利用枠の回復待ちの時間は除いて数え、待った時間は記録する）か、トークン 800 万（§4.2 の名目のトークン）の早いほうとする。上限で止めた走行は、その時点の枝の先端を採点した有効な走行とする

この違いのために、工廠は 1 走行あたりのトークンがチャット型より大きくなりうる。それを隠さず、副次の評価項目（§4.2）で並べて出す。

## 3. 結論の範囲（妥当性への脅威）

- チャット型は命令を実行できない（REQ-09）。結論は「同じ道具の単発の呼び出し」に対する比較に限り、試験を走らせられる対話型のエージェントに対する優位は主張しない
- モデルは 1 つ（REQ-01）。ほかのモデルへの一般化は主張しない
- 課題 10 本は総監督が起草し、天井の検査（W-50：チャット型の平均の通過率 0.85 以下で満点でない課題が 3 本以上）で易しすぎる束を除く
- 提供側のモデルの中身の変化は、同じ ID のまま起きれば検出できない。REQ-05 の並べ方で両条件に等しく掛かるようにする

## 4. 評価項目

### 4.1 主要な評価項目

- REQ-18：1 走行の点は、その走行の枝の先端を W-34 の `score` で採点した隠しテストの通過率（0〜1）とする
- REQ-19：主要な評価項目は、課題を束にした通過率の差（工廠 − チャット型）。課題ごとに条件ごとの点の平均を取り、10 本の課題で差を平均する

### 4.2 副次の評価項目（記述のみ。検定しない）

- REQ-20：トークンは呼び出しごとに入力・キャッシュの書き込み・キャッシュの読み出し・出力に分けて記録する（W-67 の内訳）。名目のトークンはその 4 つの和とする。工廠は計画役・監修役・実装役のすべての呼び出しの和、チャット型は 1 回の呼び出し
- REQ-21：副次の評価項目は、条件ごとの「通過率の和 ÷ 名目のトークン（百万単位）」と、内訳ごとの和。ほかに、工廠の What の試行の合計・監修の差し戻しの回数、チャット型のターン数を並べる（W-49 の表）

## 5. 有効と無効

- REQ-22：無効の走行は、環境と手続きの破れだけとする：REQ-02（モデル）・REQ-03（CLI の版）・REQ-11（漏れの跡）・REQ-13（人の介入）に当たったもの、CLI や走らせ役の異常で止まったもの（レートリミットの 3 回続けての失敗・走らせ役の例外）。無効の走行は理由とともに記録し、同じ課題・条件を新しい run-id で走らせ直す
- REQ-23：モデルの振る舞いによる失敗は無効にせず、点 0 の有効な走行とする：チャット型や工廠がパッケージとその試験（`<パッケージ>/`・`tests/test_<パッケージ>*`）の外に触れた差分（触れたパスを `violations` に記録し、点は 0）、工廠の計画が確定しなかった走行（理由を記録し、点は 0）、時間かトークンの上限で止まった走行（その時点の先端の点）
- REQ-24：同じ課題・条件の走らせ直しが 3 回続けて無効なら、その段を止める（環境が壊れている）。直した後、その段の残りから続ける。止めた事実と理由は記録と一緒に main に入れる

## 6. 段と止め方

### 6.1 段

- REQ-25：1 段は、凍結した 10 本 × 2 条件 × 1 回の有効な走行とする。段は 3 段までとする

### 6.2 判定（W-52）

- REQ-26：各段の後に、それまでのすべての段の走行から、課題ごとに条件ごとの走行を復元抽出するブートストラップ（10,000 回、乱数の種は段の番号）で、主要な評価項目の 1 − 0.05/3（約 98.33%）の両側の区間を出す
- REQ-27：区間の下限が 0 より大きければ、工廠の勝ちとしてその段で止める
- REQ-28：第 1・第 2 段の後に、区間の上限が 0.10 より小さいか、差の標本平均が 0 以下なら、損切りとしてその段で止める
- REQ-29：3 段の後に勝ちでなければ、有意差なしとして止める。どの段で何の理由で止めたかと、各段の区間を記録に残す

### 6.3 並べ方

- REQ-30：各段の課題の順は、段の番号を種にした乱数で並べ替える。課題ごとに 2 条件を続けて走らせ、偶数番目の課題はチャット型を先に、奇数番目は工廠を先にする

## 7. 再現の書類（走行の束）

### 7.1 走行のディレクトリ

- REQ-31：走らせ役は、走行ごとに 1 つのディレクトリ `<bench の out>/runs/<課題>/<条件>-<run-id>/` に次を残す
  - `env.json`：OS の版・CLI の版・Python の版・MuJoCo の版・ハーネスの base の SHA・開始のコミットの SHA・走らせたアカウントの名前・開始と終了の時刻・利用枠の回復待ちの合計の秒
  - `inputs/`：仕様と条件ごとの指示のファイルの写しと sha256（REQ-06・REQ-08）
  - `calls/<連番>-<役>/`：呼び出しごとの、標準入力に渡した全文（`prompt.txt`）・CLI の JSON の出力（`result.json`。`modelUsage`・利用量・ターン数を含む）・CLI のセッションの記録（全ターンの入出力の jsonl の写し）
  - `factory/`（工廠のみ）：計画役の出力と `planner.json`・キューが取り込んだ What とその sha256・Gate 1 の出力・report.md の最後の版
  - `git/`：走行の枝の `git bundle`（開始のコミットから先端まで）
  - `score.json`：W-34 の `score` の記録（`task`・`fingerprint`・`passed`・`total`・`rate`・`timed_out`）
  - `guard.txt`：REQ-11 の走査の出力
  - `manifest.json`：上のすべてのファイルの相対パスと sha256
- REQ-32：`bench/records/<課題>/<条件>-<run-id>.json` の記録に、`manifest.json` の sha256 と、REQ-22・REQ-23 の判定（`invalid`・`violations`）を書く。記録は git で main に入れる

### 7.2 保全と公開

- REQ-33：各段の終わりに、その段のすべての走行のディレクトリ（無効の走行も含む）を `bench-r3-stage-<段>.tar.gz` にまとめ、game-harness の GitHub Release `bench-r3-stage-<段>` の資産として置く。リポジトリには Release のタグとアーカイブの sha256 を `bench/records/stages.json` に書く
- REQ-34：隠しテストの失敗の文は、判定が出るまで公開の書類に入れない（`score.json` は数だけを持つ）。判定（REQ-27〜REQ-29）が出た後に、非公開オラクルの置き場（隠しテスト・参照実装・canary）を Release `bench-r3-oracles` として公開する。公開した隠しテストの指紋は `docs/bench/<課題>/oracle.sha256` と一致しなければならない

### 7.3 検め直し（W-47）

- REQ-35：`python -m harness.bench_verify --all --frozen` は、記録だけから、各走行の点を git の先端の採点し直しで確かめ、人の介入 0 回（キューの What がすべて計画役の出力にあり、置き直しが 0）を数える
- REQ-36：Release を展開した後、`python -m harness.bench_verify --all --frozen --package <展開したディレクトリ> --oracles <公開したオラクルの置き場>` の 1 命令で、manifest の sha256 の照合・bundle の先端の採点し直し・記録との一致を行い、すべて一致すれば 0 で終わる
