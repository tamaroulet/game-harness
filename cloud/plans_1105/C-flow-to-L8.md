# 頼み C：L6〜L8 の流れの設計（頼みの名：C-flow-to-L8）

先に `cloud/plans_1105/common.md` を読み、その決まりに従う。書く文書は `docs/design/cloud_1105/C-flow-to-L8.md`。

## 問い

1. L6（外側の周期の 1 周目、会話の席が手で回す）を、提案役の起動から取り込みの判定とマージまで、手順の通しで書く。手順ごとに、誰が（操縦士・会話の席・総監督・bench のアカウント）、何を使い（枠・トークン・時間）、何が出て、何を見て次へ進むか。戻せない手順に印を付ける。今のコード（`harness/proposer_launch.py`・`harness/bench_pair.py`・`harness/surface.py`・`harness/bench_chain.py`）で足りない所を挙げる。
2. L7（2 周を続けて人の手なしで回す）に要る部品と、作る順。人の手が今どこに残っているか（起動・承認・検め・マージ）を数え、どれを外すか・外さないかと、その守り。確立の条件（v3 §1 の 3）の検め方。
3. L8（比較の本番：取っておく組、単一コンテキスト型との比較）の設計。比べ方・回数・費用・成功と失敗の条件。v3 の線 2（環境の分離）がどこで要るか。
4. 各段（L6・L7・L8）の、走る前の予想と、外れたときの手。
5. 日程と費用の見積もり（トークン・人の手の時間・日数）。§15 の実測（段の走り 1 回のトークン・時間）から出す。
6. L6 を始めると環境を変えない前提で、L6 の前に決めておかないと L7・L8 で困ること。

## 気をつけること

- 計画の文書（v3 §7）をなぞらず、L1〜L5 の実測と今のコードから組む。v3 と違う所は、違うと明記して理由を書く。
- 批評役の 1 つは「この手順を操縦士が実際に打つ」立場で、人の手の数と分かりにくさを突かせる。
